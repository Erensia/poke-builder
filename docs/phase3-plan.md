# Phase 3 기획 — 데이터 커버리지 확장 & 세부 메커니즘 보강

> 이어서 읽기: [Phase 2 기획](phase2-plan.md) · [Phase 2.5 기획](phase2.5-plan.md)
> Phase 2에서 턴 순서·상세 데미지·명중/회피/급소·상태이상/행동방해·다중 턴 엔진·대전 로그 UI까지 라이브러리와 화면을 전부 완성했다. 이 문서는 그 과정에서 발견한 것 중 **신규 스키마 설계가 필요한 항목**만 정리한다 — "스키마는 이미 있고 데이터만 채우면 되는 것"(회피율/급소율 랭크, 풀죽음, 반동-recharge 태깅)은 [Phase 2.5 문서](phase2.5-plan.md)로 옮겼다. 코드를 다시 훑으며 `moves.json`의 `effect` 텍스트를 전수 스캔해서 실제로 몇 개 기술이 영향받는지까지 확인했다.

## 0. 착수 전 정정 사항 — "반동"은 두 가지 다른 뜻이었다

Phase 2 문서에서 흔들흔들댄스/기가임팩트류를 묶어서 `recharge`(반동)이라고 불렀는데, 실제로 데이터를 스캔해보니 **"반동"이라는 한글 단어가 완전히 다른 두 메커니즘에 쓰이고 있었다**:

1. **회복 불가 반동(recoil)** — 준 데미지의 1/3만큼 자신도 맞는 것. 불꽃세례·웨이브태클·브레이브버드·양날박치기 4개 기술의 effect 텍스트에 "반동"이라는 단어로 등장. **지금 스키마엔 전혀 없음** — 새로 만들어야 함.
2. **기가임팩트류 "다음 턴 행동 불가"** — 이건 Phase 2에서 이미 `VolatileCondition.recharge`로 구현해둔 바로 그 메커니즘. 이름은 "반동"이 아니라 "충전 필요"에 가깝다. 기가임팩트 effect 텍스트는 "반동"이라는 단어를 쓰지 않고 "사용한 다음 턴에는 움직일 수 없다"라고만 되어 있다.

**결론**: 스키마 이름(`VolatileCondition.recharge`)은 그대로 유지하되, 1번(진짜 반동 데미지)을 위한 필드를 새로 추가해야 한다. 아래 1-1 참고.

## 1. 새 스키마가 필요한 것 (아직 타입 자체가 없음)

### 1-1. 반동 데미지 (Recoil) — ✅ 완료

대상: 불꽃세례·웨이브태클·브레이브버드·양날박치기(전수 스캔 결과 4개, 전부 "1/3" 고정 비율).

- `Move.recoilFraction?: number` 추가, 4개 기술에 `1/3` 태깅
- `battleSimulator.ts`의 `resolveAction`: 데미지를 입힌 직후 `recoilDamage = Math.floor(damage * recoilFraction)`을 계산해 `attacker.currentHp`에서 차감. `damage`가 0(면역 등)이면 자연히 `recoilDamage`도 0 — 별도 분기 없이 계산식 자체로 보장됨(확인 필요 항목 해소)
- `ActionLogEntry`에 `recoilDamage` 필드 추가(발버둥의 `selfDamage`와는 계산 기준이 달라 분리), `BattleLogPage.tsx`에 반동 데미지 로그 줄 추가
- 브라우저로 거북왕(웨이브태클) vs 리자몽 실측 확인: 166 데미지 → 반동 55(=⌊166/3⌋) 정확히 계산됨
- 챔피언스 비율도 본가와 동일하게 1/3로 확인(효과 텍스트에 명시)

### 1-2. 급소 관련 두 가지 기술 태그 — ✅ 완료

기충전(급소율 +2)·그림자분신(회피율 +1)은 이미 있는 `statChanges`(EffectStatKey 확장판)로 바로 표현 가능해서 데이터만 채우면 된다 — 아래 2-1 참고. 하지만 스캔하다 보니 **스키마 자체가 없는 두 가지 급소 관련 태그**를 발견해서 새로 추가했다:

- **"급소에 맞을 확률이 높다"** (섀도클로·스톤에지·메가톤킥·블레이즈킥·크로스촙·사이코커터·에어커터, 7개) — 본가에서는 "하이 크리티컬"이라고 부르는, 그 기술 자체에 내장된 +1 급소 단계 보너스. `statChanges`(지속 랭크 변화)가 아니라 **그 기술을 쓸 때만 적용되는 일회성 보정**이라 별도 필드로 추가: `Move.highCritRatio?: boolean`
- **"반드시 급소에 맞는다"** (트릭플라워, 1개) — `Move.alwaysCrit?: boolean`
- `accuracyCrit.ts`의 `critChance(stage, highCritRatio)`가 `highCritRatio`가 있으면 급소율 카운터에 +1단계를 임시로 얹어서 계산(지속 랭크 자체는 안 건드림). `battleSimulator.ts`의 `resolveAction`은 `alwaysCrit`이면 판정 없이 바로 급소 처리, 아니면 `critChance`로 판정
- **급소율 0단계 기본 확률 정정**: 사용자가 실제 자료로 확인한 결과 `1/16`이 아니라 `1/24`(4.17%)였다 — Phase 2에서 잘못 기록했던 값을 `CRIT_CHANCE_TABLE`과 [phase2-plan.md](phase2-plan.md)에서 함께 정정(1단계 1/8·2단계 1/2·3단계 1/1은 기존 값 그대로 유지)
- 브라우저로 마스카나(트릭플라워) vs 리자몽 실측: 매 타 "급소!" 표시 확인

### 1-3. 2턴 무적 기술 (반침투/차지 기술) — ✅ 완료

공중날기·구멍파기·다이빙·고스트다이브·뛰어오르기(5개) + 솔라빔(맑음 날씨 예외, 별도 취급): "1턴째 준비(그동안 대부분의 기술에 안 맞음) → 2턴째 실제로 공격"하는 2턴짜리 기술을 구현했다. 예외 기술까지 전수 태깅하기로 사용자 확인.

- `Move`에 `chargeTurn`(2턴 기술 여부)·`chargeHideType`("underground"/"sky"/"underwater"/"hidden" — 준비 턴에 숨는 방식, 솔라빔은 숨지 않으므로 생략)·`chargeSkipWeather`(솔라빔="쾌청")·`bypassesHiding`(예외 기술이 뚫을 수 있는 hideType 배열)·`hidingBypassMultiplier`(지진·파도타기의 2배 위력 보너스) 5개 필드 추가
- **무적 예외**: moves.json에서 실제로 존재하는 기술만 전수 스캔해서 태깅 — 구멍파기(underground)는 지진만 예외(땅고르기=Bulldoze는 본가에서도 Dig를 못 뚫어서 제외, 매그니튜드는 로스터에 아예 없음), 공중날기·뛰어오르기(sky)는 번개·폭풍이 예외(돌풍·트위스터·스카이어퍼컷·스매크다운은 로스터에 없음), 다이빙(underwater)은 파도타기가 예외(소용돌이는 로스터에 없음), 고스트다이브(hidden)는 예외 기술 없음(본가와 동일)
- **위력 배가**: 지진·파도타기는 각 무적을 실제로 뚫었을 때 위력 2배(moves.json effect 텍스트에 이미 명시돼 있던 걸 그대로 구현) — 번개·폭풍은 그냥 맞히기만 하고 배율은 없음(본가와 동일)
- `battleSimulator.ts`: `BattleFighterState.chargingMoveId`로 준비 중 여부와 예정 기술을 추적(길게 고민한 VolatileCondition 확장 대신 전용 필드로 분리 — 어떤 기술을 저장해뒀는지까지 표현해야 해서 turnsRemaining만 있는 기존 volatile 구조로는 부족). `resolveAction` 맨 앞에서 "2턴째 자동 재실행" 오버라이드(PP는 1턴째에만 소모) → 이후 `move.chargeTurn`이면 준비만 하고 데미지 없이 반환 → 상대가 공격할 때 `defender.chargingMoveId`로 무적 여부와 예외 기술 통과 여부를 판정
- 솔라빔은 `state.weather === "쾌청"`이면 준비 턴 자체를 건너뛰고 1턴만에 발동
- `ActionLogEntry`에 `charging`(준비 턴 표시)·`evadedByCharge`(무적에 막혀 빗나감) 필드 추가, `BattleLogPage.tsx`는 준비 중인 쪽의 기술 선택 UI를 "OO 준비 중 — 다음 턴 자동으로 발동돼요!" 안내로 대체하고 수동 선택 없이 턴 진행 가능하도록 배선
- **브라우저 실측**: 거북왕(구멍파기) vs 리자몽(지진) — 1턴째(거북왕이 아직 무적 상태가 되기 전에 리자몽이 먼저 공격) 지진 36 데미지 기준값 확인 → 2턴째(거북왕이 여전히 준비 중일 때 리자몽이 다시 공격) 지진이 무적을 뚫고 76 데미지(36의 약 2배, 난수 오차 범위 내) 확인. 거북왕의 구멍파기 자체도 PP 1번만 소모하고 정상적으로 2턴째 자동 발동해서 리자몽에게 데미지를 입힘
- **버그를 하나 발견해서 같이 고쳤다**: `resolveAction`에서 새로 쓴 `getMove` 호출을 import 안 한 채로 커밋했는데, 검증에 쓰던 `tsc --noEmit -p .`가 루트 `tsconfig.json`(`"files": []`에 `references`만 있는 솔루션 파일)을 대상으로 해서 **아무것도 검사하지 않고 조용히 통과**하고 있었다 — 이 세션의 이전 모든 "타입체크 통과" 확인이 사실상 무효였다는 뜻. 브라우저에서 실제로 돌려보다가 `ReferenceError: getMove is not defined`로 발견했고, `tsc --noEmit -p tsconfig.app.json`(실제 앱 소스가 포함된 프로젝트)으로 바꿔서 확인하니 즉시 잡혔다. **앞으로는 `-p tsconfig.app.json`으로 타입체크할 것.**
- **스코프 밖으로 남긴 것**: 고스트다이브의 "2턴째 상대의 방어를 무시하고 공격한다"는 부분(카운터 파트인 방어 무시 자체는 이번 작업 대상이 아니었던 별개 메커니즘) — 지금은 일반 공격처럼 상대 방어를 그대로 반영해서 계산한다. 필요하면 나이트헤드류(`fixedDamage`)처럼 방어 무시 전용 필드를 추가하는 후속 작업으로 분리.

### 1-4. 상태이상 치료 효과 — ✅ 완료

물거품아리아(상대 화상 치료) 같은 "상대/자신의 상태이상을 없애는" 효과. `Move.curesStatus?: { target: "self" | "opponent"; status?: StatusCondition }` 추가 — `status`를 채우면 그 상태이상일 때만 치료(물거품아리아="화상"만, 다른 상태이상은 안 지움), 생략하면 어떤 상태이상이든 치료(향후 잠자기류용, 아직 태깅된 기술 없음). `resolveAction`에서 명중 시 대상에게 걸린 상태이상이 조건과 맞으면 지우고 `ActionLogEntry.curedStatus`에 기록, UI에 "화상 치료!" 표시.

- **스코프 밖으로 남긴 것**: 잠자기(Rest) — "체력+상태이상 모두 회복하고 2턴간 잠든다"인데, 이 프로젝트엔 HP 회복 기술 자체가 아예 구현 안 돼 있어서(광합성·뿌리박기 등도 전부 미구현) `curesStatus` 하나로 끝나지 않는 더 큰 기능. 후속 작업(HP 회복 메커니즘)으로 분리.

### 1-5. 지연형 상태이상 — ✅ 완료

하품("다음 턴 상대를 잠들게 한다"). 로스터 23마리 중 거북왕·대짱이·블래키·라우드본 4마리가 배울 수 있어 실제로 영향 있음을 확인하고 구현.

- `VolatileCondition`에 `"drowsy"`(졸음) 추가 — flinch/recharge처럼 행동을 막는 효과가 아니라 "2턴 카운터가 0이 되는 시점에 잠듦을 시도"하는 턴 종료 전용 효과. 지속 턴수는 고정 2(`volatileConditions.ts`의 `DROWSY_DURATION`) — 건 시점의 턴 종료에서 2→1(무산), 다음 턴 종료에서 1→0이 되는 순간 실제로 잠듦 시도(맞은 다음 턴 종료라는 본가 규칙과 일치)
- `하품`을 기존 `Move.inflictsVolatile`(`{ volatile: "drowsy", target: "opponent" }`)로 태깅 — 새 필드 없이 기존 스키마 재사용
- `resolveAction`의 `inflictsVolatile` 루프에 "대상이 이미 다른 상태이상이거나 이미 졸음 상태면 실패" 가드 추가(본가 규칙 — 재사용해도 카운터가 갱신되지 않음, 필드 재설치 버그와 같은 종류의 실수를 처음부터 방지)
- `runTurn`의 턴 종료 처리에 졸음 카운터 소모 + 트리거 로직 추가: 트리거 시점에 대상이 이미 다른 상태이상이거나(`isImmuneToStatus`) 타입/필드로 잠듦 면역이면 조용히 무산(실제로 맞을 때 재확인 — 하품 사용 시점이 아니라)
- `EndOfTurnLogEntry.inflictedDelayedStatus` 추가, UI는 실제로 잠들 때 §7의 표준 잠듦 onset 문구("○○은 잠들어 버렸다!")를 그대로 재사용
- 하품이 명중한 시점(졸음을 건 시점)의 문구는 표준 상태이상 onset과 달라서 사용자 확인 텍스트로 별도 적용: "상대 (포켓몬 이름)의 졸음을 유도했다!" — 처음엔 `VOLATILE_LABELS`의 범용 "· 졸음!" 표기를 썼다가 사용자 피드백으로 전용 문구·전용 줄로 교체
- **부수 수정**: 잠듦/얼음/마비처럼 턴종료 데미지가 항상 0인 상태이상도 매턴 "상태이상 데미지 0"이라는 무의미한 로그 줄이 찍히고 있었음(하품 작업 중 발견) — 데미지가 0보다 클 때만 로그를 남기도록 수정
- 브라우저 실측(거북왕 하품 vs 리자몽): 1턴째 "거북왕의 하품" + "상대 리자몽의 졸음을 유도했다!" + 상태 배지 "졸음" 표시, 2턴째 재사용은 이미 졸음 상태라 조용히 무시됨(가드 확인), 2턴째 종료에 잠듦 onset 문구 + 배지가 "잠듦"으로 전환 확인

### 1-4-1. 불꽃타입 기술의 얼음 해동 — ✅ 완료 (사용자 제보로 확인)

1-4(상태이상 치료) 작업 뒤 사용자가 "얼음 상태 상대에게 불꽃타입 기술을 쓰면 지속시간과 무관하게 즉시 해동돼야 한다"고 제보 — 확인해보니 실제로 구현이 안 돼 있었다(얼음은 매턴 25% 확률로만 풀리고, 불꽃타입 피격으로 즉시 풀리는 본가 규칙이 없었음).

- `curesStatus`(특정 기술만 태깅)와 다른 성격의 **일반 규칙**이라 별도 필드 없이 `resolveAction`에 직접 추가: 명중한 기술의 `effectiveMove.type`이 "불꽃"이고 방어측이 `freeze` 상태면 데미지 기술이든 상태이상 기술(도깨비불 등)이든 종류 무관하게 즉시 해제. `curedStatus`(1-4와 같은 로그 필드)에 `"freeze"`를 채워 재사용
- UI는 "얼음 치료!"라고 하면 어색해서 얼음만 "해동!"으로 별도 표기
- 검증: `checkStatusActionBlock`의 기존 "매턴 25% 확률 자연 해동"과는 완전히 별개 경로라 서로 간섭하지 않음(내부적으로 `inflictStatus`가 "이미 상태이상이 있으면 중첩 안 함" 규칙을 갖고 있어서, 얼음 상태에서 화상 부가효과가 있는 불꽃 기술에 맞아도 이중으로 안 걸리고 정상적으로 해동만 됨 — tsx 스크립트로 확인)
- **스코프 밖으로 남긴 것**: 얼어있는 포켓몬이 스스로 불꽃타입 기술을 쓰면 그 즉시 자기 해동되는 본가 규칙(자기 자신 발동 쪽)은 이번엔 손 안 댐 — 사용자가 언급한 "상대에게 불꽃 기술을 쓰는" 방향만 구현. 필요하면 후속 작업으로.

### 1-6. 설치형 필드 효과 (엔트리 해저드)

독압정("상대 진영에 설치, 이후 등장하는 포켓몬은 교체 시 독 상태") 같은 효과. 1v1 단일 대전 시뮬레이터에는 애초에 "교체" 개념이 없어서, 파티 단위 대전으로 확장하지 않는 이상 의미가 없다. **낮은 우선순위 — 지금의 1v1 설계 범위 밖.**

### 1-8. 기술 사용조건(usage condition) — ✅ 완료

코골기("잠든 상태에서만 사용 가능")·속이기("등장 후 첫 턴에만 사용 가능")에 `Move.usageCondition?: "sleep-only" | "first-turn-only"` 필드를 추가하고 배선했다.

- `battleSimulator.ts`: `resolveAction`에 조건 검사 추가. `first-turn-only`는 `state.turnNumber !== 1`이면 실패(1v1 시뮬레이터엔 교체가 없어 배틀의 1턴째로 취급). `sleep-only`는 두 단계로 처리 — 잠들어 있지 않으면 즉시 실패, 잠들어 있으면 **일반 잠듦 행동 차단(`checkStatusActionBlock`)을 우회**해서 실제로 기술이 나가게 하되(본가에서 코골기/잠꼬대가 잠듦의 예외인 것과 동일), 그 판정으로 이번 턴에 잠에서 깼다면 사용 조건이 깨진 것으로 실패 처리. `ActionBlockReason`에 `"usageCondition"` 추가
- `BattleLogPage.tsx`: 기술 버튼에 동일한 조건을 UI에서도 확인해 조건 불충족이면 비활성화(+ 툴팁으로 이유 표시), 턴 로그에 "사용 조건이 맞지 않아 실패" 문구 추가
- 브라우저로 거북왕(속이기+물기) vs 리자몽(화염방사) 대전 실측 확인: 1턴째엔 속이기 선택 가능·정상 발동(풀죽음까지 확인), 2턴째부터는 버튼이 자동으로 비활성화됨
- **정정(사용자 확인)**: `first-turn-only`(속이기)는 2턴째부터 버튼을 아예 비활성화하던 걸, 계속 선택 가능하게 바꾸고 실제로 눌러서 실패 결과가 뜨는 걸 직접 보여주도록 변경 — 조건을 못 채운다고 버튼 자체를 숨기지 않는다는 방향. 버튼 title도 "지금 쓰면 실패해요"로 안내.
- **UI 문구 추가 정정(사용자 확인)**: 처음엔 메인 줄에 "OO의 속이기 — 사용 조건이 맞지 않아 실패"로 한 줄에 붙였는데, 사용자가 준 형식대로 두 줄로 분리 — 메인 줄은 "OO의 속이기!"로만 끝내고, 별도 줄에 "OO의 속이기는 실패했다!"(기술명 뒤 은/는 조사는 `eunNeun`으로 자동 판별)를 추가. `usageCondition`으로 실패하는 모든 기술(속이기·코골기 둘 다)에 공용 적용
- **`sleep-only`(코골기)도 같은 방향으로 정정(사용자 확인)**: "실전 배틀에서도 조건 안 맞는다고 기술 자체를 못 내는 게 아니다"는 지적에 따라 처음엔 유지했던 코골기의 버튼 비활성화도 없앰 — 이제 잠들지 않은 상태에서도 코골기를 선택할 수 있고, 실제로 내면 위와 동일한 두 줄 실패 문구가 뜬다. 결과적으로 속이기·코골기 둘 다 "선택은 항상 가능, 조건 불충족이면 결과만 실패"로 동일한 UX가 됨
- 브라우저 재검증: 속이기(2턴째) → "거북왕의 속이기!" + "거북왕의 속이기는 실패했다!", 코골기(안 잠든 채로) → "거북왕의 코골기!" + "거북왕의 코골기는 실패했다!" 둘 다 정상 표시, PP는 실패해도 그대로 소모(기존 규칙 유지)
- 잠꼬대도 "잠든 상태에서만 사용 가능"이지만 "배운 기술 중 하나를 무작위로 사용"하는 별도 메커니즘이 엔진에 없어 이번엔 `usageCondition` 태깅을 보류(후속 작업, `moves.json`에 사유 기록)
- 짓밟기류 등 다른 유사 조건 기술은 이번 스캔에서 추가로 발견되지 않음

### 1-9. 위력 가변형 기술의 `effect` 텍스트 누락 — ✅ 완료

기사회생·안다리걸기·죽기살기·히트스탬프·자이로볼·헤비봄버 6개의 `effect`를 카운터·미러코트·바둥바둥·풀묶기와 같은 방식(정성적 설명, 정확한 수식은 별도 명기 안 함)으로 채웠다: 기사회생/죽기살기="자신의 체력이 낮을수록", 안다리걸기="상대의 몸무게가 무거울수록", 히트스탬프/헤비봄버="자신의 몸무게가 상대보다 무거울수록", 자이로볼="자신의 스피드가 상대보다 느릴수록" 위력이 커진다.
- 확인 결과 **하드플랜트는 이 목록에 해당하지 않음** — 실제 데이터를 보니 `power: 150`(고정)에 `effect`도 이미 채워져 있어(반동 없는 대신 다음 턴 행동불가) 애초에 위력 가변형이 아니었다. 원래 문서의 "7개" 표기가 부정확했던 것으로 확인 — 6개가 맞다.
- `moves.json` 전체에서 `power: null` + `effect: ""` 조합을 다시 스캔한 결과, 위 6개 외에 남은 항목은 전부 `category: "status"`(변화기) 기술로, "위력 가변형" 범주가 아니라 상태 변화 효과 자체가 아직 문서화 안 된 별개의 데이터 공백이었다 — 이번 1-9 스코프 밖이라 후속 작업으로 남긴다(예: 도발·최면술·중력·사슬묶기 등 다수).

### 1-10. 배짱(Scrappy) — 타입 면역 무시 특성 미구현 — ✅ 완료 (사용자 제보로 확인)

메가이어롭(로스터 전체에서 `배짱`을 가진 유일한 포켓몬)은 특성이 `배짱`이라 노말·격투타입 기술이 고스트타입 상대에게도 명중해야 하는데, 그대로 면역(0배)으로 처리되던 버그.

- **지난번(§6-3)에 고친 메가진화 특성 미반영 버그와는 다른 버그**였다 — `getEffectiveAbilityId`가 메가진화 중 `배짱`을 올바르게 골라내는 것 자체는 이미 정상이었고, `배짱`이 골라진 뒤에도 그 효과(면역 무시)를 계산에 반영하는 로직이 애초에 없었던 것.
- `Ability.bypassesImmunityForTypes?: PokemonType[]` 필드 추가, `배짱`에 `["노말", "격투"]` 태깅
- **1차 구현이 부정확했음 — 사용자가 재차 지적해서 정정**: 처음엔 "전체 배율이 0이면 통째로 1로 덮어쓴다"고 짰는데, 이러면 2타입 상대(예: 고스트/독)에서 다른 쪽 타입의 반감/약점 관계까지 같이 뭉개진다. 정확한 규칙은 "면역을 준 그 타입 쪽 배율 요인만 1로 무시하고, 다른 타입의 배율은 그대로 곱한다" — 예: 고스트/독에게 격투 기술 → 고스트의 면역(0)만 무시되고 독의 반감(0.5)은 남아 최종 **0.5배**, 고스트/악에게 격투 기술이면 악의 약점(2)이 남아 **2배**. `typeEffectiveness.ts`의 `getEffectiveness()`에 `{ bypassImmunity }` 옵션을 추가해서 `defending.reduce()` 안에서 방어 타입마다 개별 배율(0이면 1로 무시, 아니면 그대로)을 곱하도록 고쳤다 — 전체 결과를 사후에 덮어쓰는 대신 애초에 타입별로 정확히 계산
- `moveContext.ts`는 이제 `getEffectiveness(effectiveMove.type, defenderTypes, { bypassImmunity })`를 호출하기만 하면 됨(공격측 특성이 `bypassesImmunityForTypes`에 이 기술 타입을 포함하는지만 확인)
- `resolveMoveContext`는 대전 로그(`battleSimulator.ts`)와 매치업 화면(`matchupEvaluator.ts`)이 공유하는 함수라 양쪽 다 자동으로 고쳐졌다
- 검증(tsx 스크립트): `getEffectiveness("격투", ["고스트","독"], {bypassImmunity:true})` → 0.5, `getEffectiveness("격투", ["고스트","악"], {bypassImmunity:true})` → 2, `getEffectiveness("노말", ["고스트","독"], {bypassImmunity:true})` → 1 전부 확인. 실제 대전 엔진으로도 메가이어롭(배짱)의 드레인펀치(격투) → 팬텀(고스트/독) 63 데미지(0.5배 반영, 이전 노말기술 68 데미지 대비 절반 수준)로 정상 반영 확인

### 1-7. 다단히트 기술 — ✅ 완료

`evaluateSlotMatchup`(매치업 화면)은 `multiHitCount` 옵션으로 이미 지원했지만, `battleSimulator.ts`의 `resolveAction`은 `move.power`만 사용하고 `multiHitPowers`/`minHits`/`maxHits`를 전혀 안 봐서 트리플악셀 같은 기술을 다중 턴 대전에서 쓰면 1타 위력으로만 계산되던 걸 고쳤다.

- **명중 판정**: moves.json의 effect 텍스트에 이미 기술마다 다르게 적혀 있던 구분을 그대로 따른다(사용자 확인) — 록블라스트·독침 등 일반 2~5회/고정 2회 기술은 **첫 타만 판정**하고 이후는 자동 명중(기존의 "행동 전체 명중 판정"을 그대로 첫 타로 재사용), 트리플악셀(`multiHitPowers` 보유)은 **타수마다 따로 판정**해서 빗나가면 그 시점에서 중단
- **급소**: 다단히트 종류와 무관하게 **항상 타수마다 따로 판정**(사용자 확인) — `resolveHit()`라는 내부 헬퍼로 급소+데미지 계산을 한 타 단위로 분리해서 여러 번 호출
- **타수 랜덤 결정**: `rollMultiHitCount()` 추가 — `minHits===maxHits`면 고정값, 2~5(록블라스트류)면 moves.json에 이미 적힌 확률표(2/3회 각 35%, 4/5회 각 15%)를 그대로 사용. 스킬링크·속임수주사위는 로스터/도구 데이터에 아예 없어서(전수 검색 결과 0건) 이번엔 구현 대상에서 제외
- 상대가 다단히트 도중 쓰러지면 남은 타수는 진행하지 않고 즉시 중단(본가 규칙)
- `ActionLogEntry`에 `hitCount?: number` 추가(다단히트가 아닌 일반 공격은 `undefined`), `BattleLogPage.tsx`에 "N타 명중" 표시 + 급소가 하나라도 있었으면 "(급소 포함)"으로 표기(다단히트는 다타 중 하나라도 급소면 `critical: true`라 단일 "급소!" 표기와는 의미가 달라 구분)
- 브라우저로 가디안(트리플악셀) vs 리자몽 실측: "44 데미지 (28.8%) · 3타 명중"으로 타수별 위력(20/40/60) 합산과 3타 전부 명중이 정상 반영됨을 확인
- **스코프 밖으로 남긴 것**: 집단구타(`maxHits`만 있고 `minHits`/`multiHitPowers` 없음, 위력이 파티 전원의 공격 종족값 기반) — 1v1 시뮬레이터엔 파티 개념이 없어 구현 불가. `minHits`가 없어 이번 다단히트 분기 조건(`minHits !== undefined && maxHits !== undefined`)에 자동으로 걸리지 않으므로 기존처럼 무피해로 남아있다(1-6 설치형 필드 효과와 같은 이유로 후순위)

## 3. 확인이 필요한 파생 규칙

1. **반동 데미지가 면역(0배 데미지)일 때도 발생하는지** — 본가는 데미지가 0이면 반동도 0.
2. **하이 크리티컬(급소 확률 높음) 배율이 정확히 얼마인지** — 본가는 기본 배율에서 +1 단계(1/16→1/8). 챔피언스도 그대로인지 확인 필요, 이미 Phase 2에서 확정한 급소율 표(0~3단계)에 그대로 얹으면 될 것 같지만 검증 필요.
3. **차지 기술(2턴짜리) 1턴째의 무적 판정 예외** — 어떤 기술이 "숨어있어도 맞는" 예외인지(본가는 지진·번개 등 특정 타입/기술이 공중날기 중인 상대를 맞출 수 있음) 확인 필요.
4. **화상/독의 타입 면역 확장** — 전기=마비 면역만 확정. 불꽃=화상 면역, 독/강철=독 면역이 챔피언스에도 있는지.
5. **명중률 전용 특성/도구 배율** — 반짝가루(0.9)·모래숨기(0.8) 같은 값이 실제 몇인지, 지금 `accuracyExtraMultiplier`가 1로 고정된 상태.

## 4. 엔진에 이미 옵션은 있는데 배선이 안 된 것 (버그에 가까움)

코드를 다시 훑다가 발견한 것 — 데이터 문제가 아니라 실제 배선 누락. `computeOffensePower`/`computeDamage`(`battlePower.ts`)는 애초부터 `weatherMultiplier`/`itemMultiplier` 파라미터를 받게 설계돼 있지만, **실제로 그 값을 계산해서 넘기는 코드가 지금 어디에도 없다** — 매치업 화면·대전 로그 화면 둘 다 마찬가지. `matchupEvaluator.ts`가 옵션을 받아 넘기는 배선 자체는 있지만 호출부(`MatchupPage.tsx`)가 값을 안 채워서 결과적으로 항상 1배(무배율)로 계산되고, `battleSimulator.ts`의 다중 턴 엔진은 그 배선조차 없어서 `state.weather`를 오직 `resolveMoveContext`(특성 조건부 판정용)에만 쓴다.

날씨 배율과 도구 배율은 필요한 선행 작업이 서로 달라서 두 항목으로 나눈다.

### 4-1. 날씨 데미지 배율

본가 기준 비=물타입 1.5배/불타입 0.5배, 쾌청=불타입 1.5배/물타입 0.5배 — 별도 데이터 보강 없이 `WeatherKind` + 기술 타입만으로 배율표를 코드로 짤 수 있다.

- 필요한 것: 날씨→타입→배율 매핑 함수(예: `getWeatherDamageMultiplier(weather, moveType)`) 추가 + `battleSimulator.ts`의 `resolveAction`(데미지 계산 지점)에서 계산해 `computeDamage`에 넘기기
- 확인 필요: 챔피언스도 본가와 같은 날씨 배율 표를 쓰는지
- **우선순위 높음** — 날씨를 골라놓고 대전해도 지금은 아무 영향이 없다는 뜻이라 사용자가 체감하기 쉬운 버그. 데이터 선행 작업이 없어 바로 착수 가능.

### 4-2. 지닌 도구 데미지 배율

지금 `items.json`은 `id`/`name`/`description`/`category`만 있고 배율이 구조화돼 있지 않다(Phase 1.5까지는 효과 설명 텍스트만 있음). **사용자가 도구별 데미지 배율 표를 정리해서 전달하기로 함** — 그 데이터가 도착하기 전까지는 착수 보류.

- 데이터 도착 후 필요한 것: `Item`에 배율 필드(예: `damageMultiplier?: number` 또는 특정 타입 한정이면 `{ type: string; multiplier: number }` 형태 — 이러닝구슬처럼 "특정 타입 위력 1.2배" 류와 확대경/각오의띠처럼 조건부인 것 구분 필요) 추가 + `battleSimulator.ts`의 `resolveAction`에서 공격자 지닌 도구 기준으로 계산해 `computeDamage`에 넘기기
- 4-1(날씨) 작업과 배선 지점이 같아서(둘 다 `resolveAction`의 `computeDamage` 호출부) 같이 처리하는 게 자연스럽지만, 데이터가 없어 순서상 날씨를 먼저 끝내고 도구는 데이터 도착 시 이어서 배선

## 6. 4-1 작업 중 사용자 피드백으로 확장·완료한 것 — 날씨/필드 시스템

4-1(날씨 배율 배선)을 끝내고 나서, 사용자가 실제로 대전 로그를 써보며 "날씨 배경색 표시"·"날씨 변화 특성 자동 발동 안내"·"필드(그래스/미스트/사이코/일렉트릭) 지원"을 같이 요청해 같은 세션에서 이어서 처리했다. 범위는 사용자 확인 하에 정했다: 필드는 기본 효과만(개별 기술 상호작용은 후순위로 문서에만 기록), 날씨 변화는 특성만(비바라기 같은 기술은 후순위), 트릭룸 등 공간 변화는 이번엔 문서 기록만.

### 6-1. 날씨 배경색 + 날씨 변화 특성 자동 발동

- `Ability.setsWeather?: WeatherKind` 필드 추가, 가뭄→쾌청/잔비→비/모래날림→모래바람 태깅
- `createBattleState`가 사용자가 날씨를 직접 안 골랐을 때 양쪽 특성을 확인해 배틀 시작과 동시에 날씨를 자동 적용 + `BattleState.entryAnnouncements`에 "○○의 ○○! 날씨가 ○○로 바뀌었다!" 안내 문구를 채운다(양쪽 다 날씨 특성이면 실효 스피드가 빠른 쪽이 우선 — 확인 필요 항목으로 남김)
- `BattleLogPage`의 `.battle-board`에 날씨가 강화하는 타입 색(비=물, 모래바람=바위, 눈=얼음, 쾌청=불꽃)을 낮은 불투명도로 배경 틴트, 배지로 "날씨: ○○" 표시

### 6-2. 필드(그래스/미스트/사이코/일렉트릭) 기본 지원 — 신규 스키마

- `types/field.ts`(`FieldKind`), `Move.setsField?: FieldKind` 추가. `moves.json`의 그래스필드/미스트필드/사이코필드에 태깅하고, **데이터 자체가 아예 없던 일렉트릭필드 기술을 새로 추가**(3개와 동일한 pp/effect 패턴, 타입 전기) — 단, 어떤 포켓몬 `learnset`에도 아직 안 넣었다(배울 수 있는 포켓몬이 확인 안 됨, 후순위)
- `lib/fieldEffects.ts`: 필드→데미지 배율(그래스/사이코/일렉트릭=해당 타입 1.3배, 미스트=드래곤 0.5배), 상태이상/혼란 면역(미스트=전부, 일렉트릭=잠듦만), 우선도 기술 차단(사이코, 우선도 +1 이상 기술 실패), 턴 종료 HP 회복(그래스, 최대 HP 1/16)
- `battleSimulator.ts`: `BattleState.field`/`fieldTurnsRemaining`(5턴, 새 필드가 덮어쓰면 재충전), `resolveAction`에 위 배율·면역·차단 판정 배선, `runTurn` 종료 시 그래스 회복 적용 + 카운트다운 + 0 되면 자동 해제. **버그 발견**: `runTurn`이 새 상태를 만들 때 `weather`만 복사하고 있어서(고치기 전) 필드를 추가했다면 턴마다 초기화되는 버그가 났을 것 — 필드 작업과 동시에 `field`/`fieldTurnsRemaining`/`entryAnnouncements`도 복사하도록 고쳤다
- UI: `.battle-board`에 필드 타입 색 틴트(날씨와 동시에 있으면 그라데이션), "필드: ○○ (앞으로 N턴)" 배지, 각 턴 로그에 필드 설치("○○ 설치!") · 지속 턴수 · 소멸 안내 · 그래스 회복 줄 추가
- 개별 기술 상호작용(그래스슬라이더 우선도, 대지의파동 타입변화, 비밀의힘 확률효과, 아이언롤러, 자연의힘, 미스트버스트/와이드포스/라이징볼트/사이코블레이드 위력 변화 등)은 이번 스코프 밖 — 각 기술이 실제 로스터에 있는지부터 확인 후 후속 작업으로 남김

### 6-3. 부수 발견 — 메가진화 특성이 전혀 반영되지 않던 버그 (버그, 이번에 같이 수정)

가뭄 자동 발동을 구현하다가 발견: `resolveAction`/`evaluateSlotMatchup` 둘 다 특성을 `slot.ability`(유저가 고른 값)로만 읽고 있어서, **메가진화 중에도 항상 메가폼 고유 특성(예: 메가리자몽Y=가뭄, 메가리자몽X=단단한발톱) 대신 메가진화 전 기본 특성이 적용되고 있었다** — 데미지 계산 전체에 영향을 주는 버그였다. `lib/pokemonForm.ts`에 `getEffectiveAbilityId(form, slotAbility)`를 추가해 메가면 `mega.ability`를 우선하도록 고치고, `battleSimulator.ts`(`BattleFighterState.effectiveAbilityId`)와 `matchupEvaluator.ts` 양쪽에 반영했다.

- **알려진 갭(이번엔 미수정)**: `AbilityPickerModal`은 여전히 `pokemon.abilities`(기본 특성 목록)만 보여줘서, 메가진화 중인 포켓몬에게 "지금 특성은 사실 고정된 메가 특성"이라는 걸 화면에서 알려주지 않는다. 계산은 이제 정확하지만, UI가 유저가 고른 값을 그대로 보여줘서 혼동의 여지가 있음 — 후속 작업으로 남김

### 6-4. 부수 요청 — 메가진화 배지에 X/Y 표시

리자몽처럼 메가진화가 2개 이상인 포켓몬은 "메가" 배지만으로 X인지 Y인지 알 수 없어서(지닌 도구를 봐야 알 수 있음) 불편하다는 피드백. `lib/pokemonForm.ts`에 `megaBadgeLabel(mega)`를 추가해 폼 이름 뒤쪽("메가X"/"메가Y")을 그대로 배지에 노출하도록 `PartySlotCard`·`MatchupSlotCard`·`BattleSetupCard`·`BattleLogPage` 4곳 전부 수정.

### 6-5. 후속 작업으로 남긴 것 (문서 기록만, 이번엔 미구현)

- **트릭룸(및 다른 공간 변화)**: `moves.json`에 있고 5마리가 배울 수 있는데 턴 순서 계산(`turnOrder.ts`)에 전혀 배선 안 돼 있음 — 사용자 확인: 이번 라운드는 문서 기록만, 구현은 다음 라운드로
- **날씨 변화 기술**(비바라기 등): 데이터는 있지만(`비바라기` 확인됨) 특성처럼 배틀 중 자동 적용되도록 배선 안 됨 — 특성 우선 처리로 확인, 기술 쪽은 후순위
- **일렉트릭필드 학습 포켓몬**: 기술 데이터는 추가했지만 어떤 포켓몬이 배우는지 확인 안 됨(원본 3개 필드는 이상해꽃/가디안/엘풍/카디나르마/누리레느/마스카나 6마리 확인됨)
- **필드 개별 기술 상호작용**: 6-2 마지막 항목 참고
- **그라운드코트**(필드 지속시간 5→8턴 도구): 4-2(도구 배율)와 같은 이유로 도구 데이터 구조화가 먼저 필요

## 7. 주 상태이상 6종 전수 재검증 — 사용자가 본가/챔피언스 위키 수치를 직접 제공, 전부 반영

1-4-1(불꽃 해동) 작업 뒤 사용자가 6개 주 상태이상(독/맹독/화상/마비/잠듦/얼음)의 정확한 규칙과 UI 3단계 문구(걸렸을 때/효과 발동할 때/나았을 때)를 한 번에 정리해서 전달 — 항목별로 이미 맞았던 것과 새로 고친 것을 구분해서 기록한다.

### 7-1. 이미 정확했던 것 (검증만, 코드 변경 없음)

- **화상 물리위력 반감**: `computeStatusAttackMultiplier`에 이미 있었음(근성/객기 예외 포함)
- **마비 12.5% 행동불가 + 스피드 50%**: `PARALYSIS_ACTION_FAIL_CHANCE`/`computeStatusSpeedMultiplier`에 이미 있었음
- **전기=마비 면역**: 이미 있었음
- **잠듦 해제 확률(1턴 33.3%/2턴 66.6%, 기대 1.66턴)**: `SLEEP_WAKE_CHANCE_BY_TURN`이 이미 정확히 이 분포를 만들고 있었음 — 30만 회 몬테카를로 시뮬레이션으로 재검증(`33.30%`/`66.70%`, 기대값 1.667)
- **얼음 해제 확률(0턴 25%/1턴 18.75%/2턴 56.25%, 기대 1.3125턴)**: `FREEZE_THAW_CHANCE`(0.25) + `turnsElapsed>=3` 강제 해제 스케줄이 이미 정확히 이 분포였음 — 같은 방식으로 재검증(`25.02%`/`18.69%`/`56.29%`, 기대값 1.313)

### 7-2. 새로 추가한 것

- **타입 면역 확장** (`isImmuneToStatus`): 독/강철=독·맹독 면역, 불꽃=화상 면역, 얼음=얼음 면역 추가(전기=마비는 기존)
- **쾌청(강한 햇살) 날씨에서 얼음 상태 안 걸림**: `resolveAction`의 `inflictsStatus` 루프에 `effect.status === "freeze" && state.weather === "쾌청"`이면 스킵하는 분기 추가
- **불꽃타입 기술의 얼음 해동 범위 정정**: 지난 1-4-1에서는 카테고리 무관하게 적용했는데, "변화기(도깨비불 등)는 제외되고 물리/특수 데미지 기술만 해동시킨다"는 사용자 확인에 따라 `effectiveMove.category !== "status"` 조건 추가. `도깨비불`(불꽃타입 변화기)로 실측: 해동 안 되고 정상적으로 화상만 걸림 확인
- **얼음 상태에서 사용하면 해동 후 발동하는 기술 10종** (`Move.thawsUserOnUse`): 나무위키 목록 10개(불사르기·성스러운불꽃·스팀버스트·열사의대지·열탕·크로스플레임·플레어드라이브·화염바퀴·화염볼·휘적휘적포) 중 **지금 335개 기술 데이터에 있는 건 3개뿐**(불사르기·열사의대지·플레어드라이브) — 이 3개만 태깅. 나머지 7개는 애초에 데이터가 없어 태깅 불가(후속 데이터 보강 시 추가). `resolveAction`에서 코골기의 sleep-only 우회와 같은 자리에 분기 추가: 얼어있는 채로 이 기술을 선택하면 매턴 해제 확률 판정 없이 무조건 먼저 해동된 뒤 기술이 정상 발동
- **UI 3단계 문구 전면 교체**: 기존엔 메인 액션 줄에 "· 화상 상태!" 식으로 짧게 붙이던 걸, 사용자가 준 정확한 문구로 전부 교체하고 각각 별도 줄로 분리했다(`STATUS_ONSET_TEXT`/`STATUS_TRIGGER_TEXT`/`STATUS_CURE_TEXT`, `BattleLogPage.tsx`):
  - onset(처음 걸림): "○○의 몸에 독이 퍼졌다!" 등 — `inflictedStatus`(즉시) / `inflictedDelayedStatus`(하품 지연형)에 공용 적용
  - trigger(매턴 효과 발동): 독/맹독/화상은 턴종료 데미지 줄, 마비/잠듦/얼음은 "이번 턴 행동이 막혔다"는 뜻이라 `blockedReason === "status"`일 때 `blockedByStatus`로 어떤 상태인지 구분해서 표시("몸이 저려서"/"쿨쿨 잠들어 있다"/"얼어 버려서")
  - cure(나음): 물거품아리아 같은 치료 기술, 불꽃 데미지 기술의 해동, 잠듦/얼음의 자연 해제, thawsUserOnUse 전부 같은 문구 체계로 통일. `ActionLogEntry.curedStatusTarget`("self"/"opponent")을 새로 추가해 누구의 상태가 나았는지 구분(자기 자신이 자연 해제/thaw된 경우와 상대 상태를 치료해준 경우를 같은 문구로 다른 대상에게 적용)
- 브라우저 실측(리자몽 도깨비불 vs 이상해꽃): "이상해꽃은 화상을 입었다!"(onset) → "이상해꽃은 화상 데미지를 입었다! (남은 HP 146)"(trigger) 순서로 정확히 표시 확인

### 7-3. 부수 발견 — 플레어드라이브에 반동(recoil) 데이터가 빠져있었음 — ✅ 같이 수정

thawsUserOnUse를 태깅하며 확인: `플레어드라이브`(본가 기준 준 데미지의 1/3 반동)가 Phase 3 1-1(반동 데미지) 작업 때 태깅된 4개 목록(불꽃세례·웨이브태클·브레이브버드·양날박치기)에 없었다. `effect`도 원래 빈 문자열이었음 — 반동 기술 재스캔이 그때 놓친 데이터 공백으로 보인다. 다른 4개와 동일하게 `recoilFraction: 1/3` + effect 텍스트("사용자도 준 데미지의 1/3만큼 반동을 입는다.")를 추가해서 같이 정리했다(스키마·배선은 이미 1-1에서 완성돼 있어서 데이터만 채우면 되는 태깅 작업).

## 8. 부수 데이터 수정 — 브리두라스 타입 오류

로스터 포켓몬 데이터에서 사용자 제보로 확인: `브리두라스`가 `["드래곤", "얼음"]`로 잘못 등록돼 있었음 — 실제로는 **드래곤/강철** 타입. 배우는 기술 목록(러스터캐논·아이언헤드·철제광선·메탈버스트·하드프레스 등 강철 기술이 다수, 얼음 기술은 하나도 없음)과도 정합적이라 강철이 맞다. `pokemon.json`의 `types` 필드만 `["드래곤", "강철"]`로 수정 — 다른 필드(종족값·특성·기술 목록)는 그대로.
