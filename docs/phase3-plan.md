# Phase 3 기획 — 데이터 커버리지 확장 & 세부 메커니즘 보강

> 이어서 읽기: [Phase 2 기획](phase2-plan.md) · [Phase 2.5 기획](phase2.5-plan.md)
> Phase 2에서 턴 순서·상세 데미지·명중/회피/급소·상태이상/행동방해·다중 턴 엔진·대전 로그 UI까지 라이브러리와 화면을 전부 완성했다. 이 문서는 그 과정에서 발견한 것 중 **신규 스키마 설계가 필요한 항목**만 정리한다 — "스키마는 이미 있고 데이터만 채우면 되는 것"(회피율/급소율 랭크, 풀죽음, 반동-recharge 태깅)은 [Phase 2.5 문서](phase2.5-plan.md)로 옮겼다. 코드를 다시 훑으며 `moves.json`의 `effect` 텍스트를 전수 스캔해서 실제로 몇 개 기술이 영향받는지까지 확인했다.

## 0. 착수 전 정정 사항 — "반동"은 두 가지 다른 뜻이었다

Phase 2 문서에서 흔들흔들댄스/기가임팩트류를 묶어서 `recharge`(반동)이라고 불렀는데, 실제로 데이터를 스캔해보니 **"반동"이라는 한글 단어가 완전히 다른 두 메커니즘에 쓰이고 있었다**:

1. **회복 불가 반동(recoil)** — 준 데미지의 1/3만큼 자신도 맞는 것. 불꽃세례·웨이브태클·브레이브버드·양날박치기 4개 기술의 effect 텍스트에 "반동"이라는 단어로 등장. **지금 스키마엔 전혀 없음** — 새로 만들어야 함.
2. **기가임팩트류 "다음 턴 행동 불가"** — 이건 Phase 2에서 이미 `VolatileCondition.recharge`로 구현해둔 바로 그 메커니즘. 이름은 "반동"이 아니라 "충전 필요"에 가깝다. 기가임팩트 effect 텍스트는 "반동"이라는 단어를 쓰지 않고 "사용한 다음 턴에는 움직일 수 없다"라고만 되어 있다.

**결론**: 스키마 이름(`VolatileCondition.recharge`)은 그대로 유지하되, 1번(진짜 반동 데미지)을 위한 필드를 새로 추가해야 한다. 아래 1-1 참고.

## 1. 새 스키마가 필요한 것 (아직 타입 자체가 없음)

### 1-1. 반동 데미지 (Recoil)

- 대상: 불꽃세례·웨이브태클·브레이브버드·양날박치기 (전수 스캔 결과 4개, 전부 "1/3" 고정 비율)
- 필요한 것: `Move.recoilFraction?: number`(예: 1/3) + `battleSimulator.ts`의 `resolveAction`에서 데미지를 입힌 직후 `attacker.currentHp -= Math.floor(damage * recoilFraction)`, `ActionLogEntry`에 `recoilDamage` 필드 추가
- 확인 필요: 챔피언스도 정확히 1/3인지(본가와 동일), 상대가 데미지 0(면역)이면 반동도 0인지(본가는 그렇다)

### 1-2. 급소 관련 두 가지 기술 태그

기충전(급소율 +2)·그림자분신(회피율 +1)은 이미 있는 `statChanges`(EffectStatKey 확장판)로 바로 표현 가능해서 데이터만 채우면 된다 — 아래 2-1 참고. 하지만 스캔하다 보니 **스키마 자체가 없는 두 가지 급소 관련 태그**를 발견했다:

- **"급소에 맞을 확률이 높다"** (섀도클로·스톤에지·메가톤킥·블레이즈킥·크로스촙·사이코커터·에어커터, 7개) — 본가에서는 "하이 크리티컬"이라고 부르는, 그 기술 자체에 내장된 +1 급소 단계 보너스. `statChanges`(지속 랭크 변화)가 아니라 **그 기술을 쓸 때만 적용되는 일회성 보정**이라 별도 필드가 필요: `Move.highCritRatio?: boolean` — 있으면 `critChance(stage)` 계산 시 `stage + 1`로 판정
- **"반드시 급소에 맞는다"** (트릭플라워, 1개) — `Move.alwaysCrit?: boolean`

### 1-3. 2턴 무적 기술 (반침투/차지 기술)

공중날기·구멍파기·다이빙·고스트다이브·뛰어오르기(5개) + 솔라빔(맑음 날씨 예외 있음, 별도 취급): "1턴째 준비(그동안 대부분의 기술에 안 맞음) → 2턴째 실제로 공격"하는 2턴짜리 기술. 지금 시뮬레이터는 모든 기술을 "선택하면 그 턴에 바로 나간다"고 가정하고 있어서 이 6개는 사실상 안 맞는 채로 동작한다(1턴 준비 없이 즉시 데미지가 나감).

- 필요한 것: `Move.chargeTurn?: boolean` + 무적 판정(1턴째엔 대부분의 기술이 안 맞음 — 어떤 기술은 예외적으로 맞는지 확인 필요) + `battleSimulator.ts`에 "차지 중" volatile 상태 하나 추가(`VolatileCondition`에 `"charging"` 같은 값 추가하고, 차지 중이면 자동으로 다음 턴 저장된 기술을 실행)
- 솔라빔은 맑음 날씨면 1턴만에 발동 — 날씨 상태(`state.weather`)를 조건으로 확인하는 추가 분기 필요
- 이건 다른 항목보다 구현 난이도가 높다 — "이번 턴 선택 즉시 실행"이라는 현재 엔진의 기본 가정 자체를 건드려야 함

### 1-4. 상태이상 치료 효과

물거품아리아(상대 화상 치료) 같은 "상대/자신의 상태이상을 없애는" 효과. 지금 `Move.inflictsStatus`는 거는 것만 표현 가능하고 치료는 스키마가 없음. 필요: `Move.curesStatus?: { target: "self" | "opponent" }` 정도의 단순한 필드 + `battleSimulator.ts`에서 적중 시 `cureStatus()` 호출

### 1-5. 지연형 상태이상

하품("다음 턴 상대를 잠들게 한다") — 기술 자체는 즉시 아무 효과가 없고, 한 턴 뒤에 상태이상이 걸린다. 지금 `StatusInflictEffect`는 "명중 즉시 적용"만 가정하고 있어서 표현 불가. 우선순위 낮음(챔피언스에 하품을 쓰는 포켓몬이 지금 21마리 중 있는지부터 확인 필요).

### 1-6. 설치형 필드 효과 (엔트리 해저드)

독압정("상대 진영에 설치, 이후 등장하는 포켓몬은 교체 시 독 상태") 같은 효과. 1v1 단일 대전 시뮬레이터에는 애초에 "교체" 개념이 없어서, 파티 단위 대전으로 확장하지 않는 이상 의미가 없다. **낮은 우선순위 — 지금의 1v1 설계 범위 밖.**

### 1-8. 기술 사용조건(usage condition) 미구현 — Phase 2.5 전수 검사에서 확인

Phase 2.5에서 `moves.json` 전수 검사(중복 effect 텍스트 그룹 비교, id/name/멀티히트 정합성 체크) 중 발견. 코골기("잠든 상태에서만 사용 가능")·속이기("등장 후 첫 턴에만 사용 가능")처럼 `effect` 텍스트에 사용조건이 명시된 기술이 있는데, 이 조건을 검사하는 로직이 `battleSimulator.ts`(`resolveAction`)·`BattleLogPage.tsx`(기술 버튼 disabled 조건) 어디에도 없다. 브라우저 실측으로 확인됨: 잠들지 않은 상태에서 코골기를 써도 위력 50 공격기처럼 정상 타격(26 데미지 확인).

- 필요한 것: `Move`에 사용조건 필드(예: `usageCondition?: "sleep-only" | "first-turn-only"`) 추가 + `resolveAction`에서 조건 미충족 시 실패 처리(로그에 "조건 불충족으로 실패" 등 표시) + `BattleLogPage.tsx`에서 조건 안 맞으면 버튼 비활성화
- 현재 영향받는 기술: 코골기(수면 전용), 속이기(첫 턴 전용) — Phase 2.5에서는 풀죽음 부가효과만 태깅하고 조건은 의도적으로 스코프 밖에 남김(사용자 확인 완료)
- 다른 기술에도 유사 조건이 있는지(예: 짓밟기류) 재스캔 필요

### 1-9. 위력 가변형 기술 7개의 `effect` 텍스트 누락 — Phase 2.5 전수 검사에서 확인

기사회생·안다리걸기·하드플랜트·죽기살기·히트스탬프·자이로볼·헤비봄버가 `power: null`(위력 가변형)인데 `effect` 필드가 빈 문자열이라 위력 계산 공식 자체가 문서화돼 있지 않음. 같은 종류인 카운터·미러코트·바둥바둥·풀묶기 등은 `effect`에 공식이 적혀 있어서 대조군으로 확인됨. 데이터 보강(공식 확인) 선행 필요 — 잘못된 텍스트가 아니라 누락이라 1-7(다단히트)만큼 급하지 않음.

### 1-7. 다단히트 기술

`evaluateSlotMatchup`(매치업 화면)은 `multiHitCount` 옵션으로 이미 지원하지만, `battleSimulator.ts`의 `resolveAction`은 `move.power`만 사용하고 `multiHitPowers`/`minHits`/`maxHits`를 전혀 안 본다 — 트리플악셀 같은 기술을 다중 턴 대전에서 쓰면 1타 위력으로만 계산된다.

- 필요한 것: 명중 판정도 타수마다 따로 해야 하는지(본가는 첫 타만 판정하고 이후는 자동 명중), 타수 랜덤 결정(2~5회 등은 스킬링크 여부에 따라 확률표), 급소도 타수마다 따로 판정하는지까지 확인 후 `resolveAction`에 멀티히트 전용 서브루틴 추가
- 난이도 중상 — 1-3(차지 기술)과 함께 "한 번의 기술 선택이 여러 개의 하위 이벤트로 나뉘는" 구조를 처음 다루게 됨

## 2. 데이터 태깅만 하면 되는 것 → [Phase 2.5 문서로 이동](phase2.5-plan.md)

회피율/급소율 랭크(기충전·그림자분신), 풀죽음 7개, 반동(recharge) 재스캔·태깅은 신규 스키마가 필요 없어서 Phase 2.5로 앞당겼다.

## 3. 확인이 필요한 파생 규칙

1. **반동 데미지가 면역(0배 데미지)일 때도 발생하는지** — 본가는 데미지가 0이면 반동도 0.
2. **하이 크리티컬(급소 확률 높음) 배율이 정확히 얼마인지** — 본가는 기본 배율에서 +1 단계(1/16→1/8). 챔피언스도 그대로인지 확인 필요, 이미 Phase 2에서 확정한 급소율 표(0~3단계)에 그대로 얹으면 될 것 같지만 검증 필요.
3. **차지 기술(2턴짜리) 1턴째의 무적 판정 예외** — 어떤 기술이 "숨어있어도 맞는" 예외인지(본가는 지진·번개 등 특정 타입/기술이 공중날기 중인 상대를 맞출 수 있음) 확인 필요.
4. **화상/독의 타입 면역 확장** — 전기=마비 면역만 확정. 불꽃=화상 면역, 독/강철=독 면역이 챔피언스에도 있는지.
5. **명중률 전용 특성/도구 배율** — 반짝가루(0.9)·모래숨기(0.8) 같은 값이 실제 몇인지, 지금 `accuracyExtraMultiplier`가 1로 고정된 상태.

## 4. 엔진에 이미 옵션은 있는데 배선이 안 된 것 (버그에 가까움)

코드를 다시 훑다가 발견한 것 — 데이터 문제가 아니라 실제 배선 누락. `computeOffensePower`/`computeDamage`(`battlePower.ts`)는 애초부터 `weatherMultiplier`/`itemMultiplier` 파라미터를 받게 설계돼 있지만, **실제로 그 값을 계산해서 넘기는 코드가 지금 어디에도 없다** — 매치업 화면·대전 로그 화면 둘 다 마찬가지. `matchupEvaluator.ts`가 옵션을 받아 넘기는 배선 자체는 있지만 호출부(`MatchupPage.tsx`)가 값을 안 채워서 결과적으로 항상 1배(무배율)로 계산되고, `battleSimulator.ts`의 다중 턴 엔진은 그 배선조차 없어서 `state.weather`를 오직 `resolveMoveContext`(특성 조건부 판정용)에만 쓴다.

날씨 배율과 도구 배율은 필요한 선행 작업이 서로 달라서 두 항목으로 나눈다.

### 4-1. 날씨 데미지 배율

본가 기준 비=물타입 1.5배/불타입 0.5배, 쾌청=불타입 1.5배/물타입 0.5배 — 별도 데이터 보강 없이 `WeatherKind` + 기술 타입만으로 배율표를 코드로 짤 수 있다.

- 필요한 것: 날씨→타입→배율 매핑 함수(예: `getWeatherDamageMultiplier(weather, moveType)`) 추가 + `battleSimulator.ts`의 `resolveAction`(데미지 계산 지점)에서 계산해 `computeDamage`에 넘기기
- 확인 필요: 챔피언스도 본가와 같은 날씨 배율 표를 쓰는지
- **우선순위 높음** — 날씨를 골라놓고 대전해도 지금은 아무 영향이 없다는 뜻이라 사용자가 체감하기 쉬운 버그. 데이터 선행 작업이 없어 바로 착수 가능.

### 4-2. 지닌 도구 데미지 배율

지금 `items.json`은 `id`/`name`/`description`/`category`만 있고 배율이 구조화돼 있지 않다(Phase 1.5까지는 효과 설명 텍스트만 있음). **사용자가 도구별 데미지 배율 표를 정리해서 전달하기로 함** — 그 데이터가 도착하기 전까지는 착수 보류.

- 데이터 도착 후 필요한 것: `Item`에 배율 필드(예: `damageMultiplier?: number` 또는 특정 타입 한정이면 `{ type: string; multiplier: number }` 형태 — 이러닝구슬처럼 "특정 타입 위력 1.2배" 류와 확대경/각오의띠처럼 조건부인 것 구분 필요) 추가 + `battleSimulator.ts`의 `resolveAction`에서 공격자 지닌 도구 기준으로 계산해 `computeDamage`에 넘기기
- 4-1(날씨) 작업과 배선 지점이 같아서(둘 다 `resolveAction`의 `computeDamage` 호출부) 같이 처리하는 게 자연스럽지만, 데이터가 없어 순서상 날씨를 먼저 끝내고 도구는 데이터 도착 시 이어서 배선

## 5. 우선순위 제안

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | 4-1 — 날씨 데미지 배율 배선 | 이미 있는 기능이 조용히 무시되고 있는 실제 버그, 데이터 선행 작업 없음 |
| 2 | 1-1 — 반동(recoil) 데미지 | 스키마 신규지만 단순(4개 기술, 비율 고정), 파급력 있음 |
| 3 | 1-2 — 하이 크리티컬/필중 급소 플래그 | 스키마 신규지만 단순(8개 기술) |
| 4 | 1-7 — 다단히트 엔진 지원 | 난이도 중상, 매치업 화면엔 이미 있어서 엔진만 따라가면 됨 |
| 5 | 1-3 — 2턴 차지 기술 | 난이도 최상 — "즉시 실행" 기본 가정을 건드림, 마지막으로 미룸 |
| 6 | 1-4, 1-5 — 상태이상 치료/지연형 | 영향받는 기술 수가 적어 후순위 |
| 대기 | 4-2 — 도구 데미지 배율 배선 | 사용자가 도구별 배율 데이터를 정리해서 전달하기로 함 — 데이터 도착 시 순서 상관없이 바로 끼워 넣음 |
| — | 1-6 — 설치형 필드 효과 | 1v1 설계 범위 밖이라 보류(파티 단위 확장 논의가 먼저 필요) |

(회피/급소 랭크·풀죽음·반동-recharge 데이터 태깅은 [Phase 2.5](phase2.5-plan.md)로 이동했으니 이 표에는 없음)

1~2번은 이미 있는 기능의 배선/단순 스키마라 빠르게 처리 가능할 것 같고, 4~5번은 엔진 구조를 건드리는 큰 작업이라 뒤로 미뤄뒀다. 4-2(도구 배율)는 순위와 무관하게 데이터가 도착하는 시점에 처리한다.

## 6. 4-1 작업 중 사용자 피드백으로 확장·완료한 것 — 날씨/필드 시스템

4-1(날씨 배율 배선)을 끝내고 나서, 사용자가 실제로 대전 로그를 써보며 "날씨 배경색 표시"·"날씨 변화 특성 자동 발동 안내"·"필드(그래스/미스트/사이코/일렉트릭) 지원"을 같이 요청해 같은 세션에서 이어서 처리했다. 범위는 사용자 확인 하에 정했다: 필드는 기본 효과만(개별 기술 상호작용은 후순위로 문서에만 기록), 날씨 변화는 특성만(비바라기 같은 기술은 후순위), 트릭룸 등 공간 변화는 이번엔 문서 기록만.

### 6-1. 날씨 배경색 + 날씨 변화 특성 자동 발동

- `Ability.setsWeather?: WeatherKind` 필드 추가, 가뭄→쾌청/잔비→비/모래날림→모래바람 태깅
- `createBattleState`가 사용자가 날씨를 직접 안 골랐을 때 양쪽 특성을 확인해 배틀 시작과 동시에 날씨를 자동 적용 + `BattleState.entryAnnouncements`에 "○○의 ○○! 날씨가 ○○로 바뀌었다!" 안내 문구를 채운다(양쪽 다 날씨 특성이면 실효 스피드가 빠른 쪽이 우선 — 확인 필요 항목으로 남김)
- `BattleLogPage`의 `.battle-board`에 날씨가 강화하는 타입 색(비=물, 모래바람=바위, 눈=얼음, 쾌청=불꽃)을 낮은 불투명도로 배경 틴트, 배지로 "날씨: ○○" 표시

### 6-2. 필드(그래스/미스트/사이코/일렉트릭) 기본 지원 — 신규 스키마

- `types/field.ts`(`FieldKind`), `Move.setsField?: FieldKind` 추가. `moves.json`의 그래스필드/미스트필드/사이코필드에 태깅하고, **데이터 자체가 아예 없던 일렉트릭필드 기술을 새로 추가**(3개와 동일한 pp/effect 패턴, 타입 전기) — 단, 어떤 포켓몬 `learnset`에도 아직 안 넣었다(배울 수 있는 포켓몬이 확인 안 됨, 후순위)
- `lib/fieldEffects.ts`: 필드→데미지 배율(그래스/사이코/일렉트릭=해당 타입 1.3배, 미스트=드래곤 0.5배), 상태이상/혼란 면역(미스트=전부, 일렉트릭=잠듦만), 우선도 기술 차단(사이코, 우선도 +1 이상 기술 실패), 턴 종료 HP 회복(그래스, 최대 HP 1/16)
- `battleSimulator.ts`: `BattleState.field`/`fieldTurnsRemaining`(5턴, 새 필드가 덮어쓰면 재충전), `resolveAction`에 위 배율·면역·차단 판정 배선, `runTurn` 종료 시 그래스 회복 적용 + 카운트다운 + 0 되면 자동 해제. **버그 발견**: `runTurn`이 새 상태를 만들 때 `weather`만 복사하고 있어서(고치기 전) 필드를 추가했다면 턴마다 초기화되는 버그가 났을 것 — 필드 작업과 동시에 `field`/`fieldTurnsRemaining`/`entryAnnouncements`도 복사하도록 고쳤다
- UI: `.battle-board`에 필드 타입 색 틴트(날씨와 동시에 있으면 그라데이션), "필드: ○○ (앞으로 N턴)" 배지, 각 턴 로그에 필드 설치("○○ 설치!") · 지속 턴수 · 소멸 안내 · 그래스 회복 줄 추가
- 개별 기술 상호작용(그래스슬라이더 우선도, 대지의파동 타입변화, 비밀의힘 확률효과, 아이언롤러, 자연의힘, 미스트버스트/와이드포스/라이징볼트/사이코블레이드 위력 변화 등)은 이번 스코프 밖 — 각 기술이 실제 로스터에 있는지부터 확인 후 후속 작업으로 남김

### 6-3. 부수 발견 — 메가진화 특성이 전혀 반영되지 않던 버그 (버그, 이번에 같이 수정)

가뭄 자동 발동을 구현하다가 발견: `resolveAction`/`evaluateSlotMatchup` 둘 다 특성을 `slot.ability`(유저가 고른 값)로만 읽고 있어서, **메가진화 중에도 항상 메가폼 고유 특성(예: 메가리자몽Y=가뭄, 메가리자몽X=단단한발톱) 대신 메가진화 전 기본 특성이 적용되고 있었다** — 데미지 계산 전체에 영향을 주는 버그였다. `lib/pokemonForm.ts`에 `getEffectiveAbilityId(form, slotAbility)`를 추가해 메가면 `mega.ability`를 우선하도록 고치고, `battleSimulator.ts`(`BattleFighterState.effectiveAbilityId`)와 `matchupEvaluator.ts` 양쪽에 반영했다.

- **알려진 갭(이번엔 미수정)**: `AbilityPickerModal`은 여전히 `pokemon.abilities`(기본 특성 목록)만 보여줘서, 메가진화 중인 포켓몬에게 "지금 특성은 사실 고정된 메가 특성"이라는 걸 화면에서 알려주지 않는다. 계산은 이제 정확하지만, UI가 유저가 고른 값을 그대로 보여줘서 혼동의 여지가 있음 — 후속 작업으로 남김

### 6-4. 부수 요청 — 메가진화 배지에 X/Y 표시

리자몽처럼 메가진화가 2개 이상인 포켓몬은 "메가" 배지만으로 X인지 Y인지 알 수 없어서(지닌 도구를 봐야 알 수 있음) 불편하다는 피드백. `lib/pokemonForm.ts`에 `megaBadgeLabel(mega)`를 추가해 폼 이름 뒤쪽("메가X"/"메가Y")을 그대로 배지에 노출하도록 `PartySlotCard`·`MatchupSlotCard`·`BattleSetupCard`·`BattleLogPage` 4곳 전부 수정.

### 6-5. 후속 작업으로 남긴 것 (문서 기록만, 이번엔 미구현)

- **트릭룸(및 다른 공간 변화)**: `moves.json`에 있고 5마리가 배울 수 있는데 턴 순서 계산(`turnOrder.ts`)에 전혀 배선 안 돼 있음 — 사용자 확인: 이번 라운드는 문서 기록만, 구현은 다음 라운드로
- **날씨 변화 기술**(비바라기 등): 데이터는 있지만(`비바라기` 확인됨) 특성처럼 배틀 중 자동 적용되도록 배선 안 됨 — 특성 우선 처리로 확인, 기술 쪽은 후순위
- **일렉트릭필드 학습 포켓몬**: 기술 데이터는 추가했지만 어떤 포켓몬이 배우는지 확인 안 됨(원본 3개 필드는 이상해꽃/가디안/엘풍/카디나르마/누리레느/마스카나 6마리 확인됨)
- **필드 개별 기술 상호작용**: 6-2 마지막 항목 참고
- **그라운드코트**(필드 지속시간 5→8턴 도구): 4-2(도구 배율)와 같은 이유로 도구 데이터 구조화가 먼저 필요
