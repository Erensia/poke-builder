## 항목 메모

### M1. 기술 순서 변경 (계획만 — 세부는 착수 때 토의)
- **하려는 것**: 파티 편성 슬롯 카드의 기술 4칸을 길게 눌러(터치 300ms) 다른 기술 칸 위에서 떼면 두 기술의 자리가 바뀐다. 마우스는 HTML5 드래그앤드롭. 슬롯 순서 변경(PR #256)과 같은 방식.
- **현재 코드**: `PartySlotCard.tsx`의 `party-slot-moves`(기술 4칸, 칸마다 `onPickMove(index)`로 기술 선택 모달)와 `useParty.setMove(slotIndex, moveIndex, moveId)`. 순서 바꾸기 전용 동작은 없다. 슬롯 카드 전체가 이미 드래그 소스·드롭 타겟이라(`dragHandlers`) **기술 칸 드래그가 슬롯 드래그와 겹치지 않게 해야 한다**(`stopPropagation`·별도 MIME/타깃 식별자).
- **재료**: 길게 눌러 끌기 훅 `hooks/useLongPressDrag.ts`(타깃 판정 `findTarget`·`onDrop` 주입식) · 슬롯 순서 변경의 `data-party-slot` 패턴 → 기술 칸은 `data-move-slot="슬롯번호-칸번호"` 같은 식별자.
- **착수 때 정할 것**: ①같은 슬롯 안에서만 바꿀지(다른 슬롯 기술 칸과 교환은 막는 안이 자연스럽다) ②빈 기술 칸(null)과 맞바꾸기 허용 여부 ③같은 규칙을 배틀 설정 화면 카드(`BattleSetupCard`)·결정력 페이지(기술 1칸뿐이라 해당 없음)에 넣을지 ④기술 칸을 누르면 기술 고르기가 열리므로 짧은 탭/긴 누르기 구분(훅이 click 삼킴) ⑤순서 바꾸기가 배틀 AI·엔진에 영향이 없는지(기술 순서가 선택 우선순위에 쓰이는 곳 확인).
- **검증(예상)**: 교환 로직(`useParty`에 `swapMoves` 같은 함수)은 스크립트로 직접(빈 칸·같은 칸·범위), 화면은 사용자 위임(PC 드래그 + 모바일 길게 눌러 끌기).

### S1. 선택 팝업 검색창 위치 (계획만 — 세부는 착수 때 토의)
- **하려는 것**: 포켓몬 선택(`PokemonPickerModal`)·기술 선택(`MovePickerModal`) 팝업의 검색용 입력창(`.picker-search`)이 팝업 가장 위쪽에 나오게 한다.
- **현재 코드**: 입력창이 JSX 마지막(목록 뒤)에 있고 `position: sticky; bottom: 0`으로 하단에 붙어 있다. 기술 선택은 입력창 위에 타입·분류 필터(`move-picker-filters`)가 먼저 나온다. 같은 클래스를 `ItemPickerModal`도 쓴다.
- **왜 아래에 있었나(바꿀 때 알아둘 것)**: ver.1.6 §1-1에서 모달·프리셋 목록 등 다른 검색창과 위치를 통일하고 **엄지로 누르기 쉬운 화면 하단**에 두려고 상단에서 하단으로 옮긴 것이다(sticky가 "DOM상 뒤에 오는 형제"가 있어야 하단 고정이 돼서 JSX 순서도 바뀜). 이번 요청은 이 결정을 되돌리는 것이므로 모바일 키보드·엄지 접근성과의 균형을 화면에서 본다. 처음엔 상단 고정(sticky top)이라 목록을 스크롤해도 따라온다는 점이 중요 — 1.6 §2-1에서 "목록과 함께 흘러 매번 스크롤해야 했던" 문제가 있었다.
- **착수 때 정할 것**: ①같은 `.picker-search`를 쓰는 아이템 선택(`ItemPickerModal`)과 그 외 검색창(특성·성격 선택, 프리셋 모달 `.preset-search-input`, 도감 `.pokedex-search`)도 같이 옮겨 위치를 통일할지 ②기술 선택에서 필터(타입·분류)와 검색창의 순서(검색창이 맨 위, 그 아래 필터) ③상단 고정(sticky top)으로 스크롤해도 따라오게 할지 ④모바일 키보드가 올라올 때 목록이 가려지지 않는지.
- **검증(예상)**: 화면 위주(PC·모바일 폭), 사용자 위임.
