## V1 설계
- **원인 정리**: 7.6 — `dev` push(`71fcc3e`, 01:07:02Z) 36초 뒤 릴리스 PR 머지(01:07:38Z). 그 시각 `71fcc3e`의 Preview 빌드(01:07:24Z 시작, 약 16초)가 진행 중이었고 머지 커밋 `ca435a1`은 `71fcc3e`와 트리 해시가 같았다. Vercel 상태가 0개로 아예 안 만들어졌다. 7.5는 같은 트리의 `dev` Preview가 3일 전에 끝나 있어 Production이 20초 만에 생겼다. 4.0도 `dev`와 거의 동시에 올라간 경우였다. **추정이며 Vercel 쪽에서 확정한 것은 아니다.**
- **방법(권장)**: 저장소 루트에 `vercel.json`을 만들어 `dev`만 배포 대상에서 뺀다(현재 `vercel.json` 없음).
  ```json
  { "git": { "deploymentEnabled": { "dev": false } } }
  ```
  배포 자체를 안 만들어 PR에 "취소됨" 같은 상태도 찍히지 않는다. **Vercel 문서 기억에 의존한 설정이라, 적용 후 첫 `dev` push에서 실제로 배포가 안 뜨는지 확인해야 한다**(`gh api "repos/Erensia/poke-builder/deployments?per_page=2"`). 안 되면 대안은 프로젝트 설정의 Ignored Build Step(`VERCEL_GIT_COMMIT_REF`가 `dev`면 건너뜀)이다 — 이 경우 PR에 건너뜀 상태가 찍힐 수 있다.
- **feature 브랜치**는 이번 문제와 무관하니 그대로 둔다(`dev`만 끈다). `main`은 Production이므로 당연히 그대로다.
- **잃는 것**: `dev` 커밋의 Preview URL(핸드폰·집 PC에서 `dev`를 바로 열어 보기). 화면 확인은 localhost(`npm run dev`)로 한다.
- **릴리스 절차 변경**: V1이 적용되기 전까지는 릴리스 PR을 머지하기 전에 **`dev` 최신 커밋의 Preview 배포가 success인지 확인**한다(메모리 `vercel-production-deploy-check`). V1을 적용하고 한 번 검증한 뒤에는 이 확인이 필요 없다.
- **검증**: ① 적용 PR을 `dev`에 머지한 뒤 `dev` push에서 새 Preview 배포가 안 생기는지 ② 7.7 릴리스 PR 머지 직후 Production 배포가 20~60초 안에 생기는지. 둘 다 사용자 화면 확인 없이 `gh api`로 확인한다.
- **롤백**: `vercel.json` 한 줄 삭제.

## ② 후보 (사용자가 고른다)
7.6 마무리·7.5 마무리에서 남은 한계와 보류 항목이다.
- **상성표(공격) 이중 타입 방어 커버**(7.6 한계): 단일 타입 18개 기준이라 이중 타입 조합(171종)은 보지 않는다. 필요하면 요약을 "이중 타입 포함" 토글로 확장.
- **기술 타입 가변 반영**(7.6 한계): 노말스킨·프리즈스킨 같은 특성, 웨더볼·사이코 파워 등으로 바뀌는 타입과 고정 피해 기술의 특수 상성 처리. 엔진 `moveContext`의 타입 결정을 재사용해야 해서 크면 7.7이 아니라 보류.
- **접힘 상태 기억**(7.6 한계): 상성표 방어/공격의 펼침 상태를 브라우저에 저장. 필요가 생기면.
- **가로 잘림 패턴 점검**(7.5 한계): 고정폭 + 760px 전환점 패턴이 다른 페이지에도 있을 수 있다 — 761~890px 폭에서 가로로 잘리는 화면을 찾으면 같은 방식(전환점 920px)으로 고친다. `html, body`의 `overflow-x: hidden`은 그대로다.
- **P4 앱 아이콘 고해상도**: 고해상도 원본이 생기면(7.4에서 보류).
- **SP 새 샘플 파티**: 사용자가 txt를 주면 처리. 새 샘플이 생기면 `samplePartyTiers.json`에 임시 `"중"`을 넣고 등급을 잰다(`dev`가 `main`보다 앞서 있으면 `dev`에만 반영, 측정은 집 PC).
