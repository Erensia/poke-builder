## B1. 일렉트로빔 대전 로그 문구 수정

- 사용자 요청(2026-10-05): 일렉트로빔은 날씨가 비가 아닐 때 2턴을 쓰는 차지형 기술이다. 1턴째에 에너지를 모으며 자신의 특수공격이 1랭크 오른다.
- 현상: **특수공격이 오르는 1턴째의 로그가 출력되지 않고**, 능력치 스테이터스에만 반영된다. 로그 양을 줄이는 방법이긴 하나 진행된 턴의 내용 전달이 부족하다.
- 목표 출력(대전 로그):

  ```
  1턴째(사용한 턴)
  (포켓몬 이름)은(는) 전기를 모았다!
  (포켓몬 이름)의 특수공격이 올랐다!
  2턴째(사용한 다음 턴)
  (포켓몬 이름)의 일렉트로빔! — 데미지 xxx(퍼센트)
  ```

- 구현 지침: 문구의 **은(는) 조사는 기존 조사 처리 코드(`eunNeun` 등)를 재사용해 자동 선택**한다.
- 착수 시 확인: 날씨가 비일 때(1턴 발사)는 기존 동작 유지, 차지 문구가 다른 차지형 기술(솔라빔 등)의 1턴째 로그와 같은 경로를 쓰는지, 일렉트로빔 외 "차지 1턴째에 능력치가 오르는" 다른 기술에도 같은 로그 공백이 있는지 함께 점검.

## B2. 프리즈드라이 상성 버그 수정

- 사용자 보고(2026-10-05): 물/풀·물/비행·물/땅·물/드래곤 상대에게 프리즈드라이가 4배여야 하는데 2배만 들어가는 것 같다. 본가 상성: 2배 — 물·드래곤·땅·비행·풀 / 반감 — 강철·불꽃·얼음 / 나머지 1배.
- 확인(2026-10-05, 엔진 실행으로 재현): **상대에 물타입이 있으면 상성 전체를 2배로 고정**한다. 물이 아닌 다른 타입의 상성은 곱하지 않는다.

  | 상대 타입 | 엔진 | 본가 기준 |
  |---|---|---|
  | 물 | 2배 | 2배 |
  | 물/풀·물/비행·물/땅·물/드래곤 | 2배 | **4배** |
  | 물/불꽃·물/얼음·물/강철 | 2배 | **1배** |
  | 물/독·물/에스퍼 | 2배 | 2배 |

  물이 아닌 상대(풀 2배, 드래곤/땅 4배 등)는 정상.
- 원인: `src/lib/moveContext.ts`의 `typeEffectivenessOverride`가 `defenderTypes.includes(물)`이면 `effectiveness`(2)를 **전체 배율로 대체**한다. 데이터(`moves.json`의 `overridesTypeEffectivenessFor: { type: "물", effectiveness: 2 }`)는 "물타입 칸을 2배로 친다"는 뜻이라 그대로 두면 된다.
- 수정 방향: 상대 타입별로 곱하되 `overridesTypeEffectivenessFor.type`에 해당하는 칸만 `effectiveness`로 치환하고 나머지 타입은 타입표대로 곱한다. 면역 우선(저수 등 `absorbedByDefenderAbility`·`grantsImmunity`) 가드는 유지. 이 필드를 쓰는 곳이 `moveContext.ts` 한 곳뿐이라 배틀·결정력·AI가 같이 바로잡힐 것으로 보이나 착수 시 확인.
- 검증 방법: 위 표를 재현 스크립트로 돌려 전 케이스 일치 확인(+ `test:ai`).
- 실사용 정황(2026-10-05, B3 대조): 글레이시아 프리즈드라이 → 패리퍼(물/비행)를 스마트누오·포케챔스는 268~316, 앱은 130~154(약 2배 낮음). 앱 엔진으로 재현하면 `typeEffectiveness: 2`(4가 맞음). B3 참고.

## B3. 결정력&내구력 난수 데미지표 계산식 수정

- 사용자 질문(2026-10-05): 결정력&내구력 화면의 난수 데미지표가 다른 계산기와 다르다. 원인 파악 요청.
- **확정된 입력 조건(사용자, 2026-10-05)**: 공격측 글레이시아 / 방어측 패리퍼, 둘 다 능력포인트 0·성격 보정 없음(성실), 기술 프리즈드라이. 앞서 사용자가 값을 여러 번 정정해 **이 조건에서 다시 받은 값만 근거로 쓴다.**
- 외부 결과(사용자가 같은 조건으로 계산):
  - **스마트누오**: `268 ~ 316 (198.5% ~ 234.1%)`, 16개 값 `268, 268, 276, 276, 280, 280, 288, 288, 292, 292, 300, 300, 304, 304, 312, 316`, 확정 1타.
  - **포케챔스**: `198.5% ~ 234.1%` 확정 1타(스마트누오와 같은 값).
- 앱(`MatchupPage` → `DamageRollBlock`): `130 ~ 154 (97.0% ~ 114.1%)`, 16개 값 `130, 132, 133, 135, 137, 138, 140, 141, 143, 144, 146, 147, 149, 150, 152, 154`, 1타 격파 난수 13/16.
- (참고) 사용자가 처음 가져온 "유명 계산기" 값 `324 ~ 384 (240% ~ 284.4%)`은 이 조건의 값과 다르다 — 그 계산기의 입력 조건(도구·보정·규칙)이 달랐던 것으로 보이며 **근거에서 제외**한다. 포케챔스·스마트누오가 서로 일치한다.

### 원인(2026-10-05, 앱 엔진으로 같은 조건 재현해 확인)

앱 수치가 외부와 다른 이유는 **두 가지**다.

1. **프리즈드라이 상성 버그(B2) — 약 2배.** 패리퍼는 물/비행이라 프리즈드라이가 4배(물 2배 × 비행 2배)로 들어가야 하는데, 앱은 `typeEffectiveness: 2`로 계산한다(물타입이 있으면 상성 전체를 2배로 고정). 재현 확인: 글레이시아 SpA 150, 패리퍼 HP 135·SpD 90, 보정 1.5(자속)·상성 2.
2. **난수표 계산식 오차 — 약 −2.6%.** 난수표(`damageRollPercents` + `DamageRollBlock`)는 정수 공식을 쓰지 않고 연속식 `⌊상대 HP × 난수 ÷ ρ*⌋`로 계산한다(`ρ*`는 결정력·내구력 비율에서 거꾸로 푼 값). 기본 데미지 공식의 **"+2"와 단계별 내림이 빠진 형태**다.

### 검증: 게임 방식이 챔피언스 값과 16/16 일치

- 기본 데미지 `⌊⌊22×70×150÷90⌋÷50⌋+2 = 53` → **난수 곱하고 내림 → 자속 1.5배(0.5는 내림 쪽으로 반올림) → 상성 4배**의 순서로 단계마다 내리면 `268, 268, 276, 276, 280, 280, 288, 288, 292, 292, 300, 300, 304, 304, 312, 316` — **스마트누오와 16개 전부 일치**한다.
- 앱이 4배 상성만 고친 경우의 값(연속식): `261 … 308`(최대 −2.5%). 엔진 `computeDamage`식(보정을 모두 곱한 뒤 **한 번만 내림**)은 `270 … 318`(최대 +0.6%). **둘 다 16개가 안 맞는다.**
- 무작위 대조(2026-10-05, 4000쌍·특성·도구 없이 자속·상성만, 데미지 20 이상 45,354건): 앱 난수표는 게임 정수식보다 **평균 −3.72%**(전부 낮음), 최대 약 20.8%, 3% 초과 26,415건. 엔진 `computeDamage`는 평균 +0.30%, 최대 15.0%.
- 이 일치는 **X1의 가정("이 앱은 보정을 곱한 뒤 한 번만 내림 — 챔피언스 실제 방식 미확인")에 대한 첫 근거**다. 이 한 사례에서는 챔피언스가 **난수 → 자속 → 상성 단계별 내림**으로 보인다. 도구(생명의구슬)와 벽(빛의장막)은 상성 뒤 최종 단계, 급소·날씨는 기본 데미지 직후(난수 전) 단계로 확인(아래 추가 사례 ①~⑤). 특성은 공격 스탯 특성(선파워)만 한 표본, 나머지 특성은 미확인.

### 추가 사례 ① 도구: 생명의구슬 (사용자, 2026-10-05)

- 조건: 위와 같은 글레이시아 → 패리퍼에 **글레이시아가 생명의구슬을 지님**(그 외 동일).
- 스마트누오: `348 ~ 411 (257.8% ~ 304.4%)`, 16개 값 `348, 348, 359, 359, 364, 364, 374, 374, 380, 380, 390, 390, 395, 395, 406, 411`, 확정 1타. 포케챔스: `257.8% ~ 304.4%`(같은 값).
- 앱: `170 ~ 200 (126.1% ~ 148.3%)`, 확정 1타 — 값 `170, 172, 174, … 198, 200`(2씩 증가). 외부의 약 절반이고(348÷170 = 2.05, 411÷200 = 2.06) **원인은 같은 B2(상성 2배 고정)**다. 앱의 구슬 배율 자체(200÷154 = 1.2987 ≈ 1.3)는 맞다.
- **내림 위치 확정**: 기본 데미지 53 → 난수 곱해 내림 → 자속 1.5배 → 상성 4배 → **생명의구슬 ×5324/4096(≈1.3)을 맨 마지막에 곱하고 반올림(0.5는 내림 쪽)** 으로 계산하면 위 16개 값이 **전부 일치**한다. 비교한 다른 순서·내림 방식은 불일치:
  - 구슬을 난수 직후에 곱하고 내림: 불일치 / 구슬을 자속과 합쳐 곱함(1.5×1.3): 불일치 / ×5324÷4096 후 내림: 불일치(359·380 등 6곳이 1씩 낮음).
  - 1.3 곱하고 **반올림**도 일치하므로 두 방식(4096 기준 반올림 vs 1.3 반올림)은 이 사례로 못 가린다. 같은 도구에서 다른 값이 나오는 사례가 더 필요.
- 의미: **도구 배율(생명의구슬)은 상성 적용 뒤 "최종 보정" 단계**에서 곱해지고 거기서 반올림한다. 앱·엔진은 이 배율을 자속·상성과 한 값으로 합쳐 곱한 뒤 한 번만 내리므로, 이 보정이 있는 모든 계산이 같은 크기(약 1% 안쪽)로 어긋난다.

### 추가 사례 ② 벽: 빛의장막 (사용자, 2026-10-05)

- 조건: 구슬 사례를 뺀 **기본 조건**(글레이시아·패리퍼, 포인트 0, 성격 없음, 도구·특성 없음)에 **방어측(패리퍼)에 빛의장막** 설치.
- 스마트누오: `134 ~ 158 (99.3% ~ 117%)`, 16개 값 `134, 134, 138, 138, 140, 140, 144, 144, 146, 146, 150, 150, 152, 152, 156, 158`, 난수 1타(87.5% = 14/16). 포케챔스: `99.3% ~ 117.0%` 난수 1타 87.5%. 포챔스GG: `134 ~ 158 (99.2% ~ 117%)` 난수 1타 87.5%.
- 앱: `65 ~ 77 (48.5% ~ 57.0%)`, 2타 격파 난수 13/16. 외부의 약 절반(134÷65 = 2.06, 158÷77 = 2.05) — **원인은 같은 B2(상성 2배 고정)**. 앱은 벽 반감 자체(기본 사례 130~154의 절반)는 맞게 적용한다.
- **내림 위치 확정**: 벽 사례 값은 기본 사례(268 ~ 316)의 **정확히 절반**이다. 기본 데미지 53 → 난수 내림 → 자속 → 상성 4배 → **빛의장막 ×0.5를 그 뒤(최종 단계)에 곱**하면 16개가 **전부 일치**한다. 다른 위치는 불일치: 기본 데미지 반감(26·27 둘 다), 난수 직후 반감, 자속 직후 반감, 엔진식(전부 곱해 한 번 내림 — `135, 136, 138, 139, …`). 상성 4배 값이 4의 배수라 상성 뒤에서 반으로 나누면 내림·반올림 차이가 없다(이 사례로는 4096 기준 반올림과 구분 못 함).
- 결론: 도구(생명의구슬)에 이어 **벽도 상성 이후 최종 보정 단계**다. 앱은 벽을 내구력 쪽(`bulkMultiplier`)에 곱해 합치므로 이 단계 구분이 없다.
- 판정 표기 참고: 앱은 "2타 격파 난수 13/16", 외부는 "난수 1타 87.5%(14/16)". B2(상성)를 고치면 데미지가 맞아지며 같이 해결될 것으로 보이나 B3 수정 뒤 재확인.
