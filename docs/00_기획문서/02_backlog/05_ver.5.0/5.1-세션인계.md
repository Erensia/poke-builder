   `git log --oneline -5`에 `feat: 샘플 등급 측정을 쌍별 결과 저장 + 증분 측정으로 (5.1 A2 — 스크립트) (#323)`(`6d7883a`)과 `feat: 기본 샘플 파티 2개 추가 — 심화샘플 39개 풀 (5.1 SP)`(`26769f0`)이 보여야 한다.

3. 로컬 `localStorage`는 PC마다 따로다. 브라우저 확인이 필요하면 사용자에게 위임(아래 규칙).

## 작업 규칙 (CLAUDE.md가 우선, 요약)

- 브랜치 흐름 `dev` → 항목 브랜치 → PR(커밋 1개, squash) → `dev` → `main`(merge commit, PR 제목 `ver5.1`). **코드를 고칠 때만** 적용. `docs/**`만 고치면 브랜치·PR 없이 `dev`에 바로 커밋·push.
- 커밋 메시지는 한국어. 수정 요청이 오면 새 커밋을 얹지 말고 `git commit --amend` + `git push --force-with-lease`. `git add`는 **파일을 지정**한다.
- PR 머지는 사용자가 GitHub에서 직접 Squash and merge 하고 알려 준다. **정리(`git branch -D` + `git push origin --delete`)는 반드시 `gh pr view <번호> --json state`가 `MERGED`일 때만** — OPEN 상태에서 원격 브랜치를 지우면 PR이 닫힌다(5.1에서 한 번 실수했고 브랜치 복구 + `gh pr reopen`으로 되돌렸다).
- 병렬 측정은 프로세스당 300~450MB다. **측정 중에는 `src/`를 수정하지 않는다**(측정 프로세스가 모듈을 읽는다). 백그라운드 대기가 메모리 부족으로 종료될 수 있으니(알림이 오면 다시 시작하지 말고 사용자에게 보고) 대기는 가벼운 포그라운드 `until` 루프(10분 이내 단위)로 한다.
- Windows 경험: `python3`는 스토어 스텁이라 `python`(+`PYTHONUTF8=1`) 사용, 소스·문서 다수가 CRLF라 문자열 치환 전에 `\r\n`을 정규화하고 되돌릴 것.
- 브라우저가 필요한 확인(화면·모바일)은 사용자에게 위임, 로컬 브랜치를 먼저 전환해 둔다. `champions-party-sim.party.v1`·`...party-presets.v1`을 지우거나 덮어쓰라고 안내하지 않는다.

## 다음 할 일

### 1. A2 데이터 측정 → 데이터 PR

`rank-party-tiers.mjs`는 `scripts/sample-party-pairs.json`(쌍별 결과 표)에 없는 쌍만 측정한다. 지금은 표가 없어 **샘플 39개의 741쌍 전부**를 잰다(쌍당 시드 10 = 20판, 총 14,820판). 샘플 18·19(2026-10-22 SP로 추가, 등급 임시 "중")도 이때 정식 측정된다.

1. 여유 메모리를 확인하고(12병렬 ≈ 5.4GB) 개발 서버·무거운 앱을 닫는다. 코어 수에 맞춰 `--jobs`를 정한다(기본은 전체 코어).
2. `node scripts/rank-party-tiers.mjs 10 --jobs 12 > tiers.out` — 12코어 기준 약 2~2.5시간(5.0 실측: 시드 1·1190판이 12분). 20쌍 조각이 끝날 때마다 표에 저장되므로 중단돼도 **같은 명령**으로 이어서 돈다. 시드 수·`--params`가 저장된 표와 다르면 거부된다(처음부터 하려면 `--all`).
3. 끝나면 `tiers.out`의 파티별 승률 표를 확인한다(진행은 stderr). 등급 갱신은 `node scripts/rank-party-tiers.mjs 10 --write`(추가 측정 없이 집계 + `src/data/samplePartyTiers.json` 쓰기). 승률 순 위 1/3 상·아래 1/3 하(39개면 상 13·중 13·하 13). **"최상"은 이전에 최상이던 파티가 여전히 상일 때만 유지**하고 새로 만들지 않는다.
4. `git diff src/data/samplePartyTiers.json`으로 **등급이 바뀐 파티 목록을 사용자에게 보고**한다. 특히 샘플 16(`real-m7-new-rain`, 임시 "중") · 샘플 18(`real-m6-rank9`, 임시 "중") · 샘플 19(`real-m6-rank80`, 임시 "중") · 샘플 17(`real-mono-starmie-cycle`, 임시 "최상") · 최상 5개(`real-m6-rank2`·`real-cycle-zard-y`·`real-m5-rank3`·`real-fast-lucario-z`·`real-mono-starmie-cycle`). 최상 풀이 달라져야 하면 상등급 내부 라운드로빈(66쌍)을 따로 잰다(5.0 챔피언 최상 풀 방식, `5.0-backlog.md` R3 절).
5. 파일이 JSON이라 재직렬화 diff가 크지 않은지 확인한다(`git diff --stat` — 등급이 바뀐 줄만 나와야 한다).
6. 검증: `npm run test:rank-ai`(모든 샘플 등급 보유·최상 개수) · `npm run validate:data` · `npx tsc -b` · `npm run build`.
7. 데이터 PR 1개(브랜치 예 `feat/5.1-a2-tier-data`, 커밋 1개, `git add scripts/sample-party-pairs.json src/data/samplePartyTiers.json`)를 올린다. 커밋 메시지에 측정 조건(시드 10·AI `{}`·39개 741쌍)과 바뀐 등급 목록을 쓴다.
8. 머지 후 `5.1-backlog.md` A2에 결과(측정 시간·바뀐 등급·a편 승률)를 쓰고 `docs:` 커밋.

### 2. A4 (선택) 랭크 AI 측정 보강

5단 사다리(P0~P4)가 샘플 파티 조건에서도 단조 증가하는지 본다. **새 코드 없이** 기존 `h2h`로 한다. 결과가 나쁘면 AI 단계를 바꿀지는 측정 뒤 사용자와 따로 정한다(이 항목의 범위는 측정·판정까지).

- 단계 JSON: `src/lib/battle/ai/rankProfile.ts`의 `RANK_AI_PROFILES`와 `5.0-세션인계.md` "S2 사다리 재현"(`OFF`·`OM` 정의). P0 = L0(`OFF` + `mistake{rate:1,margin:1e9,hardOverride:true}`) · P1 = L1(rate 0.7) · P2 = L3(rate 0.3) · P3 = L4(`OFF`) · P4 = 앱 AI(`APP`).
- 샘플 파티 풀: `POOL=samples SEED_FROM=<1,26,…> node scripts/battle-ai-sim.mjs h2h 25 "<상위 JSON>" "<하위 JSON>"`을 8조각(시드 1,26,…,176)으로 나눠 병렬 실행하고 `res.aWins/bWins/other`를 합산(쌍당 400판, 무승부 제외 승률). 인접 4쌍(P1/P0, P2/P1, P3/P2, P4/P3)을 잰다. 합격선은 5.0과 같다 — 인접 55~65%이고, 완화 기준은 "단조 증가 + 양 끝 격차".
- 3선출 약화는 `selectvs`(인자 4·5번째 선출 옵션 JSON, 또는 `{"kind":"random"|"first"}`). `riskAversion` 고정은 `h2h`가 시드로 `risk`를 뽑아 코드(옵션) 추가가 필요하니 앞의 둘 결과를 보고 필요할 때만 한다.
- 결과는 `5.1-backlog.md` A4에 표로 기록하고 `docs:` 커밋.
