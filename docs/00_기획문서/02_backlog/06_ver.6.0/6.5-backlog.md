## ①-2 P1 PWA(서비스 워커)

**배경** — 서비스 워커를 넣으면 앱이 오프라인에서도 열리고, 오프라인에서 플레이·저장한 기록이 6.2 C2(온라인 복귀 자동 재시도)로 올라간다. **동기화는 깨지지 않는다** — 동기화는 Firebase SDK가 Firestore·인증 서버로 직접 보내는 요청이라, 서비스 워커가 가로채지 않으면 영향이 없다. 엔진·AI 출력에 영향이 없는 일반 기능이다.

**현황 정정(2026-11-02, 6.2 문서 대비)** — 6.2 P1의 고려사항 5(설치 가능성: manifest·아이콘 필요)는 **이미 갖춰져 있다**. `index.html`이 `/manifest.webmanifest`와 `apple-touch-icon.png`를 연결하고, 매니페스트에 이름·`display: standalone`·아이콘 192/512(`purpose: "any maskable"`)가 있다. 없는 것은 **서비스 워커뿐**이다(`src/`·`index.html`·`vite.config.*`·`package.json`에 서비스 워커 흔적 없음).

**고려할 사항** (`6.2-backlog.md` "①-4 P1"의 9가지를 그대로 옮기고 5번만 정정)
1. **캐시 범위**: 우리 정적 파일(HTML·JS·CSS·데이터 JSON·이미지)만 캐시한다. Firebase·Google 도메인 요청은 가로채지도 캐시하지도 않는다. 로그인 팝업/리다이렉트와 인증 헬퍼(`firebaseapp.com`)는 다른 도메인이라 대상이 아니다.
2. **새 버전 반영(가장 흔한 사고)**: 서비스 워커가 옛 앱을 계속 보여 주면 Vercel 배포 직후 사용자가 옛 버전에 머문다. 새 버전을 감지하면 안내하고 새로고침하게 하는 갱신 정책, 해시가 붙은 옛 번들 캐시 정리, 개발 서버(HMR)에서는 서비스 워커를 끄는 것을 정해야 한다.
3. **지연 로딩 청크**: Firebase SDK는 동적 import라 별도 청크다. 오프라인 시작에서도 로그인 상태 복원과 동기화가 되려면 이 청크도 미리 캐시해야 한다(C2의 `started=false` 경로).
4. **용량**: 포켓몬 데이터 JSON과 스프라이트 이미지를 얼마나 미리 캐시할지(개수·총 용량 실측). Cache Storage는 `localStorage`와 별개이고 브라우저가 용량 부족 때 비울 수 있다(5.5 G1의 `navigator.storage.persist()` 요청과 연결).
5. **설치 가능성**: ~~manifest·아이콘 필요~~ → **이미 있음**. 남은 확인은 아래 "확인할 점" ①②. iOS는 지원 범위가 제한적이다.
6. **구현 방법**: 직접 작성 vs `vite-plugin-pwa`(새 의존성). 필요한 것이 "정적 파일 캐시 + 갱신 안내" 정도라면 직접 작성이 더 작을 수 있어 `ponytail`로 비교한다.
7. **데이터 갱신**: 데이터 JSON이 바뀐 배포(밸런스 패치·샘플 추가)가 캐시 때문에 늦게 반영되지 않는지.
8. **Preview 도메인**: Vercel Preview URL에서도 서비스 워커가 등록된다. 로그인은 `localhost`와 Production에서만 확인한다는 기존 결정을 따른다.
9. **검증**: 브라우저가 필요하므로 사용자에게 위임한다(체크리스트 — DevTools Application 탭의 서비스 워커·Cache Storage, Offline 새로고침, 새 배포 후 갱신 안내, 로그인·동기화 회귀).

**확인할 점**
- ① 매니페스트의 `theme_color`·`background_color`가 라이트 색 하나(`#f4f2f9`)라서, `index.html`의 다크 모드용 `theme-color`(`#121121`)와 설치 앱에서 어긋나 보일 수 있다.
- ② 아이콘 하나에 `any maskable`을 같이 쓰면 마스크 때 잘릴 수 있어 안전 영역을 점검한다(`any`와 `maskable`을 별도 아이콘으로 나누는 방법도 있다).
- ③ DevTools Offline은 `localhost` 요청도 막아 새로고침이 안 된다(6.2 규칙). 오프라인 시작 검증은 서비스 워커를 넣은 뒤에야 가능하다.
- ④ 6.4 F1(프런티어 부분 병합)·S1과의 충돌은 없다(동기화·접근성 코드는 서비스 워커와 별개). 다만 서비스 워커가 새 배포를 늦게 반영하면 6.4에서 바뀐 화면도 늦게 보일 수 있다 — 갱신 정책 검증에 6.4 화면을 쓴다.

**절차**: 코드 변경이므로 feature 브랜치 → PR 커밋 1개 → `dev` squash. 서비스 워커는 한 번 설치되면 사용자 브라우저에 남아 되돌리기 어려우므로, 갱신 정책(고려사항 2)을 정하고 **자기 제거(unregister) 경로**까지 먼저 설계한 뒤 구현한다. 화면 확인은 사용자 위임이고, 해당 브랜치로 전환 → `npm run build && npm run preview`처럼 개발 서버(HMR)가 아닌 빌드 결과로 확인한다(서비스 워커는 개발 서버에서 끈다).

## 진행 결과
### C1 결정력 계산 조건 UI (PR #380, 2026-11-03)
- **환경 선택기(`EnvPicker`)**: 가로 헤더(날씨·필드·스크린·룸) → 고른 헤더의 알약 줄 → 적용 중 요약. 스크린은 내 쪽 → 상대 쪽 → 양쪽 → 해제 순환, 쪽은 알약 아래 막대의 좌·우 위치와 보라·파랑으로 구분(글자 배지는 구식이라 제외). 룸은 `ROOMS` 배열에 한 줄만 더하면 늘어난다. 헤더에 값 점, 선택기 틀은 스피드 행과 같은 유리 배경 + 보드와 같은 날씨·필드 색조.
- **페이지 정리**: 제목은 낭독용으로만 남기고 설명은 한 줄로, 탭 → 설명 → 환경 선택기 순서. 난수 데미지와 스피드 행을 `matchup-result` 카드 하나로 묶어 폭 `calc` 중복을 한 곳으로 모음.
- **카드 테두리**: 포켓몬 카드를 내 쪽 보라·상대 쪽 파랑(60% 불투명도, `color-mix`)으로 구분. 위치가 아니라 카드의 쪽(`MatchupSlotCard`의 `is-opp`, 역산 탭은 `dinf-defender`)을 따라 4개 탭 공통.
- **얻은 규칙**: ① 환경 선택기는 4개 탭이 공유하므로 보드(계산 탭에만 있음) 안으로 옮기지 않고 헤더에 두고 같은 색조를 입힌다. ② 내구 조정 탭의 상대 카드는 `role="attacker"`·`swapRole="defender"`라 쪽 구분은 `swapRole ?? role` 기준. ③ 켜진 알약(보라→파랑 배경) 안의 막대는 흰색, 요약 줄 막대만 60% 색. ④ 이 PC의 `python`은 스텁이라 ui-ux-pro-max 검색 스크립트가 안 돈다 — 데이터 CSV와 `references/quick-reference.md`를 직접 읽는다.
- **남은 후보(미착수)**: 환경 선택기를 보드 윗줄로 붙이는 안은 탭 공유 문제로 "헤더에 색조 입히기"로 대체함. 판정 배지를 결과 카드 안으로 합치는 안은 보류.
