# ver.6.0 백로그

**초안**(2026-10-29) — 6.0의 중심은 **K 계정 + 클라우드 백업(동기화)**: 저장 데이터가 브라우저 `localStorage`에만 있어 캐시 삭제·용량 확보로 사라지는 문제를 근본적으로 푼다. 5.5 G1(수동 백업)의 한계 ④("수동 백업이라 잊으면 소용없다")를 잇는 항목이다. 범위는 사용자가 정한다. 이전 버전: `../05_ver.5.0/5.5-backlog.md`(5.5 종료 — PR #347 `ver5.5`, Production 배포 sha `c7f58d9` = `main` 확인, "5.5 마무리"에 한계 전체).

6.0은 **메이저 버전**이라 작업이 끝나면 CLAUDE.md 규칙대로 `ponytail` 스킬로 **코드 전체 리팩토링**을 하고, 그 뒤 **엔진 로직 테스트와 기능 테스트**를 한다(K5). 항목별 브랜치 → PR 1개(커밋 1개) → `dev` squash, 마지막에 `dev` → `main` PR 제목 `ver6.0`(merge commit).

## 출발 상태 (2026-10-29)

- `dev` == `main` == `origin/*` (`c7f58d9`, `Merge pull request #347 from Erensia/dev`).
- 샘플 58개(심화 40·기초 18), 등급 상 20 / 중 20 / 하 18. 5.5와 같다.

## 논의 결과 (2026-10-29)

**서비스: Firebase(Firestore + Google 로그인)를 권고**한다. 무료 백엔드를 조사해 Supabase와 비교한 결과다.

| 기준 | 이 앱의 상황 | 유리한 쪽 |
|---|---|---|
| 데이터 형태 | 키 하나당 JSON 덩어리 하나. 관계형 쿼리 없음 | 동률 (SQL이 필요 없어 Supabase의 최대 장점이 안 쓰인다) |
| 사용 패턴 | 몇 주씩 안 열 수 있는 취미 앱 | **Firebase** — Supabase 무료 플랜은 7일 비활성이면 프로젝트가 자동 일시정지돼 ping 워크플로를 따로 운영해야 한다 |
| 서버 코드 | 없음 | 동률 (둘 다 브라우저 SDK로 직접 읽고 씀) |
| 로그인 | Google 하나면 충분 | 동률 |

- SQL이 필요한 요구(랭킹·통계 집계 등)가 생기면 Supabase가 낫다. 지금은 그런 계획이 없다.
- 제외한 후보: Neon·Turso(DB만 주고 인증이 없어 API 서버가 따로 필요), Cloudflare Workers + D1(Worker 코드·로그인을 직접 구성). PlanetScale은 2024-04 무료 티어를 없앴다 — 무료 티어는 사라질 수 있다.
- 조사 수치는 제3자 비교 글 기준이다. **착수 전에 Firebase 공식 요금 페이지로 Spark 한도를 확인한다**(K0).

**구조: 로컬 우선 + 클라우드 백업.** `load`가 동기라서 원격 DB를 원본으로 삼으면 호출부 전체를 async로 고쳐야 한다. 그래서 `localStorage`를 원본으로 그대로 두고, 로그인했을 때만 클라우드에 복사본을 올리고 받는다. 로그인 안 한 상태·오프라인에서도 지금처럼 동작한다.

## ① 작업 목록 (후보 — 범위는 사용자가 정한다)

### K0 착수 전 실측·확인 (코드 변경 없음)
- **키 목록과 크기**: `storage.ts`의 키 상수·`aiMemoryStoreOf` 키들, 그리고 `storage.ts`를 거치지 않고 `localStorage`를 직접 쓰는 곳(`App.tsx`의 하단 탭 표시 설정, `inferenceDraft.ts` 등)을 전수로 센다. 단일 통로가 전부는 아니다.
- **Firestore 문서 크기 제한(1MB)**: 키별 실제 저장 크기를 잰다. 특히 대전 영상(`battleVideos`)·AI 학습 기억이 클 수 있다. 넘으면 항목별 문서로 나눈다.
- **Spark 한도 공식 확인**: 일일 읽기·쓰기 횟수, 저장 용량. 디바운스 push 빈도를 여기에 맞춘다.
- **동기화 대상 결정**(사용자): G1 대상 둘(`party-presets`·`slot-presets`)에서 어디까지 넓힐지 — 내 샘플, 랭크·프런티어 기록, 대전 영상, AI 학습, 작업 중 파티(`party.v1`).

### K1 Firebase 프로젝트·보안 규칙·환경변수 (콘솔 작업은 사용자)
- Firebase 프로젝트 생성 → Authentication에서 Google 사용 → Firestore 생성 → Authorized domains에 `localhost`와 Vercel 도메인(Production·Preview) 등록.
- 보안 규칙: `users/{uid}/blobs/{key}`를 **본인만** 읽고 쓰게 한다. 키·크기·형태 검증을 규칙에도 둔다.
- `VITE_FIREBASE_*` 값을 로컬 `.env`와 Vercel 환경변수에 넣는다(웹 설정 값은 비밀이 아니고 보호는 규칙이 한다). 저장소에는 커밋하지 않는다.

### K2 로그인 + 설정 화면
- Google 로그인·로그아웃 버튼, 로그인 상태, 마지막 동기화 시각, "지금 동기화" 버튼. 새 UI는 기존 앱 스타일·CSS 변수에 맞추고 **호버에 의존하지 않는다**.
- Firebase SDK는 **동적 import로 지연 로딩**한다(로그인하지 않는 사용자는 번들 증가를 겪지 않게). 모듈식 API만 쓴다.
- 저장하는 개인정보는 `uid`뿐이다(이메일·이름은 저장하지 않는다).

### K3 동기화 계층
- `storage.ts`의 `save` 뒤에 로그인 상태면 **디바운스로 push**. 키 하나가 문서 하나(`users/{uid}/blobs/{key}`: `{ value, updatedAt, version }`).
- 로그인 직후 키별로 `updatedAt`을 비교해 pull한다. **충돌 정책은 "최신 우선 + 덮어쓰기 전 화면 안 확인"**으로 단순하게 간다(G1과 같은 방식 — 네이티브 `confirm` 금지, 기본 포커스는 안전한 쪽).
- pull한 값은 **믿을 수 없는 입력**이다. 기존 `guard`·`parseBackup`·`cleanSlot` 검증을 재사용한다.
- **작업 중 파티(`party.v1`)를 조용히 덮어쓰지 않는다**(과거 두 번 잃었다). 동기화 대상에 넣더라도 덮어쓰기 전 확인을 반드시 거친다.
- 로그아웃 시 로컬 데이터는 **지우지 않는다**(로그아웃이 삭제가 되면 안 된다).
- 오프라인·쓰기 실패는 조용히 재시도하고 화면에는 마지막 동기화 시각만 보여 준다.

### K4 검증
- `tsc -b`·`oxlint`·`build`·`test:ai`·`validate:data`·`test:sample`, 그리고 Firestore **보안 규칙 에뮬레이터 테스트**(본인 외 접근 거부·크기 초과 거부). 동기화 병합 로직(최신 우선·검증 실패 항목 건너뛰기)은 `battle-ai-scenarios.mjs`처럼 CLI 시나리오로 확인한다.
- 실제 로그인·두 기기 동기화·로그아웃 후 로컬 보존은 브라우저가 필요하므로 **사용자에게 위임**한다(체크리스트 제공). `party.v1`·`party-presets.v1`을 지우거나 덮어쓰라고 안내하지 않는다.
