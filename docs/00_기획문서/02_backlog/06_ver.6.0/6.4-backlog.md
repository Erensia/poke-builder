## ①-2 U1 모바일 랭크배틀 프로필 카드가 자리를 너무 차지한다 (사용자 제보 2026-11-02)

**증상** — 모바일(폭 358px)에서 연 랭크배틀 화면의 프로필 카드(`RankPanel`)에서 랭크 엠블럼(슈퍼볼 2) 주변 여백이 커서 카드가 약 280px 높이를 쓴다. 엠블럼이 혼자 한 줄에 놓이고 그 오른쪽이 텅 비며, 그 아래에 랭크명·전적·시즌·경고 문구·"종료하기" 버튼이 쌓인다. 그 밑의 파티 불러오기·샘플 파티 등 실제 작업 영역이 첫 화면에서 밀려난다. 데스크톱은 문제없다.

**원인 (코드 확인)**
1. `src/components/RankPanel.css`의 `.rank-profile`은 `display:flex; flex-wrap:wrap; gap:0.9rem`이고, 정보 영역 `.rank-info`가 `flex: 1 1 14rem`(기준 폭 224px)이다. 게이지 `.rank-gauge`는 `7.5rem`(120px)로 고정이다. 좁은 화면에서는 120px + 간격 14px + 224px = 358px가 카드 안쪽 폭(약 300px)보다 커서 **게이지가 줄바꿈으로 혼자 한 줄**을 차지한다. 이것이 "오른쪽이 빈다"는 느낌의 직접 원인이다.
2. 게이지 크기가 화면 폭과 무관하게 120px 고정이다(`@media` 없음). 같은 `RankGauge`를 승패 직후 `RankResultCard`가 5.5rem(88px)으로 쓰고 있어 5rem 안팎으로 줄여도 알아볼 수 있다는 근거는 이미 있다.
3. 카드 안의 부가 문구가 많다. `.rank-sub` 3줄(시즌 문구 "…(30일 시즌, 끝나면 자동 초기화)"가 모바일에서 두 줄로 꺾이고, 이탈 경고도 두 줄)이 모두 항상 노출된다. 카드 패딩(`0.7rem 0.9rem`)과 `gap`도 모바일에서 줄이지 않는다.
4. "종료하기" 버튼(`.battle-setup-load-party`)은 글자 `--fs-xs`·세로 패딩 `0.2rem`이라 높이가 약 18px이다. `tap-target`이 터치 기기에서 `::before`로 위아래 8px씩 판정을 넓혀 주지만 실제 판정 높이는 약 34px로, 모바일 지침(iOS 44pt·Android 48dp)에는 못 미친다(웹 WCAG 최소 24px는 넘는다).
5. 엠블럼 PNG(160×160)와 고리의 안쪽 여백이 얼마나 되는지는 **측정하지 못했다**(이 PC에 이미지 도구 없음). 그림상 왼쪽에 카드 글자보다 약 14px 더 들어가 보인다 — 확인 항목에 넣는다.

**디자인 근거 (`ui-ux-pro-max` 검색 결과, 2026-11-02)**
- Touch Spacing: 터치 대상 사이 간격 8px 이상.
- Touch Target Size: iOS 44pt·Android 48dp, 웹은 WCAG 최소 24px + 예외 — 지금 버튼은 웹 기준은 충족하나 모바일 권장에는 못 미친다.
- Text Reflow and Spacing: 폭이 좁아지거나 확대돼도 글이 잘리지 않아야 하고, 고정 폭·고정 높이 상자에 가두지 않는다(→ 게이지를 줄이되 문구는 `overflow:hidden`으로 자르지 않는다).
- Mobile First / Touch Friendly: 모바일 기준 스타일을 먼저 잡고 넓은 화면에서 키운다.
- 앱 내부 규칙: 새 UI는 기존 스타일·CSS 변수에 맞추고 **호버에 의존하지 않는다**(정보 아이콘은 이미 클릭으로 열리는 `InfoTooltip`을 쓴다 — 탭으로 열린다).

**권장 순서: A → (부족하면) B**. 높이 이득의 대부분(약 100px)은 줄바꿈 해소와 게이지 축소에서 나오고, 둘 다 CSS 몇 줄이다. A를 먼저 실기기로 보고 문구 줄이 아직 길면 B를 얹는다. C는 A·B를 해도 첫 화면 작업 영역이 모자랄 때만 한다. 높이 수치는 코드의 크기 값으로 계산한 **추정**이라 실기기 값으로 다시 쓴다.

**구현 메모 (A 기준)**
- 게이지는 `.rank-panel .rank-gauge`로 범위를 좁힌다 — `RankResultCard`의 5.5rem은 이 항목에서 건드리지 않는다.
- 고리 두께는 SVG 좌표(`viewBox 160`)라 게이지를 줄이면 같이 비례해서 줄어든다(7.5rem에서 약 16.5px → 5rem에서 약 11px). 눈금 4칸이 구별되는지 확인한다. 구별이 안 되면 게이지만 5.5rem으로 한다.
- `.rank-info`에 `min-width:0`을 주고 줄바꿈이 필요한 문구는 `overflow-wrap:anywhere` 없이 자연스럽게 꺾이게 한다(글자 잘림 금지).
- 터치 높이: 버튼 `min-height`는 `@media (pointer: coarse)` 안에서만 키우고, 아래 칩 줄(파티 불러오기 등)과의 간격은 8px 이상 유지한다.
- 이 PC에는 모바일 기기가 없어 `claude-in-chrome`을 직접 쓰지 않는다. 검증은 사용자 위임이다: 해당 브랜치로 전환 → `npm run dev` → 크롬 DevTools 장치 모드(폭 360·390·430) 또는 실기기.

**확인 항목 (화면 확인 체크리스트)**
1. 폭 360·390·430·768에서 게이지가 정보와 같은 줄에 있는가(줄바꿈으로 혼자 한 줄을 차지하지 않는가). 폭 320에서도 글이 잘리지 않는가.
2. 카드 높이가 제보 이미지(약 280px)보다 얼마나 줄었는가(실측값을 이 문서에 기록).
3. 랭크 3가지 상태(게이지 있는 몬스터~하이퍼, 게이지 없는 마스터볼, 챔피언)에서 엠블럼·눈금이 모두 보이는가. 승패 직후 `RankResultCard`가 그대로인가.
4. "종료하기"·"랭크 배틀 시작" 버튼이 엄지로 정확히 눌리는가(높이 40px 이상), 아래 칩 줄과 겹쳐 눌리지 않는가.
5. 데스크톱(폭 1024 이상)이 이전과 같은가.
6. 다크 모드에서 눈금·문구 대비가 유지되는가.
7. (미측정) `public/rank/*.png`의 투명 여백 — 알파 경계를 재서, 여백이 크면 이미지를 잘라 내는 쪽이 CSS보다 낫다.

### F1 프런티어 기록 부분 병합 — 메모
- **무엇이 합쳐지고 무엇이 안 합쳐지나**: 샘플별 전적(`samples`)은 마지막으로 맞춘 저장본(`cloud-sync.v1` 기준) 대비 **각 기기의 증가분을 더하면** 두 기기에서 플레이한 판이 사라지지 않는다. 현재 연승·`queue`는 판 순서에 달려 있고 판 시각이 없어 재현할 수 없다 — 한쪽을 채택(더 늦게 저장한 쪽)하거나 지금처럼 고르게 한다. 판 시각을 기록에 넣으면 C6처럼 재생 병합도 가능하지만 기록 형식이 바뀌고 `firestore.rules`·`test:rules` 영향을 따져야 한다 — 먼저 부분 병합만 한다.
- **안전장치**: C6와 같은 원칙 — "기준 + 그 쪽의 새 판만으로 그 쪽의 지금 상태가 재현되는가"를 먼저 검사하고, 아니면 선택 창으로 폴백한다. 테스트는 한 기기에서 순서대로 한 결과와 병합 결과의 전적 합계를 직접 비교한다(`test:sync`).
- **확인할 점**: 프런티어 시작·진행 중(`pendingId`) 상태는 동기화하지 않고 로컬 값을 유지한다(6.2 규칙 그대로).

### P1 PWA — 현황 정정과 메모
- **정정**: `6.2-backlog.md` P1의 고려사항 5(설치 가능성: manifest·아이콘 필요)는 **이미 갖춰져 있다** — `index.html`이 `/manifest.webmanifest`와 `apple-touch-icon.png`를 연결하고, 매니페스트에 이름·`display: standalone`·아이콘 192/512(`purpose: "any maskable"`)가 있다. 없는 것은 **서비스 워커뿐**이다.
- **확인할 점**: ① 매니페스트의 `theme_color`·`background_color`가 라이트 색 하나(`#f4f2f9`)라서, `index.html`의 다크 모드용 `theme-color`(`#121121`)와 설치 앱에서 어긋나 보일 수 있다. ② 아이콘 하나에 `any maskable`을 같이 쓰면 마스크 때 잘릴 수 있어 안전 영역을 점검한다. ③ DevTools Offline은 `localhost` 요청도 막아 새로고침이 안 되므로(6.2 규칙) 오프라인 시작 검증은 서비스 워커를 넣은 뒤에야 가능하다 — 검증은 사용자 위임.
- 나머지 고려사항 1~4·6~9(캐시 범위·갱신 정책·지연 청크·용량·구현 방법·데이터 갱신·Preview·검증)는 `6.2-backlog.md` 그대로 따른다.

### S1 알림 점 스크린리더 안내 — 메모
