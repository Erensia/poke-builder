## 2. 목표·비목표
- **목표**: ① 오프라인(비행기 모드·지하철)에서 앱이 열리고 파티 편성·계산·대전(AI 워커 포함)이 된다. ② 재방문이 빨라진다. ③ 오프라인에서 한 플레이·저장이 온라인 복귀 때 6.2 C2(자동 재시도)로 올라간다 — **동기화 자체는 건드리지 않는다**(Firebase SDK가 Firestore·인증 서버로 직접 보내는 요청은 서비스 워커가 가로채지 않으면 영향 없음).
- **비목표**: 푸시 알림, 백그라운드 동기화, 설치 유도 배너, 오프라인 최초 방문(캐시가 없으면 불가).

## 3. 구현 방식 — 직접 작성 (추천) vs `vite-plugin-pwa`
| | 직접 작성 | `vite-plugin-pwa` 2.0.0 |
|---|---|---|
| 새 의존성 | **없음** | `vite-plugin-pwa` + `workbox-build`·`workbox-window` 등 devDependencies 수십 개(빌드 시에만) |
| 코드량 | 서비스 워커 약 90줄 + 빌드 플러그인 약 30줄 + 등록 약 20줄 | 설정 약 20줄 |
| 필요한 기능 | 우리가 쓰는 건 "정적 파일 프리캐시 + HTML network-first + 갱신" 정도 | 프리캐시 매니페스트·정리·자기 파괴 모드 내장 |
| 위험 | 엣지 케이스(설치 원자성·Range·불투명 응답)를 직접 챙긴다 | Vite 8 공식 지원이나 워크박스 추상화를 따라가야 한다 |
| 결론 | `ponytail`: 라이브러리 없이 해결되는 크기. **직접 작성** | 직접 작성이 커지면 대안으로 남겨 둔다 |

- **빌드 플러그인**(`vite.config.ts`의 작은 플러그인): `generateBundle`에서 번들 파일 목록(해시 포함)과 `public/`의 프리캐시 대상 목록을 모아 `dist/sw.js`에 `PRECACHE`(경로 배열)와 `BUILD_ID`(번들 해시 합)를 박는다. 템플릿은 `src/sw/sw.js`.
- **등록**(`src/lib/registerSw.ts`, `main.tsx`에서 호출): 아래 §6.

## 4. 캐시 전략
| 대상 | 전략 | 이유 |
|---|---|---|
| `/`(`index.html`) | **network-first**, 3초 타임아웃 후 캐시 | 온라인이면 항상 최신 HTML → 최신 해시 자산을 가리킨다(옛 앱에 머무는 사고 방지의 핵심) |
| `assets/*`(해시 JS·CSS, 워커·Firebase 청크 포함) | **프리캐시**, cache-first | 해시가 바뀌면 파일명이 바뀌므로 안전. 합계 약 3.3MB |
| 매니페스트·아이콘·`favicon`·`rank/*` | 프리캐시, cache-first | 약 0.4MB |
| `/sprites/**` | **stale-while-revalidate**, 별도 캐시 `sprites-v1`(배포와 무관하게 유지) | 파일명이 고정이라 바뀌어도 갱신이 되어야 한다. 쓴 것부터 쌓인다(전체 2.1MB가 상한) |
| Google Fonts | stale-while-revalidate, 별도 캐시 `fonts-v1`(불투명 응답 허용) | 외부 도메인 |
| **그 밖의 모든 요청** | **가로채지 않는다** | Firebase·Google API·인증 헬퍼 `/__/auth/*`(같은 도메인일 때도)·비-GET·Range 요청 |
- 프리캐시 총량 약 **3.7MB**(스프라이트 제외). 설치는 **전부 성공해야 완료**(하나라도 실패하면 새 서비스 워커를 버리고 기존 것을 유지).
- 한글 경로는 `new URL(path, origin).href`로 정규화해 프리캐시 목록과 실제 요청 URL의 인코딩 차이를 없앤다.

## 5. 갱신 정책 (가장 위험한 부분)
1. **온라인 사용자는 서비스 워커 갱신을 기다리지 않는다.** HTML이 network-first라 새로고침하면 새 HTML이 온다. 새 HTML이 가리키는 새 해시 자산은 캐시에 없으면 네트워크로 받는다.
2. **서비스 워커 자체는 `skipWaiting()` + `clients.claim()`으로 바로 교체**하되, 캐시 이름을 `precache-<BUILD_ID>`로 두고 활성화 때 **"현재 + 직전" 2세대만 남기고 삭제**한다. 자산을 찾을 때는 `caches.match`(전 세대)로 찾는다. 이유: 열려 있던 옛 탭이 지연 로딩(Firebase 청크 등)을 뒤늦게 요청하면, Vercel은 최신 배포 자산만 서빙하므로 옛 해시 파일이 404일 수 있다 — 직전 세대 캐시가 그 요청을 받아 준다.
3. 새 버전 안내 토스트("새 버전이 있어요 — 새로고침")는 **이번엔 넣지 않는다**(자동 반영으로 충분. 필요하면 후속). `sw.js`는 브라우저가 기본으로 HTTP 캐시를 우회해 바이트 비교하므로 별도 헤더 설정(`vercel.json`)은 두지 않는다.
4. 데이터 JSON·샘플 변경은 번들 해시가 바뀌므로 정책 1·2가 그대로 적용된다(밸런스 패치가 캐시 때문에 늦게 반영되지 않는다).

## 6. 등록·자기 제거 (되돌릴 수 있게)
- **등록 조건**: `import.meta.env.PROD`이고 `'serviceWorker' in navigator`일 때 `load` 이후에 등록. **`npm run dev`(HMR)에서는 등록하지 않고, 이전에 남은 등록이 있으면 해제한다**(포트 5174를 preview로도 쓸 때 대비).
- **kill switch ① (배포 한 번으로 전원 제거)**: 빌드 환경변수 `VITE_PWA=off`이면 플러그인이 같은 경로(`/sw.js`)에 **자기 파괴 서비스 워커**를 낸다 — 활성화되면 모든 캐시를 지우고 스스로 `unregister()`한 뒤 열린 탭을 새로고침한다. 등록 코드도 건너뛰고 기존 등록을 해제한다. 브라우저가 24시간 안에 `sw.js`를 다시 확인하므로 재배포 후 대부분 제거된다.
- **kill switch ② (개별 긴급 수단)**: 주소에 `?sw=off`를 붙이면 `localStorage['sw-off']`를 켜고 등록 해제·캐시 삭제 후 새로고침한다(콘솔 스니펫으로도 안내).
- **kill switch ③**: DevTools → Application → Service Workers → Unregister, Storage → Clear site data(검증 체크리스트에 포함).

## 7. 알려진 함정과 결정
- **Preview 도메인**에도 서비스 워커가 등록된다. 허용한다. 로그인은 기존 결정대로 `localhost`와 Production에서만 확인한다.
- **용량**: 프리캐시 약 3.7MB + 스프라이트 최대 2.1MB. Cache Storage는 `localStorage`와 별개이고 브라우저가 부족할 때 비울 수 있다(5.5 G1의 `navigator.storage.persist()`와 연결). 캐시가 비면 서비스 워커는 네트워크로 폴백한다.
- **iOS**: 홈 화면에 추가해도 오래 안 쓰면(약 7일) 브라우저가 캐시를 정리한다. 안내만 하고 코드로 막지 않는다.
- **`aiWorker`**: ES 모듈 워커(`assets/aiWorker-*.js`)라 번들 파일 전부 대상인 프리캐시에 이미 들어간다.
- **매니페스트 확인점**(`6.5-backlog.md` ①②): `theme_color`가 라이트 한 값뿐이고 아이콘 하나에 `any maskable`을 같이 쓴다. 서비스 워커와 무관하므로 **이번 범위에서 제외**하고 별도 확인을 제안한다.

## 8. 구현 단계
한 PR(커밋 1개): ① 빌드 플러그인 + `src/sw/sw.js` ② `registerSw.ts` + `main.tsx` 호출 + kill switch ③ `VITE_PWA=off` 분기. 새 의존성 없음. 서비스 워커는 개발 서버에서 꺼 두므로 **확인은 `npm run build && npm run preview`**(HMR 서버가 아닌 빌드 결과)로 한다.

## 9. 검증 계획 (모두 사용자 위임 — 브라우저 필요)
1. `npm run build && npm run preview` → DevTools Application: 서비스 워커 `activated`, Cache Storage에 `precache-…`(약 3.7MB)·`sprites-v1`·`fonts-v1`이 보이는가.
2. **오프라인 시작**: Network → Offline 체크 후 새로고침 → 앱이 열리고 파티 편성·결정력 계산·대전(AI 워커 포함)이 되는가. (서비스 워커가 없으면 이 새로고침이 연결 오류가 나는 것이 현재 상태다.)
3. **새 배포 시뮬레이션**: 소스 한 줄을 바꿔 다시 빌드 → 같은 preview 탭 새로고침 → 새 버전이 보이고, Cache Storage에 직전 세대가 남아 있는가. 옛 탭에서 로그인(Firebase 지연 로딩)이 정상인가.
4. **로그인·동기화 회귀**(`localhost` 빌드): Google 로그인 팝업·Firestore 동기화가 그대로 되는가. 오프라인에서 한 변경이 온라인 복귀 후 올라가는가(6.2 C2).
5. **kill switch**: `?sw=off` → 등록·캐시가 지워지는가, `VITE_PWA=off` 빌드 → 기존 등록이 사라지는가.
