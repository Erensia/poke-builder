# 8.2 I2 — 프런티어 기록에 "판 시각" 넣기 (설계)

**작성 2026-11-10 — 설계 문서다. 구현은 사용자 결정 뒤.** 여기서 "판 시각"은 화면 효과가 아니라 **각 판이 끝난 시각(타임스탬프)**을 기록에 남긴다는 뜻이다.

## 1. 지금 문제
- 프런티어 저장본(`FrontierSave`, `src/lib/battleSeries.ts`)은 `streak`(현재 연승)·`best`·`samples`(샘플별 승/패)·`queue`·`pendingId`·`includeMine`뿐이고 **판 단위 기록이 없다**.
- 두 기기에서 따로 플레이한 뒤 합칠 때(`mergeFrontier`, `src/lib/cloudSyncPlan.ts:118`) 샘플별 전적은 "기준 저장본 대비 증가분"을 더해 정확하지만, **현재 연승은 어느 판이 나중인지 몰라 두 값 중 큰 쪽**을 쓴다(실제와 다를 수 있다 — 예: A기기 3연승 뒤 B기기에서 1패면 실제 연승 0인데 3으로 나온다).
- 대기열(`queue`)은 양쪽 모두 기준의 꼬리(`isTail`)일 때만 합치고(더 짧은 쪽), 아니면 선택 창으로 폴백한다.
- 랭크는 6.2 C6에서 판 기록(`history`, 각 판 `at`)을 기준 이후 판만 시각 순으로 **재생**해 해결했다. 프런티어도 같은 방식이 가능하다.

## 2. 핵심 발견 — `firestore.rules` 변경이 필요 없다
`firestore.rules`는 문서를 `{ json: 문자열, updatedAt: 정수, version: 1 }`로만 검사하고(`json.size() <= 900000`) **json 안의 필드는 보지 않는다**. 판 기록 필드를 추가해도 규칙 콘솔 게시가 필요 없고, `test:rules`도 영향이 없다. (8.0 백로그의 "규칙 영향" 우려는 기우였다.) 클라우드 문서 형식 `version`도 그대로 1.

## 3. 제안 설계
### 3-1 저장 형식 (하위 호환 추가)
```ts
interface FrontierGame { at: number; opponentId: string; won: boolean }   // 판이 끝난 시각 ms
FrontierSave { …기존…, games?: FrontierGame[] /* 최신이 앞, 최근 50판 */, pendingAt?: number | null }
```
- `games`·`pendingAt`은 **선택 필드**: 8.1 이전 저장본은 `games` 없음으로 읽고(`isFrontierSave`는 없어도 허용), 없으면 `[]`.
- `finishMatch`가 판 하나를 `games` 앞에 추가(상한 50, `HISTORY_LIMIT`와 같은 값). `beginMatch`는 `pendingAt = Date.now()`를 같이 저장하고, 이탈 정산(`settleAbandoned`)은 **앱을 다시 연 시각이 아니라 `pendingAt`을** 그 판의 `at`으로 쓴다(그래야 순서가 맞다).
- `canonical`(정규형)·`saveBattleFrontier`·백업 가져오기 검증(`isFrontierSave`)을 같이 맞춘다. `EMPTY_FRONTIER`는 `games: []`.

### 3-2 합치기 (`mergeFrontier`)
1. `gamesSince(B, X)`: 각 기기의 `games` 중 기준 `games`에 없는 판(키 `at|opponentId|won`)만 오래된 순으로. 기준 이후 새 판이 50판 이상이면 잘렸을 수 있어 null(랭크와 동일).
2. 두 기기의 새 판을 합쳐 `at` 순으로 정렬, 중복 키 제거(같은 판이 양쪽에 있을 때).
3. 기준 상태 `B`에서 `finishMatch`를 순서대로 다시 적용 → `streak`·`best`·`samples`·`queue`가 한 기기에서 순서대로 한 것처럼 재현된다. 재생 결과가 한쪽의 `samples`와 맞는지 확인하는 검증(랭크의 `stateKey` 비교)을 넣어 맞지 않으면(다른 변화가 끼었으면) null.
4. `queue`: 재생에서 만난 상대를 빼서 얻는다. 단 기기마다 무작위로 다시 섞은 큐가 달라졌거나(한 바퀴 완주) `isTail` 조건이 깨지면 기존처럼 null(선택 창).
5. `games`가 없는 쪽(8.1 이하 클라이언트가 쓴 문서)이 끼면 **기존 `mergeFrontier`(큰 연승·증가분 합산)로 폴백**한다. 새 형식은 구형 클라이언트가 저장하면 `games`를 잃을 수 있다 — PWA 업데이트 바로 두 기기가 곧 새 버전이 되므로 허용하되 한 줄 한계로 적는다.

### 3-3 UI
- 화면 변화는 필요 없다(연승이 정확해질 뿐). 선택 창 폴백이 줄어든다.

## 4. 테스트 (`test:sync` 확장)
- 시각 순 재생: A 3연승 → B 1패(이후 시각) ⇒ 병합 연승 0, 최고 3.
- 반대 순서(B 패 → A 3연승) ⇒ 연승 3.
- 같은 판이 양쪽에 있을 때 중복 제거, 50판 이상이면 null, `games` 없는 구형 문서는 기존 동작.
- 이탈 정산이 `pendingAt` 시각으로 기록되는지(`test:ai`/단위).
- `test:rules` 불필요(규칙 불변), 필요하면 형식 한 줄만 확인.

## 6. 결정할 것
1. 구현해도 되는가(위 3-1~3-2). 또는 지금처럼 "큰 연승" 근사를 유지(유지 사유: 두 기기 동시 플레이가 드묾).
2. `games` 상한을 랭크와 같은 50판으로 둘지.
3. 구형 클라이언트가 `games`를 잃는 한계를 허용할지.
