## 2-2. `ponytail-audit` 결과 (2026-11-09, 읽기 전용 스캔 + 본문 비교)
방법: `src/`·`scripts/`를 스캔(12줄 이하 소형 파일·재수출 전용 파일·같은 이름 함수의 중복 정의·직접 구현한 표준 기능·의존성 사용 여부)하고, 중복 후보는 본문을 정규화해 비교했다. 아래는 큰 컷 순. 형식: `<태그> 무엇을. 대체. [경로]`.
1. `shrink:` **추론 3종의 `emptyResult`·`prepareObservations`·`runCandidates` 삼중 구조**. 같은 골격(관측 준비 → 후보 전수 시험 → 결과 조립)이 `runCandidates` 본문 약 5천·8천·2천 자로 세 파일에 있다. 공통 러너로 합칠 수 있으나 본문이 **같지 않고**(공격·방어·스피드 규칙이 섞여 있다) `test:inference` 결합 해시를 지켜야 해서 **설계가 먼저** 필요하다 — 확정 컷이 아니라 후보. [`lib/attackInference.ts`·`defenseInference.ts`·`speedInference.ts`]
2. `shrink:` **`buildNatureCombos` 복사본 2개**(약 22줄 × 2). 공격(atk/spa)과 방어(def/spd)가 스탯 키 이름만 다르다. 스탯 키 쌍을 인자로 받는 함수 하나로 합친다(약 -20줄). `test:inference` 해시 불변으로 검증. [`lib/attackInference.ts`·`lib/defenseInference.ts`]
3. `shrink:` **`shuffled`(Fisher–Yates) 중복**. `battleSeries.ts`가 이미 `export`하는 같은 함수를 `randomSlotParty.ts`가 private로 다시 갖고 있다(본문 동일 — 이름만 다름). private 쪽을 지우고 import(약 -8줄). 난수 소비 순서가 같아 출력 불변. [`lib/randomSlotParty.ts`]
4. `shrink:` **`formTag` 중복**(7.6·7.7에서 내가 만든 것). `TypeAttackSummary.tsx`와 `TypeCoverageSummary.tsx`에 같은 "메가면 '메가'로 줄이기" 한 줄이 각각 있다. 한 곳에서 `export`해 공유(약 -4줄). [`components/TypeAttackSummary.tsx`·`TypeCoverageSummary.tsx`]
5. `native:` **`JSON.parse(JSON.stringify(x))` 2곳** → `structuredClone(x)`. 점검 스크립트뿐이라 효과는 미미(줄 수 같음). [`scripts/defense-inference-check/07-misc.mjs`·`scripts/rank-check.mjs`]
6. **확인했지만 자르지 않는 것**: `collectResult` 7개 파일(엔진·AI 각 단계의 마무리 함수로, 컨텍스트 타입이 달라 같은 코드가 아니다 — 제외 확정 영역) · `convolve`(`ai/hitsToKill.ts` ↔ `bulkAdjust.ts`, 본문이 다르고 앞쪽은 엔진 AI 보호 범위) · `standing`(`ai/partyEval.ts` ↔ `ai/search.ts`, 같은 사유).
7. **없음(깨끗)**: 소형 파일·재수출 전용 파일·직접 구현한 debounce/sleep/clamp/uniq/groupBy·미사용 `export`(0, R-A로 정리)·죽은 CSS(0)·없는 파일을 가리키는 npm 스크립트·안 쓰는 의존성(런타임 4개 전부 사용, 개발 의존성 8개는 각 `npm run`이 사용).
- **net: 약 -30줄(2·3·4번), -0 deps** (1번은 설계 결과에 따라). 작업은 4번이 가장 쉽고(5분), 2·3번은 `test:inference`·`regress 200`으로 검증한다.
- **보류한 점검**: `scripts/battle-ai-sim.mjs`(723줄, R5)·`useTurnFx`(R1)·큰 CSS(R2)의 내부 중복은 이번 스캔(이름 기반)으로는 잡히지 않았다 — 해당 항목의 설계 단계에서 따로 본다.

## 3. 중간 판단 (다음 세션에서 사용자와 확정)
- **7.0과 같은 결론이 더 강해졌다**: 안 쓰는 코드·CSS·의존성이 거의 없다. 8.0에서 줄 수가 줄 가능성은 낮고, 하는 일은 대부분 **구조 정리(읽기 쉬움)**다.
- **권고 순서**(효용 큰 순):
  1. ✅ **R-A 안 쓰는 `export` 6개 제거** — **완료(#443 `9553c6d`, 2026-11-09)**. `unused-exports.cjs` 재측정 0개.
  1-2. **R-B 중복 제거 3건**(위 2-2의 2·3·4번: `buildNatureCombos`·`shuffled`·`formTag`, 약 -30줄) — 작고 검증이 쉽다(`test:inference` 결합 해시·`regress 200`). R-A와 같은 방식으로 한 PR.
  2. **R1 `useTurnFx` 훅 분해** — 8.0에서 유일하게 읽기 쉬움 효과가 큰 후보. 연출 종류별 순수 함수(입력: 턴 결과 → 출력: 일정 목록)로 가르고 `fxhp 100` 불일치 0·`regress 200` 해시 불변을 유지한다. 위험: 연출 회귀 → **사용자 화면 확인(랭크 AI 대전, 메가진화·기절·교체·날씨)**이 필수.
  3. **R2 `BattleLogPage.css` 분할** — 이득은 탐색성뿐이고 시각 회귀 위험이 있다. 핵심 화면 체크리스트(F1)와 같이 할 때만.
  4. **R3·R4·R5**는 설계(상태 소유권·기술 구조·스크립트 옵션)를 먼저 써 보고 효용이 없으면 하지 않는다.
- **남은 R0 작업**: ① `ponytail-audit` 스킬 실행(같은 이름 형제 파일의 중복·과설계) ② R1~R5 항목별 설계(입출력·검증 방법·화면 체크리스트) ③ 사용자가 범위 선택.

## 3-2. 진행 기록과 항목별 결과 (2026-11-09 이후)
- **진행 순서(사용자 결정)**: R4 → R5 → R3 → R1-B → R2. 항목마다 한 PR(코드)이고, docs는 `dev`에 바로 반영한다.
- ✅ **R-B**(#444): `buildNatureCombos` 통합·`shuffled`·`formTag` 중복 제거. 순감 35줄, 해시 불변.
- ✅ **추론 진단 블록 통합**(#445): 3종의 `singleFeasible`·`culprits` 계산을 `diagnoseObservations` 하나로. 순감 8줄. `speedInference.buildCombos`는 그룹 id 형식(`"1.1"` ↔ `"1.1|1"`)이 달라져 합치지 않았다. `runCandidates` 본문은 규칙이 달라 합치지 않았다.
- ✅ **R1-A**(#446): `useTurnFx`의 연출 도구 18개와 연출 상수를 `turnFxPrimitives.ts`(`createFx`)로 분리. `useTurnFx.ts` 772→400줄. 본문 불변(들여쓰기만), `fxhp 100` 불일치 0, 화면 확인 완료. 훅에서만 쓰는 상수(`SETTLE`·`STATUS_HEX`·`MOVE_FX` 등)도 같은 파일에 있다 — 연출 상수는 한 파일 기준.
- ❎ **R4 하지 않음**: `useMatchupSlot`과 `useBattleSetupSlot`의 공통은 3줄짜리 세터 10여 개(특성·도구·성격·폼 순환·포인트)뿐이다. 합치려면 슬롯 타입을 제네릭으로 받는 팩토리가 필요하고(약 -25줄) 간접 참조가 늘어 읽기가 오히려 나빠진다. 기술·타수·가정 토글은 매치업 전용이라 공유 대상이 아니다. 슬롯 변경 규칙 자체는 이미 `slotMutations`로 공유 중이다.
- ❎ **R5 하지 않음**: 죽은 옵션이 없다(환경변수 17개·모드 10개 모두 문서화·사용 중 — `greedy`·`h2h`·`style`·`selectvs`·`partyvs`는 `bench.mjs`·`rank-*.mjs`가, `regress`·`logidx`·`fxhp`는 `verify.sh`가 호출). 앞쪽 약 230줄(`makeSlot`·`makeSide`·정책·`makeLearner`·`runBattle`)을 모든 모드가 클로저로 공유해, 모드별 파일로 나누면 컨텍스트 객체가 필요하고 줄 수는 줄지 않는다. 측정 모드(`h2h`·`style`·`greedy`)의 출력 비교가 모드마다 몇 분씩 걸려 검증 비용도 크다.
- ✅ **R3**(#447): AI 상태·호출을 `useBattleAi.ts`로(세션 451→388줄). 경로별 분리·선출 훅은 하지 않음. 화면 확인 완료.
- ✅ **R1-B**(#448): 일정 계산을 `turnFxSchedule.ts`로(`useTurnFx.ts` 400→293줄). 본문 불변, 화면 확인 완료.
- ✅ **R2**(#449): `BattleLogPage.css`를 연속 구간 4개로 분할. build CSS 번들 md5 동일로 검증(화면 확인 불필요).
