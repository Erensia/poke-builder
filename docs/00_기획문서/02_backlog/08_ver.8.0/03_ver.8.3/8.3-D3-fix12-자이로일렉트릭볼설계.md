## 1. 무엇이 다른가
### A. 입력 스피드 — 수정필요
| 효과 | Showdown `getStat('spe')`(위력 계산 입력) | 엔진 위력 입력 `powerSpeedOf`(`state.ts:673`) | 매치업 `effSpeed`(`matchupEvaluator.ts:373·389`) |
|---|---|---|---|
| 랭크 | `floor` 적용(fix-11 정수) | 소수 곱 | 소수 곱 |
| 구애스카프·검은철구 | ○ | ○ | ○ |
| 마비(체인 뒤 절삭)·속보(×1.5) | ○ | ○(소수 곱) | **×** |
| 날씨 특성(엽록소류)·서핑테일 | ○ | **×** | **×** |
| 곡예(도구 없음 ×2)·순풍 | ○ | **×** | **×** |
| 정수 절삭·4096 체인 | ○ | × | × |
예: 순풍을 받은 상대에게 일렉트릭볼을 쓰면 상대 스피드가 2배라 위력이 낮아져야 하는데 엔진은 반영하지 않는다. **자이로볼은 방향이 반대다** — 상대가 순풍이면 자이로볼 위력↑(일렉트릭볼↓), 내가 순풍이면 자이로볼↓(일렉트릭볼↑). 순서 판정용 `computeTurnOrderSpeed`(fix-11)는 이미 전부 반영하므로 **두 계산이 갈라져 있는 상태**다.
### B. 자이로볼 위력식 — 결정필요(Q1)
Showdown: `power = floor(25 × 상대 스피드 / 내 스피드) + 1`, 무한대(내 스피드 0)면 1, **상한 150**. 엔진(사용자 확정식): `min(150, max(1, floor(25 × (상대/나 + 1))))`, 내 스피드 0 이하면 150. **엔진이 항상 +24 높다(상한 150까지)**:
| 내 스피드 | 상대 스피드 | 엔진(확정식) | Showdown |
|---|---|---|---|
| 50 | 100 | 75 | 51 |
| 100 | 100 | 50 | 26 |
| 100 | 50 | 37 | 13 |
| 100 | 200 | 75 | 51 |
| 30 | 150 | 150 | 126 |
| 150 | 30 | 30 | 6 |
| 200 | 60 | 32 | 8 |
(직접 계산 확인, 2026-11-19.) 빠른 사용자일수록 차이가 크다 — 같은 스피드끼리 쓰면 50 vs 26으로 거의 2배 위력이다. 샘플 파티에 자이로볼이 든 파티가 1개 있고(`samplePartyPresets.json`) 매치업 화면·AI·공격·방어 역산이 이 식을 쓴다.
### C. 일렉트릭볼 — 식은 일치
Showdown `ratio = floor(내/상대)` → `[40,60,80,120,150][min(ratio,4)]`. 엔진은 소수 비율 임계(≥4 → 150, ≥3 → 120, ≥2 → 80, ≥1 → 60, 그 미만 40)라 **정수 입력에서는 같은 값**이다(`floor(r) ≥ k ⇔ r ≥ k`). 직접 비교: 50/100 → 40, 100/100 → 60, 299/100 → 80, 300/100 → 120, 400/100 → 150 모두 일치. 도달 불가한 경계만 다르다(상대 스피드 0: Showdown 40, 엔진 150 — 실능 스피드 최소가 31이라 불가능). → 식은 건드리지 않고 **입력만** 고친다.

## 3. 고칠 것
**3-1. 선행 리팩토링(출력 불변) — 스피드 배율 구성 공용화**: `computeTurnOrderSpeed`(엔진, `turnOrderInputs.ts`)와 `evaluateSpeedMatchup.speedOf`(매치업)가 각각 배율 목록(속보·서핑테일·도구·날씨 특성·곡예·순풍)을 조립한다. 여기에 위력 입력까지 같은 조립이 필요하므로 **한 함수**로 합친다: 새 파일 `src/lib/speedStat.ts`의 `computeSpeedWithEffects({ realSpe, stage, ability, item, status, weather, field, unburden, tailwind }) → number`(`battlePower.computeSpeedStat` + `speedStatusParts` + `getItemSpeedMultiplier` + 날씨·필드 배율). 엔진은 파이터에서 값을 모아 호출하고(`weather`는 `activeWeather(state)`로 날씨부정 반영된 값, `item`은 `effectiveHeldItem`), 매치업은 슬롯에서 모아 호출한다. **이 단계는 출력이 바뀌면 안 된다** — `regress`·`status60`·`test:inference`·차분 해시 전부 불변으로 증명.
**시그니처(검수 §2-2, 중요)**: 곡예는 Showdown에서 `!pokemon.item`(**실제 보유 여부**)이지 서투름·매직룸 반영값이 아니다(곡예가 켜진 채 도구를 되받았고 매직룸·서투름 중이면 도구를 "들고 있으므로" ×1). 그래서 `item`(스카프·철구용 **유효 도구** — `effectiveHeldItem`)과 곡예는 **분리**한다: 곡예는 호출 쪽이 계산한 `unburdenActive: boolean`(= 곡예 상태 ∧ 도구 없음 ∧ 특성 유효)을 받는다. 엔진은 `fighter.unburdenActive && !fighter.currentItemId`(fix-9), 매치업은 토글 값을 넘긴다. 입력 객체: `{ realSpe, stage, ability, item(유효 도구), status, weather(날씨부정 반영), field, unburdenActive, tailwind }`.
**범위 밖 효과(검수 §1-2)**: Champions M-C에서 Past인 고대활성·쿼크차지·Slow Start(Regigigas Past)·풀의서약(늪)·파워 계열·Macho Brace·Quick Powder·두꺼운우산·Embargo는 구현 범위 밖이다(도구 무효 사유는 서투름·매직룸 두 가지만). 날씨·필드 특성·곡예·속보는 틀깨기에 영향받지 않아 입력에 틀깨기를 넣지 않는다(Mega Sol도 스피드 계산과 무관).
**3-2. 엔진 위력 입력**: `state.ts`의 `gyroBallPowerValue`·`electroBallPowerValue`·`powerSpeedOf`를 삭제하고(`state.ts`가 `turnOrderInputs`를 부르면 import 순환) `preHitEffects.ts`에서 `gyroBallPowerFromSpeeds(computeTurnOrderSpeed(c.state, c.attacker), computeTurnOrderSpeed(c.state, c.defender))` / `electroBallPowerFromSpeeds(…)`로 바꾼다. `computeTurnOrderSpeed`가 `effectiveHeldItem`(서투름·매직룸)을 쓰므로 `c.attackerItem`을 넘기던 의미와 같다. 트릭룸은 `computeTurnOrderSpeed`에 없어 위력에 영향이 없다(Showdown과 같음).
**시점(검수 §2-5)**: 위력 입력은 **기술이 맞는 시점의 상태로 다시 계산**한다 — 턴 시작에 순서 결정용으로 저장한 값(`RunTurnContext.speedA`·`speedB`·`TurnOrderActor.speed`)은 **재사용하지 않는다**. Showdown은 `basePowerCallback` 시점에 `getStat('spe')`를 부르므로 같은 턴 앞선 행동의 순풍·얼어붙은바람(스피드 −1)·마비·도구 탈취가 위력에 반영된다. 매치업·AI는 정적 평가라 이 조건은 해당 없다(AI 평가는 호출 시점의 현재 state를 읽는 기존 정책 그대로). 시험 16이 엔진 쪽을 고정한다.
**3-3. 매치업·AI·화면**: 위력 분기의 `effSpeed`를 `computeSpeedWithEffects`로 교체한다. 입력: 공격·방어 슬롯의 `c.attackerRealStats`(런타임 값)·`c.attackerStages`·능력·도구(`c.attackerItem`, AI 런타임 반영)·`c.weather`(날씨부정 시 무시)·`c.field`·**상태이상**(옵션 `attackerStatus`·`defenderStatus` — 이미 있음)·**곡예·순풍**. 곡예·순풍은 매치업 데미지 옵션에 없으므로 **`attackerTailwind`·`defenderTailwind`·`attackerUnburden`·`defenderUnburden`(기본 꺼짐)을 추가**하고, 화면 `MatchupPage.tsx`는 기존 속도 판정용 토글을 데미지 옵션에도 넘기며, AI(`moveDamage.ts:369`)는 실제 state의 순풍(`tailwindTurnsRemaining`)·곡예 플래그·양쪽 상태이상을 넘긴다(Q3·Q4).
**3-4. 위력식**: 이 PR에서는 **바꾸지 않는다**. Q1 답에 따라 **Q1 결정: (나) — fix-13에서 구현한다. 아래 (가) 유지 경로(오차 14쌍·Q6)는 쓰지 않는다.** (가) 유지 — 코드 변경 없음, 주석에 근거 한 줄 보강. 단 **현행 식 `25*(t/p+1)`은 부동소수 오차로 정수 계산 `floor(25*(t+p)/p)`와 14쌍(실능 스피드 31~213)에서 1 다르다**(예: 상대 126·나 35 → 현행 114, 정수 115, 검수 §2-1) — 알면서 두거나 (가) 확정 시 정수식으로 교체(Q6, 기준값 영향 극소) / (나) Showdown식으로 변경 — fix-13에서 `gyroBallPowerFromSpeeds`를 **`Math.floor(25 * t / p) + 1`(소스와 같은 연산 순서 — 곱 먼저)** 그대로 구현한다(`25 * (t/p)` 순서로 쓰면 31~213 전 쌍 중 13쌍이 틀린다, 예: 상대 161·나 35 → 115, Showdown 116). 나 0이면 1, 상한 150. 참조 구현도 같은 순서. 그 주석·`phase7.5-plan.md`의 식·기술 설명문 점검·기준값 갱신.
**3-5. 하지 않는 것**: 일렉트릭볼 식(일치), 트릭룸·`TurnOrderActor`(fix-11에서 끝), 속임수·기어오르기 등 다른 가변 위력, 역산 알고리즘 본체.

## 4. 규칙표(시험의 기대값) — 입력을 검증하므로 위력식과 무관하게 쓴다
시험은 기대값을 **`참조 스피드`(Showdown 식을 옮긴 fix-11 참조 구현)를 `gyroBallPowerFromSpeeds`/`electroBallPowerFromSpeeds`에 넣은 값**으로 정한다. 이러면 Q1 결정에 영향받지 않는다.
| 상황 | 기대 입력 |
|---|---|
| 순풍을 받은 상대 | 상대 스피드 ×2(정수 체인) |
| 날씨 특성(엽록소 + 쾌청)·서핑테일(일렉트릭필드) | ×2, 날씨부정 시 날씨 특성 무시 |
| 곡예 + 도구 없음 | ×2, 도구 되받으면 ×1 |
| 마비 / 속보 + 상태이상 | 체인 뒤 `floor(×50/100)` / ×1.5 |
| 랭크 | `floor` 적용 후 체인(fix-11과 같은 함수) |
| 매직룸·서투름 | 도구 효과 없음(스카프 무시) — `effectiveHeldItem` |
| 일렉트릭볼 | 입력 스피드로 비율표 — 예: 내 100·상대 50 → 80, 상대 순풍(100) → 60 |
