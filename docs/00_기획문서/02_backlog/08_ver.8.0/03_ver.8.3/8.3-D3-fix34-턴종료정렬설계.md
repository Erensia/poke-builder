## 1. Showdown이 하는 일 (소스 직접 대조)

1. **한 목록**: `runAction('residual')`은 먼저 `updateSpeed()`로 모든 포켓몬의 스피드를 **다시 계산**(2854행, 트릭룸이면 `10000 − 스피드`로 반전 — `pokemon.ts` 663~667행)하고, `fieldEvent('Residual')`이 필드·편·포켓몬의 residual 핸들러를 **전부 한 배열**에 모은다(484~533행).
2. **정렬**: `speedSort(handlers)` — 비교는 `comparePriority`(409~416행): **`order` → `priority` → `speed` → `subOrder` → `effectOrder`**. `order`가 작은 효과가 먼저고, 같은 order 안에서는 **스피드가 빠른 포켓몬의 효과가 먼저**(그 포켓몬의 같은 order 효과는 subOrder 순), subOrder는 "같은 스피드(= 같은 포켓몬)" 안에서만 쓰인다.
3. **동률은 난수**: `speedSort`는 비교가 0인 항목들을 `this.prng.shuffle`로 섞는다(434~465행, 460~462행). 스피드가 같은 두 포켓몬, 그리고 **스피드가 없는 편·자리(slot) 핸들러끼리**(`speed` 미설정 = 0)가 같은 order에 있으면 무작위다.
4. **subOrder 기본값**: `resolvePriority`(957~1020행)가 효과 종류로 채운다 — 상태·휘발성(Condition) 2, 자리 효과 3, 편 효과 4, 필드·날씨 5, 특성 7, 도구 8(효과가 직접 정한 값이 우선: 먹다남은음식 5/4, 탈피·젖은접시류 5/3, 그래스필드 5/2, 가속류 28/2, 화염구슬류 28/3).
5. **핸들러마다 정산**: 핸들러 하나를 실행할 때마다 `resolveFaints(); if (this.ended) return;`(574~575행) — 전멸이면 그 자리에서 끝(PR #533이 이미 구현). **기절한 포켓몬의 핸들러는 건너뛴다**(545~549행), 단 자리 효과(미래예지·희망사항)는 건너뛰지 않는다.
6. **날씨**: 날씨는 order 1의 **필드 핸들러**(`onFieldResidualOrder: 1`) 하나이고, 그 안에서 `eachEvent('Weather')`가 포켓몬별 `onWeather`를 **스피드순**으로 돌린다 — 모래바람 피해와 날씨 관련 특성(젖은접시·건조피부)은 포켓몬 단위로 묶여 빠른 쪽부터 처리된다.

## 2. 지금 엔진 (코드 확인)

`finishTurn.ts`의 `resolveEndOfTurnAndPerish`(938행~)는 단계마다 `eotOrder()` = `["a","b"]` 고정으로 돈다.

| 단계 | 엔진 | 순서 단위 |
|---|---|---|
| ① 날씨 지속 감소·종료 | `expireWeather`(호출부) | 필드 |
| ② 날씨 피해·특성 | `eachFighter(…)`를 효과 3개 순서로(모래바람 → 젖은접시류 → 건조피부류), 각각 a→b | **효과 우선**(a, b 번갈아) |
| ③ 미래예지·희망사항 | `for key: 미래예지 → 희망사항` | 포켓몬 우선(a: 미래예지·희망사항, b: 미래예지·희망사항) |
| ④ 개별 효과 15개 | `for key: EOT_INDIVIDUAL_STEPS 전부` | **포켓몬 우선**(a의 효과를 다 끝낸 뒤 b) |
| ⑤ 멸망의노래·가속류·열매 재확인 | `for key: …` | 포켓몬 우선 |
| (후) 필드·방·벽 지속 감소 | `expireFieldAndWeather`·`expireSideEffects` | 필드·편 |

**결과가 달라지는 구체적 사례**(Showdown ↔ 엔진):
- **A. 효과 간 끼어들기**: a와 b가 모두 먹다남은음식(5)·씨뿌리기(8)를 가질 때 Showdown은 `b 먹다남은음식` → `a 씨뿌리기 흡수`(둘 다 order 5가 먼저 끝난 뒤 8). 엔진은 `a 먹다남은음식 → a 씨뿌리기 → b 먹다남은음식 → b …`이라 b의 회복이 a의 흡수 뒤로 밀린다. HP 경계에서 흡수량(실제 준 피해)이 달라진다.
- **B. 서로 다른 order에서 쓰러짐**: a에 화상(10), b에 독(9)이 걸리고 둘 다 HP 1이면 Showdown은 `독(9)` 먼저 → b 기절 → 끝(a 승). 엔진은 a의 모든 효과를 먼저 → a의 화상으로 a 기절 → b 승. **승자가 반대다.**
- **C. 같은 order, a가 느린 경우(PR #533 한계)**: 둘 다 독(9)으로 쓰러질 처지면 Showdown은 **빠른 쪽이 먼저 쓰러져** 진다. 엔진은 a가 먼저 처리돼 a가 진다 — a가 빠르면 같고 **a가 느리면 반대**다.
- **D. 스피드는 턴 시작이 아니라 residual 직전 값**: 이번 턴 행동으로 랭크·마비가 바뀐 경우 순서도 바뀐다(`FinishCtx.speedA/B`는 턴 시작 값이라 쓸 수 없다).

빈도(E6 문서 §3-1, 2만 판·60.9만 턴): 양쪽 모두 HP를 바꾸는 효과가 있는 턴 **1.90%**, 그중 누군가 기절하는 턴 **0.067%(409턴)** — 승패가 달라질 수 있는 상한. **그러나 로그 줄 순서는 양쪽 효과가 있는 턴(2.32%)마다 바뀌어** `regress` 해시는 전부 바뀐다.

## 4. 새 구조

### 4-1. 핸들러 표와 실행기

`finishTurn.ts`에 효과 하나 = 한 줄의 표를 둔다(지금 `EOT_INDIVIDUAL_STEPS`의 확장):

```ts
interface EotHandler {
  order: number;          // Showdown onResidualOrder(§3)
  sub?: number;           // onResidualSubOrder, 없으면 0 — 같은 포켓몬의 같은 order 안에서만 비교된다
  slot?: true;            // 자리(편) 효과 — 기절한 포켓몬도 처리하고 포켓몬 스피드가 아니라 §5 Q1 규칙을 쓴다
  when?: (f: BattleFighterState) => boolean; // 목록을 만들 때의 적용 조건(상태이상 9/10 분기용 order 함수 등)
  run: (ctx: EndOfTurnFighterContext) => void;
}
```
- 표는 **모듈 상수**(`EOT_HANDLERS`). 위 §3의 한 행이 한 줄이고, `tickBlockVolatiles`·`applyStatusEndOfTurnTick`처럼 order가 상태에 따라 갈리는 것만 `orderOf(fighter)` 함수를 쓴다.
- **실행기** `runEndOfTurnHandlers(c)`:
  1. 스피드 순서를 **한 번** 정한다: 두 포켓몬이 모두 살아 있으면 `orderBySpeed(c.state, c.random, ["a","b"])`(= 빠른 쪽 먼저, 트릭룸이면 느린 쪽 먼저, 완전 동속은 난수 — 턴 순서와 같은 함수·같은 결정 2026-11-19 E3-13). 한쪽이 이미 기절했으면 `["a","b"]`(순서가 의미 없음). **스피드는 `computeTurnOrderSpeed`로 지금 상태에서 계산하므로 residual 직전 값이다**(Showdown `updateSpeed`와 같다). 난수는 두 포켓몬이 모두 살아 있고 스피드가 정확히 같을 때만 소비된다.
  2. `(핸들러 × key)` 쌍을 모아 `(order, 순위, sub, 표의 위치)`로 정렬한다. 순위 = 위 순서에서의 인덱스. **자리 효과**는 순위 대신 §5 Q1의 순서를 쓴다.
  3. 쌍을 차례로 실행한다: `slot`이 아니고 holder가 기절했으면 건너뛰고, 실행 전에 `makeEotCtx`로 **컨텍스트를 새로 만들고**(도구·HP·상대 기절 여부가 앞 핸들러 결과를 반영 — §5 Q3), 실행 뒤 **`endIfWiped(c, opponentKey(key))`**로 전멸을 확인한다(PR #533). 전멸이면 중단.
- `eachFighter`·③ 루프·④ 루프·⑤ 루프·`eotOrder()`는 **삭제**하고 이 실행기 하나가 대신한다.

### 4-2. 상태에 따라 order가 갈리는 효과
- `applyStatusEndOfTurnTick`: 목록을 만들 때 `fighter.status.condition === "burn"`이면 10, 아니면 9. 앞 핸들러(탈피 5/3)가 상태를 치료해도 함수가 `!fighter.status.condition`이면 곧바로 돌아오므로 안전하다(order는 만들 때만 정한다 — 중간에 새 상태가 걸리는 경우는 이 구간에 없다).
- 아쿠아링(6)·뿌리박기(7): 지금 한 함수 안의 `for regenSource of ["aquaRing","ingrain"]`를 **함수 두 개**로 나눈다(`applyAquaRingHeal`·`applyIngrainHeal`, 본문은 PR #532 그대로, `healBlock` 검사 포함). 각 핸들러가 자기 `regenSource`만 처리.

### 4-3. 같은 포켓몬 안의 현재 순서 보존
같은 포켓몬 안에서 지금 순서(탈피 → 먹다남은음식 → …)는 위 표의 `order/sub`로 **그대로 재현된다**(`[소스]` 값이 현행 순서와 같다 — A1이 맞춰 둠). 표 안에서 동률인 쌍은 **표의 위치 순서**로 고정한다: 속박(13) → 소금절이(13), 물엿범벅(14) → 문어굳히기(14). Showdown은 이 동률을 난수로 정하지만 두 효과 모두 같은 포켓몬에 대한 **피해**라 합이 같고 기절 시점만 다를 수 있어 영향이 극히 작다(§5 Q2).

### 4-4. 자리(편) 효과(미래예지·희망사항) 순서
Showdown은 두 편의 자리 핸들러가 둘 다 스피드가 없어(0) **동률 → 난수**다. 엔진은 지금 a→b 고정. 새 구조: 자리 핸들러마다 **양쪽 편에 그 효과가 대기 중일 때만** `random() < 0.5`로 순서를 정하고(난수 1회), 한쪽에만 있으면 그쪽만 처리한다. 대기 중인 효과 수가 0이면 난수를 쓰지 않는다. **미래예지가 대기하는 턴 + 희망사항이 대기하는 턴이 양쪽 동시**인 경우는 드물어 해시에 미치는 영향은 작다.

### 4-5. F-4(멸망의노래 동시 기절 승부) 블록 삭제
- 지금: 양쪽 카운트가 동시에 0이 되면 `decideWinnerAndForcedSwitch`가 스피드가 느린 쪽(동속이면 a)을 승자로 정한다(`perishFaintedKeys`·`c.speedA/B`).
- 새 구조: 멸망의노래(24)가 스피드 순서로 처리되므로 **빠른 쪽이 먼저 쓰러지고 전멸이면 그 즉시 느린 쪽이 승자**(PR #533의 `endIfWiped`) — 같은 결과. 예비가 있으면 둘 다 쓰러져 강제 교체. 동속은 난수(Showdown).
- 따라서 `applyPerishSongCountdown`의 boolean 반환·`c.perishFaintedKeys`·`c.speedA/B`·F-4 블록을 삭제한다(**동속일 때 승자만 "a 고정" → "난수"로 바뀐다** — 이 PR에서 동속 멸망의노래 동시 기절 시험이 있으면 갱신).

### 4-6. 날씨(②)
날씨 효과도 같은 표에 order 1로 넣는다(모래 → 젖은접시류 → 건조피부류가 포켓몬 안에서 이 순서, 빠른 포켓몬이 먼저). Showdown도 날씨는 `eachEvent('Weather')`로 **포켓몬 단위**라 같다. 지금 엔진은 효과 우선(모래 a·b → 젖은접시 a·b → …)이라 로그 순서와, 한 효과가 포켓몬을 쓰러뜨리는 순서가 달라질 수 있다.

### 4-7. 바꾸지 않는 것
- A1의 ①(날씨 지속 감소가 맨 앞)·②의 효과 내용·희망사항 회복 0 로그·먹다남은음식 1/6(사용자 확정 값) 등 규칙 값.
- `expireFieldAndWeather`·`expireSideEffects`·`settleFutureSightReactions`·`decideWinnerAndForcedSwitch`(F-4 블록 삭제 외)·PR #533의 `endIfWiped`.
- 효과 함수 본문(아쿠아링·뿌리박기 분리, 컨텍스트를 매번 새로 받는 것 외).

## 7. 측정 계획과 해시 변동 원인 분리

- **구현 단계 2개로 나눠 측정**(각 `regress 200`·`regress 20000`·`STATUS=1 greedy 60`만 약 3분; 전체 `SERIAL=1 verify.sh`는 마지막에 한 번 약 10분):
  1. **S1 — 구조만**: 핸들러 표·실행기를 만들되 포켓몬 순위를 **a→b 고정**(스피드·난수 미사용)으로 둔다. 승패는 **그대로**여야 하고(`regress 20000` 승패 a 9920·b 9965·무 0·시간초과 115·**턴 546061 불변**) 로그 순서만 order 우선으로 바뀌어 해시는 바뀐다. 컨텍스트 새로 만들기(Q3) 영향도 여기서 드러난다 — **승패가 달라지면 Q3 때문**이므로 원인을 더 쪼갠다(컨텍스트 재사용 변형).
  2. **S2 — 스피드 순서**: 순위를 `orderBySpeed`로 켠다. 승패·턴 수가 변하는 것은 여기서부터(상한 약 409턴 중 일부).
- **불변 예상**: 차분 해시(데미지 계산 식)·`test:inference`·`test:damage`·`ai60` 결과(AI는 `turnRates`의 자체 모델을 쓰고 시뮬 로그를 읽지 않는다). `greedy120`·`status60`·`h2h40`은 승패가 한두 판 바뀔 수 있다(출력이 문자열 비교라 갱신).
- **예상 변동**: `regress 200`·`regress 20000` 해시(전부), 승패 수치는 ±수십 판 이내. D1·D2 재측정(샘플 등급 741쌍·랭크 AI)은 판정 불일치 <0.1%p 수준으로 예상.
- **작업·시간 보고**: 구현 후 측정 시작 전에 명령·예상 시간을 따로 보고한다.

## 8. 위험·알면서 두는 것

1. **컨텍스트 재생성(Q3)**: 가장 값싼 오류원. S1에서 승패가 변하면 곧바로 분리한다.
2. **난수 소비 변화**: 완전 동속·양쪽 자리 효과일 때만 새 난수 소비가 생기고, 변덕쟁이·탈피 등 기존 난수를 쓰는 효과는 순서가 바뀌어 **난수 소비 순서도 바뀐다**(모든 판의 난수열은 영향 없음 — 같은 시드지만 효과 처리 순서가 달라지므로 일부 판의 결과가 바뀔 수 있다. 상한은 위 409턴과 별개로 "탈피·변덕쟁이·수확이 양쪽에 동시에 있는 턴" 정도).
3. **`tickBlockVolatiles` 일괄 15**: 회복봉인 20·지옥찌르기 22·텔레키네시스 19·앙코르/사슬묶기 16/17이 한 함수라 15로 묶는다. 15~22 사이에 HP·상태를 바꾸는 엔진 효과가 없어 관측 차이는 없다. 만약 다음 버전에서 그 사이 효과(예: 악몽 11은 15 앞)를 추가하면 표에서 분리한다.
4. **면역 해제(4.5)·열매 재확인(30)** 위치는 A1이 정한 엔진 배치를 order 숫자로 옮긴 것이다(Showdown은 `onUpdate`라 residual이 아님) — 이 값은 소스에 없는 엔진 정의임을 코드 주석에 명시한다.
5. **옛 저장 영상·화면**: 저장된 로그는 그대로 표시된다. `EndOfTurnLines`는 항목마다 독립 줄을 렌더하고, HP 막대 연출(`turnFxSchedule.hpSteps`·`useTurnFx`)은 `endOfTurn`을 앞에서부터 항목 하나씩 재생하며 항목의 `actor`·`remainingHp`로 그 포켓몬 HP를 갱신하므로 **서로 다른 포켓몬의 줄이 섞여도 동작한다**(코드 확인). 다만 연출이 "줄이 포켓몬별로 묶여 있다"고 가정하지 않는지는 화면에서 한 번 보는 것이 안전하다 — 검수 때 사용자 판단(시험 대체 가능)을 받는다.
6. **화면 확인**: 줄 순서만 바뀌고 UI 코드 변경이 없어 **시험으로 대체**를 제안한다(이전 fix와 같은 방식, 사용자 승인 필요).
