## 3. 고칠 것
**3-1. 순수 함수 한 개** — `battlePower.ts`의 `computeEffectiveSpeed`를 대체하는 `computeSpeedStat({ baseSpe, stage, multipliers, halvedByParalysis })`:
```
s = stage >= 0 ? floor(baseSpe × (2+stage) / 2) : floor(baseSpe × 2 / (2−stage))   // 정수 연산 (rankStageMultiplier와 같은 식, 절삭만 추가)
if (multipliers.length) s = modify4096(s, chain4096("other", ...multipliers))      // fix-6 도구, 0.5는 내림
if (halvedByParalysis) s = floor(s × 50 / 100)                                     // 체인 뒤. 체인에 0.5로 넣지 않는다
return s                                                                           // 상한 10000은 도달 불가 — 넣으면 한 줄(Q 없음, 기본: 넣지 않음)
```
보정은 모두 정확한 분율(1.5·0.5·2)이라 **체인 순서와 무관**하다(검수 확인). `chain4096`이 1인 인자를 건너뛰므로 보정 없는 경우도 같은 호출로 처리된다.
**fix-6 시그니처 확인(검수 §2-1, 2026-11-18)**: 실제 구현은 `modify4096(value, multiplier, stage = "other")`(`damageFormula.ts:43`)와 `chain4096(stage, ...factors)`(`:48`, 반환값은 분자/4096 소수)다. `toNumerator`는 `m × 4096`이 정수에 1e-6 안으로 가까우면 그 정수를 쓰므로(1.5 → 6144, 0.5 → 2048, 2 → 8192, 체인 결과 n/4096 → n) 위 의사코드가 **그대로 맞다**. `stage = "other"`는 1.3 특례(위력 5325·최종 5324) 구분용이라 스피드 배율에는 영향이 없다. 참조 구현(시험)은 소스 그대로 `chain = (a·b + 2048) >> 12`, `modify = tr((tr(v·m) + 2047) / 4096)`를 쓴다.
**3-2. 상태이상 분리** — `computeStatusSpeedMultiplier`가 주는 값은 1(정상)·0.5(마비)·1.5(속보, 상태이상이면 마비도 포함)다. 마비(0.5)는 `halvedByParalysis`로, 속보(1.5)는 `multipliers`로 넘긴다(구분은 `=== 0.5`, 주석으로 근거 표기). 이중 구현을 피하려고 이 분리를 작은 함수 하나(`speedStatusParts(status, ability) → { multiplier, halved }`)로 `statusConditions.ts`에 둔다.
**3-3. 엔진·AI** — `computeTurnOrderSpeed`를 **랭크까지 포함한 최종 정수 스피드**를 돌려주도록 바꾼다(`computeSpeedStat` 호출, `multipliers = [서핑테일, 도구, 날씨 특성, 곡예(fix-9 판정), 순풍]` 중 1이 아닌 것). `TurnOrderActor`는 `realSpeed`+`stages` 대신 `speed`(최종 정수)로 단순화한다. 갱신할 곳: `turnOrder.ts`(`compareTurnOrder`는 `speed`를 직접 비교, 트릭룸은 비교 방향 반전 그대로), `turnOrderInputs.ts` `buildTurnOrderActor`, `runTurn.ts:244~267·666`, `ai/speed.ts`(변경 없음 — `buildTurnOrderActor`를 쓴다), `finishTurn.ts:997~998`(`speedA`가 이미 랭크 포함이므로 `rankStageMultiplier` 곱 삭제 — 멸망의노래 판정 규칙은 그대로, 정수가 되면 동점이 늘 수 있으나 `<=` 규칙 유지, 규칙 자체의 Showdown 대조는 E6).
**3-4. 매치업** — `speedOf`가 같은 `computeSpeedStat`을 쓴다(별도 구현 삭제). `SpeedMatchupResult`의 속도 값이 정수가 된다. `speedInference.ts`는 `evaluateSpeedMatchup`을 그대로 쓰므로 코드 변경 없음 — **단 결과(가능 후보 집합)가 달라질 수 있다**(§5·§6).
**3-5. 화면 표시(Q2)** — 실능치 칩 계산을 `floor`로(스피드 한정이 아니라 칩 5스탯 공통이 자연스럽다). Showdown은 랭크 적용을 모든 스탯에서 `floor`로 한다. 기본안: 포함(코드 두 줄).
**3-5-b. 보정 목록 확인(검수 §2-3, 2026-11-18)**: 엔진이 구현한 스피드 효과를 데이터 필드로 전수 확인했다 — 특성: `weatherSpeedMultiplier`(엽록소류)·`fieldSpeedMultiplier`(서핑테일)·`speedMultiplierWhenStatused`(속보)·`doublesSpeedOnItemLoss`(곡예)·가속(`boostsSpeedEachTurnEnd`는 **랭크**라 보정 목록과 무관), 도구: `speedMultiplier`(구애스카프·검은철구), 필드: 순풍, 상태: 마비. 설계서 `multipliers` 7종(서핑테일·도구·날씨 특성·곡예·순풍·속보 + 마비 분리)이 이 전부다. 소스에는 고대활성·쿼크차지·슬로우스타트·균사의힘 등이 더 있으나 **챔피언스 출전 불가·엔진 미구현**이라 이 PR 범위 밖(한 줄 기록).
**3-7. 메가진화 로그 순서(E3-13, 사용자 결정 2026-11-18: 8.3에서 처리)** — `runTurn.ts:222`의 메가진화 시도 순서가 `prevState.a.realStats.spe >= prevState.b.realStats.spe`(보정 없는 원시 스피드)로 정해진다. 둘 다 같은 턴에 메가진화하는 경우에만 의미가 있고, Showdown은 **보정 반영 스피드순**(메가진화 행동도 `getActionSpeed`, 동속은 무작위, **트릭룸이면 느린 쪽이 먼저**)이다. 고치는 법: 양쪽 모두 `action.mega`를 선언했고 교체하지 않았을 때만 `computeTurnOrderSpeed(state, …)`(메가진화 **전** 상태, 랭크 포함 정수)로 `compareTurnOrder`와 같은 규칙(동속 50% 난수·트릭룸 반전)으로 순서를 정한다. **한쪽만 메가진화하면 비교하지 않는다**(난수 소비 최소화 — 해시 영향은 양쪽 메가진화 + 동속인 판뿐). 판정·규칙에는 영향이 없고 `megaEvolutions`·턴 시작 안내 순서만 바뀐다. 사용자 지시는 "스피드가 빠른 순서대로"이며 트릭룸 반전은 Showdown 규칙을 따르는 기본안이다(확인 질문 §8-Q5).
**3-8. 시간벌기 + 선제공격손톱·퀵드로 양쪽 성공(E3-14, 사용자 결정: 함께 정리)** — Showdown은 손톱·퀵드로가 성공하면 이벤트 전달값을 +0.1로 **덮어써** 시간벌기의 −0.1이 사라진다(스피드만 비교). 엔진은 양쪽 성공이 상쇄되어 `compareTurnOrder`로 넘어갈 때 시간벌기 보유자가 다시 마지막으로 밀린다. 고치는 법(`runTurn.ts:260~267`): 선공에 **성공한 쪽의 `movesLast`를 지운 행동자**로 비교한다(`aQuickClaw ? { ...actorA, movesLast: undefined } : actorA`). 한쪽만 성공하면 이미 `quickClawWinner`로 결정되고, 둘 다 실패하면 현행 그대로다. 확률이 낮아(≈0.2×0.3 수준 × 시간벌기 보유) 해시 영향은 거의 없을 것이다. AI `firstProbability`(`ai/speed.ts:30~36`)도 같은 규칙을 쓴다 — 양쪽 성공 항(`qMe·qThem`)에서 시간벌기를 무시하도록 맞춘다.
**3-7b. [새 발견·제안] 양쪽이 같은 턴에 자발 교체할 때의 처리 순서(E3-16)** — `runTurn.ts:138~141`의 `switchOrder`도 같은 원시 스피드 비교(`prevState.a.realStats.spe >= prevState.b.realStats.spe`)다. 주석은 "로그 순서 일관성"이라 하지만 **교체 처리 순서는 등장 효과의 순서**(등장 특성·날씨·설치물 발동, 마지막에 깔린 날씨가 이김)를 정한다. Showdown은 교체 행동도 `getActionSpeed`(`battle-queue.ts:275`, 랭크·보정 반영, 트릭룸 반전)로 정렬하고 동속은 무작위다. 엔진은 ① 랭크·도구·순풍·곡예를 무시하고 ② 트릭룸을 무시하고 ③ **동속이면 항상 a 먼저**다(난수 아님). 같은 헬퍼(양쪽 순서 결정 함수 하나 — 3-7과 공유)로 고치면 되고, 교체 후 순서(`fasterFirst`, A7)는 이미 `computeTurnOrderSpeed`를 쓴다. **사용자 지시 범위 밖의 제안**이라 Q6으로 확인한다(기본안: 포함 — 같은 함수·같은 PR, 양쪽이 같은 턴에 교체하는 판의 등장 효과 순서가 바뀔 수 있어 해시 변동 대상).
**3-6. 하지 않는 것**: 10000 상한, 자이로·일렉트릭볼(`powerSpeedOf`, fix-12), 멸망의노래 동점 규칙·턴 종료 효과 스피드순(F1, E6), 우선도 계산·선제공격손톱 확률(E3-14의 시간벌기 상쇄 처리만 3-8에서 고친다), 노력치 역산 알고리즘 본체.

## 6. 구현 순서·측정·해시 예상
- **해시는 거의 확실히 바뀐다**: 정수화로 동속이 늘어(0.145% → 0.319% 조합) `compareTurnOrder`의 `random()` 소비가 달라져 난수열이 밀린다. 그러므로 **단계별로 잰다**(예상은 자주 틀린다): ① `computeSpeedStat` 신설 + 엔진·`compareTurnOrder`·`TurnOrderActor` 교체 → `regress 200`·`regress 20000`·`STATUS=1 greedy 60` ② 매치업·AI 연결 → 같은 측정 + `test:inference`(결합 해시 `4baec5f8692c1418`와 비교) ③ 화면 칩(Q2). 측정 시작 전에 "명령·예상 종료 시간"을 먼저 보고한다(약 3분, 마지막 `SERIAL=1 verify.sh` 약 8분).
- **역산(`test:inference`)**: 역산은 가능한 (스피드 포인트·성격·보정) 후보마다 선후공을 **앞으로 계산**해 관측과 맞춰 보는 구조라 "거꾸로 푸는" 식이 아니다. 정수 스피드가 되면 후보별 선후·동속 판정이 0.23% 수준에서 달라져 **가능 후보 집합이 바뀔 수 있다** — 바뀐 경우는 **Showdown 정수 규칙에 충실해진 결과**이므로 기준값 갱신 대상이다. 단 변한 케이스를 전수 목록으로 뽑아 사용자에게 보고하고 확인받은 뒤 갱신한다(메모리 규칙: 역산 변경은 결합 결과 해시로 동일성 검증 — 이번에는 "변화가 정당한지 검증").
- **화면 확인(사용자 수행)**: 매치업 화면의 `확정 선공`/`동속` 배지가 바뀔 수 있어 몇 쌍 확인(철구 60·61 같은 동속 사례, 랭크 −1 사례). 스피드 역산 화면 숫자가 달라지는 경우 화면 확인. 브라우저 검증은 사용자에게 위임.
