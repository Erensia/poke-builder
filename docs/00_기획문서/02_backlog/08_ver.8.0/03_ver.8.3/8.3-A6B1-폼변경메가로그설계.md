## 3. 엔진 설계

### 3-1. 폼 변경을 앞으로 옮기고 이벤트를 남긴다 (`preHitEffects.ts`)

**① 함수로 뺀다.** `recordUsageEffects` 안의 폼 변경 블록(`:1015~1029`)을 `applyStanceChange(c, move)`로 옮긴다. 입력은 `c`와 **쓰는 기술**(호출 기술이면 호출된 기술, 아니면 `c.move`). 동작은 지금과 같고(`nextForm` 식·실능치 재계산), 바뀌면 `c.stanceChange = { to: nextForm }`를 남긴다. 이미 같은 폼이면 아무것도 안 한다(이벤트도 없다).

**② 호출 자리 — 두 곳.** Showdown 순서(`BeforeMove` → `ModifyMove` → `onTry`)를 엔진의 조기 반환 구조에 맞추는 최소 지점이다.
1. `resolvePreHitEffects`에서 `checkActionBlockers`가 `null`을 돌려준 **직후**(= 행동 불가가 아니면), `handleChargeAndCopyMoves` **앞에서** `applyStanceChange(c, c.move)`. 차지 기술 1턴째(조기 반환)도 이미 폼이 바뀐다. 호출 기술(잠꼬대·따라하기)은 이 시점엔 `c.move`가 변화기라 폼이 유지된다.
2. `handleChargeAndCopyMoves`가 `null`을 돌려준 직후(호출 기술이 정해진 뒤), `applyStanceChange(c, c.effectiveMove)`를 한 번 더. 같은 폼이면 무동작이라 중복 안전하다. 원래 자리(`recordUsageEffects`)의 블록은 삭제한다.

**③ 사용 조건 실패(`checkUsageGates` 반환)에서도 폼을 바꾼다.** 폴터가이스트·기선제압 등 `usageCondition`으로 막히는 기술은 `checkActionBlockers`보다 **먼저** 평가된다(C2). 그래서 `checkUsageGates`가 값을 돌려주면 그 자리에서 `c.recharging`이 **아닐 때** `applyStanceChange(c, c.move)`를 부른 뒤 반환한다. 반동 턴(`recharge`)은 Showdown에서도 `BeforeMove`라 폼이 안 바뀌므로 제외한다.

**④ `blocked()`가 이벤트를 싣는다.** `c.blocked`의 기본 필드에 `stanceChange: c.stanceChange`를 넣고(`leppaRestoredPpItemName`과 같은 방식), 정상 경로의 결과(`collectResult` 등 `ActionLogEntry`를 만드는 곳)에도 같은 필드를 넘긴다. 이후 `resolveAction`이 `ActionLogEntry`로 전달하는 흐름은 `selfWokeBeforeMove`와 같은 경로(`resolveAction.ts:739` 근처)를 따른다.

> 한계(알면서 둔다): 엔진은 사용 조건 실패를 상태이상·풀죽음 판정보다 먼저 평가한다(C2). 따라서 **수면·마비·풀죽음 중인 킬가르도가 폴터가이스트(상대 도구 없음)의 사용 조건에 실패하는 턴**에는 Showdown(행동 불가가 먼저 → 폼 불변, `cant`만 나옴)과 달리 폼이 바뀐다. 킬가르도는 기습을 배울 수 없고 폴터가이스트는 우선도 0이라 풀죽음·수면·마비와 자주 겹칠 수 있다. 순서를 맞추려면 사용 조건 평가 전체를 옮겨 수면 카운터 소모 시점까지 바뀌므로 이번에는 옮기지 않고 백로그 한계로 적는다. **V1 검수 확인: 한계로 두는 결정은 타당.**

### 3-2. 메가진화 구조화 필드 (`runTurn.ts` · `switching.ts` · 타입)

- `applyMegaEvolution(state, key, log)`는 `true/false`만 돌려준다. 호출부(`runTurn.ts:209`)에서 `true`면 `megaEvolutions.push({ side: key, pokemonId: state[key].slot.pokemonId, megaForm: <적용된 mega.form> })`를 한다. `applyMegaEvolution`의 반환 타입을 바꾸지 않기 위해, 폼 id는 호출부가 `getPokemon(...).megaEvolutions.find(m => m.megaStone === state[key].megaStone)?.form`으로 구한다(적용 직후 `hasMegaEvolved`가 세워진 상태라 같은 식이 `fighterAvatar`에 이미 있다).
- `evaluator.ts:1368`(AI의 가상 상태 계산)은 `[]`를 로그로 넘기는 호출이라 영향이 없다.
- `TurnResult`·`finishTurn.ts`의 결과 조립(`:1169`, `:1184`)과 `runTurn.ts`의 두 곳(`:261`, `:286`)에 필드를 이어 넣는다(`turnStartAnnouncements`와 같은 경로).
- `battleSessionHelpers.ts:118`의 빈 `TurnResult`에는 필드를 **생략**(선택 필드)해도 된다.

## 4. 화면 설계

### 4-1. 로그 (`BattleTurnLog.tsx`)
`selfWokeBeforeMove` 줄 바로 다음, `preUseUserAnnouncement`(썰렁개그) 앞에 한 줄을 넣는다: `action.stanceChange`가 있으면 `{actorName}{은/는} {블레이드|실드}폼으로 폼체인지했다!`. 행동 불가(`blockedReason`)에는 이벤트 자체가 없으니 별도 조건이 필요 없다. 사용 조건 실패(`usageCondition`) 줄에서도 이 줄이 위에 먼저 나온다(R8-a 기대).

### 4-2. 카드 (`BattleFighterCard.tsx`)
- `fighterAvatar`의 `avatarForm`에 `stanceForm: fighter.stanceChangeForms ? fighter.currentStanceForm : undefined`를 넣는다(변신·일루전 분기에는 넣지 않는다 — 변신한 킬가르도는 폼 개념을 복제하지 않는다).
- 배지: 이름 옆에 `fighter.stanceChangeForms && !illusionAs`일 때 `[실드폼]`/`[블레이드폼]`. 메가 배지(`battle-fighter-mega-tag`)와 같은 자리·비슷한 스타일의 `battle-fighter-stance-tag`를 둔다(기존 CSS 변수 안에서, 새 색 도입 없음).
- 실능치 표시(`BattleRealStats` 계열)는 이미 `fighter.realStats`를 읽으므로 폼 변경 후 자연히 바뀐다.

### 4-3. 재생 일정 (`turnFxSchedule.ts` · `useTurnFx.ts`)
- **메가진화(B1)**: `planTurnFx`의 `megas`를 `last.megaEvolutions`에서 읽는다. 상태 비교(`wasState/nowState`의 `hasMegaEvolved`)와 `megaFighter` 보정을 지운다. 이미 재생한 만큼 건너뛰는 처리(부분 결과)가 필요한지 확인한다 — 메가진화는 턴 시작에 한 번뿐이라 같은 턴의 중간 결과에서 이미 들어 있으면 두 번 재생하지 않게 `doneActions === 0`일 때만 쓴다.
- **폼 변경(A6)**: `planTurnFx`가 `newActions`에서 `stanceChange`가 있는 행동의 `{ side, k, to }` 목록 `stances`를 만든다. `buildFxFrames`의 시각표에 **행동 k의 시작 시각 `startOf(k)`**를 넣고, `TurnFxView`에 `stance?: Partial<Record<FighterKey, "shield"|"blade">>`를 추가해 그 시각 이후에는 `to`를, 그 전에는 **그 행동 직전의 폼**(= 같은 편의 직전 `stanceChange.to`, 없으면 턴 시작 폼)을 준다. 카드는 `view.stance[side]`가 있으면 `fighter.currentStanceForm` 대신 쓴다. 팝 모션은 `useTurnFx`에서 `pop(side, startOf(k))`로 얹는다.
- 턴 시작 폼은 `prevSnap[side].currentStanceForm`이다(같은 편이 교체로 바뀐 카드는 `showPrev`가 이미 교체 모션 동안 붙잡는다).

## 9. 알면서 두는 것 (백로그 한계로 옮길 후보)

- C2의 평가 순서 차이(§3-1 한계, V1).
- 폼 변경 줄은 문자열이 아니라 필드에서 만든다. 메가진화 문구는 이번에 필드와 문구를 분리한 채 두었다(Q26) — 필드에서 문구를 만드는 통합은 하지 않는다.
- 변신(트랜스폼)한 킬가르도·다른 포켓몬이 킬가르도로 변신한 경우 폼 표시: 변신은 `stanceChangeForms`를 복제하지 않으므로 폼 이벤트·배지가 없다(현행 유지).
- 실능치 패널은 재생 중에도 턴 끝 값을 보인다(다른 상태와 같은 방식).
- **잠꼬대 줄 순서**(검수 낮은 우선순위): 잠꼬대로 기술을 부르면 Showdown은 폼 변경 줄이 "잠꼬대 사용" 줄 **뒤**에 나온다. 설계는 기술 줄 앞에 둔다. 규칙에는 영향이 없고 화면 순서만 다르다.
- Q24 확인: 교체 시 폼 이벤트가 없는 것은 Showdown과 같다(벤치의 킬가르도는 실드 폼, 재등장 때 줄 없음). B1(메가진화 구조화)은 규칙이 아니라 로그 형태만 바꾸므로 규칙 검수 대상이 아니다. 화면 설계(§4)·재생 일정·해시 측정(§6)은 Showdown에 대응이 없어 검수하지 않았다.
