## 0. 요약
- **문제**: 현행 학습은 "상대가 어떤 행동을 더/덜 고르는가"(평균 편향)만 보정하고, "예측보다 얼마나 일관되게 고르는가"(결정성)는 모른다. C2-a 오프라인 재계산에서 **상대마다 최적 온도 τ가 반대**였다 — 습관 봇(setup·switcher)은 τ=0.5(분포를 날카롭게)에서 변화기·기술 손실 10~32% 감소, 무작위 상대는 τ=2(평평하게)에서 교체·변화기·기술 12~17% 감소, noisy는 현행(τ=1)이 최적. 단일 전역 τ는 한쪽을 고치면 반대쪽을 해쳐 폐기됐다.
- **제안**: 상대마다 **온도를 온라인으로 추정**한다. 새 통계는 **τ 격자(예: 0.5·0.7·1·1.4·2)별 감쇠 누적 손실**이라 선형 합계이고, 선택 필드로 추가해도 `OpponentMemory` version 1 호환(§3-1)이며 합치기(`mergeAiMemory`)에도 선형 필드로 그대로 얹힌다. 추정이 확실할 때만 τ=1에서 벗어난다.
- **관문**: ① **M0a(오프라인, 새 측정 없음)** — 이미 기록한 원자료로 온라인 추정기가 손실을 줄이는지 · ② **M0b(승률)** — 구현해서 같은 시드 짝 비교로 승률에 옮겨지는지(C2-a의 결정 민감도 3~19%가 상한). 둘 중 하나라도 못 넘으면 폐기한다.

## 3. 설계 (두 관문을 통과할 때만)

### 3-1. 저장 — `OpponentMemory` 선택 필드 `temp`
- 형식: `temp?: { switch: number[]; move: number[]; n: number }` — 배열 길이는 τ 격자 길이(상수 `TEMP_GRID = [0.5, 0.7, 1, 1.4, 2]`), 값은 **감쇠한 누적 손실**(−log p, clip 1e-4), `n`은 감쇠한 관측 수. 필드는 15개 수준이라 문서 크기 영향 없음.
- **version을 올리지 않는다**: `isOpponentMemory`는 `version`·`battles`·`species`만 보고, `cloudSyncPlan.objectDoc`은 `memory`를 통째로 통과시킨다. 옛 클라이언트는 이 필드를 무시하고 읽을 수 있고, 그 클라이언트가 저장할 때 필드가 사라질 뿐이다(`addMemory`가 새 객체를 만들기 때문) — 학습이 조금 사라질 뿐 오류는 없다. 새 클라이언트는 필드가 없으면 `n = 0`(추정 약함 → τ=1)으로 본다.
- **갱신**: `observeOpponent`가 그 관측의 실제 행동이 **현행 보정(τ=1) 분포 p′**에서 각 격자 τ_k의 분포 `p′^(1/τ_k)`(재정규화)로 받았을 −log p를 세션 기록에 더한다(교체 분기는 이항, 기술 분기는 다항 — M0a와 같은 정의, 같은 관측 필터가 있다면 그 필터). **관측 필터(이번 필드에만 적용)**: ① 그 분기에서 합법 선택지가 2개 이상일 때만 · ② **실제 행동이 그 턴의 p′ 안에 있을 때만**(공개되지 않은 기술의 clip 손실이 τ>1 쪽으로 치우침을 만들기 때문) · ③ p′가 없는 턴(결정에 쓴 분포가 없음)은 뺀다. p′는 **결정할 때 계산한 분포를 보관**해 관측 시점에 넘긴다(앱 `useBattleAi.observe`가 이미 분포를 받는다). 현행 집계(`switchActual` 등)는 안 건드린다 — C2-a의 H0(집계 필터)는 폐기됐다. M0a 원자료(`c2a-*.json`)는 선택지 수(`ns`·`mw` 길이)와 행동·공개 기술 여부(`mw`에 행동이 있는가)가 모두 기록돼 있어 같은 필터로 재생할 수 있다.
- **감쇠·합치기**: 선형 합계라 `addMemory`가 다른 필드와 똑같이 감쇠(×0.99/0.995)하고 합치고(`commitBattle`), `mergeAiMemory`가 `comb`로 같은 식으로 합친다(필드 목록에 `temp.switch[k]`·`temp.move[k]`·`temp.n` 추가).

### 3-2. 추정 — 격자에서 고르되 확실할 때만
- 선택: 분기마다 `k* = argmin_k temp[분기][k]`. **τ=1 대비 개선이 충분할 때만** 채택: `temp[분기][τ=1] − temp[분기][k*] ≥ margin × temp.n` (margin = 0.03 nat/관측, M0a에서 조정 — 사전 등록: 처음 값으로 0.03을 쓰고 격자별로 쓰지 않는다) **그리고 `temp.n ≥ 30`**. 아니면 τ=1(현행).
- **상대 식별**: 현행 학습과 같다 — 기억은 사용자(계정) 단위이고 종별 기술 습관만 종 단위다. 상대(사용자) 한 명당 τ 하나(분기별 둘). 따라서 "한 명이 여러 파티를 섞어 쓰는" 경우 평균 결정성으로 본다(한계).
- **순서: 기존 보정 → 온도 → 교체 확률 상한 0.9**. 손실 격자(§3-1)와 실제 적용이 같은 순서를 쓴다(상한이 걸린 분포를 기준으로 τ를 골라야 실제 적용과 맞다).
- **저장 검증**: `temp.switch`·`temp.move`의 길이가 `TEMP_GRID`와 다르거나 NaN·음수가 있으면 필드가 없는 것으로 취급(`n = 0`). 합칠 때 `temp`는 한 덩어리로 0 자르기.
- 적용: `calibrateDistribution` 마지막에 `strength`(학습 사용률 λ)와 곱해 `τ_eff = τ^λ`로 반영(λ=1이면 τ 그대로, λ→0이면 τ=1). 교체 확률 `σ(logit(p)/τ_sw)`(상한 0.9 유지), 기술 분포 `p^(1/τ_mv)` 재정규화.

### 3-3. 사용 조건 (불변 보장)
- 새 동작은 `DecisionParams.learn.temp === true`일 때만 켠다(기본 끔). **관문을 통과하기 전에는 켜지 않고**, 통과하면 켜는 랭크 AI 단계(마스터볼 구간 등)는 별도 결정(사용자) — 켜는 순간 `ai60`·사다리 해시가 바뀌므로 그때 기준값을 갱신한다.
- 끔 상태에서는 `observeOpponent`가 `temp`를 **갱신하되 사용하지 않는다**(저장 크기·시간 영향 미미). 켜는 시점에 이미 쌓여 있어야 효과가 나므로 갱신은 기본 켬. 갱신이 바뀌면 `temp`를 가진 저장본이 생기므로 `canonical`·`mergeAiMemory`·`isStoredAiMemory`가 이 필드를 통과시키는지 시험으로 고정한다.

## 4. 시험 (구현 단계에서 먼저 쓰고 실패 확인)
| # | 시험 | 목적 |
|---|---|---|
| T-a | 결정적 관측열(항상 최빈 행동)에서 `temp` 선택이 τ<1, 무작위 관측열에서 τ>1, 일치할 때 τ=1 | 추정기 방향 |
| T-b | `temp.n < 30` 또는 개선이 margin 미만이면 τ=1(현행과 출력 동일) | 불변·보수성 |
| T-c | `learn.temp` 끔이면 `calibrateDistribution` 출력이 현행과 **같다**(기억에 `temp`가 있어도) | 기존 동작 불변 |
| T-d | `commitBattle`이 `temp`를 감쇠하고 합친다(없으면 0으로 시작), `observeOpponent`가 격자별 손실을 올바른 분기에 더한다 | 집계 |
| T-e | `mergeAiMemory`가 `temp`를 선형 필드로 합친다(두 순서 평균 식), 한쪽만 `temp`가 있어도(옛 클라이언트) 오류 없이 합친다 | 합치기 |
| T-f | `canonical("aiMemory", …)`가 `temp`를 통과시키고 `isOpponentMemory`도 통과한다, 옛 모양(없음)도 통과 | 호환 |
| T-g | 온도 적용 후 분포가 합 1이고 교체 확률 상한 0.9를 지킨다(순서: 보정 → 온도 → 상한) | 정규화 |
| **T-h** | **M0a와 일치**: C2-a 원자료 1판을 `observeOpponent`·`commitBattle`에 넣어 얻은 `temp` 합계가 M0a 스크립트 값과 1e-9 이내 | M0a → 구현 보증 |
| **T-i** | **저장 검증**: 길이가 다른 `temp`·NaN·음수 → 필드 없음 취급(τ=1), 합칠 때 한 덩어리로 0 자르기, 공개되지 않은 기술·p′ 없는 턴은 갱신하지 않는다 | 호환·분포 밖 행동 |

## 5. 해시·검증 예상 (믿지 말고 단계마다 잰다)
- `learn.temp` 기본 끔 → `verify.sh` 14항목 **불변** 예상. 켜면 `ai60`·사다리 단계가 바뀌므로 사용자와 켤 단계를 정한 뒤 기준값 갱신.
- **끈 상태의 갱신 비용**(플래그가 꺼져 있어도 `temp` 갱신은 돌아 처리 시간이 늘 수 있음)도 `ai60` 판단 시간으로 잰다.
- 측정 시작 전 "명령·예상 시간" 보고: **M0a** 재생 약 2~4분(`TMPDIR_C2A=/tmp node scripts/zz-c2a-analyze.mjs …`, 추정기 팔 추가) — 새 대전 측정 없음. **M0b** 봇 3종 × 600판 짝 비교 약 25~30분(C2-a와 같은 구성에 변경 전후 2회).

## 6. 구현 순서·PR
M0a(오프라인) → **미통과면 백로그에 근거를 적고 종료(문서만)** → 통과 시 시험 먼저 → `temp` 필드·추정·적용(플래그 끔) → `test:ai`·`test:sync`·`verify.sh`(불변) → M0b(플래그 켠 짝 비교) → **미통과면 브랜치를 머지하지 않고 폐기** → 통과면 켤 랭크 단계를 사용자와 정하고 기준값 갱신 → PR 1개(커밋 1개) → 머지. 화면 확인은 없음(AI 보정 수치만 바뀜).

## 7. 알면서 두는 한계(예정)
- M0a는 **관측 순서를 고정한 근사**다(온라인 재생이지만 AI 선택이 바뀌면 이후 상대 행동도 달라진다 — 실제 효과는 M0b가 확인). p′는 시간에 따라 변하는 기준 분포(보정이 바뀐다)에 대한 손실이다. **분포 밖 행동(공개되지 않은 기술)은 학습 대상이 아니다.**
- 봇은 사람과 구조가 다르고 AI 점수 계열이라 순환 소지가 있다(C2-a 한계 그대로). 사람에게서의 이득은 보장되지 않는다.
- 상대 한 명이 상황별로 결정성이 다르면(예: 위기 때만 무작위) 평균 τ로 본다.
- 옛 클라이언트가 저장하면 `temp`가 사라진다(다음 판부터 다시 쌓임).
- 승률 이득의 상한은 결정 민감도(3~19%)에 묶인다.
