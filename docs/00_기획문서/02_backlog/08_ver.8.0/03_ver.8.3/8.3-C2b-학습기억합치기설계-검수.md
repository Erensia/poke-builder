## 2. 상세 — 병합식

### 2-1. 전제 확인: 감쇠가 즉시 적용인가 (❓ 최우선)
- 설계서의 식 `L = d^kL·B + ΔL`은 `commitBattle`이 **매 판 저장된 모든 값(판에 나오지 않은 종 포함)에 d를 곱할 때만** 성립한다.
- 종별 `lastBattle`이 있다는 점이 걸린다. 만약 감쇠를 "저장값 × d^(battles − lastBattle)"처럼 **읽을 때 계산**한다면, 그 판에 나오지 않은 종의 저장값은 그대로 B와 같다. 그러면 `ΔL = L − d^kL·B = (1 − d^kL)·B`라는 **가짜 증분**이 생기고, 판을 많이 한 쪽일수록 기억이 부풀어 오른다.
- 확인 방법: `opponentMemory.ts`의 `commitBattle`(또는 `addMemory`)에서 감쇠 곱이 어디에 걸리는지 본다.
  - 즉시 적용이면: 설계서 §1에 "확인함" 한 줄.
  - lazy이면: 증분 복원을 종별로 `d^(L.battles − L.lastBattle)`을 반영해 "실효값"으로 바꾼 뒤 계산하고, 결과를 다시 저장 형식으로 되돌리는 식으로 §1을 고쳐야 한다. 이 경우 재검수한다.
- 함께 확인: 학습이 꺼진 상태(`learningEnabled = false`)에서 판을 하면 `battles`가 오르는지, 감쇠만 걸리는지. `battles`는 오르는데 감쇠가 안 걸리면(또는 그 반대) kL로 d^kL을 계산하는 전제가 깨진다.

### 2-2. 결합식 검증
- "L 다음 R": `d^kR·(d^kL·B + ΔL) + ΔR = d^(kL+kR)·B + d^kR·ΔL + ΔR`
- "R 다음 L": `d^(kL+kR)·B + ΔL + d^kL·ΔR`
- 평균: `d^(kL+kR)·B + ½[(1 + d^kR)·ΔL + (1 + d^kL)·ΔR]` — 설계서 식과 일치한다. ✅
- **실제 값의 범위**: 실제로 판이 섞인 순서(인터리브)가 무엇이든, L의 각 판에 곱해지는 추가 감쇠는 d^0 ~ d^kR 사이, R의 각 판은 d^0 ~ d^kL 사이다. 증분이 모두 0 이상이므로 **실제 값은 필드마다 두 극단 순서 결과 사이에 있다.** 따라서 평균의 오차는 그 폭의 절반 이하이며, M-b의 "사이" 판정은 의미 있는 성질 시험이다.
- 오차 수치: d = 0.99, k = 20 → 1 − 0.99^20 ≈ 0.182 → 절반 ≈ 9.1% ✅. d = 0.995(랭크)면 약 4.8%. 이 비율은 **증분 대비**이며 전체 기억 대비로는 더 작다. 또 보정은 `actual/pred` 비율로 쓰여 분자·분모가 같은 방향으로 움직이므로 실제 예측 영향은 더 작다.

### 2-3. 100종 상한 경계
- L에서 밀려난 종: L 값 없음 → ΔL = 0, 결과에는 `d^(kL+kR)·B` 몫이 남는다. kR = 0이면 결과에 L에 없는 종이 끼므로, **100종 정리(§1-5)를 거친 뒤에야 L과 같아진다.** 밀려난 종의 `lastBattle`이 가장 오래되었으므로 정리에서 다시 빠지는 것이 맞다. M-a 입력에 이 경우를 하나 넣어 "정리 후 정확히 같음"을 고정한다.
- **밀려났다가 다시 들어온 종**: L 값은 재진입 뒤의 기여 c뿐인데, 계산은 `max(0, c − d^kL·B)`가 되어 증분이 과소(또는 0) 계산된다. 저장 형식으로는 재진입을 구별할 수 없다. 드문 경계이므로 Q3 기본안(0 자르기)에 동의하고, §5 한계에 한 줄 추가한다.

## 3. 상세 — 동기화 상태 전이

### 3-1. 기준(base)을 언제 무엇으로 옮기는가 (❌ 보완 필요)
증분을 더하는 병합은 **"기준 이후의 변경"이 정확히 한 번만 더해져야** 한다. 경우별 올바른 기준은 다음과 같다.

| 상황 | 로컬 | 클라우드 | 올바른 기준 | 틀리면 |
|---|---|---|---|---|
| 병합 직후, 올리기 전 | M | R | **R** | — |
| 올리기 성공, 로컬 그대로 | M | M | M | — |
| 올리기 성공, 그 사이 로컬이 L2로 바뀜(M-h) | L2 | M | **M**(올린 내용) | 기준을 B로 두면 ΔL 이중 합산. 기준을 L2로 두면 L2−M 변경이 영구 누락 |
| **올리기 실패**(네트워크·경합) | M | R 또는 R2 | **R** | 기준을 B로 두면 다음 병합 `merge(B, M, R2)`에서 M에 이미 든 ΔR이 R2의 증분과 **다시 더해진다** |

- 설계서 §2의 "`setBase(name, local, r.updatedAt)`" 문구는 `local`이 "방금 합친 값 M"을 가리켜야 한다. 이름이 현재 로컬처럼 읽히므로 변수명 또는 주석으로 명확히 한다.
- **올리기 실패 경로**: 프런티어(`cloudSync.ts:259`)가 이 경우를 어떻게 처리하는지 확인하고, 같지 않다면 aiMemory만이라도 "합친 값을 로컬에 쓰는 순간 기준 = R(합칠 때 쓴 클라우드 본, 그 `updatedAt`)"으로 둔다. 이는 git의 병합 커밋이 클라우드 쪽을 부모로 갖는 것과 같은 원리다.
- 대안: 올리기 성공 전에는 로컬에 쓰지 않는다. 다만 그러면 실패 시 다음 동기화에서 같은 병합을 다시 계산하므로 결과는 같고 구현이 단순하다. **어느 쪽이든 하나를 정해 설계서에 적는다.**
- 시험 추가 **M-h2**: 병합 → 올리기 실패를 흉내 → 클라우드에 R2(추가 판) → 다시 동기화 → 결과의 `battles`가 `B + kL + kR + kR2`이고 선형 필드가 이중 합산되지 않는다.

### 3-2. 기준 저장본 크기 제한(Q4)
- **낡은 기준 잔존 위험**: 크기가 20만 자를 넘어 "저장하지 않는다"고 할 때, 이전(작던 시절)의 `snapshot`이 그대로 남고 `updatedAt`만 새것으로 바뀌면, 다음 충돌에서 낡은 기준으로 증분을 계산해 **이중 합산**이 생긴다. 초과·저장 실패 시에는 반드시 `snapshot`을 **삭제**(해당 문서 기준을 "기준 없음" 상태로)해야 한다. 시험에 "초과 → snapshot 없음 → `mergeAiMemory`가 null" 한 건을 넣는다.
- **저장 실패 격리** ❓: `CloudSyncMeta`가 localStorage 키 하나에 통째로 저장된다면, aiMemory 기준 때문에 `QuotaExceededError`가 나면 **다른 문서(프런티어·랭크)의 기준 갱신까지 실패**한다. 프런티어도 증분 병합이므로 그쪽 이중 합산으로 번질 수 있다. 확인 후 다음 중 하나로 둔다.
  - aiMemory 기준 저장본만 별도 키(예: `cloudSyncBase:aiMemory`)에 두고, 실패하면 그 키만 지운다. (권장)
  - 또는 meta 저장을 try/catch로 감싸 실패 시 aiMemory snapshot을 빼고 다시 저장한다.
- 20만 자라는 값: 기억이 큰 사용자일수록 합치기 이득이 큰데 그들만 폴백되는 구조다. 실측 전이므로 기본안 유지에 동의하되, 구현 뒤 실제 사용자 기억 크기(두 모드)를 한 번 재서 백로그에 남긴다. 최악 추정(두 모드 × (본문 40만 + 기준 40만) ≈ 160만 자)도 일반적인 localStorage 한도 안이므로, 값을 올릴 여지가 있다.

### 3-3. 배틀 진행 중 병합 반영 ❓
- 배틀 도중 동기화가 병합 결과 M을 저장하고, `useAiMemory`가 `onPresetListReplaced`로 다시 읽는다. 그런데 배틀 종료 시 `commitBattle`이 **배틀 시작 시점에 잡아 둔 메모리 객체**를 기준으로 계산해 저장하면, M에 들어온 클라우드 쪽 학습이 조용히 덮인다(기준은 이미 M이므로 이후 복구되지 않는다).
- 확인: `commitBattle`이 저장 시점에 최신 저장값(또는 갱신된 훅 상태)을 읽는지. 아니라면 "배틀 중에는 aiMemory 병합 결과를 로컬에 쓰지 않고 다음 동기화로 미룬다" 같은 가드가 필요하다.
- Q5 화면 확인 체크리스트에 "한쪽 기기에서 배틀 진행 중 동기화" 항목을 넣는다.

### 3-4. 감쇠 상수 변경과 버전
- 병합은 "현재 앱의 d"로 계산한다. C2-a 검수에서 감쇠 조정(H2)을 C2-b로 넘겼는데, 이번 설계서에는 H2가 빠져 있다. 앞으로 d를 바꾸면 기기마다 앱 버전이 달라 다른 d로 쌓인 기억을 합치게 되어 증분 복원이 틀린다.
- 권장: §5 한계에 "감쇠 상수를 바꾸는 변경은 기억 `version`을 올린다(→ 버전이 다르면 합치지 않음, §1-1)"를 적고, H2의 행방(폐기 또는 별도 항목)을 백로그에 남긴다.

## 6. 문서 정합성(사소)
- §0·§1: 전제 "기억은 commitBattle로 쌓이므로…"에 감쇠 적용 방식 확인 결과를 덧붙인다(§2-1).
