## 1. 확정된 규칙 (사용자 2026-11-10)
1. 날씨 지속시간 체크·날씨 종료 메시지
2. 날씨 대미지·날씨 특성 발동(모래바람 대미지, 젖은접시 등)
3. 희망사항 → 미래예지/파멸의소원 (설치 순서대로)
4. 개별 턴 종료 효과(먹다남은음식·포이즌힐·씨뿌리기 등, 스피드순)
5. 상태이상 대미지
- 희망사항은 **회복 0이어도 로그 한 줄**: "희망사항이 이루어졌지만 회복할 HP가 없었다".
- 진행 방식: 이 순서 변경만 한 PR에서 하고 `verify-kit` 기준값을 같이 갱신한다(사용자 위임, 2026-11-10).
- 위 5단계는 큰 묶음이고, Showdown 대조(§0)는 그 안의 세부 순서를 정한다. 3번 항목(희망사항 → 미래예지)과 5번 항목(상태이상 대미지를 마지막)은 Showdown과 다르다 → Q2·Q7.

## 2. 지금 엔진이 하는 일 (코드 확인)
`src/lib/battle/finishTurn.ts`의 `finishTurn`(1021행)은 다음을 **이 순서로** 부른다.
```
resolveEndOfTurnAndPerish(c)   // 턴 종료 효과 + 멸망의노래   (740행)
decideWinnerAndForcedSwitch(c) // 승패·강제 교체              (813행)
expireFieldAndWeather(c)       // 필드·룸·중력·전자부유·날씨 지속 턴 감소  (867행)
expireSideEffects(c)           // 스크린·신비의부적·순풍 지속 턴 감소       (940행)
collectResult(c)               // 결과 모음 (endOfTurn 배열 순서 = 화면 로그 순서)
```
- **포켓몬 우선 구조**: `resolveEndOfTurnAndPerish`는 `for key of ["a","b"]`로 **a가 모든 단계를 끝까지** 돈 뒤 b가 모든 단계를 돈다. 확정 순서는 "단계 우선"이다. 순서는 스피드순이 아니라 **a→b 고정**이다(`order`·`speedA/B`는 멸망의노래 동반 기절 승부에만 쓴다).
- **날씨 종료가 맨 뒤**: 날씨 지속 턴 감소와 종료(`weatherExpired`, 기분파 폼 복귀)는 `expireFieldAndWeather`에서 효과가 다 끝난 뒤에 일어난다.

### 2-1. 한 포켓몬 안의 현재 순서 (`finishTurn.ts` 785~808행)
멸망의노래 카운트(`continue`로 나머지 건너뜀) → 특성 면역 해제 → 필드 회복(그래스필드) → **먹다남은음식** → 젖은접시류 날씨 회복 → 건조피부류 날씨 피해 → 뿌리박기·아쿠아링(한 함수) → 씨뿌리기 → **미래예지** → 저주 → 속박 → 소금절이 → 물엿범벅 → 문어굳히기 → **희망사항** → 회복봉인·지옥찌르기 카운트 → 졸음(하품) → **모래바람 피해** → 상태이상 틱(포이즌힐 포함) → 탈피·촉촉바디 → 가속 → 꼬르륵스위치 → 변덕쟁이 → 자뭉·오랭열매 재확인 → 수확 → 되새김질

## 3. 새 구조
네 가지 반복으로 나눈다. 반복 안의 포켓몬 순서는 `eotOrder(c)`가 정한다 — **지금은 a→b 고정 그대로**이며 스피드순(A1-b)으로 바꿀 때 이 함수 한 곳만 고치면 된다(Q3).

| 단계 | 내용 (같은 단계 안의 순서) | 기절한 포켓몬 |
|---|---|---|
| 0 | 승패가 이미 났으면(`c.winner`) 효과 없이 ①만 한다(지금과 같다) | |
| ① | **날씨 지속 감소·종료**(`expireWeather`) — `expireFieldAndWeather`에서 날씨 부분만 떼어 맨 앞으로. 종료되면 `weather` 해제·`weatherExpired`·기분파 폼 복귀 | |
| ② | 모래바람 피해 `applySandstormDamage`(a, b) → 젖은접시류 회복 `applyWeatherHealAbility`(a, b) → 건조피부류 피해 `applyWeatherDamageAbility`(a, b) | 건너뜀 |
| ③ | 편마다 **미래예지 → 희망사항**(고정 순서, Q2) | **건너뛰지 않음** — 카운터는 줄고 효과만 실패(Q8) |
| ④ | 특성 면역 해제 → 그래스필드 회복 → **탈피·촉촉바디** → 먹다남은음식 → 뿌리박기·아쿠아링 → 씨뿌리기 → *(Q7-B면 여기서 상태이상 틱)* → 저주 → 속박 → 소금절이 → 물엿범벅 → 문어굳히기 → 회복봉인·지옥찌르기 카운트 → 졸음(하품) → *(Q7-A면 여기서 별도 반복으로 상태이상 틱)* | 건너뜀 |
| ⑤ | 멸망의노래 → 가속 → 변덕쟁이 → 수확 → 되새김질 → 꼬르륵스위치 → 자뭉·오랭열매 재확인 | 건너뜀(멸망의노래로 쓰러진 포켓몬은 나머지를 건너뜀) |

- **상태이상 틱(포이즌힐 포함)은 한 함수 그대로** `applyStatusEndOfTurnTick`을 부르기만 한다(분리 없음). `advanceStatusTurn` 호출 횟수 문제도 생기지 않는다.
- **탈피·촉촉바디**는 `applyShedSkinCure`를 ④로 옮긴다(상태이상 틱 앞이므로 치료되면 그 턴 독·화상 피해가 없다).
- **수확 → 열매 재확인 순서가 바뀐다**: 지금은 열매 재확인이 수확보다 앞이라 수확으로 돌아온 열매가 다음 턴에야 먹힌다. 새 순서(⑤)는 수확·되새김질이 먼저이므로 **수확으로 돌아온 열매를 같은 턴 종료에 HP 조건이 맞으면 바로 먹는다**(Showdown에서 열매는 HP 변화 직후 바로 먹힌다는 점과 맞다). 시나리오 R6-k.
- 반복 사이 상태(아이템 소모·특성·HP)가 바뀌므로 `EndOfTurnFighterContext`는 **반복·포켓몬마다 새로 만든다**. 지금은 포켓몬 하나당 한 번 만들던 것을 `makeEotCtx(c, key)`로 뺀다(약 15줄).
- 필드·룸·중력·전자부유 만료(`expireFieldAndWeather`에서 날씨를 뺀 나머지)와 편 단위 만료(`expireSideEffects`)는 **지금 자리 그대로**다. 그래스필드 회복(④)이 필드 만료보다 먼저라는 점은 Showdown(5 < 27)과 같다.
- 처리 시간: 컨텍스트 생성이 포켓몬당 1회 → 약 4회로 늘어난다(특성·도구 조회). 전후로 `ai60`의 `avgTurnMs`와 `regress 20000` 소요를 비교한다(§7).

## 5. 결정·해석 (기본값으로 진행. Q7만 착수 전 답 필요)
- **Q1. 날씨 마지막 턴에는 효과가 없어진다 (확정 순서의 직접 결과).** 날씨가 ①에서 먼저 끝나므로 마지막 턴에 모래바람 피해·젖은접시 회복·건조피부 피해·촉촉바디 치료·수확의 쾌청 판정이 일어나지 않는다. 날씨 5턴(`WEATHER_DURATION`)이면 피해 틱이 5번 → 4번이다. **검수에서 Showdown의 날씨(order 1)가 `duration--` 뒤 0이면 `end`를 부르고 건너뛴다는 것으로 확인됐다.** 지금 엔진은 마지막 턴에도 피해를 주므로 순서만이 아니라 효과 횟수가 바뀌는 변화다. 기본값: 확정 순서대로 적용.
- **Q2. 미래예지 → 희망사항, 고정 순서.** 확정 문구는 "희망사항 → 미래예지(설치 순서대로)"이나, Showdown은 설치 순서와 무관하게 미래예지(3) < 희망사항(4) **고정 순서**다. 두 효과가 겹치는 경우(같은 편 같은 턴 종료)를 구조로 따져도 미래예지는 쓴 지 2턴 뒤(`turnsRemaining = 3`, `preHitEffects.ts:491`), 희망사항은 다음 턴(`turnsRemaining = 2`, `mirroredEffects.ts:795`)이라 겹치면 항상 미래예지가 먼저 설치된 것이므로 두 해석이 같은 결과를 낸다. 기본값: 편마다 미래예지 → 희망사항(설치 순서 표식 필드 없음). 이 항목은 사용자 확정 문구의 "희망사항이 먼저"와 표면적으로 다르므로 PR 본문에도 적는다.
- **Q3. 스피드순.** 확정 ④와 Showdown 모두 스피드순이다. 지금 엔진은 a→b 고정이며 스피드순으로 바꾸면 양쪽 효과가 얽히는 경우(씨뿌리기 흡수·기절 순서)의 결과가 달라지는 **별도 변경**이다. 기본값: A1은 a→b를 유지하되 순서 배열을 `eotOrder(c)` 한 함수에 모아 둔다. 스피드순(트릭룸이면 반대)은 필요하면 별도 항목 **A1-b**로 분리해 기준값 변화를 따로 본다(백로그 후속 후보).
- **Q4. (폐기)** 포이즌힐 분리는 하지 않는다. Showdown도 독 틱 자리에서 피해를 회복으로 바꾸는 방식이다(검수 2번).
- **Q5. 희망사항 회복 0 로그의 조건과 문구.** 기본값: ① 살아 있는 포켓몬이 **HP가 가득 차서** 또는 **회복봉인으로** 회복이 0이면 줄을 남긴다. ② 그 자리가 **비어 있으면(쓰러져 있으면)** 줄을 남기지 않는다. ③ 문구는 확정 문구에 포켓몬 이름을 앞에 붙여 "○○: 희망사항이 이루어졌지만 회복할 HP가 없었다". (Showdown은 0일 때 줄을 남기지 않지만 이 로그는 이 프로젝트의 사용자 확정 규칙이다.)
- **Q6. 멸망의노래 위치.** 검수에 따라 ⑤ 맨 앞(Showdown 24)으로 옮긴다. 그러면 멸망의노래로 쓰러지는 턴에도 그 포켓몬의 씨뿌리기 흡수가 정상 처리돼 상대 회복이 빠지지 않는다. 지금은 맨 앞에서 카운트하고 쓰러지면 그 포켓몬의 나머지 효과를 전부 건너뛴다. 기준값 변화의 원인 분리를 더 중시하면 A1-b로 미룰 수 있다(기본값: A1에 포함 — 어차피 이번 재구성에서 위치를 새로 정해야 한다).
- **Q7. 상태이상 피해(독·맹독·화상)의 위치 — 사용자 확인 필요.** 사용자 확정은 "⑤ 상태이상 대미지(마지막)"이고 Showdown은 독(9)·화상(10)이 저주(12)·속박(13)·소금절이(13)·문어굳히기(14)보다 **앞**, 씨뿌리기(8) 바로 뒤다.
  - **A안(사용자 원 확정)**: 상태이상 틱을 ④의 저주·속박·소금절이·물엿범벅·문어굳히기·카운트·졸음 **뒤** 별도 반복으로. 독과 속박이 함께 걸리면 속박 → 독.
  - **B안(Showdown 순서, 검수 제안)**: 씨뿌리기 바로 뒤. 독과 속박이 함께 걸리면 독 → 속박. 로그 순서와 어느 피해로 쓰러지는지가 달라진다.
  - 어느 안이든 코드는 `applyStatusEndOfTurnTick` 호출 위치 한 줄이다. 설계 기본값은 **B안**(9세대 세부 순서를 숫자로 확인한 자료가 생겼고, 사용자가 이 자료로 다시 확인하라는 검수 의견을 줌)이지만 **사용자 확정 문구와 다르므로 구현 착수 전에 답을 받는다.** 시나리오 R6-l이 선택한 안의 순서를 고정한다.
- **Q8. ③은 기절한 자리도 돈다 (검수 5번).** 희망사항·미래예지는 자리(편) 효과라서 그 자리의 포켓몬이 이번 턴에 기절해도 카운터가 줄어야 한다. 지금 코드는 두 함수 모두 카운터를 줄인 뒤 `isFainted`를 확인하므로 **반복에서 기절한 포켓몬을 건너뛰지만 않으면** 된다(반복 시작의 기절 건너뛰기는 ②④⑤에만 적용). 효과는 그 자리가 비면 실패(미래예지는 빗나가 사라지고, 희망사항은 회복 대상이 없어 줄을 남기지 않는다)이며 교체로 들어온 포켓몬은 이미 소멸한 효과를 받지 않는다. 지금은 반복 위에서 건너뛰어 카운터가 멈추던 오류(Q6 초안에서 고친다고 한 것)가 새 구조에서도 되살아나지 않게 하는 조항이다.

## 6. 위험과 영향
- **기준 출력이 바뀌는 것이 정상이다**: `regress 200`·`regress 20000`·`greedy120`·`status60`·`h2h40`·`ai60`은 바뀔 수 있다. 반대로 **`test:inference` 결합 해시 `10040ffa0108c9a3`와 `matchup-hash600k`는 바뀌면 안 된다**(역산은 턴 종료 효과를 엔진이 아니라 사용자 입력 `endTurn`으로 따로 모델링하고, 매치업 해시는 데미지 계산만 센다). 이 둘이 바뀌면 의도하지 않은 변경이므로 PR 전에 원인을 찾는다.
- **원인 분리의 한계**: 이 PR의 기준값 변화는 "순서" 외에 (a) 날씨 마지막 턴 효과 소멸(Q1), (b) 멸망의노래 위치(Q6), (c) 수확→열매 순서, (d) 기절한 자리의 카운터(Q8)가 섞인다. 모두 새 순서에서 필연적으로 따라오는 변화이므로 한 PR에 두되 PR 본문에 항목별로 적는다. 원인 분리를 더 엄격히 하려면 Q6(멸망의노래)과 (c)를 A1-b로 미룰 수 있다.
- **저장된 대전 영상(`BattleVideo`)은 턴 로그를 그대로 저장**해 엔진을 다시 돌리지 않는다. 과거 영상 내용은 변하지 않는다. 다만 영상 재생 화면도 같은 `EndOfTurnLines`를 쓰므로 **옛 영상은 날씨 종료 문구가 맨 앞에 표시**된다(순서가 실제 처리 순서와 어긋나지만 내용은 같다).
- **AI 탐색은 `runTurn`을 그대로 쓰므로** 엔진 변화가 자동 반영된다. 손으로 쓴 추정식은 `turnRates.ts`의 환경 잔류 하나뿐이고 §4-5에서 맞춘다. `evaluator.ts`의 희망사항 회복 추정(1159~1182행)은 "다음 턴 종료에 절반 회복"이라 순서와 무관하다.
- 성능: §3 마지막 항목. 기준 `ai60` `avgTurnMs` 23.95ms, `regress 20000` 소요를 전후로 기록한다.
- 화면: 턴 종료 줄 순서와 날씨 종료 문구 위치가 바뀌는 **화면 확인 대상 변경**이다. 구현 뒤 feature 브랜치에서 `npm run dev`를 띄워 사용자가 확인한다(`CLAUDE.md` "검증").
