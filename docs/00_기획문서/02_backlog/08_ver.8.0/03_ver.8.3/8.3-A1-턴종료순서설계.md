## 2. 지금 엔진이 하는 일 (코드 확인)
`src/lib/battle/finishTurn.ts`의 `finishTurn`(1021행)은 다음을 **이 순서로** 부른다.
```
resolveEndOfTurnAndPerish(c)   // 턴 종료 효과 + 멸망의노래   (740행)
decideWinnerAndForcedSwitch(c) // 승패·강제 교체              (813행)
expireFieldAndWeather(c)       // 필드·룸·중력·전자부유·날씨 지속 턴 감소  (867행)
expireSideEffects(c)           // 스크린·신비의부적·순풍 지속 턴 감소       (940행)
collectResult(c)               // 결과 모음 (endOfTurn 배열 순서 = 화면 로그 순서)
```
핵심 구조 두 가지가 확정 순서와 다르다.
- **포켓몬 우선 구조**: `resolveEndOfTurnAndPerish`는 `for key of ["a","b"]`로 **a가 모든 단계를 끝까지** 돈 뒤 b가 모든 단계를 돈다. 확정 순서는 "단계 우선"(날씨 단계를 양쪽 다 한 뒤 희망사항 단계를 양쪽 다 …)이다. 또 순서는 스피드순이 아니라 **a→b 고정**이다(`order`·`speedA/B`는 멸망의노래 동반 기절 승부에만 쓴다).
- **날씨 종료가 맨 뒤**: 날씨 지속 턴 감소와 종료(`weatherExpired`, 기분파 폼 복귀)는 `expireFieldAndWeather`에서 **효과가 다 끝난 뒤**에 일어난다.

### 2-1. 한 포켓몬 안의 현재 순서 (`finishTurn.ts` 785~808행)
멸망의노래 카운트(`continue`로 나머지 건너뜀) → 특성 면역 해제 → 필드 회복(그래스필드) → **먹다남은음식** → 젖은접시류 날씨 회복 → 건조피부류 날씨 피해 → 뿌리박기·아쿠아링 → 씨뿌리기 → **미래예지**(`applyFutureSight`) → 저주 → 속박 → 소금절이 → 물엿범벅 → 문어굳히기 → **희망사항** → 회복봉인·지옥찌르기 카운트 → 졸음(하품) → **모래바람 피해** → 상태이상 틱(포이즌힐 포함) → 탈피·촉촉바디 → 가속 → 꼬르륵스위치 → 변덕쟁이 → 자뭉·오랭열매 재확인 → 수확 → 되새김질

※ 주의: 규칙 조사 R6의 "현재 엔진" 서술에서 미래예지는 씨뿌리기 **앞**, 희망사항은 속박류 **뒤**다. 위가 코드 순서이며 서술과 같다.

## 3. 새 구조
세 개의 반복으로 나눈다. 반복 안에서 포켓몬 순서는 **a→b 고정 그대로**다(§5 Q3).

| 단계 | 반복 | 내용 (같은 단계 안의 순서) |
|---|---|---|
| 0 | — | 승패가 이미 났으면(`c.winner`) 효과 없이 날씨 종료 처리만(지금과 같다) |
| ① | 한 번 | **날씨 지속 감소·종료**(`expireWeather`) — `expireFieldAndWeather`에서 날씨 부분만 떼어 맨 앞으로. 종료되면 `weather` 해제·`weatherExpired`·기분파 폼 복귀 |
| ② | a, b 각각 | 모래바람 피해 `applySandstormDamage` → (한 번 더 a, b) 젖은접시류 회복 `applyWeatherHealAbility` → 건조피부류 피해 `applyWeatherDamageAbility` |
| ③ | a, b 각각 | 편(side)마다 **미래예지 → 희망사항**(§5 Q2: 설치 순서로 풀면 이 순서가 된다) |
| ④ | a, b 각각 | 멸망의노래 → 특성 면역 해제 → 그래스필드 회복 → 먹다남은음식 → **포이즌힐(분리, §5 Q4)** → 뿌리박기·아쿠아링 → 씨뿌리기 → 저주 → 속박 → 소금절이 → 물엿범벅 → 문어굳히기 → 회복봉인·지옥찌르기 카운트 → 졸음(하품) |
| ⑤ | a, b 각각 | 상태이상 틱(독·화상 등 피해 — 포이즌힐은 ④로 빠짐) → 탈피·촉촉바디 → 가속 → 꼬르륵스위치 → 변덕쟁이 → 자뭉·오랭열매 재확인 → 수확 → 되새김질 (**지금의 꼬리 부분을 그대로** 둔다) |

- 반복 사이 상태(아이템 소모·특성·HP)가 바뀌므로 `EndOfTurnFighterContext`(`fighterAbility`·`fighterItem`·`opponentFainted` 등)는 **반복·포켓몬마다 새로 만든다**. 지금은 포켓몬 하나당 한 번 만들던 것을 `makeEotCtx(c, key)` 도우미로 뺀다(코드 중복 방지, 약 15줄).
- 반복 시작마다 `isFainted` 포켓몬은 건너뛴다(지금과 같은 규칙). 멸망의노래로 쓰러진 포켓몬(`perishFaintedKeys`)은 ④의 나머지와 ⑤를 건너뛴다(지금의 `continue`와 같은 효과).
- 필드·룸·중력·전자부유 만료(`expireFieldAndWeather`에서 날씨를 뺀 나머지)와 편 단위 만료(`expireSideEffects`)는 **지금 자리 그대로**다. 사용자 확정 순서에 없고, 그래스필드 회복이 만료 전에 계속 일어나야 하기 때문이다(필드 마지막 턴에도 회복).
- 처리 시간: 효과가 같은 횟수만 실행되고 컨텍스트 생성만 포켓몬당 1회 → 약 4회로 늘어난다(특성·도구 조회). 한 턴 비용 대비 작아 보이지만 `ai60`의 `avgTurnMs`와 `regress 20000` 소요를 전후로 비교한다(§7).

## 5. 사용자 확정과 다르거나 해석이 필요한 부분 (이견이 있으면 알려 주세요 — 기본값으로 진행)
- **Q1. 날씨 마지막 턴에는 효과가 없어진다 (확정 순서의 직접 결과).** 날씨가 ①에서 먼저 끝나므로 마지막 턴에 모래바람 피해·젖은접시 회복·건조피부 피해·촉촉바디 치료·수확의 쾌청 판정이 일어나지 않는다. 날씨 5턴(`WEATHER_DURATION`)이면 피해 틱이 **5번 → 4번**으로 줄어든다. 본가도 날씨가 끝나는 턴에는 피해가 없다고 기억하지만(**[기억]**, 자료 미확인) 지금 엔진은 마지막 턴에도 피해를 준다 — **순서만이 아니라 효과 횟수가 바뀌는 변화**다. 기본값: 확정 순서대로 적용.
- **Q2. 희망사항과 미래예지의 순서.** 확정 문구는 "희망사항 → 미래예지(설치 순서대로)"인데, 두 효과가 **같은 편의 같은 턴 종료에 겹치는** 경우는 구조상 하나뿐이다: 미래예지는 `turnsRemaining = delayedAttackTurns + 1 = 3`(`preHitEffects.ts:491`)이라 **쓴 지 2턴 뒤** 종료에 때리고, 희망사항은 `turnsRemaining = 2`(`mirroredEffects.ts:795`)라 **다음 턴** 종료에 회복한다. 겹치려면 미래예지가 희망사항보다 **1턴 먼저** 설치돼야 하므로, 설치 순서를 따르면 겹칠 때 **항상 미래예지가 먼저**다. 설치 순서 표식을 새로 두지 않고 "편마다 미래예지 → 희망사항"으로 처리하면 같은 결과이고, 겹치지 않을 때는 순서가 결과에 영향을 주지 않는다. 기본값: 편마다 미래예지 → 희망사항(상태 필드 추가 없음). 문구 그대로 "희망사항이 먼저"를 원하시면 알려 주세요(그러면 겹칠 때 설치 순서 규칙과 어긋난다).
- **Q3. 스피드순.** 확정 ④에 "스피드순"이 적혀 있으나 지금 엔진은 a→b 고정이다(스피드순으로 처리한 적이 없다). 스피드순으로 바꾸면 양쪽 효과가 얽히는 경우(씨뿌리기 흡수·기절 순서)의 결과가 달라지는 **별도 변경**이다. 기본값: A1은 a→b를 유지하고, 스피드순은 필요하면 별도 항목(A1-b)으로 분리해 기준값 변화를 따로 본다.
- **Q4. 포이즌힐 분리.** 확정 ④에는 포이즌힐이, ⑤에는 상태이상 대미지가 있다. 지금은 둘이 `applyStatusEndOfTurnTick` 한 함수라 포이즌힐이 상태이상 틱과 같이 뒤에서 일어난다. 기본값: 확정대로 포이즌힐을 ④(먹다남은음식 뒤)로 분리한다(약 15줄). 같은 상태이상의 턴 카운터 `advanceStatusTurn`은 1회만 호출한다. 효과가 작다고 보시면 분리를 빼고 ⑤에 두는 안도 가능하다.
- **Q5. 희망사항 회복 0 로그의 조건과 문구.** 기본값: ① 살아 있는 포켓몬이 **HP가 가득 차서** 또는 **회복봉인으로** 회복이 0이면 줄을 남긴다. ② 그 자리가 **비어 있으면(쓰러져 있으면)** 줄을 남기지 않는다(회복할 대상이 없음 — 지금과 같다). ③ 문구는 확정 문구에 포켓몬 이름을 앞에 붙여 "○○: 희망사항이 이루어졌지만 회복할 HP가 없었다"로 한다(다른 턴 종료 줄이 포켓몬 이름으로 시작하는 형식에 맞춤). 이름 형식이 마음에 안 들면 PR 화면 확인 때 알려 주세요.
- **Q6. 멸망의노래.** 지금은 포켓몬마다 맨 앞에서 카운트하고 쓰러지면 그 포켓몬의 나머지 턴 종료 효과를 전부 건너뛴다. 새 구조에서는 ②③(날씨·희망사항·미래예지)이 멸망의노래 **앞**에 오므로, 멸망의노래로 쓰러지는 턴에도 그 포켓몬이 날씨 피해 등을 먼저 받는다(쓰러질 포켓몬이라 결과 차이는 거의 없음). 또 지금 `continue`가 희망사항·미래예지 카운터도 건너뛰어 **그 턴 카운터가 안 줄던** 사소한 오류가 새 구조에서는 없어진다. 본가의 멸망의노래 위치는 확정 목록에 없어 손대지 않는다.

## 6. 위험과 영향
- **기준 출력이 바뀌는 것이 정상이다**: `regress 200`·`regress 20000`·`greedy120`·`status60`·`h2h40`·`ai60`은 바뀔 수 있다(턴 종료 결과가 바뀌므로). 반대로 **`test:inference` 결합 해시 `10040ffa0108c9a3`와 `matchup-hash600k`는 바뀌면 안 된다**(역산은 턴 종료 효과를 엔진이 아니라 사용자 입력 `endTurn`으로 따로 모델링하고, 매치업 해시는 데미지 계산만 센다). 이 둘이 바뀌면 의도하지 않은 변경이므로 PR 전에 원인을 찾는다.
- **저장된 대전 영상(`BattleVideo`)은 턴 로그를 그대로 저장**해 엔진을 다시 돌리지 않는다. 엔진을 바꿔도 과거 영상의 내용은 변하지 않는다. 다만 영상 재생 화면도 같은 `EndOfTurnLines`를 쓰므로 **옛 영상은 날씨 종료 문구가 맨 앞에 표시**된다(순서가 실제 처리 순서와 어긋나지만 내용은 같다).
- **AI 탐색은 `runTurn`을 그대로 쓰므로** 엔진 변화가 자동 반영된다. 손으로 쓴 추정식은 `turnRates.ts`의 환경 잔류 하나뿐이고 §4-5에서 맞춘다. `evaluator.ts`의 희망사항 회복 추정(1159~1182행)은 "다음 턴 종료에 절반 회복"이라 순서와 무관하다.
- 성능: §3 마지막 항목. 기준 `ai60` `avgTurnMs` 23.95ms, `regress 20000` 소요를 전후로 기록한다.
- 화면: 턴 종료 줄 순서와 날씨 종료 문구 위치가 바뀌는 **화면 확인 대상 변경**이다. 구현 뒤 feature 브랜치에서 `npm run dev`를 띄워 사용자가 확인한다(`CLAUDE.md` "검증").
