## 2. 불일치·누락

### 2-1. 명중 판정을 한다 (Q4 변경)
- [소스] `onEnd` → `trySpreadMoveHit([target], source, hitMove, true)`는 일반 기술과 같은 단계를 모두 거친다: 무적 은신(0) → TryHit(1) → 타입 면역(2) → 명중(4) → … `moveData.accuracy: 100`이라도 `hitStepAccuracy`가 **사용자 명중 랭크 − 대상 회피 랭크**와 `ModifyAccuracy`(밝은가루·모래숨기 등)를 적용한다. 필중 처리(`alwaysHit`)는 없다.
- [실행] 적중 턴에 대상 회피 +6 → 60시드 중 **41회 `-miss`**(이론값 33% 명중과 맞음).
- 설계 영향: `hitChance`에 `computeBattleHitChance`(`hitChance.ts:32`)를 넣는다.
  - 사용자 명중 랭크: `party[sourceIndex]`의 현재 랭크(교체·기절이면 이미 0).
  - 사용자 쪽 명중 특성·도구(복안·광각렌즈·노가드 등): 필드에 있을 때만(§0 ① 규칙과 같음).
  - 대상 쪽 노가드·밝은가루·모래숨기 등: 정상 적용.
- 로그: 새 필드 `futureSightMiss?: true`("빗나갔다!"). 빗나가도 §2-5의 생명의구슬 반동은 생긴다.

### 2-2. 무적 은신 중인 대상에게는 빗나간다 (Q5 변경)
- [소스] 0단계 `hitStepInvulnerabilityEvent`가 그대로 돈다. 미래예지는 공중날기·땅파기·다이빙·바운스·섀도다이브·고스트다이브 어느 쪽의 예외 기술도 아니다.
- [실행] 적중 턴에 대상이 공중날기 1턴째:
  ```
  |-end|p2a: Pidgeot|move: Future Sight
  |-miss|p1a: Alakazam|p2a: Pidgeot
  |-damage|p1a: Alakazam|117/130|[from] item: Life Orb   ← 생명의구슬이면 반동은 생김
  ```
- 설계 영향: `evadedByCharge`·`defenderHideType`을 정상 경로와 같게 채운다(입력 표 수정). 로그는 §2-1의 `futureSightMiss`를 같이 쓴다.

### 2-3. 틀깨기는 사용자가 필드에 있어도 적용되지 않는다
- [소스] 미래예지 적중은 `useMove`를 거치지 않으므로 **`ModifyMove`·`ModifyType` 이벤트가 돌지 않는다.** 틀깨기는 `onModifyMove`에서 `move.ignoreAbility = true`를 거는 방식이라 미래예지에는 걸리지 않는다. 같은 이유로 노멀스킨은 `onEnd`가 타입만 직접 바꾸고, ×1.2(`typeChangerBoosted`)는 **붙지 않는다**.
- [실행] 사용자(틀깨기, 필드에 있음) → 옹골참 꼬지모(풀피):
  - 미래예지: `1/145`(옹골참 발동)
  - 같은 조건의 일반 사이코키네시스: `debug|Damage handler suppressed by Mold Breaker` → 기절
- 반면 `BasePower`·`ModifySpA`·`ModifyDamage`·`ModifySTAB`·`ModifyCritRatio`·`ModifyAccuracy` 이벤트는 사용자가 필드에 있으면 정상 적용된다(테크니션·색안경·적응력·생명의구슬 배율 등).
- 설계 영향:
  - 입력 표 `defenderAbility`: `resolveEffectiveDefenderAbility`를 쓰지 말고 **항상 대상의 특성을 그대로** 쓴다(틀깨기·테라볼티지·터보블레이즈 모두 미적용).
  - §0 ② 표기 정정: "onEnd 직접 처리 = 틈새포착·노멀스킨(타입만)". 적응력은 일반 STAB 이벤트다.
  - 노멀스킨: 미래예지를 배우는 26종 중 노멀스킨을 가진 종이 없으면 생략하고 `// ponytail:` 주석만 남겨도 된다.

### 2-4. 방어는 무시하지만 버티기는 적용된다 (R3-j 기대값 교체)
- [소스] Showdown에 `removeVolatile('Protect'/'Endure')`는 **없다**. 방어가 무시되는 이유는 `moveData.flags`에 `protect`가 없어서다(방어·판별·킹실드·니들가드·토치카·실크트랩·불꽃의수호 모두 `!move.flags['protect']`이면 통과). 버티기는 `onDamage`가 `effect.effectType === 'Move'`만 확인하는데 `hitMove`가 Move라서 **발동한다**. 버티기 휘발성(`duration: 1`)은 미래예지 차례(잔류 order 3)까지 남아 있다.
- [실행] 적중 턴에 대상이 버티기: `-activate|p2a: Pikachu|move: Endure` → `1/110`. 방어를 쓰면 무시되고 기절했다.
- 설계 영향:
  - 입력 표의 **"호출 전에 `defender.activeProtect = undefined`로 비운다"를 삭제**한다. `blockedByProtect: false`만으로 방어는 무시된다.
  - 버티기 처리 코드가 `activeProtect === 'endure'`를 읽는다면 그대로 두면 Showdown과 같다.
  - §0 ⑥·Q1 본문의 "방어·버티기만 무시"를 "방어만 무시"로 고친다.
- 시험 R3-j: 기대값 → "**버틴다(HP 1)**". 방어 무시는 별도 시험으로 둔다(R3-j2).

### 2-5. 생명의구슬 반동은 빗나감·무효에도 생긴다 / 사용자 측 기술 후 효과는 생략된다
- [소스] `onEnd`는 `trySpreadMoveHit`의 결과와 관계없이 `source.isActive && hasItem('lifeorb')`이면 반동을 호출한다. 반면 일반 공격 때 사용자 측 기술 후 효과(`AfterMoveSecondarySelf`)는 `!move.flags['futuremove']`로 **생략**된다(`battle-actions.ts:600`). 생명의구슬만 `onEnd`가 직접 부르는 예외다.
- [실행]
  - 악 타입 대상(무효 `-immune`) → 반동 `117/130` 발생
  - 공중날기 대상(`-miss`) → 반동 발생
  - 대상이 적중 전에 이미 기절(불발)이면 `onEnd`가 먼저 끝나 반동 없음
  - 조개껍질방울(필드에 있음) → 회복 없음
  - 자기과신(필드에 있음)으로 대상 기절 → 공격 +1 **발동**(`onSourceAfterFaint`라 생략 대상이 아님). 교체된 상태면 미발동
- 설계 영향:
  - 반동을 파이프라인 자동 적용에 맡기지 않는다. 파이프라인이 "데미지 > 0일 때만" 반동을 넣는 구조라면 빗나감·무효에서 Showdown과 달라진다. **"사용자가 필드에 있고 생명의구슬 보유 → 적중 결과와 무관하게 반동"**을 헬퍼에서 직접 처리하고, 파이프라인의 반동 분기는 건너뛴다(`attackerItem`은 배율 때문에 넘겨야 하므로, 반동만 끄는 플래그가 필요하다).
  - 파이프라인이 다른 사용자 측 기술 후 효과(조개껍질방울, 흡수, 반동기 반동 등)를 적용한다면 미래예지에서는 끈다. 기절시켰을 때의 특성(자기과신·비스트부스트 등)은 필드에 있을 때 유지한다.
  - "보이지 않는 HP 변화를 만들지 않는다"는 Q8 취지는 그대로 맞다. 반동 줄의 조건만 넓힌다.
  - 판단 메모: 빗나감·무효 시 반동이 본가와 같은지는 이번에 확인하지 못했다. Showdown은 의도적으로 무조건 호출하므로 Showdown 동작을 기본값으로 권장한다.

### 2-6. "방어 측 효과 전부 적용"의 예외
[소스]에서 `futuremove` 플래그로 명시적으로 빠지거나, 사용자 상태에 따라 달라지는 것이다. poke-builder에 구현된 것만 가드를 넣으면 된다.

| 효과 | Showdown 동작 | 근거 |
|---|---|---|
| 탈출버튼 | **발동 안 함** | `items.ts:1700`, champions `items.ts:265` 둘 다 `!move.flags['futuremove']` (실측: 교체 없음) |
| 저주받은바디 | **발동 안 함** | `abilities.ts:787` |
| 길동무 | **발동 안 함** | `moves.ts:3502` (실측: 대상만 기절, 사용자 무사) |

| 레드카드 | 사용자가 **필드에 있으면 발동**(사용자 강제 교체), 교체·기절 상태면 미발동 | `!source.isActive` 검사. 실측: `-enditem Red Card` → `drag` |

## 3. 입력 표 수정안 (§3-1 ② 표 기준, 바뀌는 줄만)

| 입력 | 수정 후 값 |
|---|---|
| `defenderAbility` | 대상의 특성 그대로(`resolveEffectiveDefenderAbility` 사용 안 함, §2-3) |
| `evadedByCharge`·`defenderHideType` | 정상 경로와 같게(§2-2) |
| `blockedByProtect` | `false`. **`activeProtect`는 비우지 않는다**(버티기 유지, §2-4) |
| `hitChance` | `computeBattleHitChance(...)` — 사용자 랭크는 `party[sourceIndex]`, 사용자 특성·도구는 필드에 있을 때만(§2-1) |
| 생명의구슬 반동 | 파이프라인 밖에서 직접: 필드에 있음 + 보유 → 결과 무관 적용(§2-5) |
| "필드에 있음" 판정 | `activeIndex === sourceIndex && !fainted`. 교체로 내려갔다가 **적중 전에 다시 나온 경우는 필드에 있음**이다(Showdown은 같은 객체의 `isActive`를 본다) |
