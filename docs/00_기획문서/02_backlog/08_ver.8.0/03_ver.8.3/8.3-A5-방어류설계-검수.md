## 2. 상세

### 2-1. V1 — 길동무 턴에 `stall`이 만료된다 (Q18 확인)
- [소스] `stall`: `duration: 2`, 성공한 방어류가 `addVolatile('stall')`을 부르면 `onStart`(counter 3) 또는 `onRestart`(counter ×3, **duration을 2로 되돌림**)가 실행된다. 방어류를 성공하지 못한 턴은 duration이 갱신되지 않아, 성공한 다음 턴이 끝날 때 만료된다. 길동무는 `stallingMove`가 아니고 `stall`을 건드리지 않는다.
- [실행] 팬텀(빠름) vs 잠만보(튀어오르기):
  ```
  [2턴 시작 stall 없음]        Protect      → -singleturn (굴림 없음)
  [3턴 시작 counter 3, dur 1]  Destiny Bond → -singlemove
  [4턴 시작 stall 없음]        Protect      → -singleturn (굴림 없음 = 100%)
  ```
  대조(방어 → 방어): 3턴째 `|debug|Success chance: 33%`.
- 설계 영향: 없음. §5 Q18을 "Showdown 확인"으로 바꾸고, §9 V1을 닫는다. R7-a 시나리오 문구의 "`protectStreak` 불변"은 설계서의 해석("길동무가 카운터를 올리지 않는다")대로 고치는 것을 권장한다. 그대로 두면 다음 읽는 사람이 Q18과 모순된다고 오해할 수 있다.

### 2-2. Q19 — 호출 기술 길동무
- [소스] champions에서 길동무를 부를 수 있는 기술은 **잠꼬대뿐**이다. 흉내쟁이는 `failcopycat`이라 실패하고, 손가락흔들기·조수·제가먼저·따라하기·자연의힘은 `Past`다. 잠꼬대에는 `nosleeptalk` 제외 조건이 있지만 길동무에는 그 플래그가 없다.
- [소스] 길동무 볼라타일의 `onBeforeMove`는 `move.id === 'destinybond'`일 때만 예약을 그대로 둔다. 잠꼬대는 바깥 기술이 `sleeptalk`이라 이 단계에서 예약이 먼저 풀리고, 안쪽 `useMove`는 `BeforeMove`를 다시 돌지 않는다. 그래서 `onPrepareHit`의 `removeVolatile`이 거짓을 돌려주고, 길동무는 성공한다.
- [실행]
  | 순서 | 결과 |
  |---|---|
  | 길동무(직접, 성공) → 잠꼬대→길동무 → 잠꼬대→길동무 | 둘 다 `-singlemove`(성공), 매 턴 `removing Destiny Bond before attack` |
  | 잠꼬대→길동무(성공) → 길동무(직접) | 직접 쪽 `-fail` |
- 설계 영향: `c.move.protectEffect === "destinyBond" && c.destinyBondWasArmed` 조건이 두 방향 모두를 맞힌다(두 번째 행은 `c.move`가 길동무이고 예약도 남아 있으므로 실패). 단, poke-builder의 잠꼬대가 호출한 기술을 `effectiveMove`로 넘기고 `c.move`는 잠꼬대로 남기는 구조인지 구현 중에 확인한다. 잠꼬대가 없거나 길동무를 부를 수 없게 되어 있다면, 설계서 표현대로 방어 코드로 남는다. 시험 행 추가 권장: **R7-i 길동무 성공 → 잠꼬대로 길동무 → 성공 / 잠꼬대 길동무 → 직접 길동무 → 실패.**

### 2-3. 추가 1 — 방어류 성공 다음 턴에 행동하지 못해도 카운터가 사라진다
- [소스] 2-1과 같은 원리다. `stall` 만료는 "다음 턴에 무슨 기술을 썼는가"가 아니라 **"다음 턴에 방어류를 성공했는가"**로 정해진다. 풀죽음·마비·수면·반동(파괴광선 재충전) 턴도 성공하지 못한 턴이므로 만료된다. 교체하면 볼라타일이 모두 지워진다.
- [실행] 방어(성공) → 풀죽음(`cant|flinch`, 볼라타일을 직접 넣어 강제) → 방어: 4턴 시작 `stall 없음` → 굴림 없이 성공.
- poke-builder 쪽 위험: 설계서 Q18은 `:1716`의 "비방어류 기술이면 0" 갈래를 근거로 든다. 그런데 이 갈래는 **거울 단계(`protectAndFieldSetup`)가 도는 행동에만** 적용된다. C5에 따르면 행동불능 턴에도 `preHitEffects.ts:1294`(길동무 예약 지우기)는 돌지만, 거울 단계까지 가는지는 설계서에 나와 있지 않다. 가지 않는다면 지금 엔진은 **방어 → 마비로 행동불능 → 방어**를 1/3로 깎는다. Showdown은 100%다.
- 권장:
  - 구현 첫 단계에서 행동불능·반동 턴과 교체 후 재등장 때 `protectStreak`가 0이 되는지 확인한다.
  - 0이 되지 않으면 이 PR에서 함께 고친다. 가장 작은 수정은 C5와 같은 자리, 즉 "행동 시작 때 무조건 지움"이 있는 곳에서 행동불능으로 끝나는 갈래에 `protectStreak = 0`을 한 줄 넣는 것이다. 이미 이 PR이 같은 근거(Q18)로 카운터 수명을 맞추므로 범위가 자연스럽다. 해시 영향은 단계 ①에 포함한다.
  - 시험 추가: **R7-j 방어 성공 → 행동불능(마비 난수 고정/풀죽음) → 방어(난수 0.99) → 성공**, **R7-k 방어 성공 → 교체 → 재등장 방어(0.99) → 성공**(이미 맞으면 회귀용).

### 2-4. 추가 2 — 연속 횟수 상한(`counterMax: 729`)
- [소스] `stall.onRestart`: `if (counter < counterMax) counter *= 3`. counter는 3^n이므로 **연속 6회 성공 뒤로는 1/729에서 멈춘다**. 엔진(`(1/3)^streak`)과 AI(`protectSuccessChance`)에는 상한이 없다.
- 실제 영향: 방어를 굴림으로 7연속 성공할 일은 사실상 없다. 다만 이번 변경으로 **패스트가드는 굴림 없이 카운터만 올리므로**, 패스트가드 6연속 → 방어 같은 경로로는 결정적으로 도달할 수 있다(Showdown 1/729, 엔진 1/2187).
- 권장(선택, 한 줄씩): 엔진 `Math.pow(1 / 3, Math.min(streak, 6))`, AI도 같은 식. 사용자 원칙(정확한 쪽 채택)에 맞고, 시험은 R7-c2 옆에 "streak 7, 난수 1/729 − ε → 성공"을 한 행 추가하면 된다. 이 PR에 넣지 않으면 §4 "넣지 않는 것"에 적는다.

### 2-5. 그 밖에 확인한 것 (설계 영향 없음)
- 마지막 행동 판정: 상대가 교체한 턴에 버티기를 쓰면 `|move|…|Endure||[still]` → `|-fail|`. 실패한 방어류는 `stall`을 지우거나 갱신하지 않을 뿐이고 그 턴 끝에 만료된다. 설계의 "실패하면 streak 0"과 다음 턴 결과가 같다.
- 굴림 없음: Showdown은 `stall`이 없으면 `StallMove` 핸들러가 없어 난수를 쓰지 않는다. 엔진은 streak 0에서도 `random() < 1`로 난수를 하나 쓰지만 결과는 같다. 이번 범위에서 바꿀 필요는 없다(해시만 흔들린다).
- §3-1 의사코드에서 `!bounceActive` 가드가 빠져 있다. 지금 코드의 `if (protectEffect && !bounceActive)` / `else if (!bounceActive)` 구조를 그대로 유지한다는 뜻이면 문서에 한 줄 적어 둔다(Showdown 대응 없음, 정합성 메모).
- AI 길동무 `successChance`: 판단 시점(턴 시작)의 `destinyBondArmed`가 곧 "직전 행동이 성공한 길동무"라 Showdown 규칙과 같다.
