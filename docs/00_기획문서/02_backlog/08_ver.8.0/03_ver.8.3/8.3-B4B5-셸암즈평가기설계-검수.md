## 2. 상세

### 2-1. Showdown 원문 확인

[소스] 설계서 §2 인용과 같다. 분류 비교의 성질:
- 공격·특공은 사용자, 방어·특방은 대상의 `getStat(stat, false, true)` → **랭크만 적용**(각 단계 `Math.floor`)
- 특성·도구·날씨·상태(화상은 `getStat`이 아니라 데미지 단계에서 들어가므로 애초에 무관) 배율 미반영
- 동점: `physical === special && this.randomChance(1, 2)` — 단락 평가라 **동점일 때만 난수 1회**. 엔진의 난수 소비 조건과 같다
- 물리면 `move.flags.contact = 1`

챔피언스 mod는 `shellsidearm`을 재정의하지 않는다(기본 9세대 정의 그대로). 가라르 야도란 learnset에 `shellsidearm: ["9M"]`이 있다.

### 2-2. 엔진 식과 Showdown 식은 이론상 같은 분류를 낸다 (§2 "구조 차이" 보강)

원인 → 결과:
1. Showdown 비교값 = `floor(floor(floor(floor(2L/5+2) × 90 × A) / D) / 50)` = 엔진 `computeDamage`의 기본 데미지(`+2` 전)와 **같은 식**이다(`getDamage` 1772·1910행과 같은 floor 순서 — 엔진이 이 순서를 따른다는 전제).
2. 엔진은 여기에 `+2` → 난수 1.0(값 그대로) → 자속 ×1.5(4096 반올림)를 **두 분류에 똑같이** 적용한다. 상성은 `computeDamage`에 상대 타입이 안 들어가 없다.
3. `+2`·×1.0은 순서를 그대로 둔다. 자속 ×1.5(적응력 ×2.0 포함)는 4096 반올림 후에도 **엄격 증가 함수**다(입력이 1 늘면 출력이 최소 1 는다 — Python으로 x = 0~5000 전수 확인).
4. 따라서 Showdown에서 `물리 > 특수`이면 엔진도 `>`, `=`이면 `=`. **분류·동점 판정이 항상 같다.** 3만 판 0건 불일치는 이 성질의 결과다.

- 설계서 반영: §2 "이론상 반올림 경계에서 갈릴 수 있으나…" → "기본 데미지 이후 단계가 두 분류에 같은 엄격 증가 변환이라 이론상 같다. 전제: (a) `computeDamage`의 기본 데미지 floor 순서가 Showdown과 같다 (b) 분류 비교 호출에 분류마다 다른 배율이 들어가지 않는다". §8 "5만 판 100% 일치지만 보증은 아니므로"도 같은 취지로 고친다.
- S-d는 그대로 둔다. 역할은 **위 전제 (a)(b)가 깨지는 변경을 잡는 것**이다. 엔진을 Showdown 식으로 바꾸지 않는 판단도 이 증명으로 더 단단해진다.
- 참고: 이 논리는 역산 `categoryOf`(엔진 규칙 구현)에도 같이 성립한다 → V6의 "결과는 같다"의 근거.

### 2-3. 신규 — 천진(Unaware)은 분류 비교에 반영되지 않는다

[소스] `getStat`:
```ts
if (!unboosted) {
  let boosts = this.boosts;
  if (!unmodified) {
    boosts = this.battle.runEvent('ModifyBoost', this, null, null, { ...boosts });  // ← 천진은 여기
  }
  ...
}
```
천진은 `onAnyModifyBoost`로만 동작한다. 셸암즈는 `unmodified=true`라 이 이벤트를 부르지 않는다.

- 결과: **상대가 천진이어도 공격측 랭크(공격·특공 +2 등)가 분류 비교에 그대로 들어간다.** 공격측이 천진이어도 상대의 방어·특방 랭크가 그대로 들어간다. 실제 데미지 계산(`calculateStat`)에서는 천진이 적용된다 — "분류는 원래 랭크로, 데미지는 천진 반영 랭크로".
- 챔피언스에 천진 보유 종이 있다(예: 픽시). 무작위 풀 측정(§0-4)에 천진 대상이 섞였는지는 설계서에 없다.
- **엔진·평가기 확인 필요**
  - 엔진 `preHitEffects.ts:672~690`이 넘기는 `attackerStages`·`defenderStages`가 **천진 반영 전 원래 랭크**인가
  - 평가기 `c.attackerStages`·`c.defenderStages`가 평가 컨텍스트를 만들 때 **이미 천진으로 0 처리된 값**인가. 그렇다면 공용 함수에 그 값을 넘기면 엔진과 갈린다. 평가기는 "원래 랭크"를 따로 넘겨야 한다
- 설계서 반영
  - §2 표에 행 추가: "천진 | 미반영(`ModifyBoost` 생략) | 엔진 확인 필요"
  - §3-3 공용 함수 주석에 "랭크는 천진 반영 **전** 값"을 적는다
  - **S-i(신규)**: 상대 천진 + 가라르 야도란 공격 +2(또는 특공 +2)로 원래 랭크와 0 랭크의 분류가 갈리는 구성 → 평가기 분류 = 엔진 분류 = Showdown 식(원래 랭크). 공격측 천진 + 상대 방어 랭크 쪽도 1건
- 엔진이 이미 원래 랭크를 넘기고 있으면 B5 결론(변경 없음)은 그대로다. 천진 반영 랭크를 넘기고 있으면 B5에 "천진 무시" 수정이 한 줄 생긴다(사용자 확정 문구 "물리/특수 판단 뒤 적용"과도 같은 방향).

### 2-4. 참고 — 원더룸 (낮은 우선순위)

[소스] `getStat`은 `unmodified && wonderroom`일 때 **랭크만** 반대쪽 방어 스탯 것을 읽고, 실능은 원래 스탯(`storedStats[원래 이름]`)을 쓴다(주석: 다운로드 때문에 생긴 부작용). 한편 실제 데미지(`calculateStat`)는 방어·특방을 바꾼다.
- 결과: 원더룸 중 Showdown 셸암즈는 "방어 실능 × 특방 랭크"와 "특방 실능 × 방어 랭크"를 비교하는 기묘한 동작이다. damage-calc는 실능을 통째로 바꿔 비교해 Showdown 시뮬레이터와도 다르다.
- 원더룸은 챔피언스 learnset에 있다(31종). **엔진에 원더룸이 없으면 무시.** 있으면 이번 범위 밖으로 §8에 한 줄만 기록한다(재현 가치 대비 비용이 크다).

### 2-5. V1 — 동점 물리 고정: 동의, 근거 문장만 수정

- 동의 이유: 동점 비율이 낮고(1~3%), 가라르 야도란이 샘플에 없으며, 혼합 표시는 판정 배지 구조를 바꿔야 한다. Showdown 시뮬레이터는 50:50이라 "정답 결정값"이 없다. 참고로 damage-calc(`getShellSideArmCategory`)는 동점을 **특수**로 두고 랭크를 넣지 않는다 — 결정적 표시는 도구마다 다르므로 물리 고정도 근거가 충분하다.
- **수정할 문장**: §3-2 "분류 전 기준으로 같은 데미지를 출발점으로 삼아 오차가 작다" — 분류 뒤 배율은 분류마다 다르게 걸린다(화상 ×0.5는 물리만, 리플렉터/빛의장막, 방어측 특성·도구 등). 동점에서 물리로 추정했는데 엔진이 특수로 나가면 **배율 비율만큼(예: 화상 시 2배) 차이**가 날 수 있다. "동점 빈도가 낮아 영향 범위가 작다"로 바꾸고, §8 한계에 "동점 + 분류별 배율이 다른 상황에서 AI 추정이 엔진 결과의 한쪽(물리)에 고정된다"를 적는다.

## 3. 설계서 반영 목록

1. **§2 구조 차이 문단**: "이론상 갈릴 수 있음" → §2-2 증명과 전제 (a)(b)로 교체. §8 해당 줄도 같이
2. **§2 표 행 추가(천진)** + **엔진·평가기 랭크 출처 확인**(원래 랭크인가). 평가기가 천진 반영 랭크를 들고 있으면 공용 함수에는 원래 랭크를 넘긴다
3. **§3-3 공용 함수 주석**: "랭크는 천진 반영 전 값"
4. **§3-2 문장 수정**: "오차가 작다" → "빈도가 낮다", §8에 분류별 배율 차이 한계 추가
5. **시험**: S-i 추가, S-f 예시 교체, S-d 생성 조건 명시
6. (엔진에 원더룸이 있으면) §8에 원더룸 한 줄
7. V1~V6 기본안 모두 동의 — §7 사용자 답 칸은 사용자 확정 후 채운다
