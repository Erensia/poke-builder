## 0. 요약
- **문제**: 두 기기가 같은 계정으로 각자 배틀을 해서 AI 학습 기억(`aiMemory`·`aiMemoryRank`)이 갈라지면 동기화가 **충돌 창을 띄워 사용자가 한쪽을 고른다.** 고르지 않은 쪽의 학습이 사라진다.
- **발견**: 합칠 수 없다는 전제가 틀렸다. 기억은 `commitBattle`로 쌓이므로 **기준(base)에서 k판 쌓인 기억 = d^k × 기준 + (그 k판의 감쇠 가중 합)** 이다(d = 감쇠 0.99/0.995). 그래서 기준 저장본과 `battles` 차이(k)를 알면 **각 기기의 증분을 정확히 복원**할 수 있다(`증분 = 현재 − d^k × 기준`). 랭크·프런티어가 이미 쓰는 "기준 저장본(`SyncBase.snapshot`)을 둔 3-way 병합" 구조를 그대로 쓴다.
- **제안(C2-b1)**: `mergeAiMemory`(순수 함수, `cloudSyncPlan.ts`)를 추가하고 충돌 분기에 연결한다. **클라우드 문서 형식·`firestore.rules`·저장 형식·마이그레이션 변경 없음.** 합칠 수 없는 경우(기준 없음·한쪽 초기화)는 지금처럼 사용자가 고른다.

## 1. 병합 규칙

기호: B = 기준 저장본의 기억, L = 로컬, R = 클라우드, d = 그 모드의 감쇠, kL = L.battles − B.battles, kR = R.battles − B.battles.

1. **합칠 수 없으면 null(사용자가 고름)**: 기준 저장본이 없거나, kL < 0 또는 kR < 0(기억을 초기화했거나 기준보다 되돌아감), 두 문서의 `version`이 다름.
2. **증분 복원**: ΔL = max(0, L − d^kL·B), ΔR = max(0, R − d^kR·B) — **선형 필드마다**(`decisions`·`switchActual/Pred`·`statusActual/Pred`·종별 `seen`·기술별 `actual/pred`). 종 100개 상한으로 한쪽에서 밀려난 종(L에 없는 종)은 ΔL = 0(음수로 만들지 않는다).
3. **결합**: `M = d^(kL+kR)·B + ½[(1 + d^kR)·ΔL + (1 + d^kL)·ΔR]`.
   - 순서를 모를 때(어느 기기의 판이 먼저인지 시각이 없다) 두 순서 "L 다음 R"(`d^kR·ΔL + ΔR`)과 "R 다음 L"(`ΔL + d^kL·ΔR`)의 **평균**을 쓴다. 한쪽이 변하지 않은 경우(kR = 0)는 **정확히 L과 같다**(`d^kL·B + ΔL`).
   - 근사 오차: 두 순서의 차이는 ½·|1 − d^k|·|Δ| 이하. 예: k = 20판이면 약 9%(d = 0.99). 감쇠 자체가 최근 약 100판의 소프트 창이라 이 정도의 순서 불확실성은 기억의 정밀도 안이다. 한계로 기록한다.
4. **battles**: B.battles + kL + kR. 종별 `lastBattle`(100종 상한에서 오래 안 쓴 종부터 버리는 기준): 증분이 있는 쪽의 값 중 큰 것(없으면 기준값)을 쓰되 merged.battles를 넘지 않게 자른다.
5. **100종 상한**: 합친 뒤 종이 100개를 넘으면 `lastBattle`이 오래된 종부터 버린다(`addMemory`와 같은 규칙).
6. **`learningEnabled`**: 기준 대비 바뀐 쪽을 쓰고, 둘 다 바뀌어 다르면 로컬을 쓴다.
7. **정규형**: 결과는 `canonical`(기존 `objectDoc`)을 통과시켜 키 순서·`version`·`isOpponentMemory` 검증을 그대로 쓴다.
8. **합쳐도 부동소수 잡음**: 결과 값은 그대로 두고(반올림하지 않음) 시험에서는 허용오차 1e-9로 비교한다.

## 2. 연결 (`cloudSync.ts`)

- `hasSnapshot`에 `aiMemory`·`aiMemoryRank` 추가 → 기준 저장본이 `SyncBase.snapshot`에 저장된다. 이전 기록에는 기준이 없다 — `case "none"`의 기존 채움 로직(양쪽이 같을 때 `snapshot`을 채움)이 그대로 쓰인다. **첫 충돌에서는 기준이 없어 지금처럼 사용자가 고른다**(이후부터 합친다).
- `conflict` 분기: `name === "aiMemory" || "aiMemoryRank"` → `mergeAiMemory(baseOf(name)?.snapshot ?? null, local, r.json, decay)` (decay는 `aiMemoryRank`면 `RANK_MEMORY_DECAY_PER_BATTLE`, 아니면 `MEMORY_DECAY_PER_BATTLE`).
- **재판정(`rerun`) 안전**: 프런티어는 병합이 "증분을 더하는" 방식이라 같은 변경을 두 번 합치면 두 번 더해져 `setBase`를 "방금 합친 로컬"로 옮기는 처리를 둔다(`cloudSync.ts:259`). **AI 기억 병합도 증분을 더하므로 같은 처리가 필요하다** — 올리는 데는 성공했는데 그 사이 로컬이 바뀐 경우 `battleFrontier`와 같이 `setBase(name, local, r.updatedAt)`로 옮긴다. 구현 때 같은 조건에 `aiMemory`·`aiMemoryRank`를 넣고 시험(§3)으로 고정한다.
- `summarize`는 그대로(충돌 창에서 합칠 수 없을 때만 쓰인다).
- 앱 화면: 합쳐지면 기존 "두 기기의 변경을 합쳤어요." 알림이 뜬다. `useAiMemory`는 `onPresetListReplaced`로 이미 다시 읽는다.

| # | 시험 | 현행 | 목적 |
|---|---|---|---|
| M-a | 기준 B에서 L은 `commitBattle` k판, R은 변화 없음 → `mergeAiMemory`가 **L과 정확히 같다**(전 필드) | ❌ 함수 없음 | 한쪽 무변화 정확성 |

| M-d | **초기화**(L.battles < B.battles) 또는 기준 없음 → null | ❌ | 사용자 선택 폴백 |

| M-g | 결과가 `canonical`·`isOpponentMemory`를 통과하고 `battles = B + kL + kR` | ❌ | 형식 |
| M-h | `rerun` 안전: 같은 (B, L, R)를 두 번 합쳐도 같은 결과(순수 함수), 방금 합친 로컬을 새 기준으로 옮긴 뒤 다시 합치면 증분이 중복되지 않는다(R = 합친 결과 → planSync가 `none`/`push`) | ❌ | 중복 합산 방지 |

## 4. 크기·저장소 위험

- 기준 저장본이 `localStorage`의 `CloudSyncMeta`(`SyncBase.snapshot`)에 **그대로** 들어간다. 학습 기억 문서는 상한이 약 90만 자(100종 × 기술 40개 최대치도 40만 자 미만 — 6.3 A1 실측)이고 두 모드가 있어 최악이면 기준 저장본이 두 배(+기억 본문 두 배)로 `localStorage` 5MB 한도에 부담이 된다. 실제 사용자 기억은 대개 그보다 훨씬 작다(종 수십 개).
- 대응: **기준 저장본을 `battles`·선형 합계가 아니라 전체 JSON으로 두되, 크기가 20만 자를 넘으면 저장하지 않는다**(그 경우 합치기 불가 → 사용자가 고름, 지금과 같음). 저장 실패(`QuotaExceededError`)도 같은 폴백. → §6 Q4.

## 5. 범위 밖·한계(예정)
- **상대별 온도(C2-b2)**: C2-a 측정에서 상대마다 최적 온도가 반대라 여유가 컸다(`8.3-C2a-학습이득설계.md`). `OpponentMemory` 형식을 바꾸는 별개 작업이라 **합치기(C2-b1) 뒤에 따로** 설계한다. 새 통계가 선형 합계라면 §1 병합이 그대로 확장된다(필드 목록에 더하기만).
- 합친 값은 두 순서의 평균 근사다(§1-3). 판 시각이 없어 정확한 인터리브는 복원할 수 없다.
- 첫 충돌(기준 저장본이 아직 없는 경우)은 지금처럼 사용자가 고른다 — 한 번 맞춘 뒤부터 합쳐진다.
- 구형 클라이언트는 기준 저장본을 두지 않아 이전과 같이 사용자 선택(문서 형식이 같아 호환).
