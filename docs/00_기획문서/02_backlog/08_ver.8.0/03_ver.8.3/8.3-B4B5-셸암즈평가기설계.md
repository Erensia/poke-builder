**요약**
- **B4 — 고친다.** 평가기는 셸암즈의 분류를 `공격 vs 특공`(결정력)만으로 정해서, 상대의 방어·특방을 보는 엔진과 **무작위 빌드의 31.6%에서 다른 분류**로 계산한다. 평가기가 엔진과 같은 비교(`computeDamage` 물리/특수)를 쓰게 한다. 동점은 평가기가 결정적 표시라 **물리 고정을 유지**한다(엔진은 반반).
- **B5 — 고치지 않는다(본가와 같음을 확인).** Showdown 원문은 분류 비교에 **능력 랭크만 반영하고 도구·특성·날씨 배율은 넣지 않는다.** 엔진의 사용자 확정 규칙과 정확히 같다. 3만 판 대조에서 **엔진 분류 = Showdown 식 분류 100%(동점 사례까지 같음).** 코드 변경 없이 시험(회귀 감시)만 더한다.

## 0. 코드를 읽고 알게 된 것

### 0-1. 엔진(정답) — `src/lib/battle/preHitEffects.ts:672~690`
- 물리/특수 **두 번** `computeDamage(attacker.realStats, defender.realStats, attacker.types, {…move, category}, { attackerStages, defenderStages })`를 불러 `damage`(정수)를 비교한다. **옵션은 랭크뿐** — 도구·특성·날씨·급소·상성은 넣지 않는다(주석: 사용자 확정 "물리/특수 여부를 먼저 판단한 뒤 적용").
- `computeDamage`는 난수를 `1.0`(최대)로, 자속은 기본 1.5로 계산한다. 위력 90.
- 결과 `physDmg > specDmg → physical`, `specDmg > physDmg → special`, **같으면 `c.random() < 0.5`로 물리/특수**. 정해진 분류는 `c.shellSideArmCategory`로 로그에 남고(`battle.ts:362`, 화면 "○○ 판정!" `actionMainLineParts.tsx:426`), 물리면 접촉기(`makesContact`)가 된다.
- **난수는 동점일 때만 소비한다**(`physDmg===specDmg`일 때만 `c.random()` 호출). 이 호출 순서가 `regress` 해시를 지키는 조건이라 리팩토링에서 보존해야 한다.

### 0-2. 평가기(고칠 대상) — 같은 규칙이 두 곳에 있다
| 위치 | 언제 쓰이나 | 현행 비교 | 동점 |
|---|---|---|---|
| `matchupEvaluator.ts:354~369` `resolveVariablePowerMove`(→ `evaluateSlotMatchup`) | 매치업 화면(공격측·방어측 둘 다 정해짐), **배틀 AI의 데미지 추정**(`battle/ai/moveDamage.ts:381·397`), 일괄 조정 패널 등 | `computeOffensePower` 두 번 — **결정력만**: `공격(또는 특공) × 위력 × 자속 × 랭크…`. **상대 방어·특방이 식에 없다.** 위력·자속이 두 쪽에 같아 사실상 `공격 실능×랭크` vs `특공 실능×랭크` | `phys >= spec` → 물리 |
| `matchupEvaluator.ts:933~948` `computeSoloOffensePower` | 상대를 아직 안 골랐을 때 공격측 결정력만 표시(`MatchupPage.tsx:167`) | 같은 결정력 비교 | 같음 |

→ 평가기는 **"내 공격 vs 내 특공 중 큰 쪽"**이고 엔진은 **"상대 방어·특방까지 넣은 데미지가 큰 쪽"**이다. 8.2 I1 설계서 §1 표가 이미 이 차이를 적어 두었고, 역산(`defenseInference.ts`·`attackInference.ts`의 `categoryOf`)은 그때 **엔진 규칙으로 구현**했다. 평가기만 남았다.

### 0-3. 화면·AI에서 보이는 것
- `collectResult`(`matchupEvaluator.ts:701`)는 **분류를 결과에 담지 않는다.** 화면은 `damageParts`(어느 방어 스탯을 읽는지 `defenseKey`·`defenseStat`)로 간접적으로만 분류가 드러난다. 즉 지금은 "특수로 나갈 상대인데 물리 데미지로 표시"가 **조용히 틀린 숫자**로만 보인다.
- 배틀 AI는 `moveDamage.ts`로 셸암즈 데미지를 추정한다. 평가기가 틀린 분류로 추정하면 **AI가 엔진과 다른 데미지를 기대하고 기술을 고른다**(B4를 고치면 이 점도 바로잡힌다 — AI 행동이 바뀔 수 있는 이유).
- **샘플 파티 67개 중 야도란(가라르)는 0개**다(`samplePartyPresets.json` 검색 결과 없음). `POOL=samples` 측정은 이 변경에 영향이 없고, 영향이 있다면 **무작위 풀(`regress`)에서 가라르 야도란이 셸암즈를 들고 나올 때**뿐이다.

## 2. B5 규칙 확인 — Showdown 원문 대조 (결과: 엔진 = 본가)

Showdown `data/moves.ts`의 `shellsidearm`(원문, MIT 라이선스 인용):

```ts
onModifyMove(move, pokemon, target) {
	if (!target) return;
	const atk = pokemon.getStat('atk', false, true);
	const spa = pokemon.getStat('spa', false, true);
	const def = target.getStat('def', false, true);
	const spd = target.getStat('spd', false, true);
	const physical = Math.floor(Math.floor(Math.floor(Math.floor(2 * pokemon.level / 5 + 2) * 90 * atk) / def) / 50);
	const special = Math.floor(Math.floor(Math.floor(Math.floor(2 * pokemon.level / 5 + 2) * 90 * spa) / spd) / 50);
	if (physical > special || (physical === special && this.randomChance(1, 2))) {
		move.category = 'Physical';
		move.flags.contact = 1;
	}
},
```

`sim/pokemon.ts`의 `getStat(statName, unboosted, unmodified)`: `unboosted=false`면 **능력 랭크를 적용**(`[1,1.5,2,2.5,3,3.5,4]` 표, 각 단계 `Math.floor`), `unmodified=true`면 `ModifyBoost`와 **`Modify<Stat>` 이벤트(특성·도구·날씨·상태 배율이 걸리는 곳)를 건너뛴다.**

| 항목 | Showdown | 엔진 | 일치 |
|---|---|---|---|
| 공격·특공 vs 방어·특방 비교 | ✅ | ✅ | 같음 |
| 능력 랭크 | 적용 | 적용 | 같음 |
| 도구·특성·날씨·상태(화상 등) 배율 | **미반영** | **미반영**(사용자 확정) | **같음 → B5 변경 불필요** |
| 자속·상성·난수·급소 | 식에 없음 | 자속·최대 난수만 들어가나 **양쪽 같은 값이 곱해져 서열이 안 바뀜** | 측정상 같음 |
| 동점 | 물리 50% | 물리 50% | 같음 |
| 접촉 | 물리면 접촉 | 물리면 접촉 | 같음 |
| 위력 | 하드코딩 90 | `move.power`(데이터 90) | 같음 |

**구조 차이는 있다**: Showdown은 `+2`·자속·상성 없이 4단 `floor` 기본 데미지만 비교하고, 엔진은 정수 데미지 공식 전체(최대 난수·자속 포함)를 비교한다. 이론상 반올림 경계에서 갈릴 수 있으나 **§0-4의 5만 판(랭크 포함)에서 분류가 한 번도 다르지 않았다.** 따라서 **엔진 비교를 Showdown 식으로 바꾸지 않는다**(바꾸면 `regress` 기준 출력이 바뀌고 얻는 것이 없다). 대신 **시험에 Showdown 식 대조를 넣어** 훗날 `integerHitDamage`나 `computeDamage`가 바뀌어 갈라지면 바로 잡히게 한다(S-d).

> 사용자 확정 문구 "물리/특수 여부를 먼저 판단한 뒤 적용"은 Showdown 동작과 일치한다. 사용자가 이 결론에 동의하면 8.2 이월 6번(B5)은 **"변경 없음(본가와 동일)"으로 종결**한다.
> 한계: 챔피언스(본가 최신작)가 셸암즈를 같은 식으로 처리하는지는 Showdown 소스 외에 실기 확인이 없다 — 8.3 규칙조사 때 사용자가 "Showdown 대조를 규칙 근거로 쓴다"고 정한 틀(CLAUDE.md "검수는 Showdown 대조")을 그대로 따른다.

## 3. 설계 (B4)

### 3-1. 평가기의 비교를 엔진과 같게 — `matchupEvaluator.ts` `resolveVariablePowerMove`
```
현행: phys = computeOffensePower(attackerReal, types, {…move, category:"physical"}, {attackerStages, …})
      spec = computeOffensePower(…"special"…)
      resolvedCategory = phys >= spec ? "physical" : "special"
변경: resolvedCategory = shellSideArmCategory(attackerReal, defenderReal, types, move, {attackerStages, defenderStages}) 
      // "tie"이면 "physical" (§3-2)
```
- 입력은 평가기가 이미 해석해 둔 `c.attackerRealStats`(폼·메가·노력치·성격 반영)·`c.defenderRealStats`·`c.attackerForm.types`·`c.attackerStages`·`c.defenderStages`. **도구·특성·날씨는 넘기지 않는다**(엔진과 같다).
- 실전 AI(`attackerRuntime`)의 경우 평가기가 이미 현재 능력치·랭크를 `c.attackerRealStats`·`c.attackerStages`로 옮기므로(`moveDamage.ts:60`) 엔진이 비교하는 값과 같은 값이 들어간다. **어긋나는지 시험으로 확인한다(S-e).**
- 분류가 정해진 뒤의 처리(`makesContact: resolvedCategory === "physical"`, 이후 단계가 `c.resolvedCategory`로 방어 스탯·스크린·허슬·화상을 가르는 부분)는 **그대로**다.

### 3-2. 동점 — 물리 고정 유지 (V1에서 사용자 확인)
- 8.2 이월 3번 기록: 사용자 확정(2026-11-11)은 **엔진의 반반 확률**이고, 역산은 동점 50:50 혼합(진짜 값을 놓치지 않는 상위 집합)이다. **평가기(매치업 화면)는 결정적 표시라 물리 고정이 남아 있고 "엔진과의 정합은 8.3에서 판단"**으로 넘어왔다 — 그 판단이 이 절이다(아직 사용자 확정은 아님).
- 동점 비율은 2.9%(랭크가 섞이면 1% 미만)라, 반반 평균(두 결과의 `koChance` 평균·`verdict` 합성·`damageParts` 하나로 못 담음)을 만드는 비용(판정 배지 구조를 바꿈)이 효과보다 크다. **혼합 표시는 하지 않는다.**
- 동점은 **배율 전 데미지가 두 분류에서 정확히 같다**는 뜻이다. 최종 데미지는 분류 뒤에 곱해지는 배율(화상·벽·도구 등)에 따라 갈리므로, AI가 물리로 추정하면 엔진의 반반과 어긋날 수 있으나 그 경우도 **분류 전 기준으로 같은 데미지**를 출발점으로 삼아 오차가 작다. 판단 기준이 필요하면 §7 V1.

### 3-3. 규칙 공용 함수 — `battlePower.ts`
```ts
/** 셸암즈 분류 — 물리(공격 vs 방어)·특수(특공 vs 특방) 정수 데미지(최대 난수) 비교. 랭크만 반영, 도구·특성·날씨 배율은 넣지 않는다(본가와 같음, 8.3 B5). */
export function shellSideArmCategory(attackerReal, defenderReal, attackerTypes, move, options: { attackerStages?; defenderStages? }): "physical" | "special" | "tie"
```
- `preHitEffects.ts:678~689`(엔진)와 `matchupEvaluator.ts`(평가기)가 같이 쓴다. 엔진은 `"tie"`일 때만 `c.random() < 0.5`를 부르고(**난수 호출 순서 불변**), 평가기는 `"tie"` → `"physical"`.
- **이유**: 이번 B4가 존재하는 이유가 "같은 규칙이 두 곳에서 따로 구현돼 갈라졌기 때문"이다. 규칙 본체를 한 곳에 두면 다시 갈라지지 않는다.
- **역산 두 모듈의 `categoryOf`는 건드리지 않는다.** 후보 수십만 개를 도는 성능 경로이고(메모·후보별 분류) `test:inference` 결합 해시(`10040ffa0108c9a3`)를 지켜야 한다. 결과는 같으나 별도 구현으로 남는다 → §8 한계.

### 3-4. 상대 미선택(`computeSoloOffensePower`) — 그대로
상대의 방어·특방을 모르는 상태라 데미지 비교가 불가능하다. 현행 "공격 vs 특공(결정력) 비교, 동점 물리"를 유지한다. 상대를 고르는 순간 `evaluateSlotMatchup`으로 넘어가 3-1의 규칙이 적용된다. **상대 선택 전후로 분류·숫자가 달라질 수 있음**을 §8에 적는다(상대 미선택 화면이 "상대 없이 계산한 결정력"임을 어떻게 안내하는지는 구현 때 코드로 확인하고, 오해 소지가 크면 안내 문구를 사용자와 정한다 — V3).

### 3-5. 분류를 결과 필드로 — 이번엔 표시하지 않는다
`collectResult`에 `shellSideArmCategory`·`shellSideArmTie`를 더하는 것은 쉽지만, **화면에 쓰지 않을 필드를 만들지 않는다**(YAGNI). 화면 표시(예: 매치업 카드의 "특수 판정" 배지)가 필요하면 8.4(UI/UX 전용 버전) 후보로 넘긴다 — 사용자 결정 V4. 단 시험에서 분류를 확인해야 해서 시험은 `damageParts.defenseKey`(`"def"`/`"spd"`)로 판정한다(필드 불필요).

## 5. 해시·검증 예상 (믿지 말고 단계마다 잰다)

| 단계 | 내용 | 기준 출력 |
|---|---|---|
| ① | 공용 함수 추출 + 엔진이 사용(리팩토링) | **불변이어야 한다** — 같은 식, 난수 호출 순서 동일. 어긋나면 이 단계에서 잡힌다 |
| ② | 평가기가 공용 함수 사용(B4 본체) | **변함 가능, 불변일 수도** — 영향은 **가라르 야도란이 셸암즈를 들고 평가기를 타는 곳**(AI 데미지 추정·매치업)뿐이다. 샘플 0개라 `POOL=samples`는 불변 예상, `regress` 무작위 풀은 가라르 야도란+셸암즈가 뽑히면 AI 선택이 바뀔 수 있다 |

- 모든 단계가 불변일 수 있다(가라르 야도란의 등장 빈도가 낮음). 그러면 `regress 20000`으로 판정한다. **A4·A5·B2·B3·B7·B8에서 "해시 불변 예상"이 틀린 적이 많아 단계마다 `regress 200`을 재고 원인을 분리한다.**
- **측정 예정(시작 전 사용자에게 보고)**: 단계별 `regress 200`(각 약 5초) · `regress 20000`·`STATUS=1 greedy 60`(약 3분) · 마지막에 `SERIAL=1 bash scripts/verify-kit/verify.sh`(약 8분, 이 PC 직렬). 기준값 갱신(`update-baseline.sh`)은 **해시가 바뀐 경우에만**, `SERIAL=1`로 돈 깨끗한 출력에서만.
- **계산 함수 차분 해시**: 평가기를 거치므로 가라르 야도란 구성이 차분 표본에 없으면 불변, 있으면 변동(원인은 §0과 같음) — 변동 시 원인을 표로 보고한다.

## 8. 알면서 두는 것 (백로그 한계로 옮길 후보)
- **역산의 `categoryOf`는 별도 구현으로 남는다**(§3-3). 엔진 규칙이 바뀌면 세 곳(엔진·평가기·역산)을 같이 봐야 하는데, 시험 S-d(Showdown 대조)·`17-shell-side-arm.mjs`(`engineCategory`)가 감시한다. 역산 공용화는 9.x 역산 전면 재설계(`ver-9-0-plan`)에서 한다.
- **상대 미선택 결정력 표시는 공격 vs 특공 비교**라, 상대를 고르면 분류·숫자가 달라질 수 있다(§3-4).
- **동점 평가기 표시는 물리 고정**이라 엔진의 반반과 다르다(§3-2, 사용자 확정 2026-11-11).
- **분류 화면 표시 없음**(§3-5) — 8.4 후보.
- **엔진 비교는 Showdown 식과 구조가 다르다**(정수 데미지 공식 전체 vs 기본 데미지 4단 floor). 5만 판 100% 일치지만 보증은 아니므로 S-d가 지킨다.
- **적응력 보유자의 자속 2.0은 분류 비교에 안 들어간다**(엔진 기본 1.5 사용). 양쪽 같은 배율이라 서열은 불변 — 영향 없음(가라르 야도란의 특성과 무관, 규칙 근거는 Showdown이 자속 자체를 안 넣음).
