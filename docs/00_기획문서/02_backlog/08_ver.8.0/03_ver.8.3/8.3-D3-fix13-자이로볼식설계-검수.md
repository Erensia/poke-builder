## 1. 소스 대조

### 1-1. 식 (설계서 §0·§2-1)

```ts
// gyroball (moves.ts 8054) — 965a535 확인
let power = Math.floor(25 * target.getStat('spe') / pokemon.getStat('spe')) + 1;
if (!isFinite(power)) power = 1;
if (power > 150) power = 150;
```

| 항목 | 설계서 | 판정 |
|---|---|---|
| 식 | `Math.min(150, Math.floor((25*t)/p) + 1)` | ✅ 소스와 같음. JS는 `25*t/p`를 왼쪽부터 계산하므로 `(25*t)/p`와 동일 |
| 0 처리 | `p <= 0 → 1` | ✅ p=0이면 `Infinity`(t=0이면 `NaN`) → `!isFinite` → 1. 음수는 도달 불가 |
| 상한 | 150 | ✅ |
| Champions 재정의 | 없음(덤프 `championsOverride: null`) | ✅ `data/mods/champions/{moves,conditions,scripts}.ts`·`championsregmb/*.ts`에 `gyroball`·`electroball` 없음(grep 출력 0, learnsets 제외) |
| 입력 | 정수 스피드 | ✅ `getStat('spe')`(랭크·ModifySpe·마비·상한 10000). 챔피언스 `scripts.ts`는 `getStat`을 재정의하지 않고 `getActionSpeed`(47행)에서 호출만 한다. 트릭룸 부호 반전은 `getActionSpeed`에만 있어 위력에 영향 없음(재검수 확인) |
| 일렉트릭볼 불변 | 불변 | ✅ 식 동치는 fix-12 검수에서 6,760,000쌍 전수 확인. 시험 7의 5개 값 재계산 일치(40·60·80·120·150) |
| 기술 설명문 | `moves.json` "낮을수록 올라간다(최대 150)" 유지 | ✅ (나)에서도 맞다 |

본가 공식도 `25 × 상대/나`를 내림한 뒤 +1이다. (가)는 +1을 괄호 안(`25×(t/p+1)`)에 넣은 것이라 항상 약 24 높게 나온다. 설계서 §6의 "(가)와 같을 가능성 낮음"은 소스·본가 공식 모두와 맞는 판단이다.

### 1-3. 연산 순서가 중요한 이유 (§2-1 보강)
`25 * t / p`는 정수끼리 곱한 뒤 한 번만 나누므로 정수 나눗셈의 내림과 같다. `25 * (t/p)`는 `t/p`를 먼저 반올림한 뒤 25를 곱해 `…99999`·`…00001`로 어긋날 수 있다. 그래서 순서가 바뀌면 틀린다. 틀리는 쌍 수는 범위에 따라 31~213에서 13쌍, 1~300에서 39쌍, 1~700에서 96쌍, 1~1000에서 135쌍이다. 설계서의 "곱 먼저" 결정이 맞다.

### 2-2. 이 식에 닿는 다른 사본 확인 (§2-3)
"한 곳 수정으로 일괄 반영"은 모든 호출처가 `gyroBallPowerFromSpeeds`를 거칠 때만 성립한다. poke-builder에는 배틀 말고 **계산기 화면**이 있으므로 아래를 구현 첫 단계로 못 박는다.
- `grep -rn "gyro\|자이로볼\|25 \*\|25×"`로 식의 인라인 사본(계산기 화면의 위력 자동 입력, 툴팁·도움말 문구, 문서)을 찾는다. 사본이 있으면 같이 고친다.
- 시험에 "식의 사본이 이 함수뿐"임을 지키는 항목(위 grep 결과 개수 고정 또는 호출처별 값 비교)을 하나 둔다. 호출처 6곳 시험(4·5·6, 8)이 일부 대신하지만 계산기 화면은 목록에 없다.

### 2-3. 위력 임계값 효과 확인 (참고)
(나)로 자이로볼 위력이 낮아져 60 이하가 훨씬 흔해진다(같은 스피드면 26). Showdown의 테크니션은 **콜백이 계산한 위력**에 대해 `≤ 60`을 검사한다(`basePowerAfterMultiplier`, abilities.ts 4923). 엔진이 `move.basePower`(자이로볼은 0)나 고정값으로 검사하면 어긋난다. 다만 챔피언스 mod의 자이로볼 학습자 30종과 그 **메가진화 폼 11종 모두 테크니션 보유자가 없다**(재검수에서 메가 폼까지 확인, §7). 관련 특성은 골루그(Iron Fist·Klutz·No Guard), 브리가론(Overgrow·Bulletproof, 메가 브리가론 Bulletproof), 메가 메타그로스(Tough Claws — 접촉 ×1.3, 식과 무관)다. 이번 PR에는 영향이 없고, 위 grep을 돌릴 때 "임계값 검사가 최종 위력을 받는지"만 한 줄 확인하면 충분하다. 이 확인은 설계서 서술 범위 밖이라 필수는 아니다.

### 2-4. 실제 값이 들어간 시험 고정값 확인 (시험 8)
시험 8의 기대가 "통과"인 이유는 양방향 역산이 같은 함수를 쓰기 때문이다. 단 `14-speed-power-foulplay-def.mjs`·`04-attack-roundtrip.mjs`가 위력 값(예: 75, 50)이나 데미지 숫자를 **고정값으로 박아 둔 경우** 새 식에서 실패한다. 구현 전에 두 파일에서 위력·데미지 리터럴을 확인하고, 있으면 시험 기대를 "통과"가 아니라 "확인 필요"로 바꾼다.

재검수 참고: 두 식 모두 위력 1당 스피드 비 0.04 폭이라 역산 분해능 자체는 같다. 위력이 낮을수록 한 데미지 범위와 겹치는 위력 수가 적어(Lv50·A=D 기준 위력 26은 14개, 50은 23개) 역산 후보 폭은 **오히려 좁아지는 방향**이다. 결합 해시가 바뀌어도 정밀도 저하로 읽을 필요는 없다.

- **번복 기록**: 설계서·백로그·코드 주석 3곳에 남기는 방식은 타당하다(과거 계획 문서는 건드리지 않는다는 판단도 맞다). 곡예·난동 번복 때와 같은 문구 형식인지만 확인.

- **해시 예상**: 예상 목록(`regress`·`greedy120`·`status60`·`h2h40`·`ai60`·역산 결합·차분)은 합리적이다. 설계서도 밝혔듯 예상이 틀릴 수 있어 측정이 기준이다.
