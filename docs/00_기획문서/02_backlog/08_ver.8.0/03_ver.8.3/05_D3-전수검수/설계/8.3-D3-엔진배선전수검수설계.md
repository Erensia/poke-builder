## 3. 방법

### 3-1. 두 층
```
데이터 층 (E0)  ── 스크립트가 한 번에 전수 대조 ──→ 불일치 목록 → 사람이 판정
동작 층 (E1~E10) ─ 체크리스트 한 줄 = "규칙 하나" ─→ Showdown 소스 대조 → 분류
```
- **데이터 층**: 값이 필드에 들어 있으므로 기계가 비교한다(사람이 511개를 읽지 않는다).
- **동작 층**: 값이 아니라 **코드가 하는 일**이라 규칙 단위로 읽는다. 체크리스트는 Showdown 쪽에서 출발한다(그 영역의 핸들러·이벤트를 훑어 "이 규칙을 엔진도 갖는가"를 묻는다). 엔진 쪽 출발만 하면 **엔진에 없는 규칙(누락)** 을 못 찾기 때문이다.

### 3-2. 데이터 층(E0)
1. **비교 기준은 "상속이 적용된 최종 값"**: mod 파일은 `inherit: true`로 바뀐 필드만 적고 `scripts.ts` `init`이 파일 밖에서 PP를 바꾼다. 원본 TS를 파싱하지 않고 `Dex.forFormat('gen9championsbssregmc')`의 **최종 값 덤프(JSON)** 와 비교한다. 덤프는 검수 채팅(Showdown 빌드 성공)이 만들어 넘긴다(§3-3, Q3).
2. **첫 산출물 = 집합 차이**: Showdown 출전 가능 기술 515(그중 발버둥·어떤 포켓몬도 못 배우는 파워시프트 포함) ↔ 엔진 511. 어느 쪽에만 있는 기술 목록과 이유(엔진 누락·엔진 초과·의도적 제외)를 먼저 적는다. 특성 216·도구 166은 개수가 일치함을 확인했으므로 이름 대조만 한다.
3. **매핑은 PokeAPI 한국어 이름으로 자동**: PokeAPI `data/v2/csv/`의 `moves`·`move_names`·`abilities`·`ability_names`·`items`·`item_names`(`local_language_id = 3`이 한국어), 식별자에서 `-`를 빼면 Showdown id와 같다. 검수 실측 결과:

   | 대상 | Showdown 출전 가능 | 자동 연결 | 직접 정할 것 |
   |---|---|---|---|
   | 기술 | 515 | **515**(한국어 이름 중복 0) | 없음 |
   | 특성 | 216 | **213** | `auraguard`·`eelevate`·`firemane`(PokeAPI에 없는 신규 특성) |
   | 도구 | 166 | **165** | 대파(`leek`, PokeAPI 식별자가 다름) |

   엔진 한국어 id와 공식 이름은 띄어쓰기가 다를 수 있어 **공백을 지운 뒤 비교**하고 남는 것만 사람이 정한다. 지문(`type·category·power·accuracy·pp·priority`)은 **매핑 검증용**으로 돌린다(지문 불일치 = 매핑 오류 또는 데이터 오류 후보). CSV는 공개 데이터이며 저장소 밖 새 폴더에 받는다.
4. **대조 필드**:
   - 기술: 타입·분류·위력·명중·PP·우선도·**flags**(접촉·방어 가능·소리·펀치·베기·반사 가능 등 — `tags`/`makesContact`/`notReflectable`과 대응)·`secondary`(확률·효과)·흡수·반동·연속기 타수·급소 단계·`target`(싱글 기준 정규화)·`self`/`boosts`.
   - **PP 기준**: Showdown `pp`는 `init` 상한(20 초과→20)이 적용된 기본 PP이고 실제 최대 PP는 `calculatePP` = `(pp/5+1)×4`(5→8·10→12·15→16·20→20)다. 엔진 `pp` 필드가 어느 쪽인지 E0 첫머리에 적는다.
   - **`target` 정규화**: 출전 가능 기술 중 여러 체·아군 대상은 56개다. 여러 대상 공격기(지진·파도타기·스톤샤워 등)는 대상을 상대 1체로, 자기 쪽 장(리플렉터·빛의장막·순풍·신비의부적·패스트가드)은 그대로 대조, 아군 전용(도우미·코칭·드래곤옐·아로마미스트)은 **싱글에서 실패하는지만**, 아군 부분이 있는 기술(멀리짖기·생명의물방울·우유마시기)은 자기 부분만 본다.

### 3-3. 동작 층(E1~E10) — 체크리스트 한 줄의 모양
영역마다 표 하나. 한 줄 = 규칙 하나.

| 열 | 내용 |
|---|---|
| ID | `D3-E<영역>-<번호>` (예: `D3-E6-04`) |
| 규칙 | 한 문장(예: "독 데미지는 최대 HP의 1/8, 맹독은 N/16 누적") |
| Showdown | 파일·핸들러(예: `data/conditions.ts` `psn.onResidual`) + 동작 요약 |
| 엔진 | 파일:줄 + 동작 요약(`trail grep`/`trail skeleton`으로 위치 확정) |
| 증거 | `[소스]` / `[실행]` / `[기검수 문서명]` |
| 분류 | 수정필요 · 결정필요 · 개선권장 · 문제없음 |
| 영향 | 기준 출력(`regress`) 변동 예상·화면 변경 여부·샘플 영향(있으면 건수) |
| 조치 | 수정필요면 항목 번호(`D3-fix-N`)·결정필요면 질문 |

- **`[소스]`** 로 끝낼 수 있는 것: 값·조건·순서가 소스에 명시된 규칙(대부분).
- **`[실행]`** 이 필요한 것: 이벤트 우선순위가 얽혀 소스만으로 순서가 확정 안 되는 규칙(예: 같은 이벤트에 여러 핸들러, 스피드 동률 순서). 이전 검수가 `고정 시드 배틀 로그`로 확인한 방식과 같다.
  - **`[실행]` 실측은 검수 채팅이 한다**(결정 2026-11-16, Q3 ③): 그쪽에서 `npm ci --ignore-scripts && node build`가 성공했고 이전 검수도 그쪽에서 `sim-check.js`로 실측했다. Claude Code는 이 PC에서 **`[소스]` 대조를 하고 `[실행]` 대기 목록**을 쌓아 두며, 영역 검수 문서를 올릴 때 검수 채팅이 실측해 검수 문서에 결과를 적는다. **E0용 최종 데이터 덤프(JSON)** 도 그쪽에서 받는다.
  - 이 PC의 Showdown 사본(`~/showdown-ref`, `965a535`)은 **소스 읽기 전용**이다. `npm install`은 권한 분류기가 거부해 빌드하지 않았고, 검수 채팅 덕에 빌드할 필요도 없다. `claude/showdown-code-map.md`는 프로젝트 문서(검수 채팅 쪽)에 있다.

### 3-4. 분류 기준
| 분류 | 정의 | 다음 |
|---|---|---|
| **수정필요** | 명확한 불일치 또는 버그. 사용자 확정과 겹치지 않는다 | 항목별 설계서→검수→구현(PR 1개) |

| **개선권장** | 규칙은 맞지만 구조·확장성 문제(흩어진 가드 등) | D3에서 고치지 않고 **9.0 리팩토링 후보**로 백로그에 적는다(D0는 예외 — 이미 확정) |
| **문제없음** | 일치 | 분류표에 근거만 남김 |

- 한 규칙이 두 분류에 걸치면(예: 규칙은 맞지만 로그가 없음) **규칙**을 분류하고 로그는 따로 한 줄 더한다(로그 문구는 8.4 후보로 표기).
- 판정 근거가 **소스 해석뿐**이라 확신이 낮으면 증거 열에 `(소스 해석)`을 적고 `[실행]` 대기 목록에 올린다. 해석에 기대어 수정필요로 올리지 않는다.

## 7. 수정 반영 절차 (검수가 끝난 뒤)
1. 수정필요를 **원인·함수 단위로 묶는다**(같은 원인은 PR 하나, 규칙 영역이 다르면 따로). 단 **기준 출력(`regress`) 변동 원인을 분리**할 수 있게 **수치만 바뀌는 데이터 수정(E0)과 동작 수정은 같은 원인이라도 다른 PR**로 한다(검수 의견, Q5). 묶음은 사용자와 정한다.
2. 항목(묶음)마다 `설계서 → 사용자 검수 → 시나리오 먼저(실패 확인) → 구현 → 단계 측정 → PR 1개(커밋 1개)` — CLAUDE.md "작업 시작 후" 절차 그대로.
3. 단계 측정은 `regress 200`·`regress 20000`·`STATUS=1 greedy 60`만 따로 돌려 약 3분이다(교훈: 해시 불변 예상은 자주 틀리므로 단계마다 잰다). 기준값 갱신은 `SERIAL=1`로 돈 깨끗한 출력에서만.
4. 결정필요는 사용자 답을 받은 뒤 같은 절차로 처리하거나 제외(`제외(8.3, 사유)`)로 기록한다.
5. 수정필요·결정필요 처리가 끝나면 **D0 → D1·D2 → 릴리스**.
