## 0. 한 줄 요약
(E8-47) 하양허브는 5종 랭크만 복원한다. Showdown은 명중·회피 하락도 복원한다. (E8-48) 오기·승기가 랭크를 올리는데 기술 경로·접촉 반응·턴 끝 경로에는 로그 줄이 없다(`switching.ts` 위협·끈적끈적네트 경로만 "OO의 오기! …" 줄을 낸다).

## 1. E8-47 하양허브 + 명중·회피
현행(코드 읽기, 프로브 전):
- `itemEffects.ts` `shouldTriggerWhiteHerb`: `Object.values(stages).some(v => v < 0)` — **`accuracyStages`(명중·회피)를 보지 않는다.**
- `statStages.ts` `clampStagesToNonNegative`: 5종 랭크만 0으로.
- 호출처 3곳: `mirroredEffects.ts` 417·422행(행동 뒤), `switching.ts` 692행(`finishEntryBundle`, 등장 묶음 뒤). 명중·회피는 `fighter.accuracyStages`에 따로 있다(`state.ts` 112행).
변경안:
1. `shouldTriggerWhiteHerb`에 명중·회피를 포함한다(인자로 `accuracyStages`를 받거나 fighter를 받는 형태 — 구현 때 호출처 3곳을 같이 맞춘다).
2. 복원 함수가 `accuracyStages`도 0 미만을 0으로.
3. 문구는 기존 `restoredStats…ItemName` 필드를 그대로 쓴다(문구 변경은 §6 확인 요청).
엔진 위험: 명중·회피가 내려간 뒤 하양허브가 발동하므로 이후 명중 판정이 달라진다(하양허브 보유 + 진흙뿌리기·달콤한향기류). 통상 대전 해시 영향은 작을 것으로 예상(측정으로 확인).

## 2. E8-48 오기·승기 문구
현행:
- 엔진은 `state.ts` `applyOwnStatDropReaction`(랭크 +, 실제로 올랐는지 반환)을 모든 경로에서 부른다: 기술 경로 `mirroredEffects.ts` 409·410행, 턴 끝 `finishTurn.ts` 436·462행(물엿범벅 등), 등장 `switching.ts` `reactToOwnStatDrop`.
- **문구는 `switching.ts`만** "OO의 오기! 공격이 크게 올라갔다!"(능력치 이름 + `delta>=2` "크게")를 낸다. 나머지 경로는 랭크만 올라가고 줄이 없다(`finishTurn.ts` 주석에도 적혀 있음).
변경안:
- 기술 경로·접촉 반응: 행동 로그 항목(`ActionLogEntry`)에 방어측/공격측이 올린 랭크를 싣는 필드(예: 오기·승기 상승 `defiantRises`/…)를 더하고 `ActionEffectLines.tsx`가 줄을 낸다. 기존 `selfStatRises`는 **행동자**의 상승이라 방어측(맞은 쪽)의 오기는 따로 필요하다.
- 턴 끝(`endOfTurn` 항목)·등장 경로: 기존 항목에 같은 방식의 필드/줄을 더한다.
- 문구는 Showdown 기준(§6 확인 요청). 기존 `switching.ts` 문구도 같이 맞출지 포함.
엔진 위험: 로그 필드만 더하므로 **해시(턴·승패)는 불변**이어야 한다(`regress 200` 불변, `regress 20000`은 로그가 해시에 들어가면 변함 — fix-53과 같은 "턴·승패 동일, 로그만 변경" 패턴 예상).

## 3. 시험 (먼저 쓰고 현행에서 실패 확인) — 파일 `88-ver83-d3fix57.mjs`
1. 하양허브 + 명중 하락(진흙뿌리기·달콤한향기 등): 복원·소모. 회피 하락도 동일. 랭크가 + 인 능력치는 그대로.
2. 5종 랭크와 명중·회피가 함께 내려간 경우 한 번에 복원.
3. 등장 묶음 경로(`finishEntryBundle`)에서도 명중·회피 마이너스면 발동.
4. 오기·승기(검수 R2·R3 반영): 기술 경로(방어측)·접촉 반응·턴 끝(물엿범벅)·등장(위협) 각각 로그 필드가 실리고 줄이 나온다. 상승량별 문구: +2 "크게 올라갔다", **+5에서 1랭크만 오르면 "올라갔다"(크게 아님)**, **이미 +6이면 "더 이상 올라가지 않는다!" 1줄**. "줄 없음"은 하락 자체가 일어나지 않은 경우(−6 상한·클리어바디 등)뿐. 간지르기(2능력치 하락) → 상승 줄 2개, 다단 접촉 → 히트마다 1줄(줄 수 = 발동 횟수).
5. 회귀: 기존 하양허브·오기·승기 시험(fix-52 83번)이 그대로 통과(문구 대조가 있으면 기대값 갱신 — 위협 경로 67번 포함).
6. (검수) 오기+하양허브 보유자 + 진흙뿌리기 → 공격 +2·명중 0·허브 소모(오기 먼저).
7. (검수 R1) 하양허브 + 시럽봄 → **그 턴 끝에** 스피드 0·소모, 다음 턴 행동 순서가 하락 전과 같다. 내던지기 하양허브(`fling.ts`)도 명중·회피를 복원.
8. 문구: 하양허브 3곳(행동 뒤·등장 묶음·턴 끝)이 "…하양허브로 능력치를 원래대로 되돌렸다!", 위협 경로가 일반 상승 문구.

## 8. 검수 반영·확정 (2026-11-28)
- **R1 턴 끝 호출 — 포함으로 확정**: `finishTurn.ts`에 하양허브 호출이 **없음을 확인**(grep). Showdown `onResidual` order 29라 시럽봄·문어굳히기(order 14) 하락을 같은 턴 끝에 복원한다. `EOT_HANDLERS`에 `{ order: 29, run: applyWhiteHerbRestore }`를 더하고 `endOfTurn` 항목에 허브 이름 필드를 싣는다(렌더는 `EndOfTurnLines.tsx`). 호출처는 행동 뒤 2·등장 묶음 1·턴 끝 1 + `fling.ts`(명중·회피 포함) 총 5곳. 엔진 변경이라 측정에 포함.
- **R2 상한**: `applyOwnStatDropReaction`이 실제 상승량(0 포함)을 돌려준다(현행은 "올랐는가" boolean). 문구는 상승 2 = "크게 올라갔다", 1 = "올라갔다", 0 = "더 이상 올라가지 않는다!". 오기 발동 자체는 fix-52대로(하락이 실제로 일어났을 때만) — 하락이 상한으로 막히면 줄 없음.
- **R3 발동 횟수**: 줄도 발동 횟수만큼.
- **로그 필드 단순화**: 방어측·공격측을 나누지 않고 **쪽(side)을 싣는 필드 하나**(예: `dropReactionRises: { side, stat, delta }[]`)로 행동·턴 끝·등장이 같은 모양을 쓴다. 렌더 함수 하나.
- **R4 알려진 차이**: Showdown은 오기·승기 상승 앞에 `[OO의 오기]` 특성 표시 줄을 낸다. 사용자 결정으로 일반 상승 문구 한 줄로 통일한다(랭크·해시 영향 없음). 다중 하락 시 Showdown은 하락 줄·상승 줄이 능력치마다 번갈아 나오지만 엔진은 하락 줄을 모은 뒤 상승 줄을 낼 수 있다(표시 순서 차이, 랭크 결과 동일).
- **R5 측정 2단계**: ① E8-48만 적용 → `regress 200` 해시 불변·`regress 20000` 턴·승패·시간초과 불변(로그만 변경). ② E8-47(+R1) 적용 → 해시 변동, 하양허브 보유 + 명중·회피 하락 장면 수 보고. 각 단계 `regress 200`·`regress 20000`·`greedy 60`(약 9~10분씩).
- **사용자 결정(2026-11-28)**: 결정 1 = 전 경로 일반 문구(`switching.ts` 위협 문구도 변경), 결정 2 = 하양허브 문구 결정안으로 변경(§6의 확인 요청 두 건은 모두 해결).

## 6. 사용자 확인 요청 (해결됨 — §8)
1. **오기·승기 문구**: 사용자 결정은 "특성 이름 없는 일반 상승 문구"(예: "OO의 공격이 크게 올라갔다!"). 그럼 지금 `switching.ts`가 내는 "OO의 오기! 공격이 크게 올라갔다!"(특성 이름 포함)도 **일반 문구로 바꿀지**, 아니면 위협 경로만 현행 유지할지.
