## 1. 소스 대조

```ts
// data/conditions.ts tox (965a535)
onStart(...) { this.effectState.stage = 0; ... }
onSwitchIn() { this.effectState.stage = 0; }
onResidualOrder: 9,
onResidual(pokemon) {
  if (this.effectState.stage < 15) this.effectState.stage++;
  this.damage(this.clampIntRange(pokemon.baseMaxhp / 16, 1) * this.effectState.stage);
}
// lib/utils.ts clampIntRange: num = Math.floor(num); if (num < min) num = min; ...
```

### 1-1. 수치 재계산 (설계서 §1-1)

| 항목 | 설계서 | 재계산 |
|---|---|---|
| 값표 5행 | 40/40, 6/6, 25/24, 93/90, 29/27 | ✅ 전부 일치 |
| 다른 조합 | 4,515 중 3,402 (75%) | ✅ 3,402 (75.3%) |
| 방향·최대 차이 | 엔진이 항상 같거나 많음, 최대 14 | ✅ 엔진이 적은 조합 0, 최대 14 (`floor(15×15/16)`) |

### 1-2. AI 기대값 (설계서 §2-1)
`floor(HP/16) × n`은 n에 대해 선형이므로 `E[floor(HP/16) × n] = floor(HP/16) × E[n]`가 정확히 성립한다. 평균 카운터(소수)를 그대로 곱하는 방식이 맞다. 하한 1을 넣어도 선형이므로 같다.

## 2. 보완

### 2-1. [필수] 하한 1 누락
Showdown은 `clampIntRange(baseMaxhp/16, 1)`로 **곱하기 전에** 1/16 값을 최소 1로 올린다. 설계서 식은 이 하한이 없어 최대 HP 15 이하에서 0 × 단계 = 0 피해가 된다.
- 고칠 식: `Math.max(1, Math.floor(maxHp / 16)) * Math.min(BADLY_POISONED_MAX_TURNS, state.turnsElapsed)`
- 기존 코드가 결과에 `Math.max(1, …)`를 씌우고 있다면 그것과는 다르다. 곱한 뒤 하한을 걸면 HP 15·3단계가 `max(1, 0)` = 1이 되지만 Showdown은 1 × 3 = 3이다.
- 현재 영향: Lv50에서 최대 HP 16 미만은 껍질몬(HP 1)뿐이고, 껍질몬은 챔피언스에서 `Illegal`이다(`formats-data.ts` 1764). **실전 관측 차이는 없다.** 다만 §0 기준 문장과 식이 서로 어긋나고, 함수가 HP를 받는 순수 함수라 시험으로 고정할 수 있으므로 넣는다.
- 시험 추가: HP 15·단계 3 = 3 (현행 `floor(45/16)` = 2), HP 1·단계 1 = 1.

### 2-2. [필수] 시험 4 기대값 오류
HP 100의 3틱은 **현행 엔진도 36**이다(6.25→6, 12.5→12, 18.75→18). 설계서의 "현행 37"은 틀렸고, 이 시험은 현행 코드에서 실패하지 않아 "먼저 쓰고 실패 확인" 원칙을 지키지 못한다. 둘 중 하나로 바꾼다.

| 안 | 새 식 | 현행 |
|---|---|---|
| HP 155, 3틱 | 9+18+27 = **54** | 9+19+29 = 57 |
| HP 100, 4틱 | 6+12+18+24 = **60** | 6+12+18+25 = 61 |

권고: HP 155·3틱(틱마다 차이가 나서 어느 틱에서 어긋났는지 바로 보인다).

시험 1의 "현행 25·29 등으로 실패"도 정확히는 HP 100 단계 1~3은 현행과 같고 단계 4(25)·15(93)와 HP 155(29)에서만 실패한다. 실패 확인에는 충분하므로 문구만 고친다.

### 2-3. 나갈 때 초기화 — 동등성 확인 (설계서 §2-2·§6)
Showdown에서 `stage`를 읽는 곳은 `tox.onResidual`뿐이고, 이것은 필드에 있는 포켓몬에만 돈다. 대기 중에 `stage`를 읽거나 바꾸는 경로가 없으므로 "나갈 때 1로"와 "들어올 때 0 → 첫 틱 1"은 관측 결과가 같다. 판단에 동의한다.
- 구현 조건 한 가지: 물러날 때 상태를 바꾸는 특성(자연회복)과 같은 블록에 있으므로 **상태를 다시 읽고 맹독일 때만** 덮어쓴다. 자연회복이 먼저 상태를 지웠는데 미리 읽어 둔 `outgoing.status`를 펼쳐 쓰면 맹독이 되살아난다. 시험 5에 "자연회복 + 맹독 → 교체 후 상태 없음"을 추가한다.
- 파티 트래커 grep을 구현 첫 단계로 넘긴 것은 타당하다. 표시가 있다면 오히려 Showdown 클라이언트(대기 중 카운터 미표시)보다 정보가 많아질 뿐 틀린 값은 아니다.

## 5. fix-15(열사의대지 해동) 사전 메모 — 설계서 미첨부
이번 대화에 fix-15 설계서가 첨부되지 않아 정식 검수는 하지 않았다. 소스에서 미리 확인한 사항만 남긴다.
- `scorchingsands`·`scald` 모두 `flags.defrost: 1` + `thawsTarget: true`. 즉 해동이 **두 가지**다: ① 사용자가 얼어 있어도 기술을 쓰며 녹는다(`frz.onBeforeMove`·`onModifyMove`의 `defrost`), ② 맞은 상대가 녹는다(`frz.onAfterMoveSecondary`의 `thawsTarget`). `curesStatus {상대, 얼음}` 한 줄은 ②에 해당하므로, 엔진이 ①을 열사의대지에 이미 적용하는지 fix-15 검수에서 확인한다.
- **대타**: 대타에 맞으면 `spreadMoveHit`(champions `scripts.ts` 350)이 그 대상을 `null`로 바꾸고, `afterMoveSecondaryEvent`는 `null`을 걸러낸 대상에게만 돈다(575). → **대타 뒤의 얼음 상대는 녹지 않는다.** 설계서가 "알면서 둔 것"으로 남긴 항목은 소스로 판정 가능하며, 열탕과 같은 동작이 이것과 맞는지 확인하면 된다.
- 참고: champions `hitStepMoveHitLoop`는 `afterMoveSecondaryEvent`를 `suppressingSecondaries()`(우격다짐) 검사 없이 부른다(`sim/`은 검사함). 열탕·열사의대지 + 우격다짐 조합에서만 의미가 있다.
- fix-15 Q1(PR 분리): 데이터 변경과 코드 변경의 해시 원인을 나누는 것이므로 분리 권고에 동의한다.
