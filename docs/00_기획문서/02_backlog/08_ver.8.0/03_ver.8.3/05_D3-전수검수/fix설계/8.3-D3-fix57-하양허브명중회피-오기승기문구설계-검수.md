## 1. E8-47 — 하양허브 규칙 `[소스]`

- 판정 루프: `for (i in pokemon.boosts) if (pokemon.boosts[i] < 0) { ready = true; boosts[i] = 0; }` → `useItem()` → `onUse`에서 `setBoost(boosts)`.
- `pokemon.boosts`는 `{atk, def, spa, spd, spe, accuracy, evasion}` 7종이다. 그래서 명중·회피 하락만 있어도 발동하고, 함께 복원한다. **설계서 변경안 1·2와 일치**한다.
- 음수만 0으로 바꾼다. + 랭크는 그대로다(시험 1 마지막 문장과 일치).
- 로그: `-clearnegativeboost`는 `[silent]`이다. 화면 줄은 `useItem`의 `-enditem` 한 줄(`end` 문구)뿐이다. 엔진의 한 줄 구조와 같다.
- 발동 시점(Showdown 훅 4개):

| 훅 | 시점 | 엔진 호출처 |
|---|---|---|
| `onAnySwitchIn`(우선도 −2) | 등장 묶음 끝 | `switching.ts` 692행 `finishEntryBundle` ✅ |
| `onAnyAfterMega` | 메가진화 뒤 | (fix-49에서 처리) |
| `onAnyAfterMove` | 누구든 기술 사용 뒤 | `mirroredEffects.ts` 417·422행 ✅ |
| `onResidual`(order 29) | **턴 끝** | **설계서에 없음 → R1** |

- 오기와의 순서: fix-52 R1대로 오기가 먼저, 하양허브가 뒤다. 진흙뿌리기를 맞은 오기+하양허브 보유자의 기대값은 **공격 +2·명중 0·허브 소모**다(시험 추가 — §4 6번).

### R1(확인 필요) — 턴 끝 하락의 복원 시점
- 시럽봄(`spe −1`)·문어굳히기(`def·spd −1`)는 `onResidualOrder: 14`다. 하양허브 `onResidual`은 29라 **같은 턴 끝에 복원**한다.
- 엔진 `finishTurn.ts` 436·462행(오기 호출 위치) 근처에 하양허브 호출이 없으면, 복원은 다음 턴 첫 기술 뒤(`onAnyAfterMove` 대응)로 밀린다. 시럽봄은 **다음 턴 행동 순서**까지 바꾼다(보유자가 스피드 −1로 정렬됨).
- 조치: 구현 첫 단계에서 `finishTurn.ts`의 하양허브 호출 유무를 grep으로 확인한다.
  - 없으면 이 PR에 **턴 끝 호출 1곳**을 더한다. 함수를 바꾸는 김에 호출처를 맞추는 것이라 범위가 자연스럽다. 엔진 변경이므로 측정에 포함된다.
  - 이 PR에 넣지 않으면 E9 후보로 등록한다.
- 시험(추가): 하양허브 보유자 + 시럽봄 → 그 턴 끝에 스피드 0·소모, 다음 턴 행동 순서가 하락 전과 같다.
- 같이 볼 것: `clampStagesToNonNegative`의 다른 호출처(내던지기 하양허브 등)가 있으면 같은 함수로 명중·회피도 함께 복원되는지 확인한다.

## 2. E8-48 — 오기·승기 로그 `[소스]`

### 2-1. Showdown 출력
- 오기: `this.boost({atk: 2}, target, target, null, false, true)` — `effect`가 `null`이라 현재 효과(특성 오기)가 들어간다. `isSelf = true`다.
- `boost()` 분기(2080~2097행):

| 상황 | 출력 | 화면 문구(영문 템플릿) |
|---|---|---|
| 실제 상승 2 | `-ability\|오기\|boost` → `-boost\|atk\|2` | `[OO's Defiant]` + "OO's Attack rose sharply!"(`boost2`) |
| 실제 상승 1(+5에서) | `-ability` → `-boost\|atk\|1` | 특성 표시 + "rose!"(`boost1`) — **"크게" 아님** |
| 상승 0(+6에서) | `-boost\|atk\|0`만(특성 표시 없음) | "OO's Attack won't go any higher!"(`boost0`) |

- 상승 0이어도 줄이 나오는 근거: `getCappedBoost`가 0인 항목을 남기고, `boostBy === 0`이면 `else if (effect?.effectType === 'Ability') { if (isSecondary || isSelf) add(...) }`로 간다.
- 오기 발동 자체(하락이 실제로 일어났는지)는 fix-52대로다. 하락이 상한으로 막히면 `AfterEachBoost`가 불리지 않아 **아무 줄도 없다**.

### 2-2. 줄 순서 `[소스]`
- `AfterEachBoost`는 `boost()`의 능력치 루프 **안**에서 불린다. 간지르기는 **공격 하락 → 오기 상승 → 방어 하락 → 오기 상승** 순으로 줄이 끼어든다.
- 위협·끈적끈적네트는 하락 줄 바로 뒤에 오기 줄이 온다. 하양허브가 있으면 그 뒤에 허브 줄이 온다.
- 엔진이 하락 줄을 모아 출력한 뒤 오기 줄을 낸다면 다중 하락에서 줄 순서가 다르다. 랭크 결과는 같으므로 **표시 순서 차이로 §5에 기록**하면 충분하다(권고).

### 2-3. 로그 필드 설계
- `selfStatRises`(행동자)와 분리해 맞은 쪽 필드를 따로 두는 판단에 동의한다.
- 최소 형태 권고: 필드 하나에 쪽을 싣는다(예: `dropReactionRises: {side, stat, delta}[]`). 방어측(기술)·공격측(접촉 반응)을 필드 둘로 나눌 필요가 없다. 턴 끝·등장 항목도 같은 모양을 쓰면 렌더 함수 하나로 끝난다.
- `delta`는 **실제 상승량**이어야 한다(R2). `applyOwnStatDropReaction`이 "올랐는지"만 반환한다면 상승량(0 포함)을 반환하도록 바꾼다.

### R2(필수) — 상한 처리
- `delta 2` → "크게 올라갔다", `delta 1` → "올라갔다", `delta 0` → "**OO의 공격은 더 이상 올라가지 않는다!**"
- 설계서 시험 4의 "발동 안 한 경우(이미 +6)는 줄 없음"은 Showdown과 다르다. **+6이면 상한 줄 1줄**이 기대값이다. "줄 없음"은 하락 자체가 일어나지 않은 경우(하락이 −6 상한·클리어바디 등)다.

### R3(필수) — 다중 발동은 줄도 여러 개
- 간지르기(2능력치 하락) → 상승 줄 2개(+2, +2 → 결과 +4가 아니라 줄 2개). 다단 접촉(더블어택 → 미끈미끈)도 히트마다 1줄씩이다(fix-52 R2 카운터와 같은 수).
- 시험 4에 "줄 수 = 발동 횟수"를 넣는다.
