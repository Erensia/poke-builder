## 3. 포인트 3 — E8-34 시작 장면 트레이스 × 날씨

### 3-1. Showdown 구조
- 시작 장면은 **양쪽 등장이 한 `fieldEvent('SwitchIn')`**에서 스피드 순으로 처리된다. 트레이스는 자기 순서에서 `onStart` → `Update` → `setAbility` → 복사한 특성의 `Start`를 **그 자리에서** 실행한다.
- 같은 날씨를 다시 설정하면 `setWeather`가 실패한다(gen > 5). 그래서 **먼저 처리된 쪽이 날씨의 주인**이고, 지속 턴은 **주인의 날씨 바위**로 정해진다.
- 싱글 시작 장면에서 트레이스는 상대 특성을 베끼므로, **복사한 날씨 = 상대가 까는 날씨**다. 날씨 종류는 항상 같고 **차이는 주인(턴수)과 로그 순서뿐**이다.

### 3-3. R2(수정 요청)
- §2-2-b의 "복사 후 덮어쓰기 + 이미 같은 날씨면 갱신 없음"은 **TW1·TW3에서 턴수가 틀린다**. 도달: 샘플 가디안(트레이스, 스피드 80족)은 페리퍼(65)·마기라스(61)·하마돈(47)·코터스 등 대부분의 날씨 특성보다 빠르다 → 상대가 날씨 바위를 들면 Showdown 5턴 / 엔진 8턴. 샘플 모래날림 26슬롯이라 **도달 가능**.
- **권고(더 단순한 방식)**: 시작 장면에서는 트레이스 복사를 **날씨 판정 전에 먼저 확정**한다. `resolveEntryWeather`에서 "트레이스 보유 + 상대 특성이 복사 가능하고 `setsWeather`"이면 **트레이스 쪽도 그 날씨의 설정자로 취급**해 같은 시작 순서(`startOrder()`, ④와 공유)로 비교하고, 바위는 각자 자기 도구로 본다. 그러면 루프에서는 날씨 덮어쓰기 반환값이 필요 없다(이미 같은 날씨).
- 필드는 `resolveEntryAbilityEffects` 루프가 스피드 순이고 트레이스 자리에서 복사 특성을 재호출하므로 **자동 일치**(트레이스가 빠르면 트레이스의 필드연장 기준) — 구현 때 TW4 + 필드연장 변형 1건으로 확인.
- 시험 13 기대값 정정: "턴수 5" 고정이 아니라 **TW1(8)·TW2(5)·TW3(5)**. 설계서의 "TR1c 장면 추가"는 이 세 장면으로 대체한다.

## 4. 포인트 4 — E8-35 재시도 지점

### 4-1. Showdown의 재시도 시점
- 트레이스 `onUpdate`는 `seek`가 참인 동안 `eachEvent('Update')`마다 재시도한다. `Update`는 **모든 행동(교체·기술·메가) 직후**에 돈다(`runAction` 끝, gen ≥ 5).
- 교체의 경우 Update는 **교체 행동 직후, 들어온 쪽의 `runSwitch`(설치물·등장 특성)보다 먼저** 돈다.

### 4-2. `[실행]`
| 장면 | Showdown | 설계 근사 |
|---|---|---|
| TRW1 대기 중 상대가 위협+하양허브 갸라도스로 교체 | 트레이스가 **먼저** 위협 복사 → 갸라도스 −1 → 갸라도스 위협 → 트레이스 −1 → 갸라도스 하양허브 복구·소모. 다음 턴 박치기 피해 21(허브 없음 14) | 최종 상태는 같을 수 있으나 **재시도가 하양허브 반응보다 먼저**여야 한다(R3) |
| TRW2 트레이스 vs 괴짜(메타몽) | 변신 후 메타몽 특성도 트레이스(복사 불가) → 양쪽 대기 | 근사로 충분 |
| TRW3 대기 중 트레이스 보유자가 상대(일루전)에게 **고민씨** | 기술 직후 Update에서 불면 복사 | **근사에서 빠짐** |

### 4-3. 판정
- **교체·메가 두 지점 근사 승인.** 등장 외에 상대 특성이 "복사 불가 → 가능"으로 바뀌는 경로는 특성 변경 기술(고민씨·심플빔·동료만들기·스킬스왑·역할 — 챔피언스 **합법**)과 미라·향기의잔향·떠도는영혼뿐이고, 대기 중인 트레이스(상대가 탈·일루전·괴짜·트레이스 등)와 겹쳐야 해 도달이 극히 낮다.
- **R3(조건)**: `runEntryEffects` 끝의 재시도는 **R1의 하양허브 묶음 끝 호출보다 앞**에 둔다. 그래야 TRW1처럼 복사한 위협으로 떨어진 상대의 하양허브가 같은 등장 처리 안에서 복구된다. 시험 14에 TRW1(허브 있음/없음 피해 비교)을 넣는다. 로그 순서(Showdown은 복사가 상대 등장 특성보다 먼저)는 판정 대상 아님.
- **개선권장(선택)**: 엔진에 "행동 끝" 공통 후처리(현재 하양허브가 반응하는 `mirroredEffects.ts` 386·391행 부근)가 있으므로 거기에 `retryWaitingTrace`를 한 줄 더 부르면 기술 경로까지 Showdown의 Update 주기와 같아진다. 비용이 작으면 포함, 아니면 §4 "알면서 둔 것"에 고민씨 등 합법 기술 목록과 함께 기록.

## 5. 포인트 5 — E8-37 동률 / E8-39 스피드 보정

### 5-1. E8-37
- `[실행]` SP3 동속 위협 vs 트레이스: 위협이 먼저 22/40 — 시작 동률은 무작위(기존 W7 18/40과 같은 결론).
- 설계(선택 인자 `random`, 동률일 때만 소비, 없으면 a 먼저, `startOrder()` 캐시 공유) **승인**. Showdown도 시작 장면은 핸들러 한 큐를 한 번 정렬하므로 날씨·특성이 **같은 동률 결과를 공유**하는 것이 맞다. R2를 채택하면 트레이스 날씨 판정도 같은 `startOrder()`를 써야 한다.

### 5-2. E8-39 — 이번 PR에 포함 권고(R4)
- `[실행]` SP1: 잔비 왕구리(원시 90, 구애스카프 → 135) vs 가뭄 나인테일(120) → Showdown **쾌청**(스카프 보정으로 왕구리가 먼저 처리되고 나인테일이 덮어씀). 스카프 없는 대조 SP2 → 비. 엔진(원시 비교)은 SP1에서 **비** → 어긋남 확정.
- 시작 시점에 실제로 작동하는 보정: 챔피언스 합법 중 `onModifySpe`를 가진 것은 도구 **구애스카프·검은철구**, 특성 엽록소·쓱쓱·모래헤치기·눈치우기·서핑테일·속보·슬로스타트다. 시작 정렬은 날씨·상태·필드가 생기기 **전**에 한 번 이루어지므로 특성 7종은 시작 장면에서 효과가 없고(날씨 없음·상태 없음·슬로스타트 휘발 상태 전), 순풍·트릭룸·랭크·마비도 시작에는 없다.
- 따라서 **"구조 변경 필요"가 아니다** — 시작 전용으로 `realStats.spe × 도구 보정(스카프 1.5 / 검은철구 0.5)`을 구하는 작은 함수면 된다. 반올림은 턴 순서에서 쓰는 스카프 계산(D3-fix-11 스피드 정수)과 같은 함수를 재사용한다. ④에서 같은 비교식을 고치므로 **같은 단계·같은 해시**에 넣는 것을 권고한다(시험: SP1·SP1b).
- 범위 밖으로 남기는 것: 없음(시작 외 경로는 이미 `orderBySpeed`가 보정 스피드를 본다 — 엔진 쪽에서 한 줄 확인만).
