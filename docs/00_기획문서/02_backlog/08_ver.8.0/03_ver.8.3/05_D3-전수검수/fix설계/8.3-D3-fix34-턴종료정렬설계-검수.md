## 2. 보완

### 2-1. [필수] 자리 효과는 "스피드 없음"이 아니라 자리 주인의 스피드로 정렬된다

```ts
// findPokemonEventHandlers(pokemon, …) — 포켓몬별 수집 안에서
for (const conditionid in side.slotConditions[pokemon.position]) {
  handlers.push(this.resolvePriority({ effect: slotCondition, state, …, effectHolder: pokemon }, callbackName));
}
// resolvePriority
if (handler.effectHolder.getStat) handler.speed = pokemon.speed;   // ← 자리 주인의 스피드
```
- 미래예지·희망사항 핸들러는 **그 자리에 있는 포켓몬이 보유자**다. 스피드가 그 포켓몬 값이라 일반 포켓몬 효과와 똑같이 빠른 쪽 먼저 처리된다. sub 3은 자리 기본값으로 맞다.
- 따라서 §4-4의 "양쪽에 있을 때만 `random() < 0.5`"는 Showdown과 다르다. **별도 난수를 없애고 포켓몬 효과와 같은 스피드 순위를 쓴다.** 구현이 더 단순해진다. `slot: true` 표시는 "기절한 보유자도 건너뛰지 않음" 용도로만 남긴다.
- 자리 주인이 기절해 있으면 Showdown은 `updateSpeed`가 기절 포켓몬을 건너뛰어 **이전 스피드 값**을 쓴다. 그런데 그 경우 미래예지(`target.fainted`면 불발)·희망사항(기절이면 회복 없음)은 효과가 없다. 설계서 §4-1 1의 "한쪽이 기절했으면 `["a","b"]`"을 그대로 둬도 관측 차이는 엔진이 내는 불발 로그 줄의 위치 정도다.
- 고칠 곳: §1-3 둘째 문장, §3 미래예지·희망사항 행 메모("스피드 없음"), §4-4 전체, Q1의 자리 효과 부분, 시험 10.

### 2-2. [필수] 사례 A(먹다남은음식 ↔ 씨뿌리기 끼어들기)는 HP 결과가 바뀌지 않는다 — 시험 3을 바꾼다

- 회복은 같은 최대 HP로 상한이 걸리고 더해지기만 하므로, b의 먹다남은음식 회복과 씨뿌리기 회복의 **순서가 바뀌어도 b의 최종 HP는 같다**(`min(잃은 HP, 회복1 + 회복2)`). 씨뿌리기로 a가 받는 피해는 a의 HP로 정해지는데, a의 HP를 바꾸는 a 자신의 order 5–7 효과는 두 방식 모두 씨뿌리기보다 먼저다. 즉 사례 A에서 달라지는 것은 **줄마다 찍히는 회복량 분배뿐**이다. "HP 경계에서 흡수량이 달라진다"는 성립하지 않는다.
- 포켓몬 사이에 HP가 오가는 턴 종료 효과는 씨뿌리기 하나뿐이다. 결과가 실제로 갈리는 끼어들기는 아래 두 장면이다.
  1. **상호 씨뿌리기**: 둘 다 씨앗 상태, a가 느리고 HP가 최대의 1/8 미만이다. Showdown은 b의 씨뿌리기(8)가 먼저라 a가 흡수분을 회복한 뒤 자기 씨뿌리기 피해를 받아 **생존**한다. 현행은 a 효과를 먼저 처리해 a가 **기절**한다.
  2. **씨뿌리기 원천이 더 뒤 order에서 쓰러질 처지**: a(예비 있음)가 독·HP 1이고 b가 a의 씨앗 상태다. Showdown은 씨뿌리기(8) → 독(9)이라 a가 먼저 회복하고 독을 받아 **생존**한다. 현행은 a의 독으로 a가 먼저 기절하고, b의 씨뿌리기는 "원천 기절"로 **피해·회복 모두 불발**한다. 순서 차이가 승패·HP를 다 바꾸는 경우다.
- 고칠 곳: §2 사례 A 서술, §6 시험 3을 위 1로 바꾸고, 위 2를 시험 13으로 추가.

### 2-3. [필수] S1(순위 a→b 고정)에서 승패는 불변이 아니다 — 측정 단계를 하나 더 쪼갠다

- S1의 정렬 키는 `(order, a→b, sub)`다. a→b로 고정해도 **order가 먼저**이므로 사례 B(독 9가 화상 10보다 먼저)와 §2-2의 씨뿌리기 두 장면은 S1에서 이미 결과가 바뀐다. 설계서 §7은 "S1에서 승패가 바뀌면 Q3 때문"으로 판정하는데, 그러면 원인을 잘못 짚는다.
- 현행 순서를 그대로 재현하는 정렬 키는 `(단계, a→b, order, sub)`다. 단계 = ②날씨 / ③미래예지·희망사항 / ④개별 / ⑤멸망·가속·열매. 날씨는 한 포켓몬에 날씨 줄이 하나뿐이라(§1-2) 효과 우선과 포켓몬 우선이 같은 줄 순서가 된다.
- 측정을 다음과 같이 나눈다(각 단계 측정 명령은 설계서와 같음).

| 단계 | 정렬 키 | 기대 |
|---|---|---|
| **S0 구조만** | (단계, a→b, order, sub) | **해시까지 완전 불변.** 바뀌면 Q3(컨텍스트 재생성) 또는 아쿠아링·뿌리박기 분리 탓이다 |
| S1 order 우선 | (order, a→b, sub) | 해시 변동, 승패 소폭 변동(사례 B·씨뿌리기류) |
| S2 스피드 | (order, 스피드, sub) | 사례 C·D류 추가 변동 |

- S0는 최종 코드에 남지 않는 임시 키라 비용이 거의 없고, Q3 위험(설계서 §8-1)을 가장 깨끗하게 분리한다.

### 2-4. [권고] `computeTurnOrderSpeed`가 순수 스피드인지 확인

Showdown의 residual 스피드는 `getActionSpeed()`(실능 스피드 × 랭크·마비·스카프·순풍·날씨 특성 등, 트릭룸 반전)뿐이다. 선제공격손톱·느림보꼬리·만복향·애태우기처럼 **행동 순서에만 쓰는 보정**(`onFractionalPriority` 등)은 들어가지 않는다. 엔진 함수가 이런 행동 단위 보정이나 이번 턴 기술 우선도를 섞는다면, residual용으로는 그 부분을 뺀 값을 써야 한다. 구현 첫 단계에서 함수 본문을 확인해 설계서 §4-1 1에 한 줄로 명시한다.

### 2-5. [권고] 날씨(order 1)와 멸망의노래(24)는 "그룹 끝에서" 전멸 판정 — Q5와 연결

- **날씨**는 핸들러가 1개다. 두 포켓몬의 모래 피해가 모두 들어간 뒤 `resolveFaints`가 한 번 돈다.
- **멸망의노래**는 지속 종료형이다. `duration`이 0이 되면 `end()`(→ `faint()` 예약) 후 **`resolveFaints` 없이 `continue`** 한다(위 1-1의 ←). 그래서 양쪽 카운트가 같이 0이면 **둘 다 쓰러진다.**
- 동시 전멸이면 `checkWin(faintData)`가 **마지막으로 처리된 기절 포켓몬의 편을 승자**로 한다(9세대). 기절 큐는 피해 순서이므로 느린 쪽이 마지막이고, **느린 쪽이 이긴다.**
- 설계서(핸들러마다 `endIfWiped`)도 **승자는 같다.** 다만 빠른 쪽이 쓰러지는 즉시 끝나므로 느린 쪽의 모래 피해·`perish0`·기절 줄이 빠지고 HP가 남는다. 현행 F-4는 둘 다 쓰러뜨리므로, 멸망의노래는 이 PR로 오히려 Showdown에서 멀어진다.
- 최소 변경: `EotHandler`에 `deferWipe?: true`를 두고 order 1·24 행에만 단다. 실행기는 이 핸들러 뒤에서는 `endIfWiped`를 미루고, **같은 order의 마지막 핸들러 뒤에 한 번** 판정한다. 양쪽 다 전멸이면 나중에 처리된 쪽이 승자다. F-4 블록·`perishFaintedKeys`·`speedA/B` 삭제는 그대로 가능하다(승자 규칙이 정렬 순서에서 자연히 나온다).
- 예비가 있는 쪽이 있으면 결과가 원래 같다(둘 다 쓰러지고 교체).

### 2-6. [권고] `endIfWiped(c, opponentKey(key))` — 보유자가 아닌 쪽의 기절도 보는지 확인

Showdown의 `resolveFaints`/`checkWin`은 핸들러가 누구를 쓰러뜨렸든 양쪽을 다 본다. 엔진에서 핸들러가 보유자가 아닌 쪽을 쓰러뜨릴 수 있는 경로가 있으면(예: 미래예지 명중 시 공격자의 생명의구슬 반동을 구현했다면) `opponentKey(key)`만 보는 판정은 놓친다. 그런 경로가 없으면 그대로 둔다. 구현 때 `apply*` 중 상대 HP를 깎는 것을 grep으로 한 번 확인한다.

### 3-1. Q1 보강 — 동속 난수의 단위

- Showdown `speedSort`는 비교값이 0인 **묶음마다** `shuffle`한다. 서로 다른 포켓몬 둘이 같은 스피드면:
  - **order마다 동전이 따로다.** 먹다남은음식 묶음(5/4)과 독 묶음(9)의 앞뒤가 서로 독립이다.
  - **같은 order 안에서는 subOrder로 교차한다.** 그래스필드(5/2) a·b가 먼저 섞이고, 그다음 먹다남은음식(5/4) a·b가 섞인다. 설계서 키 `(order, 순위, sub)`는 a 그래스필드 → a 먹다남은음식 → b … 로 묶는다.
- 선택지:
  - **(가') 묶음별 난수(권고).** 정렬 키를 `(order, 스피드값, sub, 표 위치)`로 하고, `(order, 스피드, sub)`가 같은 **서로 다른 포켓몬** 쌍에만 난수 1회를 쓴다. 같은 포켓몬끼리는 Q2대로 고정한다. `orderBySpeed` 호출이 필요 없고 자리 효과도 같은 키로 처리되어 구현이 오히려 단순하다.
  - (가) 설계안: residual당 1회 결정. 차이는 완전 동속 + 양쪽에 같은 order 효과가 2개 이상인 턴뿐이라 승패 영향은 사실상 없다.
  - (나) a 고정.
- 어느 쪽이든 스피드가 다르면 난수를 쓰지 않는 점은 같다.
