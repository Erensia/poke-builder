## 1. 소스 대조

```ts
// getStat('spe')
stat = boost >= 0 ? Math.floor(stat * boostTable[boost]) : Math.floor(stat / boostTable[-boost]);  // ① 랭크
stat = runEvent('ModifySpe', …)   // ② chainModify 누적 → 이벤트 끝 modify 1회
                                   // ③ par(-101): finalModify 먼저, 속보 아니면 floor(×50/100)
if (stat > 10000) stat = 10000;    // ④
// champions getActionSpeed: 트릭룸이면 speed = -speed (10000− 아님, trunc 없음)
```

| 단계 | 설계서 §3-1 | 판정 |
|---|---|---|
| ① 랭크 | `floor(base×(2+s)/2)` / `floor(base×2/(2−s))` | ✅ 소스 `boostTable` 곱·나눗셈과 스탯 1~2000 × 랭크 −6~+6 **전부 일치**(부동소수 포함) |
| ② 체인 | `modify4096(s, chain4096(...))` | ✅ 스카프·철구·순풍·날씨 특성·서핑테일·곡예·속보 모두 `chainModify`. champions 재정의 없음. 모두 정확 분율이라 순서 무관 |
| ③ 마비 | 체인 뒤 `floor(×50/100)`, 속보는 체인 1.5·절삭 없음 | ✅ champions `par`는 `onBeforeMove`(1/8)만 재정의하고 `onModifySpe`는 상속 |
| ④ 상한 | 넣지 않음 | ✅ 도달 불가 |
| ⑤ 트릭룸 | 정수 비교 방향 반전, 동속 50% | ✅ champions `-speed` |

## 2. 보완

### 2-1. fix-6 인터페이스와 맞추기

fix-6 검수(§4-5)는 `modify4096(value, numerator4096)`가 **4096 분자 정수를 받게** 하라고 권고했다. 설계서 의사코드는 `chain4096("other", ...multipliers)`에 소수를 넘긴다. 스피드 배율은 모두 정확 분율이라 값은 같지만, 실제 fix-6 구현의 시그니처(모드 인자 `"other"`의 의미 포함)를 확인해 설계서 의사코드를 그것에 맞춘다. 참조 구현은 소스 그대로 `chain = (a*b+2048)>>12`, `modify = tr((tr(v*m)+2047)/4096)`을 쓴다.

### 2-2. 랭크 이중 적용 전수 확인

`computeTurnOrderSpeed`가 랭크까지 포함하게 바뀌므로, 그 반환값에 다시 `rankStageMultiplier`를 곱하는 곳이 남으면 랭크가 두 번 들어간다. 설계서는 `finishTurn.ts:997`만 짚었다. 구현 전 `rankStageMultiplier(`·`computeTurnOrderSpeed(`·`.realSpeed`·`computeEffectiveSpeed(` 호출처를 전수 grep해 목록을 설계서 §2에 붙인다(시험 7이 멸망의노래만 본다).

### 2-3. 보정 목록 = 엔진이 구현한 스피드 효과 전부

`multipliers`에 들어가는 것은 설계서 7종이다. 엔진이 그 밖의 스피드 보정(예: 고대활성·쿼크차지 스피드 ×1.5)을 구현하고 있다면 같은 체인에 넣는다. 소스에서 이들도 `chainModify`다. 구현하고 있지 않으면 이 PR 범위 밖이며 한 줄 기록으로 충분하다.
