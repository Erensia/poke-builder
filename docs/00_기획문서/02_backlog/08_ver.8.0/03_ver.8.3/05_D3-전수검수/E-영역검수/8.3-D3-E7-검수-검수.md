## 1. §6-1 `HazardState.order` vs Showdown `effectOrder`

### 1-1. 판정: 일치
| 경우 | Showdown 소스 | 설계 | 판정 |
|---|---|---|---|
| ① 층만 늘 때 | `addSideCondition`: 이미 있으면 `singleEvent('SideRestart', …, this.sideConditions[id])` — **같은 상태 객체**를 쓰므로 `effectOrder` 그대로 | 0 → 1일 때만 추가, 층 증가는 불변 | 일치 |
| ② 제거 후 재설치 | `removeSideCondition`이 객체 삭제 → 재설치 때 `initEffectState`가 `effectOrder = this.effectOrder++`(배틀 전체 단조 증가) → **맨 뒤** | 맨 뒤에 추가 | 일치 |
| ③ 코트체인지 | `courtchange.onHitField`가 id별 **상태 객체를 옮기고 `.target`만 바꿈** → `effectOrder` 보존 | `hazards` 객체째 맞바꿈 | 일치 |
| 정렬 근거 | `comparePriority`: order → priority → speed → subOrder → **effectOrder 오름차순**. 설치물은 모두 subOrder 4, 같은 포켓몬이라 speed 동일 → effectOrder만으로 갈린다(`resolvePriority`의 `SwitchIn` 주석이 바로 이 경우) | `hazardEntryOrder` | 일치 |
| 기절 시 중단 | `fieldEvent`가 핸들러마다 `resolveFaints()` → 다음 핸들러에서 `effectHolder.fainted`면 `continue`(자리 조건만 예외) | 핸들러마다 기절 확인 후 중단 | 일치 |
| 흡수된 독압정 | 핸들러 실행 전 `sideConditions[id] !== handler.state`면 건너뜀 | 흡수 시 설치물·순서에서 제거 | 일치 |

### 1-2. R2(수정): 기록 지점 누락 — 비검천중파·암반던지기
- **원인**: §2-5의 기록 지점은 `mirroredEffects.ts` 설치 분기(변화 기술)와 독치장뿐이다. 그런데 Showdown의 `ceaselessedge`·`stoneaxe`는 **공격 기술의 `onAfterHit`·`onAfterSubDamage`에서 `side.addSideCondition('spikes' / 'stealthrock')`** 을 부른다(`data/moves.ts` 2229~2239·18074~18084행). 두 기술은 champions 습득표에 있고(각 1종), 보유종 **대검귀(히스이의 모습)·사마자르가 로스터에 있다.**
- **결과**: 엔진이 이 두 기술의 설치를 변화 기술 분기 밖(예: `hitResolution`의 기술 후 효과)에서 처리한다면, 그 경로로 깐 설치물은 `order`에 기록되지 않고 기본 순서 꼬리로 처리된다 → 예: 압정(비검천중파) → 스텔스록(변화 기술) 순으로 깔아도 엔진은 스텔스록 → 압정 순으로 발동.
- **설계 수정**: 구현 첫 단계에서 `spikesLayers`·`stealthRock`에 값을 쓰는 곳을 전수 grep하고, **설치는 한 헬퍼(`addHazard(side, kind)`)로만** 하게 모은다. 시험에 "비검천중파로 압정 → 스텔스록 → 압정 피해 줄이 먼저"를 추가한다.
- **같은 이유로 확인**: 매직미러·매직코트로 **튕겨서 깔린** 설치물. Showdown은 튕긴 쪽이 기술을 다시 써서 `addSideCondition`을 부르므로 새 `effectOrder`(맨 뒤)다. 엔진의 반사 경로가 같은 설치 분기를 거치는지 시험 1건으로 확인한다.

### 1-3. S1(권고): 기록을 불변 갱신으로 — 지우는 곳 수정 제거
- 현 설계는 지우는 곳(독압정 흡수·정리정돈·고속스핀·안개제거)과 `cloneSide` 배열 복사를 모두 고쳐야 한다. 그런데 `hazardEntryOrder`가 이미 **"현재 깔린 것만"** 걸러 쓰므로, 지워진 항목이 `order`에 남아 있어도 해가 되는 경우는 **재설치 시 옛 위치에 남는 것** 하나뿐이다.
- **제안**: 기록할 때(0 → 1 순간) `order = [...(order ?? []).filter(k => k !== kind), kind]`로 **기존 항목을 빼고 맨 뒤에 붙인다.**
  - 재설치는 항상 맨 뒤 → 지우는 곳에서 `order`를 건드릴 필요가 없다(`emptyHazardState`의 `order: []`는 그대로 둬도 무방).
  - 배열을 제자리 변경(`push`)하지 않으므로 `cloneSide`가 배열을 공유해도 안전하다 → `cloneSide` 수정 불필요.
  - 설계서에 없는 제거 경로(킬러스핀 — champions 습득 1종)도 자동으로 안전해진다.
- 시험 "흡수 뒤 다시 깔면 맨 뒤"·"정리정돈 뒤 다시 깔면 새 순서"·"`cloneSide`가 배열을 공유하지 않음"은 **"원본과 사본 중 한쪽에 재설치해도 다른 쪽 순서 불변"** 으로 바꾸면 된다.

## 2. §6-2 압정 정수 분자식 — 일치
- Showdown: `this.damage(damageAmounts[layers] * pokemon.maxhp / 24)` → `spreadDamage`가 `clampIntRange(d, 1)` = **`Math.floor` 후 최소 1** → `Damage` 이벤트(매직가드는 여기서 0) → 다시 `clampIntRange(d, 1)`.
- JS는 `n * maxhp / 24`를 왼쪽부터 계산하므로 **정수 ÷ 24 한 번**이다. 정수의 몫은 정수에서 최소 1/24 떨어져 있어 부동소수점 반올림으로 `floor`가 바뀔 수 없다.
- 설계 `Math.max(1, Math.floor(maxHp * n / 24))`는 **같은 식**이다. 최대HP 1~5,000 × {3,4,6} 전수 대조에서 불일치 0건을 확인했다.
- 참고: `maxHp * (1/6)` 실수 상수도 1~5,000에서 오차는 0이었지만, 정수 분자 방식이 Showdown 식과 글자 그대로 같으므로 설계대로 가는 것을 권한다.

## 3. §6-3 문구 — S2(권고)

### 3-1. Showdown의 줄 구조
| 장면 | Showdown 로그 |
|---|---|
| 네트, 일반 | `-activate 대상 move: Sticky Web` → `-unboost 대상 spe 1` |
| 네트, 클리어바디 | `-activate …` → `-fail 대상 unboost [from] ability: Clear Body` |
| 네트, 이미 −6 | `-activate …` → `-unboost 대상 spe 0`(기술 효과라 `boostBy 0`도 줄을 낸다 → "더 떨어지지 않는다") |
| 위협, 클리어바디 | `-ability 사용자 Intimidate boost` → `-fail 대상 unboost [from] ability: Clear Body` |

- 즉 Showdown은 **"걸렸다" 줄과 결과 줄이 따로**이고, 막힘 줄은 기술로 막혔을 때와 **같은 `-fail … [from] ability`** 다.

### 3-2. 권고
1. **네트**: 한 문장 "…걸렸지만 {특성}으로 스피드가 떨어지지 않았다!"를 새로 만들기보다, ① "{포켓몬}은(는) 끈적끈적네트에 걸렸다!"(접지면 항상) + ② 결과 줄(하락 / 차단 / −6)로 나눈다. 차단 줄과 −6 줄은 **기술 경로(`hitResolution.ts` 615행 부근 `statDropBlockStatsOf` 분기)가 이미 쓰는 문구를 그대로 재사용**한다.
   - 이유: 로그를 Showdown과 줄 단위로 대조할 수 있고, 같은 클리어바디 차단이 경로마다 다른 문장으로 나오지 않는다.
   - 대안: 기존 성공 문구 "…걸려 스피드가 떨어졌다!"(한 줄)를 바꾸고 싶지 않다면 현 설계도 동작상 문제는 없다. 다만 그 경우에도 차단 부분의 표현은 기술 경로 문구와 맞춘다.
2. **위협**: 새 문구 "{상대}의 {특성}! 위협에 능력이 떨어지지 않았다!" 대신 **기술 경로의 차단 문구를 그대로** 쓴다(Showdown도 같은 `-fail` 줄). 위협 사용 줄은 지금처럼 남긴다.

## 4. §6-4 새 등장 순서·치유소원

### 4-1. Showdown 정렬값(같은 포켓몬)
| 순 | 효과 | priority | subOrder(`resolvePriority`) |
|---|---|---|---|
| 1 | 치유소원(자리 조건) | 0 | 3 |
| 2 | 설치물(편 조건) | 0 | 4 (서로는 effectOrder) |
| 3 | 등장 특성(위협 등, `onStart`) | 0 | 7 |
| 4 | 풍선 안내(도구 `onStart`) | 0 | 8 |
| 5 | **의태**(특성) | −1 | **7** |
| 6 | **시드류**(도구) | −1 | **8** |
| 7 | 기분파 | −2 | 7 |

### 4-2. R1(수정): ⑤·⑥ 순서
- 설계는 ⑤ 시드 → ⑥ 의태인데, 둘 다 우선도 −1이라 subOrder로 갈리고 **특성(7)이 도구(8)보다 먼저**다 → **⑤ 의태 → ⑥ 시드 → ⑦ 기분파**로 고친다.
- 영향: 의태 보유 **메더(가라르의 모습)가 로스터에 있다.** 시드의 랭크 상승은 타입과 무관하므로 결과는 같고 **로그 줄 순서만** 달라지지만, fix-37이 바로 이 순서를 맞추는 PR이므로 함께 바로잡는다. 시험에 "일렉트릭필드 + 시드를 든 메더(가라르) 등장 → 의태 줄이 시드 줄보다 먼저"를 추가한다(`e7b-run.cjs` ④).

### 4-3. 그 밖은 일치
- 치유소원 → 설치물 → 특성 → 풍선: subOrder 3 < 4 < 7 < 8로 일치. 기분파 −2 일치.
- **치유소원 소모 조건**: `onSwap`의 `if (!target.fainted && (target.hp < target.maxhp || target.status))` 안에서만 회복·`removeSlotCondition` → 필요 없으면 자리 조건이 남아 다음 등장 때 다시 본다. 설계와 일치. champions 재정의 없음.
- 참고(범위 밖, 변경 요청 아님): **양쪽이 동시에 등장**할 때 Showdown은 한 `fieldEvent`에서 priority → speed로 정렬하므로 "빠른 쪽 우선도 0 효과 전부 → 느린 쪽 우선도 0 효과 전부 → 빠른 쪽 −1 → 느린 쪽 −1 → …"가 된다. 엔진이 포켓몬별로 ①~⑦을 통째로 돈다면 빠른 쪽 기분파 줄이 느린 쪽 설치물·위협 줄보다 먼저 나온다. 날씨·필드 변화는 `onWeatherChange`·`onTerrainChange`로 다시 반응하므로 **결과는 같고 줄 순서만** 다르다. A7 구현이 어느 쪽인지 fix-37 때 확인만 해 두면 된다.
