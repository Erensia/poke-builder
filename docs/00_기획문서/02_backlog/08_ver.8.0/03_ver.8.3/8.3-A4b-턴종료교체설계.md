## 1. 확정된 규칙
출처: A4 설계서 §0 ⑩⑪⑫(2차 Showdown 검수, 실측), 사용자 결정 Q9·Q11·Q12(2026-11-12).

**미래예지 적중 쪽 (대상 = 맞는 쪽, 사용자 = 미래예지를 쓴 쪽)**
1. **위기회피(대상)**: 적중으로 HP가 절반 초과 → 이하(0 초과)가 되면 발동한다. 교체 요구는 **턴 종료 효과가 전부 끝난 뒤**에 나간다(먹다남은음식·뿌리박기 회복이 다 돈 뒤). 조건은 **살아 있는 예비가 있는가** 하나뿐이라 **도망봉인·뿌리박기·흡반이어도 발동하고 교체된다**. 확정 단계에서 **HP를 다시 확인하지 않는다**(발동 뒤 회복으로 절반을 넘어도 교체, 실측 105→71→80/150). 대타가 맞거나 빗나가면 미발동. 그 사이 기절했으면 취소(기절 교체가 대신).
2. **레드카드(대상이 지님)**: 사용자가 **필드에 있고**(교체·기절이면 미발동) 적중이 **본체에 닿았으면**(빗나감·타입 면역·대타 적중만 제외 — 데미지량이 아니라 "맞았는가"라 **탈이 벗겨지는 적중(데미지 0)에도 발동**) **맞는 순간 카드가 소모**된다. 소모한 **뒤에** 사용자가 끌려 나올 수 있는지 본다 — 뿌리박기·흡반이면 **카드는 소모되고 교체만 안 된다**. 교체는 턴 종료 효과가 끝난 뒤 사용자가 **무작위 예비**로 끌려 나온다. 사용자 편에 살아 있는 예비가 없으면 카드를 소모하지 않는다(`canSwitch` 선행 — A4 3차 검수에서 소스·실측으로 확인됨, 시험 R3-t6).
   - **[검수] 생명의구슬 반동과의 순서**: 레드카드 판정이 사용자 측 반동(`lifeorb.onAfterMoveSecondarySelf`, 조건 `!source.forceSwitchFlag`)보다 먼저다. 카드가 소모되고 사용자가 **끌려 나갈 예정**(`!isForcedSwitchBlocked`)이면 **반동이 없다**. 뿌리박기·흡반이면 카드는 소모되고 반동은 받는다(반동으로 쓰러지면 기절 교체). 실측: 정상·미래예지 둘 다 같다. 빗나감·무효·대타 적중은 레드카드가 돌지 않으므로 기존대로 반동이 생긴다(A4 §2-5).
3. 같은 포켓몬이 위기회피와 레드카드를 둘 다 지니면 **사용자가 먼저 끌려 나오고 그다음 대상에게 교체를 요구**한다(실측). 두 효과는 서로 다른 편을 움직여 독립이다.
4. 도구·특성 억제(매직룸·`disablesOwnItemEffects`)는 정상 경로와 같이 적용한다. 우격다짐 제외는 미래예지에 해당 없다(추가효과 없는 기술).

**정상 공격 경로 (Q11 — 같은 기준으로 같이 고친다)**
5. 위기회피: 도망봉인·뿌리박기·흡반에도 발동·교체창.
6. 레드카드: 데미지 0이어도 "맞았으면" 발동(탈 벗겨짐 포함, 대타 적중·방어 막힘·타입 면역·흡수 특성 무효는 제외). 카드를 먼저 소모하고, 공격자가 뿌리박기·흡반이면 교체만 안 된다.
7. 탈출버튼: 주인이 뿌리박기이거나 공격자가 그림자밟기여도 발동하고 교체창(사용자 결정 2026-11-12). **[검수 V1] 레드카드와 같이 "본체에 닿았는가"로 판정한다 — 데미지량 검사가 없어 탈이 벗겨지는 적중(데미지 0)에도 발동하고 버튼이 소모된다**(실측: 사이코키네시스 → 따라큐(탈, 탈출버튼) → `-enditem Eject Button`). 홀더 생존은 유지.
   - **[검수] 정상 경로의 생명의구슬 반동**: 레드카드가 공격자를 끌어내면 같은 행동의 생명의구슬 반동이 없다(정상 `AfterMoveSecondary` → `AfterMoveSecondarySelf` 순서). 공격자가 뿌리박기·흡반이면 반동 있음.
8. 우격다짐이 **추가효과 있는 기술**을 쓰면 레드카드·위기회피·탈출버튼이 모두 불발(Showdown 사양). 추가효과 없는 기술이면 정상 발동.

**범위 밖(Q12)**: 턴 종료 효과 전체의 시작·끝 HP 비교로 위기회피를 한 번 더 판정하는 규칙(57% → 독 45%면 발동)은 지원하지 않는다 — 잔류 피해 전반의 규칙이고 poke-builder는 위기회피를 행동 단위로만 판정한다. 백로그 한계로 이미 기록돼 있다.

## 3. 설계
**구현 순서(원인 분리)**: ① 정상 경로 정렬(⑥-d, §3-1)을 **먼저** 구현하고 `SERIAL=1 verify.sh`로 해시 변화를 따로 기록한다 → ② 인프라(`forceRandomSwitch` 이동·`finishTurn` 순서 변경, 출력 불변)를 넣고 해시 불변을 확인한다 → ③ 미래예지 쪽(§3-2)과 UI(§3-3)를 구현해 다시 측정한다 → ④ 기준값은 **마지막에 한 번** 갱신하고 PR 본문에 단계별 원인을 적는다.

### 3-1. 정상 공격 경로 정렬 (`runTurn.ts`, 판정 로직만)
미래예지 경로(헬퍼 값)와 정상 경로(`ActionLogEntry`)는 입력이 달라 서로 공용 함수로 뽑지 않는다(`// ponytail:` 주석: 세 번째 입력 형태가 생기면 뽑는다). **[검수 §2-1] 단, 정상 경로 안에서는 레드카드·탈출버튼이 같은 "본체에 닿았는가" 조건을 쓰므로 `runTurn.ts` 안에 지역 함수 `hitReachedBody(action)` 하나를 둔다**(`hit`·비상태·`!blockedReason`·`typeEffectiveness !== 0`·`!blockedByProtectMoveName`·`!blockedBySubstituteMoveName`·`!hitSubstitute`·`!abilityAbsorbAbilityName`·`!sheerForceAbilityName`, 아래 2의 목록). 홀더 생존·예비·`didSwitch` 같은 편 상태 조건은 각 호출부에 둔다.
1. **위기회피**(`defenderExitPause` `:453~460`): `!isForcedSwitchBlocked(state[oppKey]) && !isTrappedFromSwitching(state[oppKey])` 두 줄을 삭제하고 `!action.sheerForceAbilityName`을 더한다. HP 문턱 판정(`resolveAction.ts:699`)은 그대로 둔다.
2. **레드카드 발동 조건**(`applyRedCard` `:387~399`):

### 3-2. 미래예지 적중 반응 (`finishTurn.ts`, `switching.ts`)
**① `forceRandomSwitch` 이동**: `runTurn.ts:298`의 함수는 `RunTurnContext`를 받는다. `runTurn.ts`가 `finishTurn.ts`를 import하므로(역방향 import 금지) `switching.ts`로 옮기고 `(state, random, switches, key, extra)`를 받게 한다. 호출부(`applyRedCard`·`forceTargetSwitch`)는 `forceRandomSwitch(ctx.state, ctx.random, ctx.switches, key, extra)`로 바뀐다. **출력 불변**이어야 하며 `regress` 해시로 확인한다. `extra`에 `endOfTurn?: true`를 허용한다(§3-3 ②).

**② 반응 기록**: `FinishCtx`에 `pendingExit: Partial<Record<FighterKey, true>>`·`pendingRedCard: Partial<Record<FighterKey, true>>`(키 = **대상 = 홀더 쪽**)를 둔다. `EndOfTurnFighterContext`는 `makeEotCtx`(`finishTurn.ts:822`)에서만 만들어지므로 같은 두 객체를 `pending`으로 한 번에 전달한다.

**③ 판정(`applyFutureSight`, 적중 분기 안)** — 파이프라인이 `res`를 돌려준 직후:
- **위기회피**: 호출 전 `hpBefore`와 호출 후 `fighter.currentHp`, 호출 전 대상 특성(`abilityOf(fighter)`의 `exitsFieldAtHalfHp`)으로 `resolveAction.ts:699`와 같은 조건(`fighter.currentHp > 0 && hpBefore*2 > maxHp && currentHp*2 <= maxHp`)을 본다. 대타가 맞으면 본체 HP가 안 변해 자연히 미발동. 발동하면 `pending.exit[key] = true`, 로그 줄에 `futureSightExitAbilityName`(특성 이름)을 남긴다. 예비 유무는 **확정 단계**에서 본다.
- **레드카드**: `onField && res.hit…` 조건 — 적중이 본체에 닿았을 것(`!res.hitSubstitute`, 위 분기가 이미 빗나감·무효를 거른다), 홀더(`fighter`)가 살아 있고 대상 도구가 `forcesAttackerSwitchOnHit`(특성 억제·매직룸 반영, `effectiveHeldItem`), 사용자 편에 살아 있는 예비가 있으면 `consumeItem(fighter)` 후 `pending.redCard[key] = true`. 로그: `futureSightRedCardItemName`(도구 이름).
- 이 두 판정은 적중 직후 한 지점에서 하고 교체는 하지 않는다. 자기과신류 처리(`:293~299`)는 그대로 둔다.
- **[검수 §2-2] 생명의구슬 반동(`:301~306`)은 레드카드 판정 뒤로 두고, 끌려 나갈 예정이면 건너뛴다.** 순서: 파이프라인 → 자기과신류 → **레드카드 판정**(카드 소모, `pending.redCard`) → 반동 `if (… && !draggedOut)`. `draggedOut = 이번 판정에서 카드를 소모했고 !isForcedSwitchBlocked(src)`. 뿌리박기·흡반이면 카드만 소모되고 반동은 그대로 생긴다(반동으로 쓰러지면 정산 단계에서 사용자 생존 검사로 교체가 없고 기절 교체가 처리). 빗나감·무효·대타 적중은 레드카드가 서지 않으므로 반동이 기존대로 생긴다(A4 R3-q 회귀). 위 레드카드 판정의 "사용자 편 예비" 조건과 이 `draggedOut`의 예비 조건은 같은 값이다.

**④ 정산 단계 신설 `settleFutureSightReactions(c)`**와 `finishTurn` 순서 변경:
```
expireWeather → resolveEndOfTurnAndPerish → expireFieldAndWeather → expireSideEffects
  → settleFutureSightReactions → decideWinnerAndForcedSwitch → collectResult
```
- `decideWinnerAndForcedSwitch`를 `expire*` 뒤로 옮기는 것은 **출력 불변**이다(C2, 해시로 증명). `resolveEndOfTurnAndPerish`가 `c.winner`로 일찍 반환하는 경우(`:863`)는 `pending`이 비어 있어 정산이 아무것도 하지 않는다.
- 정산 순서: **레드카드 먼저**(홀더 키마다): 사용자 = `opponentKey(홀더)`가 살아 있고 `!isForcedSwitchBlocked(사용자)`이면 `forceRandomSwitch(..., { redCardItemName, endOfTurn: true })`. 사용자가 이미 기절했거나(생명의구슬 반동 등) 뿌리박기·흡반이면 카드는 이미 소모됐고 교체만 없다. **이어서 위기회피**: `pending.exit[k]`이고 `!isFainted(state[k])`이고 `hasLivingReserve(side k)`이면 확정한다 — 도망봉인·뿌리박기·흡반은 보지 않고 HP도 다시 보지 않는다. 확정은 `c.exitSwitch[k] = true`로 둔다.
- `decideWinnerAndForcedSwitch`: `forcedSwitch`를 "활성 기절 + 예비" **또는** `c.exitSwitch[k]`로 채운다. 활성이 이미 기절해 있으면 기절 교체가 대신하므로 `exitSwitch`는 무시한다(한 번만 요구). 레드카드로 끌려 들어온 포켓몬이 설치물로 쓰러졌으면 그 편은 기절 교체로 처리되고 승패 판정(`aHasReserve`)도 이 뒤에서 일어난다.
- `RunTurnOutcome.forcedSwitch` 문서 주석(`runTurn.ts:20~23`)을 "활성이 기절했거나, 위기회피로 살아 있는 활성이 물러나야 하는 편"으로 고친다. 형태 `{ a?: boolean; b?: boolean }`는 그대로다.

**⑤ 소비처**: 코드 확인 결과 전부 `applySwitch`만 부르므로 로직 변경 없다. 바꿀 곳은 문구·합성 카드뿐(§3-3). AI 쪽은 `search.ts:191~194`의 `livingBench` + `applySwitch`가 살아 있는 활성에도 그대로 동작하고, `chooseAiForcedSwitch`는 `evaluateOptions`의 교체 옵션을 고르는데 **활성이 살아 있을 때** 호출되는 것은 처음이라 시험 R3-x4로 확인한다. `useBattleAi.ts:71~73`의 "누가 먼저 고르나" 판정은 `faintOrder`에 없는(살아 있는) 편이면 건너뛰어 문제없다.

## 6. 위험과 영향
- **`forcedSwitch` 의미 확장**: 지금까지 "활성이 기절"이었고 이제 "살아 있는 활성의 교체 요구"도 싣는다. 소비처 전수 확인(§2)에서 기절 여부에 의존하는 코드는 없었고 바뀌는 것은 문구·합성 카드뿐이다. 구현 때 `grep forcedSwitch`·`pendingForcedSwitch`로 다시 대조한다.
- **`forceRandomSwitch` 이동**과 **`decide` 순서 변경**은 출력 불변 리팩토링이다. 단계 ②의 해시 불변이 증거다. 어긋나면 이 PR의 나머지를 진행하지 않고 원인을 찾는다.
- **UI**: 교체 줄 필터 변경(C4)은 렌더러 3곳과 연출 1곳을 건드린다. 레드카드 정상 경로(행동 직후 교체 줄)의 화면이 바뀌지 않아야 한다 — 화면 확인 항목.
- **저장 데이터**: 진행 중 `BattleState`는 저장하지 않는다. 저장된 대전 영상은 로그만 담고 새 필드(`endOfTurn`·`outgoingAlive`·`futureSightExitAbilityName`·`futureSightRedCardItemName`)는 모두 선택 필드다.
- **화면 확인(사용자 수행, 브라우저 검증은 위임)**: (1) 미래예지가 대상의 위기회피를 발동시킨 턴 — 패널 문구, 합성 카드 "▸ 가라!", 나가는 모션 (2) 레드카드 턴 종료 교체 줄과 연출이 최종 보드와 어긋나지 않는지 (3) 정상 공격의 레드카드·위기회피·탈출버튼 화면이 그대로인지. 작업 전 해당 feature 브랜치로 전환해 두고 `npm run dev` 주소를 안내한다.
