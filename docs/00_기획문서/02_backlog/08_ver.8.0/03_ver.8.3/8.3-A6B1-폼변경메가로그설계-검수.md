## 2. 상세

### 2-1. 기본 규칙 재확인
- [소스] `stancechange.onModifyMove`: 킬가르도가 아니거나 변신 상태면 무시. `category === 'Status'`이면서 킹실드가 아니면 무시. 킹실드면 실드폼, 그 밖에는 블레이드폼. 현재 폼과 같으면 `formeChange`를 부르지 않는다(= 연속 공격에 이벤트 없음, 설계의 "추가" 행과 같다).
- [소스] `runMove`의 순서는 `BeforeMove`(행동 불가·`beforeMoveCallback`) → PP 차감 → `useMove` → `useMoveInner`이고, `useMoveInner` 안에서 `ModifyMove`(폼 변경) → 로그 `|move|` → `!target` 판정(`-fail` + `[notarget]`) → `TryMove`(차지 기술 1턴째 등) → `tryMoveHit`(`onTry`·`onPrepareHit`·`TryHit`)이다.
- [실행] 행동 불가는 폼이 불변이다. 수면(`cant|slp`)·풀죽음(`cant|flinch`)·마비 행동불능(`cant|par`)·혼란 자해 모두 `-formechange` 없이 턴이 끝나고 끝 폼은 실드. → 시험 R8-b와 같다.

### 2-2. V1 — 행동 불가가 먼저다. 한계 문구의 근거만 고쳐야 한다
- [소스·실행] 수면 + 폴터가이스트(상대 도구 없음): `|cant|p1a: Aegislash|slp` 한 줄뿐이고 폼체인지는 없다. 풀죽음 + 폴터가이스트도 같다. → **설계서 V1의 전제("Showdown은 `BeforeMove`가 먼저라 폼이 안 바뀌는 게 맞는가?")는 맞다.**
- 원인 → 영향: 엔진은 사용 조건 평가(`checkUsageGates`)가 상태이상·풀죽음 판정보다 앞에 있으므로, 두 조건이 겹치면 엔진은 폼을 바꾸고 Showdown은 바꾸지 않는다. 설계 §3-1 한계의 **결과는 정확**하다.
- 그런데 한계 문구의 **근거가 현실과 다르다**: "(기습은 선공이어야 해서 풀죽음과 겹치지 않는다)"고 했지만 킬가르도는 기습을 배우지 못한다(§2-6). 실제로 겹치는 기술은 **폴터가이스트**(우선도 0)이고, 이 기술은 풀죽음·수면·마비·혼란과 모두 겹칠 수 있다. 즉 "겹치기 어렵다"는 안심은 근거가 없다. 상대 도구가 없는 상황(도구 소비·떨구기)이 전제라 빈도가 낮을 뿐이다.
- 권장: 한계로 두는 결정은 유지하되 문구를 "폴터가이스트(상대 도구 없음) + 행동 불가가 겹치는 턴"으로 고친다. 더 줄이고 싶으면 ③ 경로에서 **난수를 쓰지 않고 판정되는 행동 불가**(수면·빙결·풀죽음)일 때만 폼 변경을 건너뛰는 선택지가 있다. 마비·혼란·헤롱헤롱은 행동 불가 판정 자체가 난수라 이 방법으로 못 막는다. 순서를 완전히 맞추려면 사용 조건 평가를 옮겨야 하고, 그러면 수면 카운터 소모 시점이 바뀐다는 설계서의 판단이 맞다(별도 항목 권장).

### 2-3. V2 — `-notarget`은 `ModifyMove` 뒤라서 폼이 바뀐다
- [소스] `useMoveInner`: `runEvent('ModifyMove')` → `addMove('move', …)` → `if (!target) { [notarget]; -fail }`. 폼 변경이 먼저다.
- [실행] 상대(빠름)가 자폭으로 쓰러진 뒤 킬가르도가 섀도볼:
  ```
  |faint|p2a: Voltorb
  |-formechange|p1a: Aegislash|Aegislash-Blade||[from] ability: Stance Change
  |move|p1a: Aegislash|Shadow Ball|p2: Voltorb|[notarget]
  |-fail|p1a: Aegislash
  ```
- 설계 영향: 설계 ③("`needsLivingTarget` 처리에서도 폼을 바꾼다")이 그대로 맞다. 예외 불필요. §8 V2를 "Showdown 확인 — 바뀐다"로 닫는다.

### 2-4. 잠꼬대 — 호출 기술 기준은 맞고, 로그 줄 순서만 다르다
- [실행] 수면 + 잠꼬대 → 섀도볼:
  ```
  |cant|p1a: Aegislash|slp
  |move|p1a: Aegislash|Sleep Talk|p1a: Aegislash
  |-formechange|p1a: Aegislash|Aegislash-Blade||[from] ability: Stance Change
  |move|p1a: Aegislash|Shadow Ball|p2a: Snorlax|[from] move: Sleep Talk
  ```
  잠꼬대 → 변화기(칼춤)는 폼 불변. **블레이드 + 수면 + 잠꼬대 → 킹실드는 실드폼으로 돌아온다.**
- 원인 → 영향: 바깥 기술(잠꼬대)은 변화기라 `ModifyMove`가 무동작이고, 안쪽 호출 기술의 `useMove`에서 폼이 바뀐다. 설계 ② 2번(호출 확정 뒤 `effectiveMove`로 재호출)이 이 결과와 맞다.
- 낮은 우선순위 차이: Showdown은 폼체인지 줄이 **"잠꼬대 사용" 줄 뒤, 호출 기술 줄 앞**이다. 설계 Q27은 폼 줄을 행동의 첫 기술 줄 앞에 둔다(= 잠꼬대 줄보다 위). 화면 문구 순서만 다르고 규칙에는 영향이 없다. 맞추려면 `stanceChange`에 "호출 기술에서 발생" 표시가 필요한데, 비용 대비 효과가 작다. **알면서 두는 것(§9)에 한 줄 적으면 충분.**

### 2-5. 반동기와 차지기는 실제로 있다 (R8-i·R8-k 전제 정정)
- [소스·검증기] `gen9championsbssregmc` 검증기에서 킬가르도 + 파괴광선·기가임팩트·솔라블레이드는 팀 인원 오류만 나오고 기술 오류가 없다 → **합법**. (비교: 기습은 `Aegislash can't learn Sucker Punch.`)
- [실행] 파괴광선:
  ```
  |-formechange|p1a: Aegislash|Aegislash-Blade||[from] ability: Stance Change
  |move|p1a: Aegislash|Hyper Beam|p2a: Snorlax
  |-mustrecharge|p1a: Aegislash
  ...
  |cant|p1a: Aegislash|recharge        (다음 턴: 선택 가능한 기술은 Recharge 하나, 폼체인지 없음, 폼은 블레이드 유지)
  ```
  솔라블레이드 1턴째: `-formechange` → `|move|…|Solar Blade||[still]` → `-prepare`. 2턴째에는 이미 블레이드라 이벤트가 없다(설계의 "같은 폼이면 없음"과 일치, 공중날기로 한 실험도 같음).
- 설계 영향: 설계 ③의 "반동 턴 제외"와 ②-1의 "차지 1턴째도 이미 바뀜"이 모두 Showdown과 맞다. **다만 §5의 R8-i("킬가르도에 반동기는 없어 엔진 레벨 단위 확인으로 대체")와 R8-k("킬가르도가 쓴다고 가정")는 사실과 달라서**, 실제 기술로 시나리오를 만들 수 있다. 권장 문구:
  - R8-i: 파괴광선(또는 기가임팩트) → 다음 턴 반동: 이벤트 없음, 폼 블레이드 유지
  - R8-k: 솔라블레이드 1턴째: 블레이드 이벤트, 2턴째: 이벤트 없음

### 2-6. 킬가르도에 닿는 사용 조건 기술은 폴터가이스트와 코골기
- [소스] M-C 습득 기술 중 `onTry`/`onTryMove`가 있는 것: 폴터가이스트(도구 없으면 실패), 코골기(**깨어 있으면 실패**), 휴식·잠꼬대·와이드가드·라운드(변화기이거나 싱글에서 무관). 기습·펀치 계열 선제기는 없다.
- [실행] 코골기(깨어 있음): `-formechange` → `|move|…|Snore||[still]` → `-fail`. 폴터가이스트와 같은 순서.
- 영향: R8-h("기습 사용 조건 실패")는 해당 기술이 없으니 **폴터가이스트(R8-a와 중복)** 또는 **코골기(깨어 있을 때)**로 바꾼다. 엔진이 코골기의 "수면 중에만 성공"을 `usageCondition`으로 구현했는지 확인이 필요하다(구현 위치가 다르면 ③ 경로를 안 탄다). 수면 중 코골기는 성공해야 하며 폼은 블레이드가 된다.

### 2-7. 발버둥(PP 0)
- [실행] PP가 0인 킬가르도: `-formechange … Aegislash-Blade` → `|move|…|Struggle|…`. `ModifyMove`는 발버둥에도 적용된다(물리 기술).
- 설계 영향: 설계의 `applyStanceChange(c, move)`는 발버둥을 어떻게 다루는지 적혀 있지 않다. 엔진의 발버둥이 별도 합성 기술이면 `category`가 `physical`인지 확인한다. 시험 R8-l 추가를 권장한다(§3).

### 2-8. 그 밖에 확인한 것 (설계 영향 없음)
- 교체: 블레이드 상태에서 내려가면 벤치의 킬가르도는 **기본 폼(실드)**이다. 재등장 시 `-formechange` 줄 없이 `switch` 줄만 나온다 → Q24 "교체로 나오는 실드 복귀는 이벤트가 아니다" ✅. 폼은 **내려갈 때** 초기화되므로 교체 직후 상대편이 보는 모습도 이미 실드다.
- B1: Showdown은 메가진화를 큐의 `megaEvo`(order 104)로 처리하고 이후 속도순으로 정렬한다. 설계 B1은 기존 순서를 바꾸지 않고 로그를 구조화할 뿐이라 규칙 영향이 없다(B1-b "기존 스피드 순서와 같음"은 poke-builder 기존 동작 기준).
- R8-e(킹실드 실패에도 실드폼)는 시나리오사양서 검수 §3에서 확인을 마쳤다. 이번 `useMoveInner` 구조(폼 변경 < `onPrepareHit`)로 다시 한 번 근거가 확인된다.
