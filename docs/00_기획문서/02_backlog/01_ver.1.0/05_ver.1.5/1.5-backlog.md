# ver.1.5 백로그 — 코드 리팩토링

## 0. 이 문서의 성격

ver.1.4 완전 종료(dev==main, PR #96) 후, 기능 백로그가 소진되고 정적 검증(`tsc`/`oxlint`/
`validate:data`)도 전부 클린한 시점에 착수. 기능 추가가 아니라 **구조 정리·중복 제거** —
전체 코드베이스를 훑어 도출한 항목이다.

가장 크고 위험한 대상은 `src/lib/battleSimulator.ts`(6,884줄) 안의 `resolveAction` 함수
(약 3,400줄, `if`문 318개) — move id로 분기하는 switch가 아니라 `Move` 객체의 ~90개
optional 플래그를 순서대로 읽어나가는 하나의 긴 파이프라인이고, 지역변수 30여 개를 공유하는
클로저들이 얽혀 있어서 "안전하게 쪼개는 방법" 자체가 이번 리팩토링의 핵심 난제다.

테스트 러너가 없어 회귀 확인은 [[engine-smoke-test-via-vite-page]] 방식(dev 서버 페이지에서
`src/lib/*` 직접 import)에 의존한다. 그래서 실행 순서를 **기계적으로 안전한 것 → 로직 유지
추출 → 최고위험 구조분리** 순으로 엄격히 지킨다.

**브랜치 전략(2026-09-15 확정)**: `dev`에 바로 쌓기엔 부담스럽다는 사용자 판단으로, `dev`에서
`dev_repactoring` 중간 브랜치를 신설. §마다 독립 브랜치 → PR → `dev_repactoring` 스쿼시
머지로 쌓아가다가, ver.1.5 트랙이 전부 끝나면 `dev_repactoring`을 통째로 실사용 테스트한 뒤
`dev`에 머지 → 이후 평소대로 `dev`를 `main`에 머지한다. PR 워크플로 자체는
[[pr-merge-workflow]]와 동일(스쿼시 1커밋, 머지된 작업 브랜치는 로컬·원격 수동 삭제) —
머지 대상만 `dev` 대신 `dev_repactoring`으로 바뀐 것.

트랙 구성:
- **트랙 A** — `lib/battleSimulator.ts` + `lib/matchupEvaluator.ts` (엔진, 순차 진행 필수)

### §7. `resolveAction` 분리 (핵심, 여러 PR로 쪼갬)

**계획 대비 접근법 전면 수정 (2026-09-15, 착수 중 발견).** 원래 계획한 "7-1 스캐폴드(전체
리네임) → 7-2 리프 클로저 하나씩" 순서를 시도했으나, `applyEndurance` 등 "가장 작은" 클로저

`resolveHit`(별도 클로저)와도 공유하고 있었고, 이 6개 클로저(`resolveHit`·`applyEndurance`·
`applyDamageToDefender`·`checkDestinyBond`·`applyContactItemRecoil`·`triggerAbilityHitEffect`)
+ 그걸 부르는 바깥 오케스트레이션 코드가 단일타/다단히트/고정데미지/추가타(부자유친) 4곳의

자체가 이 구간엔 안 맞았다. 사용자와 논의 후 **자연스러운 경계 단위(여기선 ~820줄)로 한
번에 추출**하는 방식으로 전환, 이후 섹션들도 실제 코드를 먼저 읽고 경계를 확인한 뒤 그
크기 그대로 진행하기로 함(계획서의 7-2/7-3 절 구분은 더 이상 그대로 따르지 않는다).

사용 위치 비교) 후 tsc가 빠진/불필요한 항목을 잡아주는 식으로 반복 — `noUnusedLocals` +

특성만 관여하지만, 필드 자체는 나뉘어 있음). 미라화 문구 하나는 렌더 위치도 달랐다(다른

### §15. 렌더러 계열별 분리

`TurnSwitchLines`/`ActionMainLine`/타입변화·방어·상태·스탯변화·도구·특성반응 계열/

가장 큰 "특성/도구 계열"은 마지막. 검증: PR마다 S13 + 해당 계열 시나리오. §7처럼 여러 PR로

#### 15-1. `EndOfTurnLine`/`TurnFooterLines` 분리 — 완료

가장 작고 독립적인 두 계열부터 시작. 둘 다 `turn`(또는 `turn.endOfTurn`의 원소 하나)과
`turnName` 조회 함수만 있으면 렌더 가능하고, `action`/`turnIdx` 등 다른 섹션의 지역변수에
전혀 의존하지 않아 위험 없이 뗄 수 있었다.

- `TurnFooterLines({ turn, turnName })`: 턴 카드 맨 아래(필드/트릭룸/날씨 잔여턴·소멸,
  스크린/신비의부적 만료, 승패 판정) — `BattleTurnLog` 함수 바로 위에 신설.
- `EndOfTurnLine({ entry, turnName })`: `turn.endOfTurn.map()`의 원소 하나(회복/상태이상
  틱/카운트다운 등 §6의 22개 메커니즘에 대응하는 22가지 분기) — `.map()` 호출부에서
  `<EndOfTurnLine key={i} entry={e} turnName={turnName} />`로 교체, `key`는 컴포넌트가 아닌
  호출부(`.map`)가 그대로 짊어짐(React 관례).

원문 JSX는 한 글자도 안 고치고 함수 시그니처만 씌웠다(변수명 `e` → `entry` 구조분해 정도만
바뀜). `EndOfTurnLogEntry` 타입은 `battleSimulator.ts` 배럴이 재export하지 않아
`../types/battle`에서 직접 import 추가.

**검증**: `tsc -b`/`oxlint`/`validate:data`/`build` 전부 클린(신규 위반 없음). §14와 같은
방식으로 임시 스모크 파일(검증 후 삭제·미커밋)을 만들어 `BattleTurnLog`를 직접 렌더 —
`EndOfTurnLine`의 5개 분기(씨앗 흡수/뿌리박기 회복/변덕쟁이 랭크변화/멸망의노래 카운트/
상태이상 틱)와 `TurnFooterLines`의 6개 항목(필드/트릭룸/날씨 잔여턴, 스크린 만료, 신비의부적
만료, 승패)을 한 턴에 전부 채운 픽스처로 렌더한 결과 **전부 기대한 정확한 문구로 렌더**됨을
확인(콘솔 에러 0건).

**상태**: 15-1 완료.

#### 15-2. `TurnSwitchLines` 계열 분리 — 완료

교체 로그가 렌더되는 4곳(턴 시작 자발 교체 1곳 + 행동 이후 교체 3변종)을 대조한 결과, §14와
달리 **문구가 계열마다 실제로 달랐다**(누가 왜 교체됐는지에 따라: "돌아와!/가라!" 2줄 —
"트레이너의 곁으로 돌아간다!"(꼬리자르기) 추가 줄 — "강제로 교체되었다!/배틀에 끌려나왔다!"
— 레드카드는 그 앞에 "{defenderName}의 레드카드!"까지). 그래서 하나로 합치지 않고, 백로그의
"`TurnSwitchLines`"라는 이름 아래 4개의 개별 컴포넌트로 나눠 이름을 붙였다:
`PreMoveSwitchLines`(턴 시작, 유일하게 `action`과 무관)·`SelfSwitchAfterMoveLines`(유턴류
자체 교체)·`ForcedOpponentSwitchLines`(울부짖기류로 상대가 끌려나옴)·`RedCardSwitchLines`
(레드카드로 자신이 끌려나옴). 공통점(outName/inName 조회 + entryMessages 꼬리)만 있고 실제
헤더 문구는 계열마다 달라, 억지로 "content-only 함수 공유"(§14 방식)로 만들지 않고 각자
독립된 컴포넌트로 뒀다 — 문구가 같은 게 없으니 공유할 게 없다는 점 자체가 §14와의 차이.

**검증**: `tsc -b`/`oxlint`/`validate:data`/`build` 전부 클린. 임시 스모크 파일(검증 후
삭제·미커밋)로 4계열을 한 턴에 전부 채운 픽스처(턴 시작 교체 1건 + 자체교체 1건 + 강제교체
1건 + 레드카드교체 1건)를 렌더 — **4계열 전부 정확한 필터링**(각 교체가 해당하는 계열
컴포넌트에만 나타나고 다른 계열에는 안 나타남)**과 정확한 문구 구조**(josa·엔트리메시지
꼬리까지)로 렌더됨을 확인(콘솔 에러 0건, 포켓몬 이름 일부가 "포켓몬"으로 폴백된 건 픽스처의
가짜 id 때문이지 컴포넌트 로직과 무관).

**상태**: 15-2 완료.

**검증**: `tsc -b`/`oxlint`/`validate:data`/`build` 전부 클린. 실제 UI(배틀타워 화면)에서
라이브로 확인 — 포켓몬 선택 모달(커스텀 UI, 다이얼로그 아님)로 리자몽 선택 → 슬롯에 정상
반영 → `movelessWarningFor` 경고 문구("리자몽에게 기술을 최소 1개 배정해야...") 정상 노출
→ VS 버튼 비활성화 확인 → 슬롯 X(삭제) 버튼으로 `onClearPokemon` 정상 동작까지 확인(콘솔
에러 0건). "샘플로 저장"·"저장된 파티 불러오기" 버튼은 각각 `window.prompt`/모달 내부의
다이얼로그 버튼을 건드릴 위험이 있어([[native-dialog-blocks-chrome-automation]]) 클릭하지
않고 코드 리뷰로 대체(로직은 원문 그대로 `onSaveSlotAsSample`/`onOpenPicker`에 위임할 뿐).

**상태**: 16-1 완료.

#### 16-2. `BattleSelectScreen` 분리 — 완료

두 번째로 작은 화면인 선출(3+순서) 화면을 `BattleSelectScreen`으로 추출. 필요한 값 전부가
파생값/콜백 8개 props(`selection`/`buildableIndices`/`needsSelection`/`pokemonAt`/
`onToggleSelection`/`onBack`/`selectionComplete`/`onStartBattle`)로 표현 가능해
`BattleSetupScreen`처럼 훅 객체를 통째로 넘길 필요가 없었다(이 화면은 `setup`을 직접 쓰지
않고 파생 함수들만 씀). 원문 JSX는 변경 없음(`setSelecting(false)`→`onBack`,
`toggleSelection`→`onToggleSelection`, `startBattleWith(selection)`→`onStartBattle` 이름만
prop 시그니처에 맞춤). `pokemonAt`의 반환 타입을 위해 `types/pokemon`에서 `Pokemon` 타입
import 추가(기존엔 파일에 없었음).

**검증**: `tsc -b`/`oxlint`/`validate:data`/`build` 전부 클린. 실제 UI(배틀타워 화면)에서
라이브로 확인 — 내 파티 6마리(4마리 이상이라 선출 필요) + 상대 파티 1마리(3마리 이하라
자동 선출)를 콘솔에서 커스텀 UI 버튼을 순서대로 `.click()`해 채운 뒤(다이얼로그 없는
포켓몬/기술 피커만 사용) VS 버튼으로 선출 화면 진입 → "내 선출 0/3"·"상대 선출 빌드
순서대로 선출" 문구 정확히 노출 확인 → 포켓몬 3마리 순서대로 클릭해 `onToggleSelection`으로
1/2/3번 정확히 매겨지는지 확인 → "3/3" 카운트로 `selectionComplete`가 참이 되며 "대전 시작"
버튼이 활성화되는지 확인 → "뒤로" 버튼(`onBack`)으로 빌드 화면 복귀까지 확인(콘솔 에러 0건).

**상태**: 16-2 완료.

#### 16-3. `BattleBoard` 분리 — 완료, **§16 전체 종료**

마지막이자 가장 큰 화면(실시간 배틀판+HP게이지+상태태그+실능치+파티트래커+기술/교체

`inputMode`/`setInputMode`/`megaDeclared`/`setMegaDeclared`/`pendingForcedSwitch`/

개별 `useState`를 직접 다룸) 24개를 이름 그대로 각자 prop으로 넘겼다.

**타입 정리**: 그동안 `useState<{ a: ...; b: ... }>`로 인라인 선언되던 복합 상태 타입 5개

양쪽이 같은 타입을 참조하게 했다(타입 중복·드리프트 방지). `Dispatch`/`SetStateAction`
(react)도 새로 import.

**추출 기법**: §15-5(`ActionEffectLines`)와 동일하게 Node 스크립트로 정확한 줄 범위를
그대로 잘라 옮김(원문 JSX 텍스트 무변경, 들여쓰기만 조정). 스크립트의 "이전 블록" 경계
계산에서 실수로 `{battleState && (` 가드 줄이 중복 삽입되는 버그가 있었는데(오프바이원),
`tsc -b`가 그 즉시 구문 오류로 잡아줘서 한 줄 삭제로 바로 수정 — 이후 클린.

## §9. 명시적 보류/스킵 (트랙 D)

- **피커 모달 6종 통합** — 잘못된 CSS import(`MovePickerModal.css`를 5개 무관 컴포넌트가
  공유)만 바로잡고, 공용 `<PickerModal>` 베이스 추출은 다음에 그 컴포넌트를 건드릴 일이
  생길 때로 미룸.
- **`PartySlotCard`/`BattleSetupCard`/`MatchupSlotCard`** 공용 베이스, **프리셋 모달 2종
  통합**, **도감 페이지 2종 통합** — 전부 보류(prop 네이밍은 이미 통일돼 있어 나중에 하기
  쉬움, 지금 급하지 않음).
- **`move.ts`/`ability.ts`를 discriminated union으로 재구성** — 스킵. `resolveAction`의
  필드 접근 순서가 타입 선언 순서와 무관하다는 게 조사에서 확인됐음 — `resolveAction` 분리와
  별개 작업이고, 블라스트 반경 대비 이득이 낮음(가독성 목적뿐).
- **`scripts/validate-data.mjs`의 자체 `STAT_KEYS`/`TYPES` 중복** — 우선순위 낮음, §3에서
  거저 되면 같이 하고 아니면 스킵.
- **`strict`/`strictNullChecks` 활성화** — 범위 밖. `move.ts`/`ability.ts`가 optional
  필드투성이라 별도의 큰 작업.
- **`BattleLogPage`의 11-useState → useReducer 전환** — 보류. 동작에 인접한 구조 변경이라
  수동 스모크 테스트만으로 회귀를 잡기 어려움. §16의 화면 분리만으로 가독성 이득 대부분 확보
  가능.
