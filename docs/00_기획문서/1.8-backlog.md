# ver.1.8 백로그

## 0. 이 문서의 성격

ver.1.7(`1.7-backlog.md`, 착수 전 계획 문서)와 별개로, 사용자가 전달한
`백로그 1.8 수정 내용.txt`(다운로드 파일, 2026-09-18)를 이 프로젝트의 백로그 문서 형식으로
옮겨 적은 것이다. **아직 착수 전** — 다만 원본 텍스트를 그대로 옮기지 않고, 각 항목을
실제 코드·데이터와 대조하는 착수 전 조사를 먼저 진행했다(계획 문서보다 실제 코드가
우선이라는 이 프로젝트의 기존 원칙 — ver.1.5 §7, ver.1.6 §3-1/§3-4, ver.1.7 §0 등에서
반복 확인된 패턴). 그 결과 원본 요청 중 일부는 "문구만 바꾸면 되는 것"과 "실제로는 로직이
아예 없거나 이미 다른 형태로 구현돼 있는 것"이 섞여 있음이 드러났다 — 항목별로 구분해
기록했다.

원본 텍스트의 UI 문구(특성 설명문 등)는 사용자가 준 문구를 한 글자도 안 바꾸고 그대로
옮겼다 — 구현 시에도 그 문구를 정확히 반영할 것(조사 표기 자동 매칭 등 부가 지시사항 포함).

구성:
- **트랙 J — 포켓몬 도감 설명문(특성) 수정** (§1): 특성 문구 8건. 이 중 §1-1(갈지자걸음)·
  §1-9(총대장)는 착수 전 조사 결과 **엔진 로직이 아예 없는** 것으로 확정돼 단순 문구
  수정이 아니라 신규 구현이 필요하다. §1-5·§1-6(플러스·마이너스)은 이 프로젝트가
  63싱글배틀 전용이라 새 문구가 요구하는 "아군(동료)" 조건이 애초에 성립하지 않는 문제가
  있어 사용자 확인이 필요하다. 나머지(§1-2·§1-3·§1-4·§1-7·§1-8)는 이미 구현된 로직과
  대조해 문구만 바꾸면 되는 것으로 확인됐다.
- **트랙 K — 포켓몬 도감 페이지 폼별 종족값·특성 표기 정비** (§2): 대상 5종 전부 이미
  폼별 데이터(`formVariants`)와 렌더링 코드가 존재하지만, 종족값이 스탯별 상세가 아니라
  총합 숫자 하나로만 표기돼 실전에 중요한 스탯 배분 차이가 가려지는 문제를 발견했다 —
  원본 요청("표기가 안 됨")과 실제 코드 상태가 달라 작업 범위를 재정의할 필요가 있다.

**상태**: 트랙 J(PR #132)·트랙 K 완료. AI 후속 과제(아래 이관 절)는 파티 단위 평가부터 설계 합의 후 착수.

### ver.1.7에서 이관(2026-09-24)

ver.1.7(배틀타워 AI 어려움 난이도)을 마무리하며 넘긴 AI 후속 과제. 착수 순서·버전 배정은 착수 시 사용자와
다시 정한다(규모가 커서 별도 버전으로 뗄 수도 있음). 상세 근거는 `배틀AI 기획/battle-ai-decision-layer.md` §11-1.

- **파티 단위 평가**(가장 큰 구조적 한계): 지금 점수식은 현재 1:1 대면만 본다. 내 대기 포켓몬 × 상대 대기
  포켓몬 대면표로 모든 옵션을 평가해 "3:2에서 교환하면 2:1" 같은 수 싸움을 반영. 길동무 교환 후 판단((b)안),
  교체 후보 선택, 서로 피해를 못 주는 교착 대면(방어 연타·첫 선택지 반복) 처리가 여기에 걸려 있다.
- **쉬움 난이도(불완전 정보)** — 1.7 §3-4: 관측한 정보만 쓰는 상태 추적 + 안 드러난 기술 추정.
- **3선출 AI** — 1.7 §3-4: 6빌드 중 3마리 선출 규칙.
- **나머지 변화기**: 썰렁개그(날씨 + 교체 평가), 혼란·헤롱헤롱·하품·씨뿌리기·대타출동·강제교체·꼬리자르기 등.
- **도발 가치 보정**: 상대의 미래 랭크업·회복을 모델링해야 도발의 진짜 가치를 셀 수 있음.
- **파티 단위 평가 합의 사항(2026-09-24)**: 설계안(대면표 + 이어지는 대면 계산)으로 진행.
  ① 최종 점수 = 남은 HP 비율 합 차이 + λ × 남은 마릿수 차이(λ 시작값 0.5, 튜닝 대상) — (b)안.
  ② 상대의 다음 포켓몬 선택은 미니맥스(양쪽 다 최선). ③ PR 2개: (1) 대면표·이어지는 대면 계산 + 공격·교체·유턴류·
  강제 교체 연결, (2) 변화기·랭크업·회복·방어류·길동무 (b)안 + 설치기 이월 항 정밀화. 상세는 착수 시
  `배틀AI 기획/battle-ai-decision-layer.md` §4-5에 기록.
- **턴 종료 효과를 대면 계산에 반영**: 먹다남은음식·모래바람·그래스필드 회복 등(지금은 방어류 시뮬레이션 한 턴만 정확).

### §1-1. 갈지자걸음 — 문구 변경 + 신규 로직 필요

현재문구(확인됨, `abilities.json:785`): `혼란 상태일 때 회피율이 올라간다.`
수정문구: `혼란 상태일 때 회피율이 50% 상승한다(랭크업과 중첩 가능).`

**착수 전 코드 확인**: `abilities.json`에 이 특성 전용 필드가 전혀 없다 — 순수 플레이버
텍스트일 뿐, 실제로 회피율에 영향을 주는 엔진 로직이 없다(랭크 기반 회피율
`accuracyStages.evasion`과는 별개 축으로 추가 배율을 곱하는 처리 자체가 없음). 참고할 기존
패턴: 모래숨기(`weatherOpponentAccuracyMultiplier`, 날씨 조건부 상대 명중률 배율,
`types/ability.ts:219`)가 정확히 같은 구조("랭크 기반 회피율과는 별개 축이라 중첩 가능")를
쓰고 있음 — 이를 본떠 "혼란 상태 조건부" 버전(가칭 `confusedOpponentAccuracyMultiplier`)을
신설해 상대 명중률에 곱하도록 배선하면 됨(회피율 50% 상승 = 명중률 1/1.5배 환산, 정확한
공식은 착수 시 본가 자료 대조). **단순 문구 수정이 아니라 신규 엔진 로직 추가 작업.**

**대상**: `src/data/abilities.json`(문구), `src/types/ability.ts`(필드 신설), 명중률 계산부
(모래숨기 적용 지점과 동일한 곳 — 착수 시 위치 확인).

**상태**: 완료 — 본가 규칙(상대 명중률 ×0.5, 사용자 확정)으로 `Ability.confusedOpponentAccuracyMultiplier` 신설, `battle/hitChance.ts`(엔진·AI 공용 명중 계산)에서 방어측이 혼란일 때 모래숨기와 같은 축으로 곱한다(랭크 회피율과 중첩, 틀깨기류에 무시). 문구는 원문 그대로.

확인됨 — 오기/총대장/프레셔 조합, HP100·공135·방120·특공60·특방85·스피드50로 스탯 대조
완료) 두 곳뿐. `abilityModifiers.ts`, `battle/state.ts`, `battle/switching.ts` 어디에도
이 특성의 등장 시 스탯 상승 로직이 없다. **사용자가 요청한 "로직이 존재하는지 확인"이
정확했음 — 완전 미배선 상태.** 참고할 유사 기존 패턴: 성묘(기술 위력, "쓰러진 같은 편 수"
기반)가 `types/matchup.ts:43` 등에 이미 있어 "쓰러진 같은 편 수 카운트" 자체는 다른 곳에서
이미 세고 있을 가능성 있음(착수 시 그 카운트 소스를 재사용할 수 있는지 확인) — 다만 총대장은
"등장 시 스탯 상승"이라 매치업 페이지의 정적 위력 배율과는 적용 지점이 다르다(배틀 엔진의
등장 특성 처리부, `state.ts`/`switching.ts`의 다른 등장 특성들과 같은 자리로 추정).

**대상**: `src/data/abilities.json`(문구), 신규 로직(등장 특성 처리부 —
`src/lib/battle/state.ts`/`src/lib/battle/switching.ts`의 다른 등장 특성 배선 지점 참고),
로그 렌더(`src/lib/battleLogLabels.ts`/`BattleTurnLog.tsx` 계열, 조사 자동 매칭), 배틀타워
특성 발현 UI 문구 출력부(원인 미확인 — 착수 시 조사).

**상태**: 완료 — `Ability.powerBoostPerFaintedAlly`(0.1 × 수, 최대 5) 신설. 교체 등장 시(`switching.ts` `applyEntryAbilityOnSwitchIn`) 같은 편 기절 수를 세어 `BattleFighterState.supremeOverlordCount`에 두고, 1 이상이면 로그 2줄(`○○의 총대장!` / `○○은(는) 쓰러진 동료에게서 힘을 받았다!`, 조사 자동)을 낸다. 물러나면 초기화. 공격 위력 배율은 `battlePower.supremeOverlordMultiplier`로 엔진(`hitResolution`)과 AI(`ai/moveDamage`)가 공유 — 랭크가 아니라 위력 배율이라 랭크 UI에는 안 나온다. "특성 발현 문구가 없던" 원인은 로직 자체가 없었던 것. (AI는 교체 후보의 총대장 수를 아직 세지 않음 — 등장 전이라 1배로 봄.)

## 2. 트랙 K — 포켓몬 도감 페이지 폼별 종족값·특성 표기 정비

### §2-1. 루가루암·스트린더·에써르·대쓰여너·시비꼬 — 폼별 종족값·특성 표기

사용자 요청: 위 5종의 포켓몬 도감 페이지에 "각 모습별 종족값, 특성"이 표기되도록 할 것.

**착수 전 코드·데이터 확인 결과(원본 요청과 실제 상태가 다름)**: 5종 전부 `pokemon.json`에
`formVariants` 배열로 폼별 `types`/`baseStats`/`abilities`/`hiddenAbility`가 이미 데이터로
존재하고(루가루암 한낮/한밤중/황혼, 스트린더 하이/로우, 에써르·대쓰여너·시비꼬 수컷/암컷
또는 색상별), `PokedexPage.tsx:159`~`172`가 이 `formVariants`를 이미 렌더링하고 있다 —
"표기가 아예 없다"는 요청과 달리 **완전히 빈 기능은 아니다.**

다만 실제 렌더링 내용을 보면 진짜 문제가 보인다 — 종족값을 기본 폼에서 쓰는 `StatBars`
(HP/공격/방어/특공/특방/스피드 각각 막대로 보여주는 상세 컴포넌트, `:152`)가 아니라
**`Object.values(f.baseStats).reduce(...)`로 합산한 총합 숫자 하나**로만 보여준다(`:165`).
예를 들어 루가루암 한낮의모습(HP75/공115/방65/특공55/특방65/스피드112)과
한밤중의모습(HP85/공115/방75/특공55/특방75/스피드82)은 **종족값 합계가 487로 완전히
동일**하지만 스피드가 112 vs 82로 실전에 결정적인 차이가 있다 — 지금 UI로는 이 차이가
전혀 안 보인다. 특성 표기는 이미 폼별로 정상 나열되고 있어(`abilities`/`hiddenAbility`)
요청 중 "특성" 부분은 이미 충족된 것으로 보인다.

**정정된 작업 범위(안, 사용자 확인 필요)**: 원본 요청을 "완전 신규 기능 추가"가 아니라
"폼별 종족값 표기를 총합 숫자 → 기본 폼과 동일한 스탯별 상세 표기(`StatBars`류)로 개선"으로
재정의하는 것이 실제 코드 상태에 부합한다. 착수 시 사용자에게 이 해석이 맞는지 먼저 확인하고
진행할 것.

**대상**: `src/components/PokedexPage.tsx:159`~`172`(폼별 종족값 렌더 부분을 합계 텍스트에서
`StatBars`류 상세 표기로 교체).

**상태**: 완료 — 사용자 결정으로 "폼 탭 전환" 방식 채택. 상세 헤더 아래 폼 칩(기준 폼이 기본 선택)을 두고, 고른 폼 기준으로 아바타·타입·종족값 막대(`StatBars`)·방어 상성·특성(설명 포함)·기술 목록(폼 전용 learnset이 있으면 그것) 전체가 바뀐다. 기존 총합 숫자 목록은 제거. 종을 바꾸면 `key`로 다시 마운트돼 기준 폼으로 초기화.

## 3. 트랙 L — 엔진 미배선 기술(트랙 J 작업 중 발견)

### §3-1. 성묘 — 배틀 엔진에서 위력이 항상 50(쓰러진 동료 수 미반영)

**발견 경위**(2026-09-24, 트랙 J 총대장 배선 중): "쓰러진 같은 편 수" 카운트 소스를 찾다가 확인. `moves.json`의 성묘는
`power: 50`뿐이고 전용 필드가 없으며, `src/lib/battle/` 어디에도 성묘 처리가 없다 — **배틀타워에서는 동료가 몇 마리
쓰러졌든 항상 위력 50**. 매치업 페이지만 슬롯 토글(`graveVisitFaintedAllies` 0/1/2, `MatchupPage.tsx:84`)로
`50 + 50 × 수`를 반영하고 있다. 습득: 대쓰여너·묘두기.

**본가 규칙**: 위력 = 50 + 50 × (배틀 중 쓰러진 같은 편 수), 최대 300. 총대장과 달리 등장 시점이 아니라 **기술을 쓰는
시점**의 수를 센다(자신은 제외). 3선출에서는 최대 2마리라 50/100/150.

**수정 방향(안)**: 가변 위력 기술들(`preHitEffects.ts`의 기사회생·무게 비례류 등 `power` 덮어쓰기 지점)과 같은 자리에서
`sideOf(state, key).party`의 기절 수로 위력을 계산. 데이터는 `Move`에 `powerPerFaintedAlly`류 필드를 신설하거나 id
분기 — 착수 시 기존 가변 위력 기술의 표현 방식에 맞춘다. AI(`ai/moveDamage.ts`)도 같은 위력을 쓰도록 공유 헬퍼로.
regress 해시는 성묘가 무작위 파티에 들어가면 바뀔 수 있음(의도된 변경).

**대상**: `src/lib/battle/preHitEffects.ts`(위력 계산), `src/data/moves.json`·`src/types/move.ts`(필드 신설 시),
`src/lib/battle/ai/moveDamage.ts`, 시나리오 테스트.

**상태**: 미착수.
