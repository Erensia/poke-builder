# ver.1.5 백로그 — 코드 리팩토링

## 0. 이 문서의 성격

ver.1.4 완전 종료(dev==main, PR #96) 후, 기능 백로그가 소진되고 정적 검증(`tsc`/`oxlint`/
`validate:data`)도 전부 클린한 시점에 착수. 기능 추가가 아니라 **구조 정리·중복 제거** —
전체 코드베이스를 훑어 도출한 항목이다.

가장 크고 위험한 대상은 `src/lib/battleSimulator.ts`(6,884줄) 안의 `resolveAction` 함수
(약 3,400줄, `if`문 318개) — move id로 분기하는 switch가 아니라 `Move` 객체의 ~90개
optional 플래그를 순서대로 읽어나가는 하나의 긴 파이프라인이고, 지역변수 30여 개를 공유하는
클로저들이 얽혀 있어서 "안전하게 쪼개는 방법" 자체가 이번 리팩토링의 핵심 난제다.

테스트 러너가 없어 회귀 확인은 [[engine-smoke-test-via-vite-page]] 방식(dev 서버 페이지에서
`src/lib/*` 직접 import)에 의존한다. 그래서 실행 순서를 **기계적으로 안전한 것 → 로직 유지
추출 → 최고위험 구조분리** 순으로 엄격히 지킨다.

**브랜치 전략(2026-09-15 확정)**: `dev`에 바로 쌓기엔 부담스럽다는 사용자 판단으로, `dev`에서
`dev_repactoring` 중간 브랜치를 신설. §마다 독립 브랜치 → PR → `dev_repactoring` 스쿼시
머지로 쌓아가다가, ver.1.5 트랙이 전부 끝나면 `dev_repactoring`을 통째로 실사용 테스트한 뒤
`dev`에 머지 → 이후 평소대로 `dev`를 `main`에 머지한다. PR 워크플로 자체는
[[pr-merge-workflow]]와 동일(스쿼시 1커밋, 머지된 작업 브랜치는 로컬·원격 수동 삭제) —
머지 대상만 `dev` 대신 `dev_repactoring`으로 바뀐 것.

트랙 구성:
- **트랙 A** — `lib/battleSimulator.ts` + `lib/matchupEvaluator.ts` (엔진, 순차 진행 필수)
- **트랙 B** — `hooks/*` + `lib/storage.ts` (상태/저장소 중복 제거, A와 독립)

### §4. 레이어링 역전 수정 (타입 전용, 기계적)

`PartySlots`를 `types/party.ts`로 이동(partyAnalysis.ts/storage.ts/usePartyPresets.ts가
hooks/useParty.ts 대신 거기서 import) — 계획대로 완료.

`battleSimulator.ts`의 타입 블록 이동은 **착수 중 계획을 수정**했다: 원래 15개 전부를
`types/battle.ts`로 옮길 생각이었는데, `BattleFighterState`(`slot: EvaluatorSlot`)와
`SideInit`(`slots: EvaluatorSlot[]`)이 `EvaluatorSlot`(`lib/matchupEvaluator.ts`의 타입)에
직접 의존하고, `BattleSide`/`BattleState`/`ApplySwitchOutcome`/`RunTurnOutcome`/
`RunTurnPaused`/`RunTurnContext`도 그 둘을 통해 전이 의존한다는 걸 발견했다 — 이 8개를
그대로 옮기면 `types/battle.ts`가 `lib/matchupEvaluator.ts`를 import하게 돼서, 고치려던
"types가 lib에 의존하는" 역전을 없애는 게 아니라 **자리만 옮기는** 꼴이 된다.

그래서 범위를 실제로 `lib/` 의존이 전혀 없는 9개로 좁혔다: `HazardState`, `FighterKey`,
`ActionBlockReason`, `HitAbilityEvent`, `ActionLogEntry`, `EndOfTurnLogEntry`, `TurnResult`,
`SwitchLogEntry`, `TurnAction` — 전부 "로그/결과" 계열이라 `Move`/`BattleStatKey`/
`StatusConditionState` 등 순수 `types/*` 참조뿐이었다. 나머지 8개(살아있는 배틀 상태 축)는
`battleSimulator.ts`에 그대로 남기고 그 이유를 주석으로 남겼다 — `EvaluatorSlot` 자체를
`types/`로 옮기는 건 `matchupEvaluator.ts` 구조까지 건드리는 더 큰 작업이라 범위 밖.

다행히 애초에 고치려던 `types/battleVideo.ts` → `lib/battleSimulator.ts` 역전은 딱
`FighterKey`·`TurnResult`만 썼어서, 옮긴 9개 안에 둘 다 포함돼 목적은 그대로 달성했다
(`battleVideo.ts`가 이제 `../types/battle`에서 import). `battleSimulator.ts`는 옮긴
5개(`FighterKey`/`TurnAction`/`TurnResult`/`HitAbilityEvent`/`ActionLogEntry` — 외부
소비처가 있는 것만)를 `export type ... from "../types/battle"`로 재export해서
`BattleLogPage.tsx`/`BattleTurnLog.tsx`/`useBattleVideos.ts`는 import 경로를 안 바꿔도 되게
했다.

추출은 수작업 복붙 대신 Node 스크립트로 정확한 줄 범위를 잘라 옮기는 방식으로 진행(수천 줄
규모 JSDoc 주석까지 수동 전사하면 오타 위험이 크다고 판단). `npm run build` 결과물 해시가
이 작업 전후로 완전히 동일(`index-O8FdYPSX.js`, 바이트 단위 무변화)해서 런타임 동작이
전혀 안 바뀌었음을 스모크 테스트보다 더 강하게 증명함.

**상태**: 완료. 검증: tsc -b/oxlint/validate:data/build 전부 클린 + 빌드 산출물 해시 동일.

### §5. josa 중복 제거 + "미러" 중복 3건 통합

battleSimulator.ts:660-684의 자체 구현 `roEuro`/`eulReul`/`eunNeun` 삭제, `lib/josa.ts`
import로 교체. 이어서 친밀도/허슬/스크린 배율 계산을 `battlePower.ts`에 공용 함수로
추출(기존 `resolveMoveContext` 공유 패턴과 동일하게), battleSimulator.ts·matchupEvaluator.ts
양쪽이 호출하도록.

**두 구현이 실제로 어긋나 있었는지 확인**: 친밀도·허슬은 완전히 동일한 로직이라 그대로
공용 함수로 추출. 스크린은 구조가 달랐다 — battleSimulator는 진영 상태(스크린+오로라베일이
동시에 걸려있을 수 있음)에서 두 불리언을 뽑고, matchupEvaluator는 1턴 스냅샷이라 단일
`screen` 옵션 하나에서 뽑는다. 두 입력 모양을 억지로 하나로 합치는 대신, 실제 중복이던
곱셈 공식 `(카테고리스크린?2:1)×(오로라베일?2:1)`만 `screenMultiplierFromFlags`로
공유하고, "두 불리언을 어떻게 도출하는지"는 각자 유지 — 케이스 분석 결과 원래 두 로직은
모든 입력 조합에서 동일한 값을 냈음(어긋남 없었음).

**검증**: 로직 치환 3건 전부 Node로 전수(exhaustive) 프로퍼티 테스트 — josa 3함수는 한글
전체 음절 범위(11172자) 샘플링, 스크린 배율은 가능한 전 조합(2×4×4=32가지) 비교, 전부 신구
일치 0건 불일치. tsc -b/oxlint/validate:data/build 클린. (참고: 플랜엔 S10 실브라우저
스모크도 적혀 있었으나, 추출이 전수 테스트로 수학적 동치가 증명되는 순수 함수 치환이라
브라우저 스모크는 생략 — 필요하면 추가로 돌릴 수 있음.)

**상태**: 완료.

통합. 두 경로가 이미 미묘하게 어긋났을 수 있으니 주의(§5와 같은 이유). 검증: S4+S9 양쪽 렌더
결과 diff.

**상태**: 미착수.

### §15. 렌더러 계열별 분리

`TurnSwitchLines`/`ActionMainLine`/타입변화·방어·상태·스탯변화·도구·특성반응 계열/

**상태**: 미착수.

### §16. `BattleLogPage.tsx` 화면 분리

`BattleSetupScreen`/`BattleSelectScreen`/`BattleBoard`(presentational)로, `BattleLogPage`는
11개 useState+핸들러를 쥔 오케스트레이터로 남김. **useReducer 전환은 하지 않음**(§9 참고).
검증: S14 전체 UI 플로우.

**상태**: 미착수.

## §9. 명시적 보류/스킵 (트랙 D)

- **피커 모달 6종 통합** — 잘못된 CSS import(`MovePickerModal.css`를 5개 무관 컴포넌트가
  공유)만 바로잡고, 공용 `<PickerModal>` 베이스 추출은 다음에 그 컴포넌트를 건드릴 일이
  생길 때로 미룸.
- **`PartySlotCard`/`BattleSetupCard`/`MatchupSlotCard`** 공용 베이스, **프리셋 모달 2종
  통합**, **도감 페이지 2종 통합** — 전부 보류(prop 네이밍은 이미 통일돼 있어 나중에 하기
  쉬움, 지금 급하지 않음).
- **`move.ts`/`ability.ts`를 discriminated union으로 재구성** — 스킵. `resolveAction`의
  필드 접근 순서가 타입 선언 순서와 무관하다는 게 조사에서 확인됐음 — `resolveAction` 분리와
  별개 작업이고, 블라스트 반경 대비 이득이 낮음(가독성 목적뿐).
- **`scripts/validate-data.mjs`의 자체 `STAT_KEYS`/`TYPES` 중복** — 우선순위 낮음, §3에서
  거저 되면 같이 하고 아니면 스킵.
- **`strict`/`strictNullChecks` 활성화** — 범위 밖. `move.ts`/`ability.ts`가 optional
  필드투성이라 별도의 큰 작업.
- **`BattleLogPage`의 11-useState → useReducer 전환** — 보류. 동작에 인접한 구조 변경이라
  수동 스모크 테스트만으로 회귀를 잡기 어려움. §16의 화면 분리만으로 가독성 이득 대부분 확보
  가능.
