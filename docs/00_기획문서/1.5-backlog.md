# ver.1.5 백로그 — 코드 리팩토링

## 0. 이 문서의 성격

ver.1.4 완전 종료(dev==main, PR #96) 후, 기능 백로그가 소진되고 정적 검증(`tsc`/`oxlint`/
`validate:data`)도 전부 클린한 시점에 착수. 기능 추가가 아니라 **구조 정리·중복 제거** —
전체 코드베이스를 훑어 도출한 항목이다.

가장 크고 위험한 대상은 `src/lib/battleSimulator.ts`(6,884줄) 안의 `resolveAction` 함수
(약 3,400줄, `if`문 318개) — move id로 분기하는 switch가 아니라 `Move` 객체의 ~90개
optional 플래그를 순서대로 읽어나가는 하나의 긴 파이프라인이고, 지역변수 30여 개를 공유하는
클로저들이 얽혀 있어서 "안전하게 쪼개는 방법" 자체가 이번 리팩토링의 핵심 난제다.

테스트 러너가 없어 회귀 확인은 [[engine-smoke-test-via-vite-page]] 방식(dev 서버 페이지에서
`src/lib/*` 직접 import)에 의존한다. 그래서 실행 순서를 **기계적으로 안전한 것 → 로직 유지
추출 → 최고위험 구조분리** 순으로 엄격히 지킨다.

**브랜치 전략(2026-09-15 확정)**: `dev`에 바로 쌓기엔 부담스럽다는 사용자 판단으로, `dev`에서
`dev_repactoring` 중간 브랜치를 신설. §마다 독립 브랜치 → PR → `dev_repactoring` 스쿼시
머지로 쌓아가다가, ver.1.5 트랙이 전부 끝나면 `dev_repactoring`을 통째로 실사용 테스트한 뒤
`dev`에 머지 → 이후 평소대로 `dev`를 `main`에 머지한다. PR 워크플로 자체는
[[pr-merge-workflow]]와 동일(스쿼시 1커밋, 머지된 작업 브랜치는 로컬·원격 수동 삭제) —
머지 대상만 `dev` 대신 `dev_repactoring`으로 바뀐 것.

트랙 구성:
- **트랙 A** — `lib/battleSimulator.ts` + `lib/matchupEvaluator.ts` (엔진, 순차 진행 필수)

### §7. `resolveAction` 분리 (핵심, 여러 PR로 쪼갬)

**계획 대비 접근법 전면 수정 (2026-09-15, 착수 중 발견).** 원래 계획한 "7-1 스캐폴드(전체
리네임) → 7-2 리프 클로저 하나씩" 순서를 시도했으나, `applyEndurance` 등 "가장 작은" 클로저
4개조차 `hitSubstitute`/`substituteBroke`/`defenderHpBeforeLastHit` 같은 바깥 변수를
`resolveHit`(별도 클로저)와도 공유하고 있었고, 이 6개 클로저(`resolveHit`·`applyEndurance`·
`applyDamageToDefender`·`checkDestinyBond`·`applyContactItemRecoil`·`triggerAbilityHitEffect`)
+ 그걸 부르는 바깥 오케스트레이션 코드가 단일타/다단히트/고정데미지/추가타(부자유친) 4곳의
호출부에 걸쳐 서로 뗄 수 없게 얽혀 있다는 걸 확인 — "가장 작고 독립적인 것부터"라는 전제
자체가 이 구간엔 안 맞았다. 사용자와 논의 후 **자연스러운 경계 단위(여기선 ~820줄)로 한
번에 추출**하는 방식으로 전환, 이후 섹션들도 실제 코드를 먼저 읽고 경계를 확인한 뒤 그
크기 그대로 진행하기로 함(계획서의 7-2/7-3 절 구분은 더 이상 그대로 따르지 않는다).

"통째로 함수로 감싸기" 방식. 다만 이번엔 스크립트로 입출력 변수를 자동 판별(선언 위치 vs
사용 위치 비교) 후 tsc가 빠진/불필요한 항목을 잡아주는 식으로 반복 — `noUnusedLocals` +
"Cannot find name" 두 방향 다 컴파일러가 강제해줘서, 83개(입력 25 + 출력 58)에 달하는
변수 목록도 끝까지 정확하게 맞출 수 있었다. 이 과정에서 찾은 진짜 버그 소지 하나: 세
필드(`mentalMoveBlockedByAbilityName` 등)는 이 구간에서 항상 `undefined`/`0`으로 초기화만
되고 실제로는 훨씬 뒤(변화기 효과 적용부)에서만 쓰인다는 게 oxlint(`no-unassigned-vars`)로
드러나서, 해당 선언들은 `resolveAction`에 그대로 남기고 추출 대상에서 뺐다.

#### 7-1. `resolveHitAndApplyDamage` 추출 완료

`resolveAction`(원래 ~3,400줄) 중 "명중 판정 이후 ~ 길동무 판정까지"(원본 기준 2583~3401줄,
~820줄) — `resolveHit`·`applyEndurance`·`applyDamageToDefender`·`checkDestinyBond`·
`applyContactItemRecoil`·`triggerAbilityHitEffect` 6개 클로저가 전부 이 안에 포함된
"히트 판정 + 데미지 적용 + 그 직접 결과" 단일 클러스터 — 를 신설 `resolveHitAndApplyDamage`
함수로 추출. `resolveAction`은 이 구간을 `let { ...58개 출력 } = resolveHitAndApplyDamage({ ...25개 입력 })`
한 번의 호출로 대체. 6개 클로저는 여전히 이 새 함수 안에 중첩된 채로 남아있음(추가로 더
쪼개는 건 다음 §7 항목들 몫).

`resolveAction` 자체 길이: 원래 ~3,400줄 → 이번 추출로 ~2,570줄(약 820줄, 24% 감소).

**검증**: git worktree A/B 비교. 21개 시나리오(S2·S7은 랜덤시드 10~15개씩 추가)로 이 구간이
다루는 거의 모든 분기를 커버 — 무보정 데미지, 접촉 반동 도구+특성(울퉁불퉁멧+정전기),
다단히트(스케일샷), 고정데미지(나이트헤드), 기합의띠/옹골참(확정 버팀), 기합의머리띠(확률
버팀, 15시드), 길동무, 카운터, 메탈버스트, 부자유친 추가타, 매지션 도구강탈, 대타
부분흡수·파괴 양쪽, 생명의구슬 반동, 조개껍질방울 회복, 흡수기(기가드레인), 반동기
(우드해머), 죽기살기, 발버둥 반동. **21개 시나리오 전부 해시 완전 일치**(0건 불일치).
tsc -b/oxlint/validate:data/build 전부 클린.

**상태**: 7-1 완료. 나머지(§1610~2467 사전 처리 구간, `resolveAction` 잔여 ~2,570줄의

## §9. 명시적 보류/스킵 (트랙 D)

- **피커 모달 6종 통합** — 잘못된 CSS import(`MovePickerModal.css`를 5개 무관 컴포넌트가
  공유)만 바로잡고, 공용 `<PickerModal>` 베이스 추출은 다음에 그 컴포넌트를 건드릴 일이
  생길 때로 미룸.
- **`PartySlotCard`/`BattleSetupCard`/`MatchupSlotCard`** 공용 베이스, **프리셋 모달 2종
  통합**, **도감 페이지 2종 통합** — 전부 보류(prop 네이밍은 이미 통일돼 있어 나중에 하기
  쉬움, 지금 급하지 않음).
- **`move.ts`/`ability.ts`를 discriminated union으로 재구성** — 스킵. `resolveAction`의
  필드 접근 순서가 타입 선언 순서와 무관하다는 게 조사에서 확인됐음 — `resolveAction` 분리와
  별개 작업이고, 블라스트 반경 대비 이득이 낮음(가독성 목적뿐).
- **`scripts/validate-data.mjs`의 자체 `STAT_KEYS`/`TYPES` 중복** — 우선순위 낮음, §3에서
  거저 되면 같이 하고 아니면 스킵.
- **`strict`/`strictNullChecks` 활성화** — 범위 밖. `move.ts`/`ability.ts`가 optional
  필드투성이라 별도의 큰 작업.
- **`BattleLogPage`의 11-useState → useReducer 전환** — 보류. 동작에 인접한 구조 변경이라
  수동 스모크 테스트만으로 회귀를 잡기 어려움. §16의 화면 분리만으로 가독성 이득 대부분 확보
  가능.
