## 1. 포켓몬 프로필 — 이니셜 뱃지 → 실제 포켓몬 이미지  *(post-1.0 §2에서 이월)*

> 원문 전체는 `post-1.0-backlog.md` §2 참조. 아래는 요약 + 미결정 사항.

### 1-1. 현재 방식

포켓몬 아바타는 전부 **이름 첫 글자 + 타입 색 그라디언트**로 그려진다.
`pokemon.name.at(0)` + `linear-gradient(135deg, TYPE_COLORS[type0], TYPE_COLORS[type1 ?? type0])`.

등장 위치 5곳:

| 위치 | 클래스 | 크기 | 모양 |
|---|---|---|---|
| 파티 빌더 슬롯 (`PartySlotCard.tsx`) | `.party-slot-avatar` | 36×36 | radius 10px |
| 배틀 셋업 카드 (`BattleSetupCard.tsx`) | `.party-slot-avatar` 재사용 | 36×36 | radius 10px |
| 매치업 슬롯 (`MatchupSlotCard.tsx`) | `.matchup-slot-avatar` | 42×42 | radius 11px |
| 도감 리스트 (`PokedexPage.tsx`) | `.pokedex-list-avatar` | 28×28 | 원형 |
| 도감 상세 (`PokedexPage.tsx`) | `.pokedex-detail-avatar` | 56×56 | 원형 |

### 1-2. 목표

각 크기에 맞는 포켓몬 이미지로 교체. 이미지가 없거나 로드 실패 시 **현재 이니셜+그라디언트로 폴백**.

### 1-3. 잠정 방향 (post-1.0 메모에서 제안, 미확정)

- `pokemon.json`에 `dexNo`(전국도감 번호) 필드 추가 → 로스터 병합 스크립트에 `dexNo` 채우는 단계 추가.
- 외부 CDN 참조(PokéAPI 스프라이트 / Pokémon HOME 렌더) + 이니셜 뱃지 폴백.
- 공유 `<PokemonAvatar pokemonId size formLabel />` 컴포넌트로 5곳 통합
  (현재 `avatarGradient` 계산이 컴포넌트마다 중복).
- `<img loading="lazy" onError={폴백}>`, `object-fit: contain`, 배경에 기존 그라디언트 옅게.

### 1-4. 결정해야 할 것

- **이미지 소스 & 키잉**: (a) `dexNo` 필드 + CDN 참조 / (b) `public/sprites/` 번들 / (c) 외부 CDN
  직접 참조. 오프라인·속도·안정성 트레이드오프.
- **스프라이트 스타일**: 28px는 박스 아이콘, 36~56px는 gen5 도트 / Showdown / HOME 렌더 중 택.
  픽셀 아트면 작은 크기에서 `image-rendering: pixelated`.
- **메가 폼**: `megaEvolutions[].form`(예: `"리자몽-메가X"`)도 별도 이미지 매칭, 없으면 기본 폼 폴백.
- **라이선스**: 포켓몬 스프라이트/아트워크는 저작권물. 개인·비영리 토이 프로젝트 범위 확인.
- 로스터 현황: 약 228마리, `dexNo` 필드 없음, 세대별 확장 중.

관련: `docs/00_기획문서/engine-smoke-test-via-vite-page` 방식으로 렌더 검증.

## 2. UI 개선 (2026-09-07 접수)

### 2-1. 파티 빌더 타입 상성표 — 포켓몬별 약점 요약 "종합" 행 추가

> **✅ 구현 (2026-09-07, PR #19 dev 머지).** 표 `<tfoot>`에 종합 행 추가.
> - 헤더 이름 구분: 오른쪽 열 `종합` → **`종합(상성별)`**, 마지막 행 라벨 **`종합(포켓몬별)`**.
> - `종합(포켓몬별)` 셀 = **그 포켓몬의 약점(×2·×4) 타입 수**(숫자만). `×4`도 타입 1개로 집계,
>   `¼`·면역 등 저항은 세지 않음. 취약/보통/강점 판정은 쓰지 않음(그 규칙을 세로로 재사용하면
>   대부분 "강점"으로 쏠려 무의미했음). 검증: 이어롭-메가 = 격투·비행·에스퍼·페어리 → `4`.
> - `computePartyDefenseMatrix`가 `memberWeakCounts: number[]` 추가 반환. 좌하단 코너 셀은 공란.
> - **후속 (2026-09-07, PR #21):** 종합(포켓몬별) 행 배경을 헤더와 동일한 `--surface-2`로 통일
>   (숫자 셀만 흰색으로 튀던 문제). 그 외 표 색상·디자인 정리는 별도 후속으로 미룸(사용자 결정).

#### 현재 방식

`TypeCoverageSummary` = **포켓몬(열) × 공격타입 18종(행)** 매트릭스. 셀은 방어 배율(`½`/`¼`/`×2`/`×4`/
`면역`, 등배는 공란). 오른쪽 끝 **"종합" 열**이 그 타입 행에 대해 파티 전체가 `취약`/`보통`/`강점`
중 무엇인지 표기한다. 판정 규칙(`post-1.0` §1-3, 2026-09-02 확정): 그 행에서 약점 인원 `w`, 저항
인원 `r`(면역 포함)일 때 `강점 = r≥w ∧ r≥2` / `취약 = w−r≥2` / 그 외 `보통`.

즉 **가로 방향(타입별 파티 유불리)만 요약되고, 세로 방향(포켓몬 한 마리의 약점 분포)은 요약이 없다.**

#### 기대

표의 **가장 마지막 행**에도 "종합" 요약을 추가한다. 이 행의 각 셀은 **그 열 포켓몬 한 마리의 방어
상성 종합** — 약점이 얼마나 많은지 / 얼마나 단단한지를 한눈에 보여준다. 목적은 "타입별 파티
유불리"뿐 아니라 **개별 포켓몬의 약점 상성 파악**.

#### 대상 코드

- `src/components/TypeCoverageSummary.tsx` — `<tbody>` 마지막에 요약 행, 헤더 `<th>종합</th>` 대응.
- `src/components/TypeCoverageSummary.css` — 마지막 행 강조 스타일(`tbody tr:last-child` 규칙 이미 있음, 조정 필요).
- `src/lib/partyAnalysis.ts` — `computePartyDefenseMatrix`가 열별(포켓몬별) 요약도 계산해 반환
  (`PartyDefenseMatrix`에 `memberVerdicts: MemberDefenseSummary[]` 추가).

#### 설계 논점 / 결정해야 할 것

- **셀에 무엇을 표기?** 후보:
  - (a) 약점 수만 (`약점 3`) — 가장 단순.
  - (b) 약점 수 / 저항 수 (`3약 · 4저`).
  - (c) 열 verdict 라벨 (`무름` / `보통` / `단단` 같은 3단계) + 색상(기존 `tm-verdict-*` 재사용).
  - (d) (b)+(c) 조합.
- **열 verdict 규칙**: 행 규칙(`r≥w ∧ r≥2` / `w−r≥2`)을 세로로 그대로 재사용할지, 한 마리
  기준에 맞는 별도 임계값을 둘지(한 마리는 표본이 18타입으로 크므로 임계가 달라야 자연스러움).
  예: `×4` 존재 시 가중, 약점 4개 이상이면 `무름` 등. → **규칙 확정 필요.**
- **좌하단 코너 셀**(행 헤더 열 × 마지막 행 교차): 빈 칸 vs `"종합"` 라벨.
- **약점 타입 나열**: 셀 hover 툴팁으로 그 포켓몬의 `×2`/`×4` 타입 목록을 보여줄지.
- **정렬 없음** 원칙 유지(`post-1.0` §1-5) — 요약 행은 항상 맨 아래 1행 고정.

### 2-2. 배틀타워 셋업 — "대전 시작" 버튼 제거, VS 클릭으로 배틀 시작

> **✅ 구현 (2026-09-07, PR #20 dev 머지).** `.battle-setup-vs`를 `<button>`으로 —
> `onClick={handleProceed}` · `disabled={!canProceed}`. 셋업 화면의 별도 `.battle-start-button`
> 제거(선출 화면 쪽은 유지). "다음 (선출)"/"대전 시작" 구분은 `aria-label`·`title`로만,
> 비활성 시 `"양쪽 파티를 먼저 완성하세요"`. `:hover` 그라디언트 채움 / `:active` 축소 /
> `:disabled` opacity 0.4, skew 유지. **사용자 확인 완료, 지적 없음.**

#### 현재 방식

`BattleLogPage`의 셋업 화면 `.battle-setup-center`에 두 요소가 세로로 있다:

1. `.battle-setup-vs` — `<div aria-hidden="true">VS</div>` (레터마크, `skewX(-8deg)`, 클릭 불가).
2. `.battle-start-button` — 그 아래 별도 버튼. 라벨은 선출 필요 여부에 따라
   `"다음 (선출)"` 또는 `"대전 시작"`, `disabled = !canProceed`, `onClick = handleProceed`.

(코드: `BattleLogPage.tsx` 약 583~597행 / `BattleLogPage.css` 약 70~108행.)

#### 기대

**`.battle-start-button`을 삭제하고, VS 레터마크 자체를 누르면 배틀이 시작(=`handleProceed`)되도록** 변경.

#### 세부 / 결정해야 할 것

- `.battle-setup-vs`를 `<div aria-hidden>` → `<button type="button">`로 교체. `aria-hidden` 제거,
  접근성 이름 제공(`aria-label`), `cursor: pointer`, `:disabled` 스타일, 포커스 링(skew 변형과
  포커스 아웃라인 겹침 확인).
- **`disabled = !canProceed`** 유지 — 양측 빌드가 유효하지 않으면 못 누름.
- **이원 라벨 처리**: 지금은 버튼 텍스트로 `"다음 (선출)"` / `"대전 시작"`을 구분했다. VS만 남으면
  그 정보가 사라짐. 후보:
  - VS 아래에 작은 캡션 텍스트(`다음: 선출` / `대전 시작`)를 두고 클릭 대상은 VS.
  - VS의 `aria-label` / `title`에만 반영하고 시각적으로는 VS만.
  - VS 밑에 상태 문구(`양쪽 파티를 완성하세요` 등 disabled 사유)까지 노출.
  → **표시 방식 확정 필요.**
- **선출 화면(`.battle-select-actions`)의 "대전 시작" 버튼**은 이번 요청 범위 밖(셋업 화면 한정으로
  해석)이라 **유지**. 일관성을 위해 그쪽도 바꿀지는 별도 확인.
- GIF/스크린샷으로 클릭 → 배틀 진입 흐름 확인.

### 2-4. 배틀 로그 — 변환자재/리베로 타입 변경 문구를 별도 줄로

#### 현재 방식

`BattleLogPage.tsx`의 액션 로그 메인 줄(`.battle-turn-line`, ≈1365행)에서 데미지·다단히트
표기 **뒤에 `·`로 이어붙여** 인라인 출력한다:

```
마스카나의 트리플악셀 — 87 데미지 (53.7%) · 3타 명중 · 변환자재 발동! 타입이 얼음으로 바뀌었다!
```

(`action.changedOwnTypeAbilityName` / `action.changedOwnTypeTo` / `roEuro` 사용.)

#### 기대

데미지 줄과 분리해 **자체 줄**로:

```
마스카나의 변환자재!
마스카나는 얼음타입이 되었다!
```

- 급소(`급소에 맞았다!`)·상성 문구가 이미 메인 줄 아래 별도 `.battle-turn-line`으로 빠져 있으니
  같은 패턴을 따른다(≈1380행대).
- 문구도 `~ 발동! 타입이 ~로 바뀌었다!` → 2줄(`~의 변환자재!` + `~는 ~타입이 되었다!`)로 교체.
  조사 처리는 기존 `eunNeun` 헬퍼 재사용.

#### 대상 코드

- `src/components/BattleLogPage.tsx` — `action.changedOwnTypeTo` 인라인 렌더(≈1365~1371행)를
  메인 줄에서 빼서 별도 줄 블록으로.

### 2-5. 배틀 로그 — 연타(멀티히트) 기술 적중 횟수를 별도 줄로

#### 현재 방식

`action.hitCount`가 있으면 데미지 표기 뒤에 `· 3타 명중`을 인라인으로 붙인다
(`BattleLogPage.tsx` ≈1205행). 급소가 있으면 `(급소 포함)`도 인라인.

```
마스카나의 트리플악셀 — 87 데미지 (53.7%) · 3타 명중
```

#### 기대

적중 횟수를 데미지 줄에서 빼서 **자체 줄**로:

```
마스카나의 트리플악셀 — 87 데미지 (53.7%)
3번 맞았다!
```

- 급소 포함 표기(`action.critical`)를 이 새 줄에 어떻게 얹을지 확인 필요
  (현재 다단히트는 급소를 인라인 `(급소 포함)`으로 처리 — ≈1381행 조건이 `hitCount === undefined`라
  별도 "급소에 맞았다!" 줄을 안 냄). `3번 맞았다! (급소 포함)` 정도로 이어가면 됨.
- `N타 명중` → `N번 맞았다!` 문구 변경.

#### 대상 코드

- `src/components/BattleLogPage.tsx` — `action.hitCount` 인라인 렌더(≈1205~1207행) 제거 +
  데미지 줄 아래 별도 줄, 급소 인라인 조건(≈1381행) 정리.

### 2-14. 능력 포인트 에디터 — 로딩바형 슬라이더 + 매직 넘버·성격 보정 표시 (2026-09-08)

> **✅ 구현 (브랜치 `feat/points-slider`).**

`PointsEditorModal`의 `−`/숫자입력/`+`와 실수치 사이 빈 공간에 로딩바 형태 슬라이더를 넣었다.

- **슬라이더**: 스탯별 상한(32) 기준의 진행바. 클릭·드래그·방향키(←→=±1, Home/End)로 포인트 배분.
  방향키는 `onStep`(델타)으로 처리해 키 반복에도 안전. `role="slider"` + aria 값.
- **매직 넘버**: 그 스탯에서 포인트를 올리는 순간 실수치가 **+2** 되는 지점(성격 ×1.1 보정에서만
  생김)에 굵은 흰색 눈금. `computeRealStats`와 같은 공식으로 인접 차이를 재서 찾으므로 공식이
  바뀌어도 자동. HP·무보정·×0.9 스탯은 눈금 없음.
- **성격 보정 색상**: 상승 스탯 라벨 = 붉은색(`--danger`) + ▲, 하락 스탯 = 파란색(`--blue`) + ▼.
  모달 하단에 `▲ 성격명: 스탯 +10% · ▼ 스탯 −10%` 안내 줄.
- **예산 상한 표시**: 지금 남은 총 예산으로는 못 올리는 구간을 옅은 틴트 + 점선으로.
- 대상: `src/components/PointsEditorModal.tsx` / `.css`. `−`/숫자/`+`는 그대로 두고 슬라이더만 추가.
- 좁은 폭(≤560px)에선 숫자 입력창을 접고 슬라이더에 폭을 몰아줌.
