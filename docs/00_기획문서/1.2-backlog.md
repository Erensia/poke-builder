# ver.1.2 백로그

## 0. 이 문서의 성격

ver.1.1(포켓몬 이미지 배선 §1 포함, PR #19~#39)을 소진한 뒤 접수된 항목을 모은다.

- **§1 이미지/아이콘을 더 넓게 쓰는 것** — 1.1에서 슬롯 카드·도감 아바타 5곳만 실제
  스프라이트로 바꿨고, 나머지 화면과 타입 표기는 여전히 텍스트다. (§1-1~§1-6 머지 완료,
  §1-7 도구 도감 이미지 추가 접수)
- **§2 포챔스 레귤레이션 M-C 대응(2026-09-09~)** — 신규 포켓몬 26종(메가진화 포함) +
  로스터·기술·도구 데이터 확장 + 메가진화Z 이미지.
- **§3 UI 정리** — 배틀타워 셋업 날씨 선택 제거 + 저장된 파티 불러오기 + 사이드바/헤더 명칭 통일.

정적 검증은 `npx tsc -b` + `npx oxlint` + `npm run build`. 워크플로는 1.1과 동일 —
`dev`에서 항목별 브랜치 → PR로 `dev` 머지 → 주기적으로 `dev` → `main`.
스프라이트 매니페스트는 `npm run sprites`(`scripts/gen-sprite-manifest.mjs`)로 재생성.

관련 기반(1.1에서 구축):
- `src/lib/sprites.ts` `resolvePokemonSpriteUrl(pokemon, opts)` — 폼별 스프라이트 해석
- `src/data/spriteManifest.json` — `{ 공백제거 파일명 stem: "/sprites/..." }`
- `src/components/PokemonAvatar.tsx` — 공유 아바타(이미지 + 이니셜 폴백)
- 준비된 에셋(PR #39, 미배선): `public/sprites/타입/*.svg` 18종, `public/sprites/메가진화/메가진화.webp`

## 1. 이미지·아이콘 확대

### 1-1. 포켓몬 선택 모달 리스트에 아이콘

`PokemonPickerModal`(파티·매치업·배틀타워의 "포켓몬 선택" 모달)의 결과 리스트가 아직
**텍스트(이름 + 타입 배지 + 메가 수)만**이다. 각 행 앞에 작은 `<PokemonAvatar size={24~28}>`
추가. 스크롤 리스트라 `loading="lazy"` 그대로.

- 대상: `src/components/PokemonPickerModal.tsx` (+ 필요한 CSS)
- 참고: 도감 리스트(`.pokedex-list-avatar`, 28px 원형)와 같은 패턴

### 1-2. 소지 도구 아이콘을 포켓몬 아바타 옆에 표기

파티 빌더 · 매치업 · 배틀타워에서 슬롯에 도구가 장착돼 있으면, **포켓몬 아이콘 옆에 작게**
그 도구 아이콘을 표기한다(예: 아바타 우하단에 겹치는 작은 뱃지, 또는 이름 줄 앞).

- 에셋: `public/sprites/도구/{도구명}.webp` (+ 메가스톤은 `도구/메가스톤/{스톤명}.png`).
  매니페스트에 `.webp`/`.png` 둘 다 이미 들어와 있음.
- 공유 `<ItemIcon itemId size>` 컴포넌트 신설 — 매니페스트에서 `도구명` 키로 조회, 없으면
  숨김(폴백 아이콘 없이). `PokemonAvatar`와 나란히 놓는 작은 래퍼(`<PokemonAvatar>` + 도구 뱃지)
  를 두거나 각 카드에서 조합.
- 대상: `PartySlotCard.tsx` · `MatchupSlotCard.tsx` · `BattleSetupCard.tsx` (+ 배틀타워 대전 화면은
  1-3에서 아바타를 넣을 때 같이) + 각 `.css`. `slot.item` 이 있을 때만 렌더.
- 표시 위치·크기(겹침 뱃지 vs 별도 칩)는 구현 시 시안 비교 후 결정.

### 1-3. 포켓몬 도감 상세 — 메가진화 폼에도 아이콘

도감 상세(`PokedexPage.tsx`)의 "메가진화" 섹션은 폼 이름 + 타입 배지 + 종족값만 보여준다.
각 메가폼 카드에도 그 메가폼 스프라이트(`메가진화/메가{종족명}[XY].webp`)를 붙인다.

- `resolvePokemonSpriteUrl(pokemon, { activeMegaForm: mega.form })`이 이미 메가폼 URL을 돌려줌 — 그대로 사용
- 대상: `src/components/PokedexPage.tsx` 메가진화 섹션 + `.css`

### 1-4. 배틀타워 대전 화면 — 활성 포켓몬 아이콘

배틀타워(`BattleLogPage.tsx`)의 **대전 진행 화면** `.battle-fighter` 카드에는 아바타가 없다
(이름 + HP 바 + 실능치 칩만). `.battle-fighter-head`에 `<PokemonAvatar>` 추가.

- 폼 옵션: `fighter.slot`(EvaluatorSlot = FormSource)에서 `activeMegaForm`·`item`·`cosmeticForm`·
  `sizeForm`·`formVariant`, 성별은 `getEffectiveGender(pokemon, fighter.slot)`.
  일루전(§6-1) 중이면 위장 대상(`fighter.illusionAs`) 스프라이트를 써야 상대가 안 눈치챈다 —
  `illusionAs`가 있으면 그 종의 `getPokemon(illusionAs)`로 아바타를 그린다.
- 메가진화 선언 후(`fighter.hasMegaEvolved`) 스프라이트도 메가폼으로 바뀌어야 함
- 소지 도구 아이콘(1-2)도 이 아바타 옆에 같이
- 대상: `src/components/BattleLogPage.tsx` `.battle-fighter` 렌더 + `BattleLogPage.css`

### 1-5. 배틀타워 메가진화 버튼에 아이콘

배틀타워 입력부의 메가진화 선언 토글(`.battle-mega-toggle`)에 `메가진화/메가진화.webp`(범용
메가 심볼) 아이콘을 넣는다.

- 대상: `src/components/BattleLogPage.tsx` `.battle-mega-toggle` + `.css`
- 에셋: `public/sprites/메가진화/메가진화.webp` (PR #39에 이미 커밋됨)

### 1-6. 타입 배지를 글자 → 마크 이미지로

현재 타입 표기는 전부 **한글 텍스트 배지**(`TypeBadge`, 배경색 = `TYPE_COLORS`). 준비된
`public/sprites/타입/{타입명}.svg` 18종으로 아이콘화한다.

- **표시안 (2026-09-09 결정)**: 우선 **(a) 아이콘만**으로 전 화면 배선 → 프리뷰에서 디자인
  확인 후 그대로 갈지 / 일부 자리에 텍스트를 되살릴지 재결정. 접근성용 텍스트는 `aria-label`/
  `title`로 유지.
- **배선 방식**: SVG는 매니페스트 생성기가 스캔 안 함(`.webp|png|jpg|jpeg|gif|avif`만) — 별도
  처리 필요. 후보: `src/assets/타입/`로 옮겨 `import.meta.glob('...svg', { eager, query:'?url' })`
  로 번들, 또는 매니페스트 생성기에 `svg` 확장자 + `타입/` 하위경로 전용 맵 추가.
  SVG를 인라인(`currentColor` 틴트)할지 `<img>`로 둘지도 이때 결정.
- 영향 범위: `TypeBadge`를 쓰는 전 화면(도감·파티 슬롯·매치업·상성표·기술표·배틀 로그) — 공유
  컴포넌트 한 곳만 바꾸면 되지만 레이아웃(폭·정렬) 회귀 확인 필요.
- 대상: `src/components/TypeBadge.tsx` (+ `TYPE_COLORS`/`typeColors.ts` 관계 정리), 각 소비처 CSS

### 1-7. 도구 도감 페이지 — 각 도구에 이미지

도구 도감(`ItemDexPage`)은 리스트가 도구 이름만, 상세 헤더 아바타는 이름 첫 글자
(`.itemdex-detail-avatar` = `{item.name.at(0)}`)다. §1-2에서 만든 `<ItemIcon>` +
`resolveItemSpriteUrl`로 실제 도구 스프라이트를 붙인다.

- 리스트 각 행(`.itemdex-list-item`) 이름 앞에 작은 `<ItemIcon size={20~24}>`. 스크롤
  리스트라 `loading="lazy"` 그대로.
- 상세 헤더 `.itemdex-detail-avatar`의 이니셜을 `<ItemIcon size={44}>`로 교체 —
  스프라이트가 없으면(§1-2처럼 6종) 기존 이니셜 폴백 유지.
- 도구 스프라이트 144/150 커버(나머지는 §2-3 메가스톤Z 등 아직 없는 것).
- 대상: `src/components/ItemDexPage.tsx` + `ItemDexPage.css`(`.itemdex-list-item`·`.itemdex-detail-avatar`)

## 2. 포챔스 레귤레이션 M-C 업데이트 (2026-09-09~)

Pokémon Champions 레귤레이션 M-C 시행에 맞춰 데이터셋을 확장한다. 순수 데이터 작업이
대부분이라 §1(아이콘)과 병행 가능하지만, 스프라이트·매니페스트가 엮이므로 에셋 수급이
선행 조건이다.

### 2-1. 신규 포켓몬 26종 추가 (메가진화 포함)

레귤레이션 M-C에서 추가된 26종을 `src/data/pokemon.json`에 편입한다.

- 각 종: `id`(한국어 이름) · `name` · `types` · `baseStats` · `abilities` · `hiddenAbility` ·
  (해당 시) `megaEvolutions[]`(`form` · `megaStone` · `types` · `baseStats` · `ability`).
  1.1 겉모습/성별 필드(`cosmeticForms` · `genderedSprite`)는 해당 종만.
- 스프라이트: `public/sprites/{세대}/{종족명}.webp` + 메가는 `메가진화/메가{종족명}.webp`.
  추가 후 `npm run sprites`로 `spriteManifest.json` 재생성.
- **선행**: 26종 목록 확정(종별 종족값·특성·타입 출처) + 스프라이트 26장(+메가분) 수급.
- 대상: `src/data/pokemon.json`, `public/sprites/**`, (재생성) `src/data/spriteManifest.json`

### 2-2. 로스터 · 기술 · 도구 데이터 확장

신규 포켓몬이 쓰는 기술·도구가 기존 데이터셋에 없으면 함께 추가한다.

- **기술**: `src/data/moves.json` — 신규 기술의 위력·명중·타입·분류·PP·부가효과.
  엔진(`battleSimulator`)이 부가효과를 해석하려면 기존 effect 스키마에 매핑되는지 확인,
  안 되면 엔진 분기 추가(별도 하위 항목으로 뺄 수 있음).
- **도구**: `src/data/items.json` — 신규 지닌 도구 + 효과. 메가스톤이면
  `public/sprites/도구/메가스톤/{스톤명}.png`도 같이.
- **로스터**: 신규 종의 습득 기술 목록(`learnset` 등 현행 pokemon.json 구조에 맞춰) 반영.
- 대상: `src/data/moves.json` · `src/data/items.json` · `src/data/pokemon.json` (+ 필요 시 엔진)

### 2-3. 메가진화Z 이미지 추가

메가루카리오Z · 메가한카리아스Z · 메가앱솔Z 등 "메가진화Z" 폼 스프라이트를 추가한다.

- 파일 위치·명명 규칙 확정 필요 — 기존 `메가진화/메가{종족명}.webp`의 변형인지
  (`메가{종족명}Z.webp`?) 별도 하위폴더인지. `resolvePokemonSpriteUrl`의 메가폼 해석
  (`activeMegaForm`)이 새 명명을 커버하는지 확인, 안 되면 분기 추가.
- 대응하는 `megaEvolutions[].form` 값과 스프라이트 stem이 1:1이어야 함.
- 대상: `public/sprites/메가진화/**`, `src/lib/sprites.ts`, `src/data/pokemon.json`,
  (재생성) `src/data/spriteManifest.json`

## 3. UI 정리

### 3-1. 배틀타워 셋업 화면 날씨 선택 제거

배틀타워 셋업 헤더의 `<WeatherPicker>`(시작 날씨 지정)를 없앤다 — 실제로 안 쓰는 기능.

- 제거: `BattleLogPage.tsx` L686 `<WeatherPicker weather={setup.weather} onChange={setup.setWeather} />`
  + 시작 상태에 날씨를 밀어넣던 `weather: setup.weather ?? undefined`(L490).
- `useBattleSetup.ts`의 `weather`/`setWeather` state도 다른 소비처 없으면 같이 제거.
- **범위 한정**: 전투 중 특성·기술로 바뀌는 날씨(모래뿜기, `setWeather` 액션, 날씨 지속턴
  표시 등) 로직은 그대로 둔다. 없애는 건 "시작 날씨 수동 지정" UI 하나뿐.
- `WeatherPicker` 컴포넌트 자체는 매치업 페이지(`MatchupPage.tsx`)에서 계속 쓰므로 삭제 금지.
- 대상: `src/components/BattleLogPage.tsx`, `src/hooks/useBattleSetup.ts` (+ 헤더 CSS 여백 확인)

### 3-2. 셋업 화면에 "저장된 파티 불러오기"

배틀타워 편측 빌드에서 6마리를 매번 손으로 고르기 번거롭다. 파티 빌더에서 이름 붙여 저장한
파티 프리셋(`usePartyPresets`, `champions-party-sim.party-presets.v1`)을 한 번에 불러오는
버튼을 각 진영 상단에 둔다.

- 프리셋의 `slots: PartySlots`(6칸)를 그 진영 6개 `BattleSetupSlot`에 순서대로 `loadSlot()`.
  `PartySlot` == 배틀 셋업 슬롯 타입이라 변환 없이 그대로 대입 가능(빈 칸은 `clearPokemon()`).
- UI: 기존 `PartyPresetsModal`(또는 `PresetListModal`) 재사용 — "불러오기" 액션만 노출.
  진영 A/B 각각 트리거.
- 저장 기능은 이 화면에 안 붙인다(빌더 전용). 불러오기만.
- 대상: `src/components/BattleLogPage.tsx` 셋업 렌더 + `src/hooks/useBattleSetup.ts`
  (진영 단위 `loadSide(slots)` 헬퍼 추가) + `usePartyPresets` 재사용

### 3-3. 사이드바 ↔ 페이지 헤더 명칭 통일

사이드바 내비 라벨과 각 페이지 `<h2>` 제목이 안 맞는 곳이 있다. 한쪽으로 통일한다.

| 뷰 | 사이드바(`Sidebar.tsx` `NAV_ITEMS`) | 페이지 헤더 | 상태 |
|---|---|---|---|
| party | 파티 빌더 | 파티 편성 (`PartyBoard.tsx` L78) | ❌ 불일치 |
| itemdex | 도구 도감 | 포켓몬 도구 도감 (`ItemDexPage.tsx` L98) | ❌ 불일치 |
| matchup | 결정력 & 내구력 | 결정력 &amp; 내구력 | ✅ |
| battle-log | 배틀타워 | 배틀타워 | ✅ |
| pokedex | 포켓몬 도감 | 포켓몬 도감 | ✅ |
| movedex | 기술표 | 기술표 | ✅ |

- **명칭 확정 (2026-09-09)**:
  - party: **"파티 샘플 작성"** — 사이드바 라벨(`파티 빌더`)·페이지 헤더(`<h2>파티 편성</h2>`)
    둘 다 `파티 샘플 작성`으로 변경. 사이드바 로고 서브타이틀(`<small>파티 빌더</small>`)은
    앱 브랜딩이라 그대로 둔다.
  - itemdex: **"도구 도감"** — 헤더 `<h2>포켓몬 도구 도감</h2>` → `도구 도감`으로 변경(사이드바에 맞춤).
- 확정된 명칭이 `document.title`·`aria-label`·안내 문구 등 다른 곳에도 쓰이면 같이 맞춘다.
- 대상: `src/components/Sidebar.tsx`, `src/components/PartyBoard.tsx`, `src/components/ItemDexPage.tsx`
  (+ 확정 시 문자열 전수 검색)

### 3-4. 도구 도감 페이지 정렬 (추가: 2026-09-10) — ✅ 완료 (2026-09-11)

도구 도감(`ItemDexPage`) 리스트의 현재 순서가 뒤죽박죽이다(`items.json` 원본 순서 그대로).

- **1차: 메가스톤을 맨 뒤로.** 일반 도구 그룹이 먼저, 메가스톤 그룹이 그 뒤.

## 4. 엔진 버그 수정

### 4-1. 꼬리자르기(Shed Tail) 로직 미구현

`꼬리자르기`(Shed Tail)는 **최대 HP의 1/2을 깎아 대타를 세운 뒤 교대 포켓몬과 교체**하고,
세운 대타를 나온 포켓몬이 물려받는 기술이다. 현재 `moves.json`의 `꼬리자르기` 항목에는
`setsSubstitute`·자체 교체 플래그가 전혀 없어서(그냥 `category: "status"` 무효과 기술) —
**테스트 결과(2026-09-09)**: HP가 절반 이하여도 실패 문구가 안 나오고, 대타도 안 생기고,
교체도 안 일어난다(조용히 아무 일도 안 함).

기대 동작:
- 사용 시 **최대 HP의 1/2**(`Math.floor(maxHp/2)`)을 소모. 현재 HP가 그 이하이거나, 교체할
  예비 포켓몬이 없으면 **실패**(`하지만 실패했다!` 류 문구 + 대타 미생성 + 교체 없음).
- 성공하면 그 즉시 HP를 깎고 같은 양(1/2)의 대타를 세운 뒤, 사용측을 교체한다. 세운 대타는
  **나오는 포켓몬이 물려받는다**(배턴터치의 대타 인계와 동일 — `performSwitch`의 `passBaton`
  경로가 `substituteHp`를 넘겨줌).
- 대타 유지 중 relevant volatile 인계 범위는 대타출동 기준(랭크 등은 인계 안 함, 배턴터치와 다름).

구현 메모:
- `moves.json` `꼬리자르기`: 대타 비용이 1/2이라 `setsSubstitute`(=1/4 고정, `battleSimulator.ts`
  L4558~4566)를 그대로 못 쓴다. `substituteCostFraction` 같은 필드를 새로 두거나 전용 플래그
  (`shedTail: true`)로 분기.
- 자체 교체: 유턴류(`selfSwitchAfterDamage`)·배턴터치(`passesStatsOnSelfSwitch`)가 타는
  `runActionPhase` L5361~5378 경로에 `꼬리자르기`도 태우되, **대타 세팅이 성공했을 때만**
  교체하도록(실패 시 교체 안 함). 대타 인계가 필요하니 `passBaton`(또는 대타만 넘기는 옵션)
  경로 사용.
- 실패 문구: `substituteSetFailed` 렌더 경로(`setSubstitute`/`substituteSetFailed` — L1276~1278,
  L4982) 재사용 또는 확장.
- 대상: `src/data/moves.json`, `src/lib/battleSimulator.ts`, `src/components/BattleLogPage.tsx`
  (실패/교체 로그 줄)

**로그 문구 확정 (2026-09-09, PR #45):**
```
[사용자]의 꼬리자르기 · 꼬리를 잘라 분신을 만들었다!
[사용자]은(는) 트레이너의 곁으로 돌아간다!
돌아와! [사용자]!
```
꼬리자르기 교체 줄은 유턴류의 `돌아와!/가라!` 2줄 대신 위 2줄로(`SwitchLogEntry.shedTail`
플래그로 분기). 실패 시 인라인 `· 그러나 실패했다!`.

### 4-2. 기술 엔진 미배선 전수 감사 (추가: 2026-09-10)

**배턴터치(Baton Pass) 자체 교체가 실전에서 안 먹는다** — 테스트에서 발견. 데이터는 있다
(`moves.json` `배턴터치` = `category:"status"` + `passesStatsOnSelfSwitch:true`), 교체 인프라도
있다(`performSwitch`의 `passBaton` 스냅샷/인계, `runActionPhase` L5490~5519가
`passesStatsOnSelfSwitch`를 유턴류와 같은 `awaitingSelfSwitch` 경로에 태움). 그런데도 실제로는
교체가 일어나지 않음 → 그 사이 어딘가가 끊겨 있다. 후보:

- `resolveAction`이 순수 변화기(데미지·상태이상·랭크 등 인식 가능한 효과가 하나도 없는
  `배턴터치`)를 "아무 일도 안 한 기술"로 처리해 `hit:true` 성공 객체를 안 돌려주는 경우
  (L5491~5500 조건의 `action.hit`가 false로 떨어짐).
- UI(`BattleLogPage`)가 `awaitingSelfSwitch`(passBaton=true)를 받아 교체 슬롯을 요구하는
  경로가 배턴터치 케이스에서 누락.
- 재현: 배틀타워에서 랭크 올린 뒤 배턴터치 선택 → 교체 슬롯 선택 창이 뜨는지 / 안 뜨면
  어디서 멈추는지 로그 확인.

**✅ 근본 원인 확정 (2026-09-11, 실제 UI 클릭 재현).** 엔진(`sim.runTurn`/`resumeTurn`)은 완전히
정상 — 동일 시나리오를 직접 호출하면 `awaitingSelfSwitch` pause, 랭크 인계 전부 정확했다.
그런데 배틀타워 화면에서 **번치코(배턴터치) + 라이츄(기술 없음)** 2마리로 실제 클릭 재현
시 배턴터치가 아무 일 없이 끝났다(교체 안 됨). 원인은 `BattleLogPage.tsx`의
`buildableIndices(side)`:
```
const buildableIndices = (side: Side): SlotIndex[] =>
  SLOT_INDICES.filter((i) => {
    const s = slotCtl(side, i).slot;
    return s !== null && s.moves.some((m) => m !== null);
  });
```
**기술을 하나도 안 배정한 슬롯은 "빌드 안 된 것"으로 취급돼 전투 시작 시(`startBattleWith`)
파티에서 통째로 빠진다** — HP바도 안 뜨고 교체 후보로도 안 잡힌다(디버그 로그로 확인:
`hasLivingReserve:false, partyLen:1` — 2마리를 골랐는데 엔진엔 1마리만 전달됨). 라이츄에게
기술 1개(10만볼트)를 배정하고 똑같이 재현하니 **정상 작동**(`번치코는 돌아온다! → 라이츄
내보내기` pause → 교체 완료, 랭크 인계, 상대 공격까지 로그 전부 정상).

**영향 범위**: 배턴터치뿐 아니라 유턴·볼트체인지·꼬리자르기·위기회피·탈출버튼 등 "교체 상대가
있어야 하는" 모든 효과가 같은 이유로 조용히 무산될 수 있다 — 예비 포켓몬에 기술을 아직 안
채운 상태로 테스트하면 재현됨. **더 큰 문제는 실패를 알려주는 로그가 전혀 없다는 것** —
"번치코의 배턴터치"만 찍히고 끝나서, 유저 입장에선 기능이 고장난 것처럼 보인다.

**✅ 완료(2026-09-11) — 사용자 결정: 대전 시작 시점에 기술 슬롯을 검수한다.** 위 두 후보
대신, "기술을 하나도 안 배정한 슬롯이 있으면 애초에 대전을 시작할 수 없게" 막는 세 번째
방식으로 확정 — `buildableIndices`가 조용히 슬롯을 빼는 상태 자체가 아예 발생하지 않는다.
기준은 단순히 **그 슬롯에 기술이 1개 이상 있는가**(포켓몬을 배정한 슬롯 전부 대상, 실제로
선출/전투에 쓰일 슬롯인지는 안 가림 — 빌드해둔 이상 기술 없이 대전에 들어갈 일 자체를
없앤다).

- `BattleLogPage.tsx`에 `movelessIndices(side)`(포켓몬은 있는데 기술이 0개인 슬롯) +
  `movelessWarningFor(side)`(그 편 소속 포켓몬 이름만 모은 안내 문구) 신설. `canProceed`가
  이 경고가 없을 때만 통과하도록 조건 추가 — VS 버튼이 비활성화되고, 문제가 있는 쪽 파티
  컬럼 상단("6마리까지 빌드 …" 힌트 바로 아래)에 "OO 포켓몬에게 기술을 최소 1개 배정해야
  대전을 시작할 수 있습니다." 문구가 뜬다(`.battle-lock-warning` 재사용). 처음엔 중앙(VS
  버튼 밑)에 뒀다가 사용자 피드백으로 각 파티 상단으로 옮김.
- 브라우저로 실제 클릭 흐름 확인: 기술 없는 포켓몬 추가 → VS 비활성화 + 해당 파티 컬럼에
  정확한 이름으로 경고 표시 → 기술 배정 → 경고 해제·정상 진행. 기존 "양쪽 파티를 먼저
  완성하세요"(빌드 자체가 없을 때) 케이스와도 안 겹침.

**추가 작업: 그 외 엔진 미배선 기술 전수 확인** — `docs/00_기획문서/1.3-backlog.md` §1로
이관(2026-09-11). ver.1.2 범위가 아니라 별도 탐색성 조사라 다음 버전으로 넘김.

### 4-3. 도발 중복 시전이 실패로 처리되지 않음 (추가: 2026-09-10) — ✅ 완료 (PR #74)

**재현**: 이미 도발에 걸린 상대에게 도발을 다시 시전 → 실패해야 하는데(본가 "But it failed!")
성공한 것처럼 `· 도발!` 로그가 다시 뜨고, 걸린 도발의 지속 턴수가 3턴으로 리셋된다.

**원인**: `resolveAction`의 `inflictsVolatile` 루프(`battleSimulator.ts` L4280~4341)에 재시전
가드가 `drowsy`(L4305)·`wish`(L4314)·`attract`(L4327)에만 있고 `taunt`에는 없다. 도발이면
`hasVolatile(target.volatile, "taunt")` 확인 없이 곧장 `inflictVolatile`로 덮어써서(턴수 리셋)
`inflictedVolatile = "taunt"` 마커까지 세운다.

**기대 동작**: 대상이 이미 `taunt`면 `continue`하고 실패로 표시한다. 이 볼라틸 루프는
실패 시 `statusInflictFailed`를 세우지 않으므로(`inflictsStatus` 루프의 L4142만 세움) 그
연결도 같이 손봐야 함 — 도발 재시전 실패 시 `statusInflictFailed = true`(또는 전용 마커)로
`그러나 실패했다!` 문구를 낸다.

**같이 확인**: `disable`(사슬묶기)·`encore`(앙코르)도 같은 루프에 재시전 가드가 없다 — 이미
걸린 대상에게 다시 걸면 턴수·대상 기술이 조용히 덮어써질 수 있다. 도발 고칠 때 세 개(도발·
사슬묶기·앙코르)를 한 번에 점검한다. (단 사슬묶기·앙코르는 "다른 기술을 새로 지정"하는 재시전이
본가에서 어떻게 처리되는지 확인 필요 — 무조건 실패인지, 대상 기술만 갱신인지.)

- 대상: `src/lib/battleSimulator.ts`(L4280~ 볼라틸 루프 + 실패 마커), `src/components/BattleLogPage.tsx`(실패 문구 렌더 경로 재사용)

### 4-4. 풀죽음(flinch)이 다음 턴까지 남아 행동을 막음 (추가: 2026-09-10) — ✅ 완료 (PR #74)

**재현**: 배틀타워에서 교체로 나온 한카리아스에게 메가갑주무사가 아이언헤드 → 풀죽음 발동,
그 턴 종료. **다음 턴** 한카리아스가 기술을 고르면 "풀이 죽어서 움직일 수 없다"가 다시
떠서 행동 불가. 풀죽음은 걸린 그 턴만 유효해야 한다.

**원인**: 풀죽음 volatile은 `turnsRemaining: 1`로 걸리고, **걸린 포켓몬이 자기 행동을 개시할
때에만** `resolveAction`(`battleSimulator.ts` L2422~2425)이 `consumeVolatileTurn("flinch")`으로
소모한다. 그런데 그 포켓몬이 **그 턴에 교체로 나왔으면**(`runTurn`의 `didSwitch[key]` → L5632
`continue`로 `resolveAction` 스킵) 소모 경로를 안 타서 풀죽음이 `turnsRemaining: 1`인 채 다음
턴으로 넘어간다. 다음 턴 행동 시 그제서야 소모되며 `blocked("flinch")` → 잘못된 행동 불가.
(교체가 아니어도, 풀죽음을 건 기술이 걸린 포켓몬이 이미 행동을 마친 뒤에 명중한 경우 —
느린 쪽이 아이언헤드 — 도 같은 방식으로 다음 턴까지 샐 수 있음. 확인 필요.)

**기대 동작**: 풀죽음은 "이번 턴만" 효과 → 턴이 넘어갈 때 무조건 사라진다.

**수정 위치**: `runTurn` 턴 시작 리셋 블록(L5470~ `activeProtect`·`moveTypeOverrideThisTurn`을
지우는 곳)에 `state.a/b.volatile`에서 `flinch` 제거를 추가. (EOT 블록은 `!isFainted` 가드가
있어 한쪽이 기절한 턴엔 안 도므로 턴 시작 쪽이 안전. `recharge`는 원래 1턴 넘겨 지속하는
효과라 건드리지 않는다.)

- 대상: `src/lib/battleSimulator.ts`(L5470~ 턴 시작 리셋에 flinch 클리어 1줄)

  계산 쪽엔 6곳 넘게 나오는데(`opponentEffectsBlocked`로 각 효과 적용을 건너뜀),
  `BattleLogPage.tsx`엔 "황금몸" 문자열이 단 한 번도 없다 — 즉 막혔다는 사실 자체를 UI가
  절대 표시하지 않는다. 반면 같은 축인 방음·방탄은 전용 필드 + 문구가 있다
  (`soundproofBlockedByAbilityName` → `"{defenderName}의 {ability}! 소리 기술은 통하지
  않는다!"`, `bulletproofBlockedByAbilityName`도 동일 패턴).

**기대 동작**: 황금몸이 명중한 변화기의 효과를 무효화했으면 방음·방탄과 같은 패턴으로
`goodAsGoldBlockedByAbilityName` 같은 필드를 세우고 `"{defenderName}의 황금몸! 변화기는
통하지 않는다!"` 류 문구를 낸다. `blockedByGoodAsGold`가 이미 계산돼 있으니(L2644 부근)
그 값을 `ActionLogEntry`로 실어 나르기만 하면 됨 — 새 판정 로직은 필요 없음.

- 대상: `src/lib/battleSimulator.ts`(`blockedByGoodAsGold` 계산 지점 + return 객체),
  `src/components/BattleLogPage.tsx`(방음/방탄과 나란히 렌더)

**✅ 완료(2026-09-11).** `ActionLogEntry.goodAsGoldBlockedByAbilityName` 필드 추가, `hit`까지
확인한 뒤에만 채운다(`blockedByGoodAsGold && hit`) — 그래야 진짜 빗나감(C-5)과 안 섞인다.
UI는 방음/방탄과 나란히 두 줄로 렌더(사용자 지정 문구):
```
{defenderName}의 {ability}!
{defenderName}에게 효과가 없는 듯하다...
```
Vite 페이지 컨텍스트에서 `runTurn(밀로틱 최면술 → 황금몸 타부자고)`을 `random=0.1`(명중)과
`random=0.9`(빗나감) 양쪽으로 직접 호출해 확인 — 명중 시에만
`goodAsGoldBlockedByAbilityName: "황금몸"`이 실리고 상태이상은 안 걸림, 빗나감 시엔 필드
자체가 안 실림(기존 미스 로그와 정상적으로 구분됨).

### 4-6. 기술 사용자 자신의 랭크가 떨어지는 부가효과가 로그에 안 뜸 (추가: 2026-09-11) — ✅ 완료 (2026-09-11)

**재현**: 타부자고가 골드러시(자신의 특수공격 2랭크 하락 부가효과) 사용 → 데미지는 정상
처리되지만 "타부자고의 특수공격이 크게 떨어졌다!" 같은 안내가 로그에 전혀 안 뜬다.

**코드 확인 (Vite 페이지에서 직접 재현)**: `runTurn`으로 타부자고 vs 타부자고, 골드러시 사용
후 `nextState`를 까 보면 `stages.spa === -2`로 **랭크 하락 자체는 정확히 적용**되는데, 그
행동의 `ActionLogEntry`엔 `selfStatRises`도 `opponentStatDrops`도 안 실린다 — 즉 안내를 낼
방법이 있는 필드가 아예 없다.

원인은 `battleSimulator.ts`의 `selfStatRises` 수집 루프(L4114 부근)가 **"자기 대상 +
확정(chance 없음) + `delta > 0`"만** 골라서, 자기 대상 확정 하락(`delta < 0`)은 애초에 이
필드에도 `opponentStatDrops`에도 잡히지 않는다는 것 — 대칭축이 하나 빠져 있다(현재는
"자기 상승"·"상대 하락" 두 축만 있고 "자기 하락" 축이 없음).

**영향 범위**: 골드러시뿐 아니라 자기 대상 확정 랭크 하락 부가효과를 가진 기술 전부 동일하게
무안내다. `moves.json`에서 `statChanges`가 `target:"self"`·`delta<0`·`chance` 없음인 기술을
전수 조사한 결과 14종: 골드러시·용성군·오버히트·리프스톰(특공 2하락류), 인파이트·엄청난힘·
아머캐논·껍질깨기·들이받기(방어+특방 또는 공격+방어 동반 1하락류), 스케일샷·스케일노이즈
(방어 1하락), 암해머·아이스해머(스피드 1하락), 저주(고스트 타입이 아닐 때만 스피드 1하락).

**기대 동작**: `selfStatRises`와 대칭인 `selfStatDrops` 필드를 신설해 `delta < 0`인 자기
대상 확정 변화를 모으고, `BattleLogPage.tsx`에 `opponentStatDrops`와 같은 문구 패턴("OO의
X가 (크게) 떨어졌다!", 주어만 항상 `actorName`)으로 렌더한다. 판정 로직은 이미 있으니
`selfStatRises` 수집 루프(L4112~4121)의 `delta <= 0` 제외 조건 바로 옆에 대칭 루프만 추가하면
됨.

- 대상: `src/lib/battleSimulator.ts`(`selfStatRises` 수집 루프 근처 + `ActionLogEntry`/return
  객체), `src/components/BattleLogPage.tsx`(`opponentStatDrops` 렌더 블록 근처에 자기 하락용
  블록 추가)

**✅ 완료(2026-09-11).** 계획대로 `selfStatRises` 수집 루프를 확장해 `delta > 0`(상승)과
`delta < 0`(하락)을 한 번에 판정하고, `ActionLogEntry.selfStatDrops`에 `{stat, delta(양수)}`로
담는다. `BattleLogPage.tsx`엔 `opponentStatDrops` 렌더 블록 바로 옆에 주어만 `actorName`으로
바꾼 동일 패턴 블록을 추가. Vite 페이지에서 골드러시(스탯 1개, spa -2)와 인파이트(스탯 2개
동시, def·spd 각 -1)로 실제 `ActionLogEntry.selfStatDrops` 값을 확인함(각각
`[{stat:"spa",delta:2}]`, `[{stat:"def",delta:1},{stat:"spd",delta:1}]`).
