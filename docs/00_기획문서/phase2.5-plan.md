# Phase 2.5 기획 — UI 정리 & 즉시 처리 가능한 보강

> 이어서 읽기: [Phase 2 기획](phase2-plan.md) · [Phase 3 기획](phase3-plan.md)
> Phase 3(신규 스키마·엔진 확장)로 들어가기 전에, 사용자가 대전 로그 화면을 실제로 써보다가 발견한 버그 2건과 "스키마는 이미 있는데 데이터만 안 채워진" 항목들을 먼저 정리한다. 전부 기존 구조를 유지한 채로 끝나는 작업이라 Phase 3(신규 스키마 설계)보다 먼저 처리한다.
>
> **✅ 완료.** 아래 1~3번(원래 기획)에 더해, 대전 로그를 실제로 계속 써보면서 추가로 발견·수정한 사항을 [6절](#6-대전-로그-실사용-중-추가로-발견수정한-사항)에 정리했다.

## 1. 페이지 폭 불일치 (UI 버그)

**증상**: 파티 편성 페이지와 결정력·내구력/대전 로그 페이지의 좌우 여백이 다르게 보임.

**원인 확인**: 사이드바(`margin-left: 64px`)는 `App.css`의 `.app-main`에서 모든 페이지에 동일하게 적용되고 있어 원인이 아니었다. 실제 원인은 각 페이지 컴포넌트가 콘텐츠 폭을 서로 다른 방식으로 지정하고 있던 것:

| 페이지 | 폭 지정 |
|---|---|
| `PartyBoard.css` `.party-board` | `width: 100%; max-width: 560px;` |
| `MatchupPage.css` `.matchup-page` | `width: 100%; max-width: 740px;` |
| `BattleLogPage.css` `.battle-log-page` | 지정 없음 — `app-main`의 `display:flex; justify-content:center`에서 콘텐츠 크기만큼만 차지 |

매치업과 대전 로그가 "일치해 보인다"고 하신 건 대전 로그가 폭 지정이 아예 없어서 콘텐츠 크기가 우연히 740px 근처로 나온 것이지, 의도적으로 맞춘 값이 아니다.

**작업**:
- 세 페이지가 공유할 표준 폭 값을 하나 정한다 (560/740 중 하나로 통일하거나, 콘텐츠 성격이 다르니 페이지별로 다른 값이 필요하면 의도적으로 다르게 유지 — 파티 편성은 2열 그리드라 좁아도 되지만 대전 로그는 로그 텍스트가 많아서 더 넓어야 할 수 있음. **사용자 확인 필요**: 통일할지, 페이지 성격에 맞게 의도적으로 다르게 갈지)
- `BattleLogPage.css`의 `.battle-log-page`에 명시적 `width`/`max-width`를 추가해서 최소한 "지정 안 함" 상태는 없앤다

## 2. 대전 로그 화면의 메가진화 표시 버그

**증상**: 셋업 단계에서 메가스톤을 장착해 "메가 이어롭"으로 표시되던 포켓몬이, "대전 시작" 후 배틀 화면에서는 그냥 "이어롭"으로 보임. 내 포켓몬/상대 포켓몬 둘 다 동일.

**원인 확인** (스모크 테스트로 검증 완료): **내부 계산은 정상**이다. `createFighterState()`가 `getEffectiveForm()`으로 메가폼의 타입·종족값을 정확히 반영해서 `BattleFighterState.types`/`realStats`에 저장한다 — 메가 이어롭으로 테스트하니 타입 노말/격투, 실능치 공격 156·스피드 155(둘 다 메가 스탯 기준)로 정확히 나왔다. 문제는 오직 **표시 쪽**: `BattleLogPage.tsx`의 배틀 보드가 `getPokemon(fighter.slot.pokemonId).name`(항상 기본 포켓몬 이름)만 그리고, `BattleSetupCard`가 쓰던 `getEffectiveForm()` 기반 폼 라벨/메가 배지를 전혀 안 씀 — 데미지·판정에는 영향 없는 순수 표시 버그.

**작업**:
- `BattleFighterState`(`lib/battleSimulator.ts`)에 폼 라벨 정보를 저장하거나, `BattleLogPage`에서 `getEffectiveForm(pokemon, fighter.slot)`을 직접 호출해서 배틀 보드의 이름 옆에 메가 배지를 셋업 카드와 동일하게 그린다
- 양쪽(내 포켓몬/상대 포켓몬) 다 동일하게 적용

## 3. 데이터 태깅 — 스키마는 이미 있고 데이터만 채우면 되는 것

Phase 3 문서 초안에 있던 항목 중, **신규 스키마 설계가 필요 없고 이미 만들어둔 필드에 값만 채우면 되는 것들**을 Phase 2.5로 앞당긴다 (사용자 확인: "데이터 태깅도 2.5에 넣어줘 스키마 이미 있는거니까"). Phase 2에서 `moves.json` 전수 스캔으로 정확한 개수까지 확인해뒀다.

### 3-1. 회피율/급소율 랭크 변화 (2개)

| 기술 | 채울 `statChanges` |
|---|---|
| 기충전 | `{ target: "self", stat: "critStage", delta: 2 }` |
| 그림자분신 | `{ target: "self", stat: "evasion", delta: 1 }` |

(드래곤옐은 "아군 전원 대상이라 1v1에서 의미 없음"으로 Phase 2에서 의도적으로 스킵한 상태 그대로 유지)

### 3-2. 풀죽음(flinch) — 8개, 확률까지 전부 확인됨

| 기술 | 확률 |
|---|---|
| 에어슬래시 | 30% |
| 사념의박치기 | 20% |
| 아이언헤드 | 30% |
| 물기 | 30% |
| 악의파동 | 20% |
| 코골기 | 30% (※ "잠든 상태에서만 사용 가능"이라는 사용 조건은 스키마 밖 — 풀죽음 부분만 태깅) |
| 폭포오르기 | 20% |
| 속이기 | 100% (※ 원래 `effect` 텍스트가 트릭/바꿔치기에서 잘못 복사된 "도구 교환" 문구였던 데이터 버그. 스탯(위력40·우선도+3·노말·접촉기)은 페이크아웃과 정확히 일치해서 "풀죽" 키워드 스캔에 안 걸렸던 것 — 태깅하며 effect 텍스트도 같이 수정. "등장 후 첫 턴에만 사용 가능"이라는 사용 조건은 스키마 밖 — 풀죽음 부분만 태깅) |

`inflictsVolatile: [{ volatile: "flinch", target: "opponent", chance: N }]` 형태로 바로 채운다(속이기는 100%라 `chance` 생략).

### 3-3. 반동(recharge, "다음 턴 행동 불가") — 재스캔 + 태깅

기가임팩트("사용한 다음 턴에는 움직일 수 없다")만 확인된 상태. "반동"이라는 단어 대신 "충전"/"움직일 수 없다" 등 다른 표현을 쓸 수 있어서, `moves.json`의 `effect` 텍스트를 더 넓은 키워드로 재스캔해 하이퍼빔류가 더 있는지 확인 후 `inflictsVolatile: [{ volatile: "recharge", target: "self" }]`로 태깅한다.

## 4. Phase 3 문서와의 관계

Phase 3 문서([docs/phase3-plan.md](phase3-plan.md))의 "2. 데이터 태깅만 하면 되는 것" 절은 이 문서로 이동했다 — Phase 3은 이제 진짜 신규 스키마가 필요한 항목(반동 데미지, 다단히트, 2턴 차지기, 상태이상 치료 등)에만 집중한다.

## 5. 제안 순서

1. 2번(메가진화 표시 버그) — 원인 이미 확인 끝났고 수정 범위가 명확해서 가장 빠름

## 6. 대전 로그 실사용 중 추가로 발견·수정한 사항

1~3번(원래 기획)을 끝낸 뒤에도 대전 로그를 계속 실제로 돌려보면서(스모크 테스트) 추가로 발견한 버그·요청을 같은 세션에서 이어서 처리했다. 전부 "대전 로그 화면을 실제로 써보다가 발견"이라는 이 문서의 원래 취지에 맞는 항목이라 여기 이어 붙인다.

### 6-1. 발버둥(Struggle) 자동 사용 미구현 — 버그

**증상**: 포켓몬의 4개 기술 PP가 전부 0이 되면 사용할 기술이 없어져서 턴을 진행할 수 없었다.

**수정**: `battleSimulator.ts`에 `STRUGGLE_MOVE`(???타입·물리·위력50·필중·사용자가 최대 HP 1/4 반동, `moves.json`에는 추가하지 않음 — 사용자 확인)와 `hasUsableMove()`를 추가. `BattleLogPage.tsx`는 기술 PP가 전부 0인 쪽엔 기술 선택 그리드 대신 안내 문구를 띄우고, "턴 진행" 클릭 시 그 쪽은 선택 없이 자동으로 발버둥을 낸다.

### 6-2. 자폭·대폭발류 "사용자는 반드시 기절한다" 페널티 미반영 — 버그 + 데이터 버그

`moves.json`에 "자폭"·"대폭발" 둘 다 `effect`가 빈 문자열이라 페널티가 아예 태깅돼 있지 않았다. 조사하다가 **데이터 중복 버그**도 발견: "대폭발"(정상 이름, 빈 effect)과 오타로 보이는 "대폭팔"(효과는 맞는데 이름이 오타, PP도 다름)이 별개 항목으로 둘 다 존재했다. "대폭팔"을 삭제하고, "자폭"·"대폭발" 둘 다 `Move.selfFaints: true` + 올바른 effect 텍스트로 정리. `battleSimulator.ts`는 명중/기절 여부와 무관하게 사용자 HP를 0으로 만들도록 처리했다.

### 6-3. 나이트헤드 고정 데미지 미구현

`effect`가 "사용자의 레벨만큼 고정 데미지를 준다"인데 `power: null`이라 아무 데미지도 안 나갔다. 챔피언스는 레벨 50 고정이므로 `Move.fixedDamage: 50`을 추가하고, `resolveAction`에서 상대 방어·랭크·특성·도구·급소를 전부 무시하고 고정 수치만 깎도록(타입 면역만 존중) 구현.

### 6-4. 동시 기절 시 로그가 끝나지 않는 버그 → 승자 판정을 인과관계 기반으로 개편

처음엔 "양쪽 다 기절하면 무승부"로 고쳤는데, 사용자가 실제 대전 사례로 지적: 자폭류나 발버둥처럼 "상대를 쓰러뜨린 다음에 반동으로 자신도 쓰러지는" 경우는 실제 게임에서 상대를 먼저 쓰러뜨린 쪽이 승자다. `resolveAction`에서 `selfFaints`/발버둥 반동을 상대 데미지 적용 **이후**에 처리하도록 순서를 맞추고, `runTurn`에서 한 번의 행동 안에 "상대도 쓰러지고 자신도 쓰러지면" 그 행동의 주체를 승자로 확정하도록 수정. 양쪽이 각자 턴 종료 상태이상으로 동시에 쓰러지는, 인과관계 없는 경우만 진짜 무승부(`"draw"`)로 남겼다.

### 6-5. UI 개선 — 실능치 패널·기술 타입 배경색·셋업 화면 폭

- 대전 중엔 자신이 맞춘 포인트·능력치를 확인할 방법이 없다는 피드백 반영 — 배틀 보드에 HP·공격·방어·특공·특방·스피드 실능치 패널 추가
- 대전 화면의 기술 버튼에도 셋업 카드와 동일하게 타입별 배경색 적용
- 대전 로그 셋업 화면(`.battle-setup-board`)이 grid로 두 카드를 폭 전체에 꽉 채워서 결정력&내구력 페이지(카드 폭 280px 고정, 가운데 정렬)보다 커 보이던 것을 동일한 비율(카드 폭 300px 고정 + 가운데 정렬)로 수정

### 6-6. 턴 로그 텍스트 분리 — 데미지와 상태(기절)를 별도 줄로

"메타그로스의 대폭발 — 172 데미지 (112.4%) · 기절! · 사용자도 반드시 기절!"처럼 데미지 옆에 상태가 붙어있던 걸 요청대로 분리:
```
메타그로스의 대폭발 — 172 데미지 (112.4%)
리자몽은 쓰러졌다
메타그로스는 대폭발의 여파로 쓰러졌다
```
한글 "은/는" 조사는 이름 마지막 글자의 받침 유무로 자동 판별(`eunNeun()`), "○○의 여파로 쓰러졌다"의 기술명은 실제 사용한 기술(`action.move.name`)을 그대로 꽂아 넣어 자폭/대폭발/발버둥 어떤 경우든 자동으로 맞는 이름이 나오게 했다.

### 참고 — 이 세션에서 같이 처리했지만 Phase 2.5 범위 밖인 것

기술표 아티팩트 갱신분 반영(신규 기술 5개: 일렉트로빔·기어오르기·불새·쪼아대기·회전부리)과 신규 포켓몬 2종(브리두라스·아머까오) 추가는 버그 수정이 아니라 콘텐츠 데이터 확장이라 이 문서(버그 수정 위주)에는 포함하지 않는다.
