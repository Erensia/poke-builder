## 1. 파티 빌더 — 타입 상성 요약 컴포넌트 개편안

> **✅ 해결 (2026-09-04, 브랜치 `feat/type-coverage-matrix`).** 수량 집계 그리드 + 클릭 상세
> 패널 → **포켓몬 × 18타입 매트릭스**로 전면 교체. `computeTypeCoverage`/`TypeCoverageCell` 폐기,
> `computePartyDefenseMatrix`(members 열 + 18행 고정, POKEMON_TYPES 순서, null=등배) 신설.
> 종합 열은 확정 규칙(강점 `r≥w ∧ r≥2` / 취약 `w−r≥2` / 보통) 그대로. 셀 색상은 기존 `cnt-*`
> 재사용, 좁은 폭 가로 스크롤, 클릭 상세 제거(hover 툴팁만). 검증: 리자몽메가X 포함 6마리
> 파티로 18×8 표 렌더 + 종합 판정 스팟체크 전부 일치.

### 1-1. 대상

- 컴포넌트: `src/components/TypeCoverageSummary.tsx` (+ `TypeCoverageSummary.css`)
- 집계 로직: `src/lib/partyAnalysis.ts`의 `computeTypeCoverage` / `getPartyMembers`
- 렌더 위치: `src/components/PartyBoard.tsx:117` (`<TypeCoverageSummary slots={slots} />`)

### 1-2. 현재 방식

- 공격 타입 18종을 나열하고, 각 타입 칸에 "이 타입 기술에 약한/견디는 파티원 **수**"를 뱃지로 표기
  (`×4 n` / `×2 n` / `½ n` / `¼ n` / `면역 n`).
- 타입 칸을 누르면 하단에 "그 타입에 대해 등배가 아닌 파티원 목록 + 각자 배율"이 펼쳐진다.
- 즉 **타입 축은 있지만 포켓몬별 표는 없다** — 개별 포켓몬의 방어 상성은 클릭해야 보인다.

### 1-3. 개편안 — 포켓몬 × 타입 매트릭스

선택한 6마리를 항상 표로 펼쳐, 포켓몬별 방어 상성을 한눈에 본다.

**레이아웃**

| | 몬1 | 몬2 | 몬3 | 몬4 | 몬5 | 몬6 | **종합** |
|---|---|---|---|---|---|---|---|
| 노말 | ½ | | ×2 | | | 면역 | 취약 |
| 불꽃 | ×2 | ½ | | ×4 | | | 취약 |
| 물 | | | ½ | | ½ | | 강점 |
| … (18타입) | | | | | | | |

- **가로축(열)**: 빌드한 6마리 포켓몬 전부(선출 3마리로 좁히지 않음). 헤더에 포켓몬 아이콘/이름 + (메가 시 폼 태그).
- **세로축(행)**: 방어 상성 기준이 되는 **공격 타입 18종 전체 (18행 고정)**.
  - 사용자 표현의 "포켓몬의 총 타입"은 이 18종 축을 의미. 파티에 등장하는 타입만 추리지 말고 전부 표기
    (빈 행이 정보 — "아무도 안 걸리는 타입"도 보임). 필터 토글 없음 (1-5 확정).
- **셀(포켓몬 × 타입)**: 그 포켓몬이 해당 타입 기술을 받을 때의 방어 배율.
  - 표기는 **현재 방식 그대로**: `½` / `¼` / `×2` / `×4` / `면역`. 등배(×1)는 공란.
  - 색상도 현재 `cnt cnt-weak / cnt-quad / cnt-resist / cnt-quadresist / cnt-immune` 클래스 재사용.
  - 메가스톤 장착 반영은 `getPartyMembers`가 이미 `getEffectiveForm`으로 처리 중 — 그대로 사용.
- **종합 열 (6마리 열 다음, 7번째 열)**: 그 타입 행에 대해 파티 전체가 **취약 / 보통 / 강점** 중 무엇인지.
  - **판정 규칙 (확정, 2026-09-02)**. 그 타입 행에서
    `w` = 약점 인원 수(배율 > 1: `×2`·`×4`), `r` = 저항 인원 수(배율 < 1: `½`·`¼`·면역)일 때:

    | 결과 | 조건 |
    |---|---|
    | **강점** | `r ≥ w` **그리고** `r ≥ 2` |
    | **취약** | `w − r ≥ 2` |
    | **보통** | 그 외 |

    - 두 조건은 상호배타적(강점은 `r ≥ w`, 취약은 `w ≥ r + 2`). 겹치지 않는다.
    - `면역`은 저항(`r`)에 포함 — 사용자 예시에서 "무효 2마리"를 "저항 2마리"와 동일 처리.
    - `×4`·`¼`도 현재는 **인원 1로만** 집계(가중치 없음). 필요 시 1.0.x에서 재검토.
    - 검증한 예시 (w, r → 결과): (1,1)→보통 · (1,2)→강점 · (2,2)→강점 · (2,3)→강점 ·
      (3,1)→취약 · (3,2)→보통. 전부 일치.

### 1-4. 상호작용

- 현재의 "타입 클릭 → 하단 상세 패널" 동작은 표 자체가 상세를 대체하므로 **제거.**
  대신 행(타입) 헤더 hover 시 그 타입 설명, 셀 hover 시 배율 툴팁 정도.
- 파티가 비었을 때 문구(`포켓몬을 배치하면 상성 요약이 표시됩니다.`)는 유지.

### 1-5. 확정 사항 (2026-09-02)

- **행 개수**: **18행 고정.** 필터 토글 없음. 빈 행(아무도 안 걸리는 타입)도 그대로 표기 — 그 자체가 정보.
  좁은 폭에서 18×7 표는 가로 스크롤 처리.
- **기준 인원**: **빌드한 6마리 전부.** 선출 3마리로 좁히지 않는다(선출 방식과 무관하게 6마리 매트릭스 유지).
- **행 정렬**: **타입 고정 순서.** "취약 행 위로" 같은 동적 정렬 없음 — 매번 같은 위치에서 찾도록.
  순서는 `POKEMON_TYPES`(`src/types/pokemon-type.ts`) 배열 순서를 따른다.
- **기존 컴포넌트 처리**: `TypeCoverageSummary`(수량 집계형 `TypeCoverageCell` + 클릭 상세 패널)는
  **완전 폐기.** 매트릭스가 대체하며 병행 표시하지 않는다. `computeTypeCoverage`/`TypeCoverageCell`도
  다른 소비처가 없으면 함께 제거하고, 매트릭스용 집계 함수(`getPartyMembers` + 포켓몬×타입 배율 표)를
  `partyAnalysis.ts`에 새로 둔다.

## 2. 포켓몬 프로필 — 이니셜 뱃지 → 실제 포켓몬 이미지

### 2-1. 현재 방식

포켓몬 프로필(아바타)은 전부 **이름 첫 글자 + 타입 색 그라디언트**로 그려진다.

- 렌더 패턴: `pokemon.name.at(0)` + `linear-gradient(135deg, TYPE_COLORS[type0], TYPE_COLORS[type1 ?? type0])`
- 등장 위치 및 크기:

  | 위치 | 클래스 | 크기 | 모양 |
  |---|---|---|---|
  | 파티 빌더 슬롯 (`PartySlotCard.tsx:94`) | `.party-slot-avatar` | 36×36 | radius 10px |
  | 배틀 셋업 카드 (`BattleSetupCard.tsx:97`) | `.party-slot-avatar` 재사용 | 36×36 | radius 10px |
  | 매치업 슬롯 (`MatchupSlotCard.tsx:125`) | `.matchup-slot-avatar` | 42×42 | radius 11px |
  | 도감 리스트 (`PokedexPage.tsx:270`) | `.pokedex-list-avatar` | 28×28 | 원형 |
  | 도감 상세 (`PokedexPage.tsx:128`) | `.pokedex-detail-avatar` | 56×56 | 원형 |

  (`ItemDexPage`의 `.itemdex-detail-avatar`는 아이템용이라 대상 아님.)

### 2-2. 목표

각 위치 크기에 맞는 포켓몬 이미지를 구해 이니셜 뱃지를 대체한다. 이미지가 없거나 로드 실패 시
현재의 이니셜+그라디언트로 **폴백**.

### 2-3. 결정해야 할 것

- **이미지 소스 & 키잉**. 현재 `pokemon.json`은 한글 이름을 `id`로 쓰고 전국도감 번호·스프라이트 URL 필드가 없다. 후보:
  - (a) `pokemon.json`에 `dexNo`(전국도감 번호) 필드 추가 → 번호로 스프라이트 파일/CDN 참조.
    로스터를 세대별로 확장 중이므로 병합 스크립트에 `dexNo` 채우는 단계 추가 필요.
  - (b) 스프라이트를 레포에 번들(`public/sprites/`)하고 `dexNo`(또는 슬러그)로 파일명 매칭.
  - (c) 외부 CDN 직접 참조(PokéAPI 스프라이트 raw, Pokémon Showdown 스프라이트 등). 오프라인/속도/안정성 트레이드오프.
- **스프라이트 스타일**. 위치별로 다르게:
  - 28×28 도감 리스트 → 박스 아이콘(dex box icon)류 작은 픽셀 이미지.
  - 36~56px → gen5 도트 / Showdown 스프라이트, 또는 HOME 렌더(고해상도라 축소 시 선명).
  - 픽셀 아트면 작은 크기에서 `image-rendering: pixelated`, HOME 렌더면 일반 스케일.
- **메가 폼**. `megaEvolutions[].form`(예: `"리자몽-메가X"`)도 별도 이미지가 필요. 폼 키로 매칭.
  없으면 기본 폼 이미지로 폴백.
- **라이선스**. 포켓몬 스프라이트/아트워크는 저작권물. 개인·비영리 토이 프로젝트 범위에서만 사용한다는 전제 확인.

### 2-4. 구현 메모

- 5개 위치가 같은 로직(이미지 or 폴백)을 쓰므로 **공유 `<PokemonAvatar pokemonId size formLabel />` 컴포넌트로 통합**하면서 교체.
  현재는 컴포넌트마다 `avatarGradient` 계산이 중복돼 있다(`PartySlotCard`·`BattleSetupCard`·`MatchupSlotCard` 거의 동일, `PokedexPage`는 함수형).
- `<img>` `loading="lazy"` + `onError`로 폴백 스위치.
- `object-fit: contain`, 배경은 기존 그라디언트를 옅게 깔아도 됨(투명 스프라이트 뒤 배경).

## 3. 배틀타워 — 6슬롯 빌더 + 3선출·순서 화면

> **✅ 해결 (2026-09-04, 브랜치 `feat/battle-tower-team-select`).** 편측 빌드 슬롯 3→6
> (`BATTLE_BUILD_SIZE=6`·`BATTLE_SELECT_SIZE=3`). 3-5 결정: **3~6 유연 허용**(유효 빌드 ≤3인
> 편은 선출 화면 스킵, 4+면 3마리 선출) · 순서 = **클릭 순서대로 1·2·3 번호 부여**(재클릭 해제 +
> 자동 재넘버링) · 상대 팀·리드 전부 노출 · "다시 선출" 없음(전체 리셋만). 엔진 무변경 —
> `startBattleWith(sel)`이 선출 인덱스를 순서대로 파티 배열에 담아 `createBattleState` 호출.
> 검증: 5마리 빌드 → 선출 화면 → 밀로틱·엘풍·팬텀 순 선택 → 배틀 A 트래커가 그 순서, 밀로틱 리드.

### 3-1. 배경

Phase 8(배틀타워 리뉴얼)은 **2026-09-03 착수 결재에서 "3슬롯만 빌드"로 확정**했다 — 편측 3마리를 그대로 빌드하고, 슬롯 0이 리드. 선출·순서 개념이 없다. `phase8-plan.md` §2가 "미확정"으로 남겨뒀던 `6빌드→3선출 vs 3만 빌드` 갈림길에서 후자를 택한 것.

6마리 풀에서 3마리를 골라 **순서까지 정하는 선출 UX**는 교체 인프라(Phase 8)와 의존성이 없다 — 엔진은 이미 편측 파티를 가변 길이 배열로 받으므로, 3마리를 순서대로 담아 넘기기만 하면 된다. 그래서 여기로 분리해 ver.1.0.x 업데이트로 처리한다.

### 3-2. 대상

- `src/hooks/useBattleSetup.ts` — 편측 3슬롯 배열 → **6슬롯 배열**로 확장.
- `src/components/BattleLogPage.tsx` — 빌드 완료 후 **선출 화면** 단계 신설(빌드 → 선출 → 대전).
- `src/components/BattleSetupCard.tsx` — 슬롯 입력 카드. 그대로 6개 반복 렌더.
- `createBattleState` — **변경 없음.** Phase 8에서 이미 `{ slots: EvaluatorSlot[]; movesList: Move[][]; leadIndex? }`를 받는다. 선출 결과 3마리를 고른 순서대로 배열에 담아 넘기면 끝.

### 3-3. 현재(Phase 8 이후) 방식

- 편측 `BattleSetupCard` ×3. 슬롯 0 = 리드 고정. 선출/순서 선택 없음.
- 상대(B)도 플레이어가 3슬롯 수동 구성.

### 3-4. 개편안

- **빌드 단계**: 편측 `BattleSetupCard` ×6 (양측 12개). 좁은 폭에서 접기/스크롤 처리.
- **선출 화면**: 빌드 완료 후 진입. 양측이 자기 6마리 중 **3마리 + 순서**를 고른다. 첫 슬롯이 리드.
  - 상대(B) 선출도 우선 **수동**(플레이어가 상대 팀도 직접 선출). 자동 선출 로직/AI는 스코프 밖(별도 항목).
- **대전 시작**: 선출된 3마리를 순서대로 `slots` 배열에 담아 `createBattleState` 호출.
- 샘플 프리셋(`slotPresets`)은 **슬롯 단위 유지.** 팀 단위(6마리 세트) 저장은 별도 검토.

### 3-5. 결정해야 할 것

- **6빌드 강제 여부**: 6마리를 다 채워야 선출로 넘어가게 할지, 3~6마리 유연하게 허용할지(3마리만 빌드하면 선출 화면을 스킵).
- **순서 지정 UI**: 드래그로 정렬 vs 클릭 순서대로 1·2·3번 부여 vs 번호 드롭다운.
- **상대 팀 프리뷰**: 선출 화면에서 상대 6마리를 서로 다 보여줄지(수동 구성이라 어차피 노출), 리드 결정 시 상대 리드를 가릴지.
- **선출 결과 편집**: 대전 시작 후 "다시 선출"로 돌아갈 수 있게 할지(로그 초기화 동반).

## 4. 배틀타워 — 메가진화 버튼 (턴 중 메가진화 선언)

### 4-1. 현재 방식

메가진화는 **메가스톤을 도구로 장착하면 자동**으로 적용된다. `getEffectiveForm`이 `findMegaFormByStone`으로
스톤을 감지해 타입·종족값·특성을 메가폼 기준으로 덮어쓰고(`src/lib/pokemonForm.ts`), 배틀에서는
`createFighterState`가 배틀 시작 시점에 그 값을 그대로 굳힌다. 즉 **스톤을 들면 1턴부터 항상 메가 상태**이고,
"이번 턴에 메가진화한다"는 선언도, "팀당 1회" 제약도 없다.

### 4-2. 개편안 — 본가식 메가진화 선언

- 스톤을 든 포켓몬은 배틀 시작 시 **기본 폼**으로 나온다.
- 매 턴 기술 선택 UI에 **"메가진화" 토글**을 둔다. 켜고 기술을 고르면 그 턴 **행동 직전에 메가진화**가 처리된다
  (타입·종족값·특성 교체 + 실능치 재계산 + 스피드 재산정 → 턴 순서에 반영).
- **팀당 1회.** 한 번 메가진화하면 그 배틀 내내 유지되고, 그 편의 다른 포켓몬은 더 못 한다.
- 교체로 물러났다 다시 나와도 메가 상태 유지(본가 규칙).
- 로그 문구: `~는 ~로 메가진화했다!`.

### 4-3. Phase 8 의존성 / 작업량

- **Phase 8의 `runTurn` 액션 리팩터(§3)에 얹힌다.** 메가진화는 `move｜switch`에 이은 **세 번째 축**이 아니라
  `{ kind: "move"; moveId; mega?: true }`처럼 move 액션의 플래그로 붙이는 게 자연스럽다(행동 직전 처리라).
- `BattleFighterState`에 `megaStone`(장착 스톤 id)·`hasMegaEvolved`(폼 상태)·편별 `megaUsed` 플래그 추가.
  현재 배틀 시작 시 굳히는 메가 적용 로직을 "선언 시점에 적용"으로 옮기는 게 핵심 변경.
- 매치업(결정력·내구력) 페이지는 1턴 스냅샷이라 **지금처럼 "스톤 장착 = 메가"로 계속 취급**(별도 토글 불필요).
  파티 빌더 아바타/스탯 표시도 현행 유지(빌드 시점엔 메가폼을 보여주는 게 편함).

### 4-4. 결정해야 할 것

- **빌더 표시**: 파티 빌더·배틀 셋업 카드에서 스톤을 들면 지금처럼 메가폼 스탯·타입·아바타를 보여줄지,
  아니면 "메가 예정" 배지만 달고 기본 폼으로 보여줄지.
- **기본값**: 메가 토글의 턴 기본 상태(항상 꺼짐 시작 vs 마지막 선택 기억).
- **강제 메가**: 스톤을 들었는데 배틀이 끝나도록 토글을 안 켰으면 그대로 기본 폼으로 두는 게 맞음(본가도 그러함) — 확인만.
- **AI/상대측**: 상대(B)도 수동이라 플레이어가 상대 메가 타이밍도 고른다. 자동 로직은 스코프 밖.

### 6-1. 일루전 (조로아크 / 히스이조로아크)  ✅

- **본가**: 파티의 **마지막 슬롯**에 있다가 등장하면 그 마지막 포켓몬의 **이름·아이콘·성별로 위장**하고,
  데미지를 받는 순간 위장이 풀린다. 타입·실능·특성은 조로아크 그대로(위장은 표시만).
- **현재**: `abilities.json`에 설명만, `일루전` 로직 미배선. 교체 인프라(Phase 8)는 깔렸으니
  "등장 시점에 마지막 슬롯 여부 확인" 자체는 가능하지만, **위장 표시(트래커·배틀보드·로그에서
  다른 포켓몬 이름/아이콘)**·**피격 시 위장 해제 연출**이 UI+엔진 양쪽 작업이라 분리.
- 배선 시: `BattleFighterState.illusionAs?: string`(위장 대상 종 id) + `applyEntryAbilityOnSwitchIn`에서
  세팅, `applyDamageToDefender`에서 첫 피격 시 해제 + 로그, BattleLogPage의 이름 표시 지점이
  `illusionAs`를 우선 참조.
- **완료**: 위 그대로 + 리드가 조로아크류면 `createBattleState`에서도 세팅, `computeIllusionTarget`
  (파티 뒤에서부터 자신 아님·안 쓰러짐 첫 슬롯), `performSwitch` 물러날 때 해제, 로그 교체 줄
  (`switches[].inPokemonId`)·파티 트래커 칩에도 위장 이름. 데미지 경로만 해제 트리거라 상태이상·
  날씨·설치물로는 안 풀린다(본가 일치). 성별 위장은 스킵(엔진에서 성별 표시 안 함).

### 6-2. 희망사항(Wish) — 슬롯 이월  ✅

- **본가**: 희망사항은 사용한 포켓몬이 아니라 **2턴 뒤 그 자리에 있는 포켓몬**을 회복시킨다.
  사용 후 교체하면 새로 나온 포켓몬이 회복받는다.
- **현재**: `wish`가 `BattleFighterState.volatile`에 붙어 있어 **교체로 물러나면 소멸**한다
  (`performSwitch`가 volatile을 통째로 비움). 사용자가 희망사항 → 교체하면 회복이 사라진다.
- 배선 시: `wish`를 fighter volatile이 아니라 **`BattleSide`에 큐**(`{ turnsLeft, healAmount }`)로
  옮기고, 턴 종료 시 그 편 활성에게 적용. `performSwitch`의 volatile 클리어 대상에서 빼야 함.
- **완료**: `BattleSide.wish = { turnsRemaining, healAmount }`. `inflictsVolatile` 루프에서 `wish`를
  `inflictVolatile` 대신 편 큐로 가로채고(자기 편 겨냥이라 반사 무관), `healAmount`는 시전 시점
  시전자 `maxHp/2` 고정(수령자 기준 아님 — 본가 일치). EOT 카운트다운은 편별로, 발동 시 그 편
  현재 활성이 회복. 재사용 실패 판정도 `BattleSide.wish` 유무로. `VolatileCondition` union의
  `"wish"`는 무브 데이터 타입용으로 남겨둠(런타임엔 절대 세팅 안 됨). 상태 태그에 "희망사항 대기".
- 검증: 시전 → 교체 → EOT에 새로 나온 포켓몬이 시전자 절반(예: 71)만큼 회복, 편 큐 소멸.

### 6-3. 스크린(리플렉터·빛의장막·오로라베일) — 편 기반 이전  ✅

- **현재**: `screens`가 `BattleFighterState`에 붙어 있어 교체하면 그 포켓몬과 함께 사라진다.
  본가는 **편(side) 전체**에 걸리는 효과라 교체해도 남아야 한다.
- Phase 8 §1에서 설치물(hazards)만 `BattleSide`로 옮기고 스크린은 남겨 둔 알려진 단순화.
- 배선 시: `BattleSide.screens: Partial<Record<"reflect"|"lightScreen"|"auroraVeil", number>>`로 이전,
  데미지 감산·턴 종료 카운트다운·배리어프리(clearsAllScreensOnEntry) 지점을 side 기준으로.

> 넣었으나, 본가는 유턴 사용측 교체가 **그 턴 안에서**(상대 행동·턴 종료 처리보다 먼저) 일어난다.
> 이제 사용측이 기술과 함께 나올 슬롯을 미리 지정하고(`TurnAction.selfSwitchTo` — 기술 그리드
> 아래 인라인 셀렉터), `runTurn` 행동 루프가 명중 직후 `performSwitch`를 인라인 실행한다 →
> 느린 상대는 새로 나온 포켓몬을 상대하고 EOT도 새 포켓몬에게 간다. 카트리지처럼 명중을 본 뒤
> 팝업으로 고르는 게 아니라 미리 커밋하는 방식이며(runTurn을 재개 가능한 상태머신으로 만드는
> 대규모 리팩터를 피함), "양쪽 수를 미리 정하고 턴을 돌리는" 이 시뮬레이터 흐름에 맞다.

### 7-1. 길동무 상호 기절 시 배틀이 그대로 끝남 (버그)

- **증상**: 길동무(Destiny Bond)로 양쪽이 동시에 기절하면, 파티에 안 쓰러진 슬롯이 남아 있어도
  배틀이 즉시 끝난다(무승부 또는 한쪽 승리로 확정).
- **원인**: `battleSimulator.ts` `runTurn`의 자폭 콤보 판정
  `if (action.fainted && action.selfFainted) { winner = key; break; }`(≈4954행)이 예비 슬롯을
  보지 않는다. Phase 8 §S8에서 예비 슬롯 인식(`hasLivingReserve`)은 EOT 무승부·멸망의노래 더블
  기절 블록에만 넣었고, 이 mid-loop 자폭 경로는 빠졌다.
- **기대**: 자폭 콤보로 활성이 쓰러져도, 그 편에 예비 슬롯이 있으면 배틀을 끝내지 말고
  `forcedSwitch`로 넘긴다. 양쪽 다 예비 없으면 지금처럼 `winner = key`(자폭 실행 쪽 승리), 한쪽만
  없으면 그쪽만 패배.
- **대상**: `runTurn` mid-loop 승자 판정 + 최종 winner/`forcedSwitch` 블록 통합.

### 7-2. 유턴(U-turn)류 자체교체 미구현 (미구현)

- **증상**: 유턴·볼트체인지·배턴터치가 데미지(또는 랭크 인계)만 하고 **사용측 교체가 일어나지 않는다.**
- **기대**: 명중해 효과를 준 뒤(대상 기절 여부 무관), 그 턴 안에서 사용측이 교대 슬롯을 골라
  교체 → 등장 파이프라인(설치물·위협 등) 실행 → 턴 종료 → 다음 턴. 교대할 슬롯이 없으면 교체
  없이 진행. 대상이 유턴에 기절했으면 대상 쪽은 강제 교체(§3 기존 흐름).
- **배선안**: `Move.selfSwitchAfterDamage?: boolean` 신설(유턴·볼트체인지·번개날개·톤보가에리 등).
  `resolveAction` 후 이 플래그면 `runTurn`이 사용측에게 교체 UI를 요구(강제 교체 `forcedSwitch`
  흐름을 "자발 교체" 변형으로 재사용). 배턴터치는 랭크·일부 volatile까지 인계(별도 플래그).
- **참고**: `phase8-plan.md` §3은 "플레이어 선택 교체"만 다뤘고 기술 유발 교체는 스코프 밖이었음
  — 여기서 추가.

### 7-5. 앙코르∩도발 등으로 고를 기술이 없을 때 턴 진행 불가 (버그, 2026-09-04 추가)

- **증상**: 서로 교체 불가 상황에서 A가 명상 → B가 앙코르 → A는 명상만 강제 → B가 도발 →
  A는 앙코르로 명상만 써야 하는데 도발로 변화기를 못 쓴다. 이때 배틀타워는 **턴 진행이
  막힌다**(고를 수 있는 기술 0, "턴 진행" 게이트가 안 풀림). 본가는 이 상황에서 발버둥.
- **원인**: (1) 엔진 `resolveAction`의 도발·사슬묶기·앙코르 판정이 `STRUGGLE_MOVE`도 앙코르
  위반으로 막았다. (2) UI `isStruggling`이 PP·구애잠금만 봐서 "합법 수 0" 상태를 발버둥으로
  인식하지 못했다.
- **해결 (완료)**: 엔진은 제약 판정에서 `STRUGGLE_MOVE`를 통과(지속 턴수 소모는 유지).
  UI `isStruggling`은 전 슬롯에서 `moveRestrictionMessage`가 non-null이면 발버둥으로 처리 —
  도발 상태 전부 변화기·앙코르 강제 기술 PP 0 케이스도 함께 해결.
- **대상**: `battleSimulator.ts` 2-0 제약 블록, `BattleLogPage.tsx` `isStruggling` + 발버둥 안내.
