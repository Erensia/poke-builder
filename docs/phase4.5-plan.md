# Phase 4.5 기획 — 포켓몬 로스터 확장 & 사이드 메뉴 활성화

> 이어서 읽기: [Phase 4 기획](phase4-plan.md)
> Phase 4에서 계획했던 5개 항목(§2 명중률 배율·§4 트릭룸·§1 회복 엔진·§3 날씨 지속시간+스크린·§7 UI 정합성)을 전부 마쳤다([PR #2](https://github.com/Erensia/poke-builder/pull/2)). 이 문서는 사용자가 이번에 새로 요청한 두 항목(포켓몬 로스터 확장, 사이드 메뉴 활성화)과, Phase 4에서 스코프 밖으로 남긴 백로그(§5·§6·§8·§9)를 한데 정리한 것이다.

## 0. 이 문서의 성격

새로 발견한 문제가 아니라 (1) 사용자가 이번에 직접 요청한 신규 작업 두 건과 (2) `phase4-plan.md`에 "우선순위 낮음"으로 남아있던 이월 항목을 재우선순위한 것. 이월 항목의 배경은 `phase4-plan.md`와 그 위 링크를 따라가면 된다.

## 1. 포켓몬 로스터 확장 (신규 요청)

현재 로스터는 23종. 구체적으로 몇 마리를 추가할지, 어떤 포켓몬을 넣을지는 작업하면서 사용자가 지정한다.

- **일렉트릭필드를 배우는 포켓몬 반영**: [phase4-plan.md §7](phase4-plan.md#7-ui-정합성-갭)에 남아있던 이월 항목 — Phase 3에서 일렉트릭필드 *기술* 데이터는 추가했지만 로스터 어떤 포켓몬의 `learnset`에도 넣지 않았다(그래스/미스트/사이코필드는 각각 6마리씩 확인된 것과 대비). 이번 로스터 확장에서 일렉트릭필드를 쓸 수 있는 포켓몬을 실제로 넣으면서 함께 해결한다.
- 새 포켓몬을 넣을 때마다 같이 확인할 것: 메가진화 여부/전용 스톤, `learnset`(신규 기술 포함 여부), 특성(숨겨진 특성 포함), 능력치, 그리고 §3(아래, 필드 개별 기술 상호작용)에 나오는 필드 전용 기술(그래스슬라이더·대지의파동 등)을 배우는지 — 이걸 로스터 추가 시점에 같이 체크해두면 §3 작업이 나중에 훨씬 수월해진다.

## 2. 사이드 메뉴 활성화 — 포켓몬 도감 / 기술표 (신규 요청)

[Sidebar.tsx](../src/components/Sidebar.tsx)의 `NAV_ITEMS`에 "포켓몬 도감"·"기술표"가 `view: null`로 박혀 있어 클릭해도 아무 반응이 없다(버튼 자체가 `disabled`). `AppView` 타입(`"party" | "matchup" | "battle-log"`)에 새 뷰가 아예 없어서 단순히 플래그를 켜는 게 아니라 페이지 컴포넌트를 새로 만들어야 하는 실제 기능 작업이다.

- **포켓몬 도감**: 로스터 전체를 훑어보는 조회 페이지. 타입·능력치·특성(숨겨진 특성 포함)·메가진화 폼·`learnset`을 한눈에 볼 수 있으면 됨
- **기술표**: 현재 335개 기술을 타입·분류(물리/특수/변화)·위력·우선도 등으로 필터·정렬해서 보는 조회 페이지
- 둘 다 기존 데이터 조회 함수(`getPokemon`/`getMove` 등)만 있으면 되고 시뮬레이터 로직(`battleSimulator.ts` 등) 변경은 필요 없다 — 순수 조회/필터 UI라 리스크가 낮음
- `App.tsx`에 뷰 분기 추가, `Sidebar.tsx`의 `view: null` → 실제 뷰로 교체

## 4. 우선도·상태이상·기타 개별 도구 효과 (Phase 4 §6 이월)

도구표에서 각각 서로 다른 개별 메커니즘이 필요해 미뤄온 항목들 — 우선순위 낮음(도구 1개당 기술/상황 1개라 서로 재사용 가능한 부분이 적음):

| 도구 | 필요한 메커니즘 |

| 하양허브 | 능력 하락을 원래대로 되돌림(1회용) |
| 구애스카프 | 스피드 1.5배 + "교체 전까지 같은 기술만" 제약 |
| 전기구슬 | 피카츄 전용 스탯 배율(로스터에 피카츄 없어 우선순위 낮음) |
| 기합의띠·기합의머리띠 | HP 1 남기고 버티기(1회용/확률부) |
| 멘탈허브 | 헤롱헤롱·도발 등 특정 행동방해 일괄 해제(1회용) |

| 왕의징표석 | 데미지 시 10% 추가 풀죽음 확률 |
| 검은철구 | 스피드 0.5배 + 의사 땅타입 부여 |
| 초점렌즈 | 급소율 랭크 +1 |
| 아름다운허물 | 교체 방해 무시(1v1엔 교체 자체가 없어 사실상 의미 없음) |

## 5. 데이터 완성도 (Phase 4 §8 이월)

- **변화기 `effect` 텍스트 누락 다수**: 도발·최면술·중력·사슬묶기 등 `power: null` + `effect: ""`인 상태변화 기술이 다수 남아있음. 효과 자체가 뭔지 텍스트도 없는 상태라 데이터 보강이 최우선(구현은 그다음)
- **해동 기술 7종 데이터 없음**: 나무위키 기준 얼음 상태에서 쓰면 자동 해동되는 기술 10종 중 3종(불사르기·열사의대지·플레어드라이브)만 현재 335개 기술 데이터에 있음. 성스러운불꽃·스팀버스트·열탕·크로스플레임·화염바퀴·화염볼·휘적휘적포는 애초에 기술 자체가 없음
- **`Ability.setsWeather` 양쪽 동시 보유 시 우선권 규칙 미확인**: 지금은 실효 스피드가 빠른 쪽이 이긴다고 임시로 정했는데 챔피언스 실제 규칙(본가는 스위치인 순서 기준) 확인 필요

(출처: [phase4-plan.md §8](phase4-plan.md#8-데이터-완성도))

## 6. Phase 4 §3 작업 중 새로 발견한 것 — 그라운드코트 · 오로라베일

Phase 4 §3(날씨/필드 지속시간) 작업 때 계획과 실제 데이터가 어긋나는 걸 발견해서 사용자 확인 후 스코프를 조정했던 부분 — 그 과정에서 나온 후속 확인 사항만 여기 남겨둔다.

- **그라운드코트**: `items.json`에 데이터 자체가 없다(이름조차 없음). Phase 3/4 문서에는 "필드(그래스필드 등) 지속시간 5→8턴 연장 도구"로 적혀 있었는데, 정작 빛의점토는 실제로는 필드가 아니라 **스크린(리플렉터/빛의장막)** 연장 도구였다(Phase 4 §3에서 확인, 이미 배선 완료). 그라운드코트가 실제로 존재하는 챔피언스 도구인지, 필드 전용 연장 도구가 따로 있는 건지 재확인 필요
- **오로라베일**: `moves.json`에 데이터 자체가 없다(로스터 학습자 0마리). 데이터가 보강되면 리플렉터/빛의장막과 같은 방식(`Move.setsScreen`)으로 추가하되, 오로라베일은 물리·특수를 동시에 반감시키고 날씨(눈)가 있어야 쓸 수 있는 예외 규칙이 있어 그 부분만 별도 로직이 필요

## 7. 설계 범위 밖 — 파티 단위 확장이 먼저 논의돼야 함 (Phase 4 §9 이월)

1v1 단일 대전 시뮬레이터라는 지금 설계 전제 자체를 안 건드리면 의미가 없는 항목들. 파티 배틀 확장을 언젠가 논의하게 되면 그때 같이 검토:

- **엔트리 해저드**(독압정 등): "교체" 개념이 없으면 무의미
- **집단구타**: 위력이 파티 전원의 공격 종족값 기반이라 파티 개념 필요
- **고스트다이브의 "상대 방어 무시"**: 나이트헤드류(`fixedDamage`)처럼 방어 무시 전용 필드를 추가하면 되긴 하지만, 1v1 범위 안에서도 할 수 있는 작업이라 파티 확장과는 무관 — 우선순위만 낮게 잡아둠
- **잠꼬대**("배운 기술 중 하나를 무작위로 사용"): 파티 확장과 무관하지만 별도 메커니즘이 필요해서 함께 낮은 우선순위

## 8. 설명 텍스트만 있고 전투 로직 미구현인 특성 정리 (라이츄 추가 중 발견)

라이츄 추가 때 정전기·피뢰침·일렉트릭메이커·노가드를 abilities.json에 "설명 텍스트만" 넣고 전투 로직 연결은 보류하기로 했는데(사용자 확인), 그러면서 보니 이 패턴이 이미 기존 로스터 특성 다수에 광범위하게 퍼져 있었다. `abilityModifiers.ts`가 실제로 소비하는 필드는 `modifiers`(offense/defense 배율)·`setsWeather`·`stabOverride`·`bypassesImmunityForTypes` 4가지뿐이고, 이 필드가 하나라도 채워진 특성만 전투 계산에 실제로 반영된다. 지금 abilities.json 54개 중 이 4개 필드가 하나도 없는 **43개**가 설명 텍스트만 있고 실제로는 아무 효과도 없다(`battleSimulator.ts` 680행 "모래숨기 같은 특성 쪽 배율은 아직 없음" 주석이 사실상 이 전체를 대표하는 TODO).

**이미 연결된 11개** (참고용): 단단한발톱, 가뭄, 메가런처, 두꺼운지방, 페어리스킨, 모래의힘, 모래날림, 적응력, 테크니션, 잔비, 배짱

**미구현 43개**를 메커니즘 유형별로 묶으면:

| 유형 | 필요한 확장 지점 | 해당 특성 |
|---|---|---|
| HP 1/3 이하 위력 1.5배 (특정 타입) | `modifiers`에 `hpBelowThird` 같은 조건 추가 | 맹화, 급류, 심록, 벌레의알림 |
| 날씨 조건부 배율/회복 | `modifiers`의 `weatherIs`는 있지만 스탯 배율·회복은 별도 로직 필요 | 선파워, 엽록소, 쓱쓱, 모래숨기(회피), 옹골참, 젖은접시 |
| 접촉 피격 시 발동(확률부 상태이상/데미지/랭크변화) | 방어측 트리거 훅 전체가 없음 — 가장 큰 신규 인프라 | 정전기, 저주받은바디, 까칠한피부, 헤롱헤롱바디, 깨어진갑옷 |
| 특정 타입 기술 피격 시 발동 | 위와 같은 방어측 트리거 훅 | 정의의마음, 타오르는불꽃, 지구력, 피뢰침 |
| 타입 면역 부여 | `bypassesImmunityForTypes`(면역 무시)의 반대 방향 — 아직 없음 | 부유, 피뢰침(중복 표기, 무효화+랭크업 둘 다 필요) |
| 상태이상 면역/반사/전이 | 상태이상 판정 훅 필요 | 유연, 정신력, 싱크로, 클리어바디, 미러아머 |
| 명중률/회피율 특수 규칙 | `accuracyCrit.ts` 확장 | 날카로운눈, 노가드 |
| 등장 시 1회 발동(필드/특성복사 등) | `setsWeather`와 같은 패턴으로 `setsField` 등 신설 | 일렉트릭메이커, 트레이스, 긴장감, 습기, 그림자밟기 |
| 우선도 조작 | `Move.priority`와 별개로 특성발 우선도 가산 필요 | 짖궂은마음 |
| 벽/대타 무시 | `setsScreen` 방어 로직에 예외 추가 | 틈새포착 |
| 랭크변화 무시(데미지 계산) | `moveContext.ts`에서 랭크 반영 전 분기 필요 | 천진 |
| 기타(무게·PP·타입변경·도구무효화 등 1회성) | 각각 별도 메커니즘, 재사용성 낮음 | 라이트메탈, 프레셔, 서투름, 촉촉보이스, 변환자재, 텔레파시, 굳건한신념 |
| (신규, 이번에 추가) | 위 항목들과 동일한 유형에 이미 포함 | 정전기·피뢰침(접촉/면역), 일렉트릭메이커(필드), 노가드(명중) |

이 43개를 전부 한 번에 구현하는 건 범위가 너무 크다 — Phase 4 §6(도구 개별 효과)처럼 항목별로 서로 다른 메커니즘이 필요해서 우선순위를 매겨 나눠 진행하는 편이 낫다. 특히 "접촉 피격 시 발동" 훅은 정전기·저주받은바디·까칠한피부·헤롱헤롱바디·깨어진갑옷 5개가 동시에 덕을 보는 공용 인프라라 먼저 붙이면 투자 대비 효율이 가장 좋다.
