# Phase 6.5 기획 — 매치업 페이지 개선 및 로그 문구 정비

> 이어서 읽기: [Phase 6 기획](phase6-plan.md)
> Phase 6 §2-1 정비 후보 중 "매치업 페이지에 반영 안 된 축들"을 사용자와 논의하면서, 이 페이지 자체를 손보는 작업으로 범위가 커져 별도 페이즈로 분리했다(2026-08-26). 이후 Phase 6 §1-4(대전 로그 UI 문구 정비)도 착수 직전 사용자 재검토로 이 문서에 합류했다(2026-08-27, §4 참고) — 서로 직접 연관은 없지만 둘 다 "기존 걸 다듬는" 성격이라 같이 묶었다.

## 0. 배경

Phase 6에서 매치업 페이지(`MatchupPage.tsx`, `evaluateSlotMatchup`)에 반영 안 된 축 4개(매지션/곡예 도구 강탈, 곡예 스피드 2배, 고스트다이브 방어류 무시)를 발견했다. 이 프로젝트에는 페이지가 두 개 있다는 걸 먼저 정리해둔다:

- **대전 로그 페이지**(`BattleLogPage.tsx`, `runTurn`): 턴을 실제로 하나씩 진행시키는 배틀 시뮬레이터. 매 턴 상태(도구를 뺏겼는지, 직전에 무슨 기술을 썼는지 등)를 그대로 들고 가기 때문에 위 4개 효과가 이미 정상 반영돼 있다 — **손댈 것 없음**.
- **매치업 페이지**(`MatchupPage.tsx`, `evaluateSlotMatchup`): "결정력 vs 내구력" 한 방 비교 계산기. 턴 개념이 없는 스냅샷이라 "직전 턴에 뭘 했는지"에 의존하는 축이 반영될 자리가 없다.

**사용자 확인(2026-08-26)**: 매치업 페이지도 어디까지나 "1대1 포켓몬 대결"을 상정한 페이지이므로, 1대1 대결에서 실제로 반영돼야 하는 로직은 전부 반영돼야 한다는 게 사용자 의견 — 단, 이 축들은 "이전 턴에 뭘 가정하느냐"에 따라 결과가 달라지므로 **토글(켜고 끄기)로 사용자가 직접 가정을 선택**하는 방식으로 넣기로 확정했다.

## 1. 토글형 "이전 턴 가정" 4종

매치업 페이지 양쪽 슬롯에 각각 다음 토글을 추가한다(기본값은 전부 꺼짐 = 지금과 동일한 계산):

- **매지션/곡예로 상대 도구를 뺏었다고 가정** — 켜면 이 슬롯의 `item`을 없는 것으로 계산(또는 매지션/곡예 보유 슬롯이 상대 도구를 가져온 것으로 반영 — 세부 UX는 착수 시 결정).
- **곡예 발동 직후(스피드 2배)라고 가정** — 켜면 이 슬롯의 실효 스피드를 2배로 계산.
- **고스트다이브 2턴째(방어류 무시)라고 가정** — 켜면 이 슬롯이 상대의 방어/판별/버티기/킹실드를 무시하는 것으로 계산.

세부 구현 시 확인 필요: 토글이 "공격측/방어측 중 어느 슬롯"에 붙어야 하는지(효과별로 다름 — 예: 도구 강탈은 강탈한 쪽, 곡예 스피드는 곡예를 쓴 쪽 자신), 토글 간 상호 배제 필요 여부(예: 도구 강탈 토글을 켰는데 그 슬롯이 애초에 매지션/곡예 보유가 아니면 의미 없음 — UI에서 막을지 그냥 허용할지).

## 2. 스피드 비교 신설 (사용자 신규 요청, 2026-08-26)

매치업 페이지가 지금은 결정력·내구력만 비교하고(`computeOffensePower`, `computeBulkPower`, `evaluateMatchup`) 스피드는 아예 안 보여준다. 실제로 "누가 먼저 움직이는지"가 결정력/내구력만큼 중요한 축이라 스피드 비교를 신설한다.

- 최소 요구사항: 양쪽 슬롯의 실효 스피드(특성/도구/날씨/랭크 반영)를 계산해서 어느 쪽이 먼저 움직이는지 표시.
- 위 §1의 "곡예 스피드 2배" 토글과 자연히 연동돼야 한다(토글을 켠 슬롯의 스피드 계산에 2배가 반영된 상태로 비교).
- 세부 구현 시 확인 필요: 트릭룸 가정 토글도 같이 넣을지(스피드 역전), 마비로 인한 스피드 0.5배 가정도 넣을지 — 우선순위는 착수 시 사용자와 조율.
- **대안 검토 후 기각(2026-08-27)**: 사용자가 1차 정리 항목에서 "결정력&내구력 페이지와 같은 UI를 가진 완전히 별도의 새 페이지"로 다시 요청했으나, 재확인 결과 위 계획대로 **매치업 페이지 내 통합을 유지**하기로 확정 — 새 페이지 신설 없음.

## 4. 대전 로그 UI 문구 전면 정비 (Phase 6 §1-4에서 이월 → **다음 페이즈로 미룸**, 2026-08-27)

> **상태(2026-08-27, 2차 테스트 후)**: 사용자가 대전 로그를 직접 돌려보며 정리한 수정 항목(§6-2)이 늘어나면서, "문구를 전부 나열해 톤·형식을 한 번에 통일하는" 이 전면 정비는 **뒤로 미루기로 확정**. 대신 §6-2에 모인 개별 항목 중 문구 성격인 것(탈/지구력 문구, 랭크업 결과 문구, 랭크 상한 문구, 방어 실패 문구 등)은 각자 필요한 로직 수정과 함께 Phase 6.5에서 처리한다 — 전면 통일은 그 뒤에 남은 문구를 대상으로 별도 페이즈에서.

원래 Phase 6 §1-4로 편성돼 있던 항목인데, 착수 직전 사용자 재검토로 이 문서로 옮겨왔다. 매치업 페이지 개선과 직접 연관은 없지만, 두 작업 모두 "새 기능보다 기존 걸 다듬는" 성격이라 Phase 6.5에서 같이 다룬다.

Phase 5에서 특성/기술 로직을 워낙 많이(70종 넘게) 새로 붙이면서 `BattleLogPage.tsx`의 로그 문구가 그때그때 개별적으로 추가돼왔다 — 한 번에 모아서 톤·형식·정보량을 통일하는 리뷰가 필요하다.

- **지금 상태**: 로그 문구가 최소 6가지 서로 다른 패턴으로 흩어져 있다 — `STATUS_ONSET_TEXT`/`STATUS_TRIGGER_TEXT`/`STATUS_CURE_TEXT`(상태이상 3단계, 함수 맵), `VOLATILE_LABELS`(행동방해류, 칩 전용 라벨), 메인 라인에 인라인으로 박힌 `· OO 발동!` 조각들(수십 개), 특성 전용 문구(예: 흑안개 "양쪽의 능력 변화가 전부 원래대로 돌아갔다!", 대타출동 "대타가 대신 맞았다!"), 방어류 전용 문구, `moveRestrictionMessage`(도발/사슬묶기/앙코르). 특성이 발동했을 때 "OO의 [특성명]!"으로 시작하는 것도 있고 그냥 결과만 말하는 것도 있어 형식이 일관되지 않다.
- **필요한 작업**: (1) 전체 로그 문구를 한 번에 나열해서 톤(예: 전부 "OO의 [원인]! [결과]" 형식으로 통일할지)·정보량(포켓몬 이름을 매번 반복할지, 대명사로 줄일지)·기절 시 문구(현재 `battle-fighter-fainted`로 " (기절)"만 붙는데 더 명확한 문구가 필요한지)를 검토. (2) 함수 맵 방식(STATUS_*_TEXT)과 인라인 조각 방식이 혼재하는데 특성/기술이 계속 늘어날 걸 감안하면 어느 한쪽으로 통일하는 게 유지보수에 유리한지 결정. (3) 실제 대전 로그를 몇 판 돌려보면서 정비.
- **범위**: 로직 자체는 건드리지 않고 표시 문구만 다듬는 순수 UI 작업이라 회귀 위험은 낮지만, 문구가 수십 곳에 흩어져 있어 손이 많이 간다.

## 6. 대전 로그 페이지 추가 정비 후보

### 6-1. 1차 정리 (2026-08-27)

1차 정리 파일에서 대전 로그 페이지 관련 항목. §4(문구 전면 정비)가 뒤로 밀리면서, 여기 문구 항목들도 §4를 기다리지 않고 §6-2와 함께 Phase 6.5에서 개별 처리한다.

- **랭크업 로그 표기**: 랭크업 기술 사용 시 "OO의 스피드가 크게 올라갔다!" 같은 결과 문구가 지금은 아예 없음. 중간 규모(문구 추가 자체는 대전 로그의 여러 지점에 배선 필요). → **§6-2 ⑦과 통합** (방어 vs 랭크업 매치업에서 정확한 결과 문구 형식을 사용자가 지정함).
- **실능치 UI에 랭크 변화 반영(UX)**: 위 항목과 짝 — 랭크업 결과를 대전 로그의 실능치 표시에도 반영. → **§6-2 ⑧과 동일 항목**.
- **특성 발동 문구(깨어진 갑옷 등) 부재**: 확인 결과 깨어진 갑옷(Weak Armor) 자체가 특성 로직으로 배선돼 있는지부터 확인이 필요 — 로직이 이미 있는데 문구만 없다면 문구만 추가, 로직 자체가 없다면 별도 기능 추가. §6-2 ②(탈)·③(지구력)이 같은 성격(로직은 있는데 문구가 없음)이라 같이 훑는다.
- **차징 기술 전용 문구(공중날기 등)**: 순수 문구 — §4(전면 정비)로 미룸.
- **판별/방어류 문구 버그**: 1차엔 "차징 기술과 판별이 겹칠 때 문구가 이상함"이라고만 적혀 있었는데, **2차 테스트에서 재현 시나리오가 구체화됨 → §6-2 ⑦**(방어 + 랭크업 기술). 연속 사용 성공률 감소(`protectStreak`)는 이미 구현돼 있고, 문제는 "방어가 막을 수 없는 것(자기 대상 랭크업)을 막은 것처럼 문구가 뜬다"는 것.
- ~~**일렉트로빔 chargeTurn 누락**~~ — **완료(2026-08-27)**, Phase 6 §2-1에서 처리(메테오빔도 같이 발견된 스탯 상승 누락 버그를 함께 수정). 자세한 내용은 [phase6-plan.md](phase6-plan.md) §2-3 참고.

### 6-2. 2차 테스트에서 추가 (사용자 실사용, 2026-08-27)

사용자가 대전 로그를 직접 돌려보며 정리한 항목. 각 항목 뒤 `[조사 결과]`는 착수 전 코드 확인 메모. **① ② ③ ⑥ ⑧은 소규모(로직 한 줄 또는 문구/표시만), ④ ⑦은 중간 규모, ⑤는 향후(§8)로 분리.**

- **① 특성 가속 — 첫 턴부터 적용**: 대전 로그는 교체 없는 1대1 대면 전용이므로, 첫 턴도 "교체로 나온 턴"이 아니다 → 가속은 첫 턴 종료부터 발동해야 함. (파티 선출 시뮬레이터로 확장하면 그때 교체턴 예외를 되살린다.)
  - `[조사 결과]` `battleSimulator.ts` ~2786 `if (fighterAbility?.boostsSpeedEachTurnEnd && state.turnNumber > 1 && ...)` — `state.turnNumber > 1` 가드가 원인. 이 조건만 제거하면 됨(주석도 "교체가 없어 turnNumber 1이 곧 등장한 턴"이라고 스스로 근거를 달아뒀는데, 사용자 판단은 그 반대). **로직 1줄.**
- **② 특성 탈(따라큐) — 문구 교체**: 현재 `[ 따라큐의 탈! 공격이 무효화되었다! 따라큐는 반동으로 16 데미지를 입었다! ]` → "공격이 무효화되었다!" 를 빼고 **"따라큐의 정체가 드러났다!"** 로. 최종: `[ 따라큐의 탈! 따라큐의 정체가 드러났다! 따라큐는 반동으로 16 데미지를 입었다! ]`
  - `[조사 결과]` `BattleLogPage.tsx:772-777` 인라인 JSX. `hitNegatedByAbilityName` 조건 블록의 가운데 문장만 교체. **문구만.**
- **③ 특성 지구력 — 발동 문구 부재**: 데미지를 받으면 방어 +1랭크가 **실제로 적용은 되는데**(로직 정상) 로그에 아무 문구가 없어 반영 여부를 알 수 없음. → `[ 브리두라스의 지구력! 브리두라스의 방어가 올라갔다! ]` 출력.
  - `[조사 결과]` `abilities.json` 지구력 = `hitTrigger.selfStatChanges [{def:+1}]`. `battleSimulator.ts:1644-1648` `triggerAbilityHitEffect`에서 `defender.stages`에 적용은 되지만(정상), 다른 hitTrigger 분기(정전기 상태이상 등)와 달리 **로그 이벤트 필드를 안 채운다**. 이벤트 필드 추가 + `BattleLogPage` 렌더 라인 추가. **문구(+이벤트 배선).**

  - `resolveAction`: 스텔스록은 **항상 상대 진영**에 깔린다(사용자 확인 — 문구 Q1 답 A). 이미 그 진영에 깔려 있으면 실패.

- **⑦ 방어(판별) vs 랭크업 기술 매치업**: 두 포켓몬이 각각 방어 / 랭크업 기술(나쁜음모·칼춤)을 쓴 턴.

### 매직미러(Magic Bounce) — 조사 필요 (§6-2 ④에서 분리, 2026-08-27)

현재 코드에 이 특성이 아예 없다. 본가 매직미러는 스텔스록뿐 아니라 **상대를 겨냥한 변화기 전반**(도발·씨뿌리기·도깨비불·전기자석파·짓궂은태도류·설치기 등)을 시전자에게 되돌려보낸다. 착수 전 확인할 것:
- 반사 범위를 어디까지 볼지(스텔스록만? `isOpponentTargetingMove` 전체?).
- 반사된 기술의 처리 주체(시전자가 자기 자신에게 쓴 것으로 재평가할지, 결과만 뒤집을지).
- 이 프로젝트에서 매직미러를 가질 포켓몬이 있는지(없으면 데이터는 비워두고 로직만).
- `isOpponentTargetingMove`(현재 fieldEffects에서 export, 사이코필드·방어 판정과 공유 중)를 그대로 반사 판정에 재사용할 수 있는지.

**정의**: 변화 기술 중 상대방 진영에 부정적인 장치를 설치하는 기술("장판기"). 압정류는 중복 사용으로 효과가 누적된다.

**해당 기술 6종**: 끈적끈적네트 · 독압정 · 비검천중파 · 스텔스록 · 암석액스 · 압정뿌리기

**스택 규칙**:
- **독압정**: 1장 = 일반 독, 2장 = 맹독.
- **압정뿌리기**: 1장 = 최대 HP 1/16, 2장 = 1/8, 3장 = 1/4.
- 스텔스록·끈적끈적네트 등 나머지는 1장으로 고정(중복 무의미).

**제거 방법**:
- **고속스핀 / 안개제거**: 자기 진영(고속스핀) 또는 양 진영(안개제거)의 설치물을 걷어낸다.
- **독압정 한정**: 독 타입 포켓몬이 교체로 나오면 그 즉시 사라진다.

**설치 시 문구(스텔스록, §6-2 ④에서 선반영)**: `우리 편 필드에 뾰족한 바위가 떠다니기 시작했다!`
