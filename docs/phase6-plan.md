# Phase 6 기획 — MVP 완성도 다듬기 (데이터·기능 정비, 버그 수정, UI 개선)

> 이어서 읽기: [Phase 5 기획](phase5-plan.md)
> Phase 5에서 특성/기술 전투 로직을 대거 완성하면서 사용자가 Phase 6으로 명시적으로 이월한 3개 항목(헤롱헤롱 성별 데이터, 샘플파티/샘플 저장, 로그 UI 정비)을 그대로 가져왔고, 여기에 더해 Phase 6 전체의 성격을 "새 대규모 기능보다는 기존 데이터·기능 재점검, 작은 버그 수정, UI 개선 — MVP 완성도를 다듬는 페이즈"로 사용자가 확정했다(2026-08-26).

## 0. 이 문서의 성격

Phase 1~5는 매번 "새 엔진 인프라를 만드는" 확장 페이즈였다. Phase 6은 방향이 다르다 — 새 기능보다는 지금까지 쌓인 것들을 다시 살펴보고 다듬는 데 집중한다. 이 문서는 두 부분으로 나뉜다:

- **§1**: Phase 5에서 이미 "이건 Phase 6에서 한다"고 확정해둔 3개 항목. 배경·요구사항은 phase5-plan.md에 이미 적혀있던 걸 그대로 옮겨왔다.
- **§2**: 사용자가 이번에 확정한 "다듬기" 방향에 따른 정비 후보. Phase 5 §5(발견된 버그)와 같은 성격의 living 섹션이라, 작업하면서 계속 추가·정리한다 — 지금 적힌 건 착수 시점에 이미 알려진 것들뿐이고 전수 조사 결과가 아니다.

## 1. Phase 5에서 이월된 확정 작업

### 1-1. 헤롱헤롱(매혹) — 포켓몬 성별 데이터 모델링

Phase 4.5 §5-1부터 미뤄져 온 "상대 기술 선택을 제약하는 변화기 4종(도발·사슬묶기·앙코르·헤롱헤롱)" 중 유일하게 남은 항목. 도발·사슬묶기·앙코르 3개는 Phase 5에서 완료됐다(phase5-plan.md §2 참고).

- **막힌 지점**: 포켓몬 성별 데이터가 이 프로젝트에 아예 없다. 헤롱헤롱(기술)과 헤롱헤롱바디(특성, phase5-plan.md §1의 "접촉 피격 시 발동" 훅에서 이미 한 번 발견됨)는 둘 다 "이성 관계일 때만 성립"하는 조건부 효과라, 이 데이터 없이는 구현할 수 없다.
- **필요한 결정**: 종족별 성비(대부분 87.5:12.5 등 혼합)를 배틀마다 어떻게 확정할지(고정 성별 vs 랜덤 배정), 무성별 종은 어떻게 표시할지 — 이 정책부터 정해야 데이터 스키마를 잡을 수 있다.
- **구현 자체는 어렵지 않음**: 확률부 행동불능 로직은 마비와 같은 매 턴 확률 판정 축이라, 성별 데이터와 "이성일 때만" 조건 판정만 추가하면 된다. 헤롱헤롱바디(특성)는 `hitTrigger` 인프라가 이미 완성돼 있어서, 헤롱헤롱(매혹) volatile만 새로 만들면 그 인프라를 그대로 재사용해 같이 끝낼 수 있다(phase5-plan.md §1 55번째 줄에 이미 메모돼있음).
- **제안 순서**: 성별 데이터 정책부터 사용자에게 확인 → `pokemon.json`에 성별 필드 추가 → `types/status.ts`의 `VolatileCondition`에 헤롱헤롱(매혹) 추가 → `resolveAction`에 "이성 관계 확인 + 확률부 행동불능" 판정 추가 → 헤롱헤롱바디는 기존 `hitTrigger` 배선에 이 volatile만 꽂으면 끝.

### 1-2. 샘플파티 저장 기능 — 파티(6슬롯) 여러 개를 이름 붙여 저장/불러오기

- **지금 상태**: `useParty.ts`가 `PartySlots`(6슬롯) 하나만 들고 있고, 슬롯이 바뀔 때마다 `saveParty()`로 덮어쓴다. 여러 파티를 만들어뒀다가 나중에 다시 불러오는 개념 자체가 없음 — 새 파티를 구성하면 이전 파티는 사라진다.
- **필요한 것**: (1) `storage.ts`에 "현재 작업 중인 파티"(기존 단일 자동저장, 유지)와 별도로 "이름 붙인 파티 프리셋 목록"을 저장하는 새 스토리지 키/스키마 신설(`{ id, name, slots: PartySlots, savedAt }[]`). (2) 저장/불러오기/삭제/이름변경 UI(사이드 메뉴나 `PartyBoard.tsx` 쪽에 프리셋 목록 패널 추가). (3) 불러오기 시 현재 작업 중인 파티를 덮어쓸 건지 확인하는 흐름(사용자 확인 필요 — 데이터 유실 방지).

### 1-3. 샘플 저장 기능 — 포켓몬 빌드 1개(파티 슬롯 하나)를 이름 붙여 저장/재사용

- **지금 상태**: `PartySlot`(포켓몬+특성+도구+성격+노력치+기술 4개) 하나를 독립적으로 저장하는 기능이 없음 — 같은 조합("이 라이츄는 항상 이 기술/노력치")을 여러 파티에서 매번 처음부터 다시 입력해야 함.
- **필요한 것**: (1) `PartySlot` 단위로 저장하는 별도 스토리지 키/스키마(`{ id, name, slot: PartySlot, savedAt }[]`) — 1-2의 파티 프리셋과는 저장 단위가 다르므로 별개 목록. (2) 슬롯 편집 UI(포켓몬/기술/특성 피커가 모여있는 곳)에 "이 빌드를 샘플로 저장" 버튼과, 포켓몬을 고르는 시점에 "저장된 샘플에서 불러오기" 선택지 추가. (3) 저장된 샘플의 포켓몬을 나중에 로스터에서 빼면(포켓몬 삭제는 현재 없지만) 참조가 깨질 수 있는데, 지금 로스터는 삭제가 없어서 당장은 문제 안 됨 — 향후 로스터 정리 시 참고.
- **1-2와의 관계**: 두 스토리지가 독립적이면 "샘플 파티를 불러왔는데 그 안의 슬롯 하나만 따로 샘플로 다시 저장" 같은 조합도 자연스럽게 가능 — 설계 시 서로 얽히지 않게 분리하는 편이 나을 듯.

### 1-4. 대전 로그 UI 문구 전면 정비

Phase 5에서 특성/기술 로직을 워낙 많이(70종 넘게) 새로 붙이면서 `BattleLogPage.tsx`의 로그 문구가 그때그때 개별적으로 추가돼왔다 — 한 번에 모아서 톤·형식·정보량을 통일하는 리뷰가 필요하다는 사용자 판단으로 Phase 6에 편성됐다.

- **지금 상태**: 로그 문구가 최소 6가지 서로 다른 패턴으로 흩어져 있다 — `STATUS_ONSET_TEXT`/`STATUS_TRIGGER_TEXT`/`STATUS_CURE_TEXT`(상태이상 3단계, 함수 맵), `VOLATILE_LABELS`(행동방해류, 칩 전용 라벨), 메인 라인에 인라인으로 박힌 `· OO 발동!` 조각들(수십 개), 특성 전용 문구(예: 흑안개 "양쪽의 능력 변화가 전부 원래대로 돌아갔다!", 대타출동 "대타가 대신 맞았다!"), 방어류 전용 문구, `moveRestrictionMessage`(도발/사슬묶기/앙코르). 특성이 발동했을 때 "OO의 [특성명]!"으로 시작하는 것도 있고 그냥 결과만 말하는 것도 있어 형식이 일관되지 않다.
- **필요한 작업**: (1) 전체 로그 문구를 한 번에 나열해서 톤(예: 전부 "OO의 [원인]! [결과]" 형식으로 통일할지)·정보량(포켓몬 이름을 매번 반복할지, 대명사로 줄일지)·기절 시 문구(현재 `battle-fighter-fainted`로 " (기절)"만 붙는데 더 명확한 문구가 필요한지)를 검토. (2) 함수 맵 방식(STATUS_*_TEXT)과 인라인 조각 방식이 혼재하는데 특성/기술이 계속 늘어날 걸 감안하면 어느 한쪽으로 통일하는 게 유지보수에 유리한지 결정. (3) 실제 대전 로그를 몇 판 돌려보면서 정비.
- **범위**: 로직 자체는 건드리지 않고 표시 문구만 다듬는 순수 UI 작업이라 회귀 위험은 낮지만, 문구가 수십 곳에 흩어져 있어 손이 많이 간다.

## 2. MVP 완성도 다듬기 (신규, 사용자 확정 2026-08-26)

사용자가 이번에 Phase 6의 성격을 확정했다: "전체적으로 다시 한번 데이터나 기능들을 다듬고, 기타 작은 버그들 처리, UI변경 등 MVP의 완성도를 다듬는 페이즈." 아래는 착수 시점 기준으로 이미 알려진 정비 후보다 — Phase 5 §5(발견된 버그)와 같은 패턴으로, 작업하면서 계속 채워나간다.

### 2-1. 알려진 데이터/로직 정비 후보

- **우격다짐 도구 상호작용 미반영**: 생명의구슬 반동 면제, 이젝트버튼/타면목걸이 등 부가효과 트리거형 도구 — Phase 5 §4-4에서 사용자 확인 없이 범위 밖으로 명시적으로 남긴 항목.
- **매치업 페이지(1턴 스냅샷)에 반영 안 된 축들 재검토**: 천진/성스러운칼(랭크 무시), 매지션/곡예(도구 강탈), 곡예(스피드 2배), 고스트다이브(방어류 차단) — Phase 5 내내 "1턴 스냅샷 구조상 안 맞아서(이전 턴 개념이 없음) 의도적으로 제외"라고 판단해왔는데, 실제 사용 패턴을 보면서 이 판단이 맞는지 재확인이 필요할 수 있다.
- **잠꼬대 후보 제외 로직의 정확도**: 지금은 "usageCondition이 있는 기술"만 제외하는 근사치로 구현했다(Phase 5 §4-6) — 본가의 정확한 제외 목록과 다를 수 있어 필요시 정밀화.
- **기습(Move.usageCondition: "opponent-damaging-move-only")의 범위 밖 케이스**: 상대가 상태이상 등으로 아예 행동을 못 해도 이 시뮬레이터는 성공 처리한다 — Phase 5 §5-1에서 "실전 영향 낮음"으로 보류해뒀던 것 재검토.
- **로스터/데이터 규모 문서화 최신화 습관**: README의 데이터 규모 절이 실제 로스터보다 한참 낮게 적혀 있던 걸 이번에 발견해서 갱신했다(42종/393개/78개/96종/21종) — 앞으로 로스터·기술·특성·도구를 추가할 때마다 README도 같이 갱신하는 걸 점검 항목에 넣는다.

### 2-2. UI/UX 개선 후보

- (실사용하면서 발견하는 것들을 계속 채워나간다)

### 2-3. 버그 수정

- (Phase 5 §5와 동일한 패턴 — 사용자 리포트나 작업 중 발견되는 대로 이 절에 기록한다. 착수 시점엔 알려진 게 없음)

## 3. 제안 순서 (초안)

1. 헤롱헤롱 성별 데이터 정책 확인 → 구현(§1-1) — 가장 오래(Phase 4.5부터) 미뤄진 항목
2. 샘플파티·샘플 저장 기능(§1-2·1-3) — UI+스토리지 확장, 서로 독립적이라 순서 무관
3. 대전 로그 UI 문구 정비(§1-4)
4. §2 정비 후보 — 우선순위는 진행하면서 사용자와 그때그때 조율

Phase 4.5·5 내내 그랬듯, 실제로 작업하다 보면 우선순위가 바뀔 가능성이 높다 — 그때그때 재조정한다.
