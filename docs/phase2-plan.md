# Phase 2 기획 — 턴 순서 + 대전 로그가 있는 전투 시뮬레이터

> 이어서 읽기: [Phase 1 회고](phase1-review.md) · [Phase 1.5 회고](phase1.5-review.md)
> 이 문서는 Phase 1.5 완료 세션 마지막에 논의된 내용을 착수 전에 정리한 **기획 문서**다. 아직 구현은 시작하지 않았다. Phase 1.5 문서 8절("Phase 2로 이월된 것")에 남긴 4개 항목을 출발점으로, 실제로 뭘 만들지 스키마 갭(C)과 신규 기능(D) 두 갈래로 나눠 구체화한다.

## 0. Phase 2의 목표

Phase 1.5까지는 "이 기술 한 방이 몇 타에 상대를 쓰러뜨리는가"를 판정하는 **1턴 스냅샷 매치업**(`evaluateSlotMatchup`)까지 만들었다. Phase 2는 여기서 한 단계 더 나가서, **양쪽이 기술을 고르고 → 턴 순서가 정해지고 → 데미지·상태이상·랭크·PP가 여러 턴에 걸쳐 누적되는** 것을 실제로 진행시키는 시뮬레이터와, 그 결과를 턴별로 읽을 수 있는 대전 로그 화면을 만드는 것이 목표다.

기존 매치업 화면을 대체하는 게 아니라 **그 위에 얹는다**: `evaluateSlotMatchup`은 "재사용 가능하게 설계"돼 있으므로, 시뮬레이션 엔진의 매 턴 데미지 계산은 이 함수(정확히는 그 하위 함수인 `computeOffensePower`/`computeBulkPower`)를 그대로 재사용하고, 새로 짜는 건 "턴을 진행시키는" 로직과 "결과를 기록하는" 로직이다.

## 1. 스키마 갭 메우기 (엔진 착수 전 선행 작업)

시뮬레이션 엔진을 짜기 전에 먼저 채워야 하는 데이터/계산 갭. 순서대로 진행한다.

### 1-1. 턴 순서 비교 함수

- `computeEffectiveSpeed(realSpeed, stages)`는 이미 있음 ([battlePower.ts](../src/lib/battlePower.ts)) — 스피드 랭크·(추후) 트릭룸까지 반영한 실효 스피드 하나를 낸다.
- 없는 것: **우선도(`Move.priority`) → 실효 스피드** 순으로 두 슬롯 중 누가 먼저 움직이는지 판정하는 비교 함수.
- 새로 만들 것: `lib/turnOrder.ts`
  - `compareTurnOrder(a: TurnActor, b: TurnActor): -1 | 0 | 1` — 우선도 다르면 우선도로, 같으면 실효 스피드로, 그것도 같으면 동속(현재는 결정론적 처리가 필요 — 아래 2절 참고).
  - 트릭룸 등 "스피드 역전" 필드 효과는 Phase 2 범위에 넣을지 별도 확인 필요 (2절 열린 질문 참고).

### 1-2. 회피율/급소율 랭크

- 현재 `BattleStatKey`는 `atk`/`def`/`spa`/`spd`/`spe` 5개뿐. 그림자분신(회피율 +1)·기충전(회피율 -2 등 상대에게)·안개제거(랭크 초기화) 같은 기술이 이미 데이터에 있는데 `statChanges`에서 스킵되고 있을 가능성이 높음.
- 확인 필요: 실제로 몇 개 기술이 영향받는지 `moves.json`에서 회피율/급소율 관련 기술을 전수 스캔.
- 스키마 변경 (예정):
  - `types/battleStats.ts`의 `StatStages`에 `accuracy`/`evasion` 두 필드를 추가하되, 이 둘은 "실능 계산"이 아니라 "명중 판정용 배율"이라 랭크업 배율 공식(`rankStageMultiplier`)이 그대로 적용되는지, 아니면 챔피언스 전용 별도 표가 있는지부터 확인해야 함(나무위키 등 자료 재확인).
  - 급소율은 랭크 체계가 아니라 "급소율 상승 단계"(0~3단계, 각 단계별 확률표)로 완전히 다른 방식일 가능성이 높음 — 별도 타입(`CritStage`)으로 분리하는 게 맞아 보임.
- 시뮬레이션에서 실제로 쓰이는 지점: 명중 판정(회피율)과 급소 판정(급소율)은 둘 다 "매 턴 확률 굴림"이 필요한 로직이라, 이 항목은 사실상 D절 다중 턴 엔진의 선행 조건이기도 하다.

### 1-3. 상세 데미지 공식 (레벨 항 포함)

- 지금은 결정력 vs 내구력의 **비율**로 5단계 판정만 함 (`evaluateMatchup`). 실제 데미지 숫자·% HP 계산은 없음.
- 대전 로그 UI에 "냐오닉스가 47%의 데미지를 입었다!" 같은 문구를 넣으려면 실제 데미지 값이 필요 — 비율 판정만으로는 부족.
- **먼저 확인해야 할 전제**: Pokémon Champions가 챔피언십 매치에서 고정 레벨(본가처럼 50/100 등)을 쓰는지, 아니면 레벨 개념 자체가 없는지. Phase 1.5에서 실수치 공식은 이미 "레벨 없음"으로 확정했는데(`HP = 종족값+75+능력포인트` 등), 나무위키 데미지 공식의 레벨 항이 챔피언스에도 살아있는 상수로 대체됐는지, 아니면 완전히 빠지는지가 불명확함.
- 확인되면 `lib/battlePower.ts`에 `computeDamage(offensePower, bulkPower, ...)` 형태로 실제 데미지 값(또는 %HP)을 내는 함수를 추가하고, 난수 폭(0.85~1.0 등 16단계)까지 반영해 "최소~최대 데미지 범위"를 낸다.

## 2. Phase 2 신규 기능 — 턴 순서 + 대전 로그

### 2-1. 턴 동시 선택 → 정렬

- 양쪽이 이번 턴 쓸 기술을 각각 고르면, 1-1의 `compareTurnOrder`로 정렬해서 실행 순서를 정한다.
- 인터페이스 초안: `resolveTurnOrder(actorA: TurnActor, actorB: TurnActor): [TurnActor, TurnActor]` — 먼저 움직이는 쪽이 앞.
- `TurnActor`는 `EvaluatorSlot`(기존 재사용) + 선택한 `Move` + 현재 `StatStages` + 현재 HP를 담는 새 타입으로 정의.

### 2-2. 다중 턴 시뮬레이션 엔진

- 새 모듈: `lib/battleSimulator.ts`
- 상태를 담는 `BattleState`: 양쪽 슬롯의 현재 HP(실제 HP 실수치 기준), `StatStages`, 상태이상(`StatusCondition`: 화상/마비/독/맹독/얼음/잠듦 — 이것도 스키마에 아직 없으면 신규 추가), 남은 PP, 필드 상태(날씨 잔여 턴 등).
- 한 턴 처리 흐름: 기술 선택 → `resolveTurnOrder` → 순서대로 각 행동자에 대해 (명중 판정 → 급소 판정 → `evaluateSlotMatchup`류 계산 재사용해 데미지 산출 → HP 차감 → 이번 기술의 `statChanges` 적용 → 상태이상 부여) → 턴 종료 시 상태이상 매턴 데미지(화상/독 등) → PP 소모.
- 기존 `evaluateSlotMatchup`을 얼마나 재사용할 수 있는지가 핵심 설계 포인트: 지금 시그니처는 "정적인 슬롯 + 랭크 옵션"을 받는데, 시뮬레이터에서는 "매 턴 갱신되는 `BattleState`"에서 그때그때 옵션을 뽑아 넘겨주는 얇은 어댑터만 있으면 그대로 쓸 수 있을 것으로 보임 — 함수 자체를 고칠 필요는 크지 않을 듯. 실제 착수 시 재검증.
- 종료 조건: 한쪽 HP가 0 이하가 되면 시뮬레이션 종료.

### 2-3. 대전 로그 UI

- 새 화면 또는 매치업 화면 확장: 턴별로 무슨 일이 일어났는지 텍스트/타임라인으로 표시.
- 최소 구성: 턴 번호, 행동 순서(누가 먼저), 사용 기술, 명중 여부, 데미지(%HP), 랭크 변화, 상태이상 발생/틱, 남은 HP 게이지.
- 컴포넌트: `BattleLogPage.tsx` + `BattleLogEntry.tsx` (턴 1개 = 로그 카드 1개), 기존 `MatchupSlotCard`류 스타일 재사용.
- 여러 턴을 자동 재생(다음 턴 버튼 / 전체 재생)할지, 사용자가 매 턴 기술을 골라가며 진행할지는 열린 질문(3절).

### 2-4. `evaluateSlotMatchup` 리팩터

- 지금 있는 그대로도 재사용 가능한 구조지만, 시뮬레이터에서 쓰려면 다음이 필요할 수 있음:
  - 데미지가 아니라 **비율 판정**만 반환하는 현재 반환 타입(`SlotMatchupResult`)에 2-3에서 필요한 실제 데미지/%HP 값(1-3의 결과)을 옵션으로 얹기.
  - 명중/급소 판정은 현재 함수 밖에 있음 — 시뮬레이터의 턴 처리 로직이 이 함수를 감싸는 형태(호출 전 명중 판정, 호출 후 급소 배율 적용)가 될 가능성이 높음.
- 기존 매치업 화면(`MatchupPage.tsx`)은 그대로 두고, 시뮬레이터는 같은 하위 함수(`computeOffensePower`/`computeBulkPower`)를 공유하는 별도 상위 계층으로 둘 계획 — 1턴 스냅샷 화면과 다중 턴 화면을 억지로 하나로 합치지 않는다.

## 3. 열린 질문 — 리서치 결과 (2026-08-20 웹 검색)

착수 전 확인이 필요했던 5개 질문을 웹 검색으로 1차 조사했다. ✅는 여러 소스가 일치해 신뢰도가 높은 것, ⚠️는 소스끼리 상충하거나 챔피언스 전용 자료가 부족해 그대로 못 믿는 것.

### 1. 레벨/데미지 공식 — ✅ 해결

챔피언스 랭크전은 **레벨 50 고정**. 본가 데미지 공식의 레벨 항 `(2×Level÷5+2)`가 그대로 살아있고 50 대입 시 상수 22로 고정된다. 이 결과는 Phase 1.5에서 이미 검증해둔 내구력 상수 0.411(레벨 50 대전 기준 중간값)과도 정합적 — 같은 전제 위에서 만들어진 값이라는 뜻. `computeDamage()` 설계 시 레벨=50 상수로 박아 넣으면 됨.
Sources: [chouten.dev - Level 50 Mechanics](https://chouten.dev/articles/level-50-mechanics), [saavage.com - Damage Formula Explained](https://saavage.com/stories/pokemon-champions-how-damage-works), [나무위키 - 결정력·내구력](https://namu.wiki/w/%EA%B2%B0%EC%A0%95%EB%A0%A5%20%C2%B7%20%EB%82%B4%EA%B5%AC%EB%A0%A5)

### 2. 회피율/급소율 랭크 공식 — ✅ 해결 (사용자 제공 자료로 확정)

웹 검색만으로는 상충됐지만, 사용자가 챔피언스 1차 자료 기준 공식을 직접 확인해줘서 확정.

**명중률/회피율**

```
최종 적중률 = 기술 기본 명중률 × (명중 랭크 배율 ÷ 회피 랭크 배율) × 특성/도구 보정(독립 곱연산)
```

- 랭크 배율(공격측 명중 랭크, 방어측 회피 랭크 각각에 동일하게 적용):
  - +1~+6: `(3 + 랭크) / 3` → 4/3, 5/3, 2, 7/3, 8/3, 3배
  - -1~-6: `3 / (3 + |랭크|)` → 3/4, 3/5, 1/2, 3/7, 3/8, 1/3배
- 특성/도구(반짝가루 0.9배, 모래숨기 0.8배 등)는 랭크와 별개로 최종 확률에 곱연산.
- 예: 명중률 100 기술, 상대가 모래숨기+모래바람+반짝가루+작아지기(회피 +2랭크) → `100% × (3/5) × 0.8 × 0.9 = 43.2%`
- 스키마 영향: 명중/회피는 기존 `StatStages`(atk/def/spa/spd/spe)와 별도 축이므로 `accuracy`/`evasion`을 같은 타입에 넣기보다 **별도 필드(또는 별도 타입)**로 분리하는 게 맞다 — 랭크업 배율 공식도 `rankStageMultiplier`(k=2 방식)와 다른 별개 공식이라 재사용 불가, 새 함수(`computeAccuracyMultiplier` 등) 필요.

**급소율**

랭크 시스템이지만 명중/회피와는 또 다른 별도 단계표 — "급소업 상태 랭크" 0~3단계, 3랭크에서 100%(필중) 도달:

| 랭크 | 확률 | 예시 조건 |
|---|---|---|
| 0 | 1/24 (4.17%) | 기본 상태 — Phase 3(1-2)에서 사용자가 1/16→1/24로 정정 |
| 1 | 1/8 (12.5%) | 깜짝베기 등 급소 잘 맞는 기술 |
| 2 | 1/2 (50.0%) | 초점렌즈 + 급소 잘 맞는 기술 등 조합 |
| 3+ | 1/1 (100%) | 기충전 가동, 또는 대운 특성+초점렌즈+급소 기술 조합 |

- 스키마 영향: 급소율은 -6~+6 랭크가 아니라 0~3(+) 별도 카운터 — `CritStage`를 `0 | 1 | 2 | 3`(또는 number, 3 이상은 클램프) 타입으로 새로 정의. 어떤 기술/도구/특성이 이 카운터를 몇 단계 올리는지는 데이터 보강 필요(예: 초점렌즈 +1단계, 기충전 사용 시 +2단계 등 — 조합 규칙은 착수 시 재확인).

### 3. 상태이상 스키마 — ✅ 대부분 해결

여러 영어권 챔피언스 전용 자료(Game8, ChampsDex, pkmnchamps.com 공식 가이드 등)가 일치:

| 상태이상 | 매턴 효과 |
|---|---|
| 화상(Burn) | 매턴 최대 HP 1/16 데미지 + 물리 공격력 0.5배 |
| 독(Poison) | 매턴 최대 HP 1/8 고정 데미지 |
| 맹독(Badly Poisoned) | 1턴째 1/16, 이후 매턴 1/16씩 누적 증가 |
| 마비(Paralysis) | 스피드 0.5배 + **12.5% 확률로 행동 불가** (본가는 25% — 챔피언스는 하향됨) |
| 얼음/잠듦 | 지속 턴수·해동 확률 등 상세 수치는 못 찾음 — 추가 확인 필요 |

한 포켓몬은 주요 상태이상 중 하나만 가질 수 있음(중첩 없음). `Move.inflictsStatus` 같은 신규 필드가 필요하다는 원래 추정은 맞음 — 어떤 기술이 몇 %로 어떤 상태이상을 거는지는 기술 데이터에 아직 없어서 이 부분은 데이터 보강 작업이 별도로 필요.

### 4. AI vs 수동 진행 — ✅ 결정됨

**매 턴 양쪽 다 수동 선택.** 사용자가 내 포켓몬과 상대 포켓몬의 기술을 매 턴 직접 골라가며 "가상 대전"을 진행하는 도구로 만든다. 상대 AI 자동 선택 로직은 Phase 2 범위에서 제외 — 덕분에 2-2 엔진은 "행동 선택"과 "턴 처리"가 분리된 구조로만 만들면 되고, AI 의사결정 로직을 설계할 필요가 없어 범위가 줄어든다. (자동 모드는 이후 필요해지면 별도 확장 포인트로 남겨둠.)

### 5. 동속 처리 — ✅ 해결 (사용자 확인)

**완전 동속(우선도·실효 스피드 모두 같음)이면 50% 확률로 랜덤.** 사용자가 직접 확인해줌 — 웹 검색에서 상충됐던 두 설 중 VGC 표준 방식(랜덤 코인플립)이 맞고, 아카라이브의 "도감순서" 설은 근거대로 채택하지 않는다. `compareTurnOrder`가 동속 케이스를 만나면 결정론적으로 정하지 않고 50/50 난수로 승자를 정하도록 구현한다(테스트에서는 시드 고정 가능하게 난수 함수를 주입받는 형태 고려).

## 5. 제안 착수 순서 / 진행 상황

1. ✅ **1-1 턴 순서 비교 함수** — [`lib/turnOrder.ts`](../src/lib/turnOrder.ts). `compareTurnOrder`/`resolveTurnOrder`, 동속은 50/50 랜덤(주입 가능한 `random` 파라미터로 테스트 시 고정 가능)
2. ✅ **1-3 상세 데미지 공식** — [`lib/battlePower.ts`](../src/lib/battlePower.ts)에 `computeDamage()` 추가. 레벨 50 상수(`LEVEL_50_TERM`=22)로 실제 데미지·%HP 계산. 급소 배율(1.5배, 랭크 하락 무시 규칙)은 본가값을 임시로 쓰는 중 — ⚠️ 챔피언스 실측 필요
3. ✅ **1-2 회피율/급소율 스키마 + 계산 함수** — [`types/battleStats.ts`](../src/types/battleStats.ts)에 `AccuracyEvasionStages`/`CritStage`/`EffectStatKey` 추가, [`lib/accuracyCrit.ts`](../src/lib/accuracyCrit.ts)에 `computeAccuracyMultiplier`/`computeHitChance`/`critChance`/`applyMoveAccuracyEvasionChanges`/`applyMoveCritStageChanges` 구현. `Move.statChanges[].stat`도 `EffectStatKey`로 확장, 기존 `applyMoveStatChanges`(5스탯 전용)는 `isBattleStatKey` 가드로 걸러내도록 수정. **남은 일**: 실제로 어떤 기술(그림자분신/기충전/안개제거 등)이 이 카운터를 얼마나 움직이는지 `moves.json` 데이터 보강 — 아직 안 함
4. ✅ **상태이상 스키마 — A/B 두 축으로 확정** — 사용자가 화상/독/맹독/마비/잠듦/얼음 매턴 수치와 잠듦·얼음의 해제 스케줄, 혼란 지속턴수를 직접 조사해줘서 전부 반영함.
   - **A. 주 상태이상(Major, 상호 배타적)**: [`types/status.ts`](../src/types/status.ts)의 `StatusCondition`/`StatusConditionState`. [`lib/statusConditions.ts`](../src/lib/statusConditions.ts)에 화상(1/16+물리 0.5배)·독(1/8)·맹독(n/16 누적, 최대 15/16 클램프)·마비(스피드 0.5배+12.5%)까지는 확정 수치대로, 잠듦(1턴째 0%→2턴째 33%→3턴째 100% 강제)·얼음(매턴 25%, 3턴째 100% 강제)은 `checkStatusActionBlock`이 턴별 해제 스케줄로 자체 판정. 화상/독/맹독/마비는 치료 전까지 무한 지속(사용자 확인)
   - **B. 행동방해(Volatile, 별도 축·중첩 가능)**: 신규 `VolatileCondition`(`flinch`/`recharge`/`confusion`) + [`lib/volatileConditions.ts`](../src/lib/volatileConditions.ts). 풀죽음·반동은 고정 1턴 행동불가, 혼란은 1~4턴 지속하며 매 행동마다 1/3 확률로 자멸(물리 40위력 자가타격, 타입/자속 없음) — 전부 사용자 확인 수치
   - [`lib/battleSimulator.ts`](../src/lib/battleSimulator.ts)의 `resolveAction`이 "주 상태이상 차단 → 풀죽음/반동 차단 → 혼란 자멸 판정 → 정상 진행" 순서로 두 축을 함께 처리하도록 배선 완료. 단위 테스트로 잠듦/얼음 스케줄·맹독 클램프·마비 확률·풀죽음/혼란 소모까지 15개 케이스 전부 통과 확인
   - ✅ **화상 근성/객기 예외 반영 완료** — 사용자 확인: 근성 특성이거나 객기 기술이면 화상의 물리 공격력 0.5배 페널티를 무시한다(감소만 무시, 본가처럼 오히려 공격력을 올려주는 효과는 미확인이라 반영 안 함). `lib/statusConditions.ts`의 `ignoresBurnAttackPenalty()` + `computeStatusAttackMultiplier()` 세 번째 인자로 구현, `battleSimulator.ts`에서 공격자 특성 id/기술 id로 판정해 전달

### 상태이상 데이터 보강 완료 + 실전 버그 2건 수정

사용자가 "Champions 기술표" 아티팩트에 기술별 상태이상 확률을 정리해줘서, 로컬에 저장한 HTML을 스크립트로 파싱해 `moves.json`에 반영함 (331개 기술 전수 스캔):

- **45개 기술**에 `inflictsStatus`/`inflictsVolatile` 구조화 데이터 추가 (화상/독/맹독/마비/잠듦/얼음 40개 + 혼란 유발 8개, 일부 중복). 아티팩트 표에 빠져있었지만 기존 `effect` 텍스트로 확인되는 것들(불꽃세례·찬물끼얹기 화상, 부추기기 혼란)도 함께 찾아서 보강
- **전기 타입 마비 면역** 규칙을 `lib/statusConditions.ts`의 `isImmuneToStatus()`로 엔진에 반영(누르기 기술표 각주로 확인). 화상/독의 타입 면역(본가는 불꽃=화상 면역, 독/강철=독 면역)은 챔피언스에서 아직 미확인이라 넣지 않음
- **스키마 밖이라 스킵**: 하품(다음 턴 지연 발동), 독압정(교체 시 발동하는 설치형 필드 효과), 드래곤옐(1v1 시뮬레이터에서 의미 없는 아군 전원 대상 효과) — 셋 다 지금 스키마로 표현 불가
- **트라이어택**(화상·마비·얼음 중 하나 20%)은 세 상태이상을 각 20/3%로 순차 독립시행 근사 — 정확히 균등한 20%는 아니지만 근사치로 처리

**실전 버그 2건 발견·수정** (데이터 보강 후 스모크 테스트로 실제로 걸어보다가 발견):

1. **위력 없는 변화기가 상태이상을 아예 못 걸었음** — `resolveAction`이 "데미지 없는 기술"이면 무조건 조기 리턴하던 로직이라, 도깨비불·최면술·독가루처럼 상태이상 자체가 목적인 변화기(`category: "status"`, `power: null`)는 명중해도 `inflictsStatus`/`statChanges` 코드에 도달하지 못했다. 데미지 계산과 "명중 후 효과 적용"을 분리해서 수정 — 이제 명중만 하면 데미지 유무와 무관하게 랭크/명중회피/급소/상태이상/행동방해가 전부 적용됨
2. **타입 상성 0배(면역)인데도 최소 1 데미지가 나가던 버그** — `computeDamage()`의 `Math.max(1, ...)` 최소 데미지 보정이 면역 매치업까지 덮어써서 생긴 문제. `typeEffectiveness === 0`이면 무조건 0으로 처리하도록 수정

두 버그 다 `battlePower.ts`/`battleSimulator.ts` 수정 후 재검증(도깨비불 100% 화상이 실제로 걸리는 것, `isImmuneToStatus` 단위 테스트, 기존 데미지 회귀 테스트 동일 결과) 완료.

### 화상 근성/객기 예외 반영

사용자 확인: 근성 특성이거나 객기 기술이면 화상의 물리 공격력 0.5배 페널티를 무시한다(감소만 무시 — 본가처럼 상태이상일 때 오히려 공격력을 올려주는 효과는 미확인이라 반영 안 함). `lib/statusConditions.ts`의 `ignoresBurnAttackPenalty()` + `computeStatusAttackMultiplier()` 세 번째 인자로 구현, `battleSimulator.ts`에서 공격자 특성 id/기술 id로 판정해 전달. 단위 테스트로 확인 완료. (근성은 지금 21마리 커버리지·45개 구조화 특성 어디에도 없어 실제로 발동하는 조합은 아직 없지만, 향후 포켓몬 추가 시 바로 동작하도록 엔진 레벨에 미리 반영해둠)

### 2-4. `evaluateSlotMatchup` 리팩터 완료

### 2-3. 대전 로그 UI 완료

사이드바에 새 메뉴 "대전 로그"를 추가하는 방식으로 진입점을 결정(파티 빌더/매치업과 동일선상의 독립 화면). 구성:

- **셋업 단계** — [`hooks/useBattleSetup.ts`](../src/hooks/useBattleSetup.ts)(양쪽 슬롯 상태, `PartySlot`을 그대로 재사용 — `EvaluatorSlot`을 만족해서 `createBattleState`에 바로 넘어감) + [`components/BattleSetupCard.tsx`](../src/components/BattleSetupCard.tsx)(포켓몬/기술4개/특성/도구/성격/포인트, `PartySlotCard`와 같은 CSS 재사용). "대전 시작" 버튼은 양쪽 다 포켓몬+기술 1개 이상 있어야 활성화
- **배틀 단계** — [`components/BattleLogPage.tsx`](../src/components/BattleLogPage.tsx)가 `createBattleState`/`runTurn`을 직접 호출. 양쪽 HP바(위험도 3단계 색상)·주 상태이상/행동방해 태그·기술별 남은 PP를 보여주고, 매 턴 양쪽이 기술을 고르면 "턴 진행" 버튼으로 `runTurn` 실행 → 결과를 로그에 쌓고 상태 갱신. 로그는 최신 턴이 위로 오도록 표시하며, 명중/빗나감/급소/데미지%/상태이상·행동방해 부여/기절/승자까지 한 줄씩 풀어서 보여줌
- **브라우저로 실제 검증** — 리자몽(불대문자) vs 거북왕(냉동빔)으로 4턴 진행: 우선도·데미지·PP 차감·화상 부여(불대문자 10%)와 그 다음 턴 매턴 데미지(154/16=9)까지 실제 걸리는 것 확인, 상대가 기절하며 승리 배너 노출, "다시 설정하기"로 셋업 화면 복귀(직전 편성 유지)까지 전부 정상 동작. 콘솔 에러 없음

⚠️ **알려진 한계**: 다단히트 기술(트리플악셀 등)은 시뮬레이터가 아직 처리 안 함(기본 위력만 사용) — `evaluateSlotMatchup`의 `multiHitCount` 옵션과 달리 `battleSimulator`에는 대응 로직이 없음. 회피율/급소율/상태이상을 실제로 거는 기술 중 일부(그림자분신·기충전 등)는 여전히 데이터 미태깅 상태.

라이브러리 레이어와 UI 모두 완료됐다. Phase 2의 핵심 목표(턴 순서 + 다중 턴 대전 로그)는 이걸로 달성 — 남은 건 데이터 커버리지 확장(회피/급소 부여 기술, 다단히트 지원)과 화상 근성/객기처럼 세부 규칙을 하나씩 더 확인해나가는 정도.
